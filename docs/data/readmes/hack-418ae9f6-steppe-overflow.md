# SteppeWind — Agentic AI прогноз выработки ВЭС

**Сайт: https://steppewind.energy** · **Видео (75 с): [docs/media/demo.mp4](docs/media/demo.mp4)**

![Демонстрация SteppeWind: прогноз, AI-агент, качество, чат](docs/media/demo.gif)

## Кратко

SteppeWind прогнозирует почасовую выработку ветроэлектростанции из двух турбин (Алматинская область, 43.64° с. ш., 78.54° в. д.) на следующие 24–48 часов.

**Для кого:** оператор ВЭС и диспетчер. Выработка ветра нестабильна, а график поставки в энергосистему нужно заявить заранее, за сутки. Ошибка прогноза оборачивается штрафами за небаланс и неэффективным планированием.

**Главное требование задачи — честная ретроспектива.** Прогноз на каждый день тестового периода (февраль 2026) строится только по тем прогнозам погоды, которые уже были опубликованы на момент прогноза. Фактическая погода, ставшая известной позже, не используется. Это гарантируется кодом и проверяется тестами.

**AI-агент** сам проходит весь цикл:
1. получает прогнозы погоды;
2. проверяет их качество;
3. запускает модель;
4. анализирует результат;
5. публикует прогноз с объяснением;
6. пересчитывает его, когда выходит новый прогон погоды.

## Что реализовано

- **Прогноз на тестовый период.** 28 ежедневных выпусков (31.01–27.02.2026) по 48 часов, мощность каждой турбины и ВЭС, интервал P10–P90. Для каждого выпуска есть манифест: какие прогоны погоды использованы и когда они были опубликованы. Всё лежит в `artifacts/submission/`.
- **Защита от утечки будущего.** Все данные проходят через `DataStore(as_of)`:
  - он отдаёт только прогоны, опубликованные к моменту прогноза, и только завершившиеся часы SCADA;
  - попытка взять более поздние данные вызывает `LeakageError`.
- **Основная модель** — ансамбль из трёх компонентов:
  - градиентный бустинг с MAE-потерей;
  - градиентный бустинг с MSE-потерей;
  - физическая кривая мощности турбин.

  Бустинг обучен на ~90 признаках из прогнозов ECMWF, ICON и GFS: ветер на разных высотах, направление, сдвиг ветра, плотность воздуха, разброс между погодными моделями и между последними прогонами ECMWF, календарь.
- **Интервал P10–P90:** квантильный бустинг с конформной калибровкой (CQR).
- **AI-агент** (подробнее — в разделе [AI-агент](#ai-агент)):
  - 8 инструментов, режим LLM (OpenAI) и режим правил;
  - ревизия прогноза после выхода нового прогона погоды;
  - проверка фактов в тексте LLM;
  - демо-сценарии сбоя данных;
  - журналы всех 28 выпусков LLM-агента.
- **Живой режим.** Прогноз на настоящее «завтра» по свежим прогнозам Open-Meteo. Планировщик на сервере каждые 15 минут проверяет, вышел ли новый прогон ECMWF, и сам запускает агента.
- **Бэктест** на трёх контрольных периодах по протоколу теста, 6 моделей для сравнения, метрики MAE, RMSE, смещение, покрытие интервала.
- **Веб-интерфейс** (Streamlit):
  - «Прогноз»: карточки, объяснение AI-агента с причинами уверенности, график с предыдущим прогнозом и ветром в подсказке, режимы «Февраль 2026 · тест», «Сейчас», «История» (прогноз против факта);
  - «Погода»: прогнозы четырёх моделей на момент выпуска и проверка времени их публикации;
  - «Качество прогноза»: метрики, «прогноз против факта», распределение ошибок;
  - «Данные»: загрузка своего CSV и мгновенная оценка точности;
  - «AI-агент»: схема цикла, шаги и решения, версии прогноза, живой запуск, демо сбоев;
  - плавающий чат с AI-помощником;
  - установка как приложение (PWA).
- **Развёртывание:** Docker Compose — приложение, планировщик агента, Caddy с автоматическим HTTPS.
- **Проверки:**
  - 79 автотестов (`uv run pytest`);
  - `scripts/check_site.py` проходит основной пользовательский сценарий на сайте.

## Как это работает

```
                ┌──────────────────────── AI-агент (LLM или правила) ────────────────────────┐
CSV турбин ─►   │ погода ─► проверка ─► модель ─► анализ ─► публикация ─► новый прогон? ─► пересчёт │
Open-Meteo ─►   └────────────────────────────────────────────────────────────────────────────┘
                   │ все данные только через DataStore(as_of): опубликованное к моменту прогноза
                   ▼
   признаки (48 ч × ~90) ─► ансамбль + интервал P10–P90 ─► прогноз + манифест + объяснение ─► сайт
```

1. Выпуск для даты D делается в D 14:00 по местному времени (UTC+6) и покрывает D+1 00:00 … D+2 23:00.
2. `DataStore` выбирает самый свежий прогон ECMWF, опубликованный к этому моменту (обычно 00Z того же дня). Для GFS, ICON и ECMWF 0.25° берётся самый свежий прогноз из уже вышедших.
3. Из прогнозов погоды строится таблица признаков: 48 целевых часов × ~90 признаков.
4. Модель выдаёт прогноз по каждой турбине и по ВЭС с интервалом P10–P90.
5. Агент проверяет прогноз:
   - правдоподобие;
   - согласованность с ветром;
   - сравнение с климатической нормой и прошлым выпуском;
   - уверенность.

   Затем публикует версию v1 с объяснением.
6. Когда выходит следующий прогон ECMWF, агент пересчитывает прогноз. Если изменение существенное, публикует ревизию v2.

**Интервал P10–P90** (номинальное покрытие 80%): фактическое покрытие 73% (фев 2025), 77% (дек 2025), 78% (янв 2026). Небольшой недобор объясняется сезонным сдвигом между окном калибровки и периодом прогноза.

**Выводы**
- Ансамбль лучше всех моделей для сравнения на каждом периоде: MAE −9% относительно лучшей из них, −49% относительно климатологии. Систематическое смещение близко к нулю.

- **Проверено и не принято:**
  - прогноз ECMWF в 4 соседних точках сетки (MAE 0.1682 против 0.1684 — в пределах шума);
  - повышенный вес свежих данных — тоже без выигрыша.

  Код оставлен как опция: `neighbors.use_in_model` в `config/settings.yaml`.

## AI-агент

Агент выпускает прогноз сам, вызывая инструменты. Все числа считают инструменты (детерминированный код), а агент выбирает порядок действий, принимает решения и пишет объяснение для диспетчера.

| Инструмент | Что делает |
|---|---|
| `check_available_runs` | какие прогоны погодных моделей уже опубликованы на текущий момент |
| `fetch_weather` | собирает прогнозы ECMWF, ICON и GFS на 48 часов (только опубликованные) |
| `validate_weather` | проверяет покрытие, физичность значений, согласие моделей и свежесть прогона; предлагает исключить подозрительные источники |
| `run_forecast` | запускает модель; можно исключить источники |
| `analyze_forecast` | правдоподобие, согласованность с ветром, сравнение с климатической нормой и прошлым выпуском, уверенность |
| `publish_forecast` | публикует версию прогноза с объяснением (в LLM-режиме — после проверки фактов) |
| `advance_to_next_update` | переводит время до выхода следующего прогона ECMWF |
| `compare_with_published` | сравнивает новый расчёт с опубликованной версией и советует, нужна ли ревизия |

**Цикл выпуска.**
1. В 14:00 агент публикует версию **v1**. Это и есть прогноз для сдачи, он построен строго по данным на момент выпуска.
2. Затем агент дожидается следующего прогона ECMWF (обычно в 19:00) и пересчитывает прогноз.
3. Если прогноз изменился существенно (в среднем больше 3 п.п. или хотя бы на один час больше 15 п.п.), агент публикует ревизию **v2** и объясняет, что изменилось.

За февраль 2026 ревизия понадобилась в 23 выпусках из 28. Журналы всех выпусков, сделанные LLM-агентом (`gpt-5.6-terra`, ~30 с на выпуск), лежат в `artifacts/agent/<дата>/`: в `run.json` все шаги и решения, рядом CSV каждой версии.

**Режимы с одним набором инструментов.**
- **LLM** — OpenAI Responses API с вызовом инструментов. Модель сама решает, какой инструмент вызвать, исключать ли источник и нужна ли ревизия, и пишет объяснение. Включается ключом `OPENAI_API_KEY` в `.env`.
- **Правила** — тот же цикл с решениями по порогам и объяснением по шаблону. Работает без ключа и без интернета. Если LLM недоступна или не опубликовала прогноз, агент автоматически завершает выпуск по правилам.

**Проверка фактов.**
- Каждое число в объяснении LLM сверяется с результатами инструментов, с учётом единиц: доли, проценты, п.п.
- Если в тексте есть число без источника, публикация отклоняется, и модель переписывает текст.
- На подменённых числах проверка ловит 90% подмен.

**Демо сбоев данных.** На странице «AI-агент» можно выбрать один из трёх сценариев и увидеть, как агент реагирует:
- **«испорчен прогноз ICON»** — агент исключает ICON и объясняет почему;
- **«пропуски в GFS»** — агент исключает GFS;
- **«опоздал прогон ECMWF»** — агент работает на старом прогоне и понижает уверенность.

**Живой режим.** `windagent live` строит прогноз на настоящее «завтра» по свежим прогнозам Open-Meteo. `windagent live --watch` — планировщик: каждые 15 минут он проверяет новые прогоны ECMWF и при появлении нового запускает агента. На сервере это отдельный контейнер `scheduler`. На сайте живой прогноз — режим «Сейчас» на странице «Прогноз».

## Технологии

- **Python 3.12**, менеджер окружения [uv](https://docs.astral.sh/uv/)
- **pandas, numpy, pyarrow** — обработка данных, хранение в Parquet
- **scikit-learn** — градиентный бустинг (`HistGradientBoostingRegressor`), изотоническая регрессия для кривой мощности
- **httpx** — запросы к Open-Meteo (с ограничением частоты и повторами)
- **OpenAI API** (Responses API, вызов инструментов) — LLM-режим агента и чат; необязательно
- **Streamlit, Plotly** — веб-интерфейс и графики
- **Docker Compose, Caddy** — развёртывание, HTTPS (Let's Encrypt), PWA
- **pytest** — тесты; **Playwright** — проверка сценария на сайте и запись демо-видео (`scripts/`)
- **Open-Meteo API** — архивные и свежие прогнозы погоды (ECMWF IFS, ECMWF 0.25°, GFS, ICON), реанализ ERA5

## Установка и запуск

**Вариант 1 — uv (рекомендуется).** uv сам скачает Python 3.12 и точные версии библиотек из `uv.lock`.

```bash
# установка uv (macOS / Linux), если его нет:
curl -LsSf https://astral.sh/uv/install.sh | sh

git clone https://github.com/BAITC-Hacks/hack-418ae9f6-steppe-overflow.git
cd hack-418ae9f6-steppe-overflow
uv sync
```

**Вариант 2 — pip.** Нужен Python 3.12.

```bash
python3.12 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt pytest
pip install -e . --no-deps
```

Во втором варианте команды ниже запускаются без префикса `uv run`.

**Вариант 3 — Docker.** Ничего, кроме Docker, не нужно.

```bash
docker build -t steppewind .
docker run --rm -p 8501:8501 steppewind
```

Интерфейс откроется на http://localhost:8501.

**LLM-режим и чат (необязательно):**

```bash
cp .env.example .env
```

Затем впишите в `.env` свой `OPENAI_API_KEY`. Файл `.env` не попадает в git.

## Как проверить

Всё ниже работает **без интернета и без API-ключей**: данные, архив погоды, модель и готовый прогноз уже лежат в репозитории.

```bash
# 1. Автотесты (79), в том числе: ни один из 28 выпусков февраля не использует данные из будущего
uv run pytest

# 2. Данные турбин и архив прогнозов погоды
uv run windagent data
uv run windagent weather status

# 3. Прогноз одного выпуска: какие прогоны погоды использованы и когда опубликованы + 48 часов
uv run windagent forecast --date 2026-02-10

# 4. Все 28 выпусков → artifacts/submission/ (~15 с); с закоммиченной моделью совпадает с файлами побайтно
uv run windagent submission

# 5. AI-агент на одной дате: шаги, решения, объяснение, ревизия (режим правил без ключа)
#    перезаписывает журнал LLM-агента в artifacts/agent/2026-02-10/ (вернуть: git checkout artifacts/agent)
uv run windagent agent --date 2026-02-10

# 6. Бэктест на трёх контрольных периодах (~2 мин) → artifacts/reports/backtest.md
uv run windagent features build
uv run windagent backtest --period all

# 7. Веб-интерфейс на http://localhost:8501
uv run python app/serve.py --server.port 8501
```

Дополнительно:
- `uv run windagent train` — переобучить итоговую модель с нуля (~1 мин, после `features build`);
- `uv run windagent agent --period test` — агент на всех 28 выпусках;
- `uv run windagent backtest --baselines-only` — только модели для сравнения, ~10 с.

**Сценарий в интерфейсе (или на https://steppewind.energy):**
1. «Прогноз» → листайте выпуски кнопками ‹ ›. Карточки, объяснение AI-агента, график с предыдущим прогнозом. «Пересчитать» строит выпуск заново и сверяет с сохранённым.
2. Режим «История» — прогноз против фактической выработки на прошлых датах. Режим «Сейчас» — живой прогноз на завтра.
3. «AI-агент» → выберите «Демо сбоя: испорчен прогноз ICON» → «Запустить агента». Агент сам исключит источник и объяснит решение.
4. «Данные» → «Попробовать на примере» или загрузите CSV с фактом за февраль 2026 (формат датасета организаторов, одна или две турбины). Точность прогноза посчитается сразу.
5. Кнопка чата внизу справа — вопросы о прогнозе (нужен ключ OpenAI на сервере).

**Автоматическая проверка сценария на сайте** (нужны `pip install playwright` и Google Chrome):


## Данные и интеграции

### Данные турбин — `Dataset/`

Две турбины, 10-минутные записи с 11.03.2023 по 31.01.2026:
- время (UTC+6);
- средняя скорость ветра (м/с);
- нормализованная активная мощность (0–1);
- температура (°C).

Часовой пояс UTC+6 установлен сопоставлением с реанализом ERA5. Пропуски: 6.6% у турбины 1 (включая перерыв 18.05–17.07.2024) и 1.9% у турбины 2. Если у одной турбины нет данных, для ВЭС используется вторая.

### Прогнозы погоды — [Open-Meteo](https://open-meteo.com/) (бесплатно, без ключа)

| API | Что берём | Роль |
|---|---|---|
| [Single Runs](https://open-meteo.com/en/docs/single-runs-api) | прогоны `ecmwf_ifs` 00/06/12/18 UTC с точным временем старта, с 15.03.2024 | основной прогноз ветра |
| [Previous Runs](https://open-meteo.com/en/docs/previous-runs-api) | `ecmwf_ifs025`, `gfs_seamless`, `icon_seamless`: прогнозы, выпущенные 1–3 суток назад | дополнительные модели |
| [Historical Weather](https://open-meteo.com/en/docs/historical-weather-api) (ERA5) | реанализ | только анализ (проверка часового пояса); в прогнозе не используется |

**Задержка публикации.** Прогон считается доступным через фиксированную задержку после старта: ECMWF — 7 ч, GFS — 5 ч, ICON — 4 ч (`config/settings.yaml`).

**Previous Runs.** Сравнением с прогонами ECMWF проверено, что значение «N суток назад» для часа V берётся из прогона, стартовавшего примерно за 24·N часов до V. Для каждого целевого часа используется минимальное N, прогон которого уже опубликован.

### OpenAI API (необязательно)

LLM-режим агента и чат на сайте. Без ключа агент работает в режиме правил, а чат отключён.

| Переменная (`.env`) | По умолчанию | Назначение |
|---|---|---|
| `OPENAI_API_KEY` | — | ключ OpenAI |
| `OPENAI_MODEL` | `gpt-5.6-terra` | модель агента |
| `OPENAI_CHAT_MODEL` | `gpt-6-luna` | модель чата |
| `CHAT_LIMIT_PER_IP` / `CHAT_LIMIT_TOTAL` | 20 / 500 | вопросов в чат в день: с одного адреса / всего |
| `AGENT_LLM_LIMIT_PER_IP` / `AGENT_LLM_LIMIT_TOTAL` | 3 / 40 | LLM-запусков агента в день с сайта |

Планировщик живого режима делает не больше 8 LLM-запусков в сутки, дальше работает по правилам.

## Ограничения

- **Данных SCADA за февраль 2026 нет**, поэтому прогноз на тестовый период строится только по прогнозам погоды, без коррекции по свежим наблюдениям.
- **Точность упирается в прогноз ветра:** ошибка ECMWF на сутки вперёд — 2–2.5 м/с. Внезапные простои и ограничения мощности модель не предсказывает, а оценка идёт по фактической выработке.
- **Отдельные прогоны ECMWF есть только с 15.03.2024**, поэтому модели, использующие погоду, обучаются на ~22 месяцах. В марте–августе 2024 в архиве нет прогонов 06/18 UTC; на выпуски это не влияет, используется прогон 00 UTC.
- **Интервал P10–P90** на контрольных периодах накрывает факт в 73–78% случаев при номинале 80%.
- **Разные платформы.** Журналы агента посчитаны на сервере (x86), файл сдачи — на Mac (ARM). Из-за разного округления на процессорах версия v1 в журналах на 5 датах отличается от файла сдачи в отдельных часах, меньше чем на 1 п.п. На одной платформе результаты совпадают точно.
- **Проверка фактов** гарантирует, что в тексте LLM нет чисел без источника. Но она не проверяет, что число приписано правильной величине.
- **Время в интерфейсе** везде UTC+6, как в данных SCADA. Официальное время Алматы с 2024 года — UTC+5.
- **Бесплатный Open-Meteo** ограничен 10 000 запросов в сутки на IP; для проверки проекта интернет не нужен.
