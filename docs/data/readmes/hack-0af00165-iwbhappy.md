# ИИ-ассистент для чата ekt.kz

Прототип для HackAlem AI, трек «Торговля». Кейс партнёра — ТОО «Электрокомплект» (ekt.kz).

Консультант в одном окне чата на сайте: отвечает по каталогу электротехники —
наличие, технические характеристики, сертификаты, аналоги, условия покупки —
и добавляет товары в корзину **только после явного подтверждения клиента**.
Последний шаг — ссылка на корзину; заказ клиент оформляет сам.

- **Настоящие данные.** 300 позиций из API ekt.kz: артикулы, цены,
  характеристики, остатки по складам, рекомендации партнёра. Условия покупки —
  с публичных страниц ekt.kz. Синтетические только сертификаты, и они помечены.
- **Подтверждение проверяет сервер, а не промпт.** Модель может только
  предложить товар. Добавление исполняется после проверки реплики клиента
  на согласие — одноразово и не больше остатка.
- **Работает без сети.** Нет ключа или интернета — записанный режим проходит
  сценарий, и интерфейс честно помечает его бейджем `MOCK`.

**Попробовать:** [витрина с чатом](https://hackalem10.vercel.app) ·
[чужой сайт с виджетом](https://hackalem10.vercel.app/demo-site) ·
[закладка для ekt.kz](https://hackalem10.vercel.app/try)

## Проверка за 5 минут

Нажмите «Новый диалог». Демо-артикулы берутся из каталога (`npm run demo`
печатает текущие): `R9F12110` — в наличии, `404029х` — без остатка
(последняя буква — кириллическая «х»; латинская «x» тоже найдётся).

1. **Наличие, характеристики, сертификат.** «Расскажи про артикул
   R9F12110: есть в наличии, какие характеристики, есть ли сертификат?»
   Ожидается карточка из каталога: 558 шт., 2 295 ₸, номинальный ток 10 А
   и сертификат с явной отметкой «демонстрационный».
2. **Аналог с обоснованием.** «А 404029х есть? Если нет — что посоветуешь
   взамен и почему?» Ожидается нулевой остаток и хотя бы один аналог
   в наличии; ответ объясняет, что совпадает и чем аналог отличается.
3. **Условия покупки.** «Какие условия оплаты и доставки?» Ожидается
   ответ по условиям с сайта ekt.kz: способы оплаты, стоимость и сроки
   доставки, когда нужен менеджер.
4. **Добавление с подтверждением.** «Добавь R9F12110 в корзину, 2 штуки».
   Появляется карточка-предложение, корзина остаётся пустой. Затем
   «Да, добавь» или кнопка «Да» — в корзине 2 шт. на 4 590 ₸. Запрос
   сверх остатка сервер урежет до доступного, и агент об этом скажет.
5. **Актуальная корзина.** «Открыть страницу корзины» — те же позиция
   и количество. В адресе `/cart?c=…` токен только для чтения, а не
   идентификатор сессии.
6. **Попытка обойти подтверждение.** В новом диалоге: «Добавь R9F12110
   в корзину, 1 штуку» — карточка, корзина пуста. «А можно добавить?» —
   это вопрос, корзина пуста. «Если есть на складе, добавь» — это условие,
   корзина пуста. «Да» — позиция добавлена. Карточка после этого теряет
   кнопки, а повторное подтверждение того же предложения сервер отклонит:
   оно одноразовое (smoke, раздел 4).

## Запуск

Нужен Node.js 20 или новее (проверено на 22).

```bash
git clone https://github.com/BAITC-Hacks/hack-0af00165-iwbhappy.git
cd hack-0af00165-iwbhappy
npm install
npm run dev
```

Открыть http://localhost:3000. Ключ к модели не обязателен: без него
приложение работает в записанном режиме и проходит весь сценарий.

С живой моделью — создать `.env.local`:

```
LLM_MODE=auto
OPENAI_API_KEY=<ключ>
LLM_MODEL=gpt-4.1-mini
```

### Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_MODE` | `auto` — модель, при сбое записанный режим; `live` — только модель; `mock` — только записанный | `auto` |
| `OPENAI_API_KEY` | ключ модели; живёт только на сервере | — |
| `LLM_MODEL` | основная модель | `gpt-4.1-mini` |
| `LLM_FALLBACK_MODEL` | запасная модель при rate limit | `gpt-4.1-nano` |
| `OPENAI_BASE_URL` | совместимый прокси, если доступ выдадут на площадке | — |
| `DB_URL`, `DB_AUTH_TOKEN` | база: `file:…` локально, `libsql://…` — удалённая (Turso) | `file:./.data/hack.db` |
| `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` | то же; их подставляет интеграция Turso в Vercel | — |
| `EKT_API_BASE`, `EKT_API_USER`, `EKT_API_PASSWORD` | только для `npm run seed` — перевыгрузки каталога | — |

Ключи и пароль к API партнёра — только в `.env.local`, он в `.gitignore`.
В репозитории лежит `.env.example`: значения по умолчанию заполнены,
ключи и пароли — пустые.

### Проверки

```bash
npm run verify
```

Одна команда перед сдачей: проверка типов → smoke → demo → mock-check.
Останавливается на первой ошибке. Demo и mock-check работают в записанном
режиме без вызова внешней модели, каждый со своей тестовой базой.

| Команда | Что проверяет |
|---|---|
| `npm run smoke` | 92 детерминированные проверки через инструменты, без модели: пять тестов ТЗ и отрицательные случаи — подтверждение в том же ходу, без согласия, на другой товар, повторное; маскирование, поиск, вложения |

| `npm run mock-check` | 22 свободные реплики в записанном режиме: русский и казахский, смена товара, согласие и отказ — страховка на случай без сети |

### Устойчивость

- **Нет сети или ключа** — `LLM_MODE=auto` уводит в записанный режим,
  сценарий доходит до конца. В шапке загорается `MOCK`: выдавать
  записанный ответ за живую модель нельзя.
- **Rate limit, 5xx, таймаут** — три попытки с экспоненциальной паузой,
  затем запасная модель, затем mock. Повтор запрещён, если часть ответа
  уже ушла пользователю.
- **Мусор в аргументах** — схема отклоняет, текст ошибки уходит модели,
  даётся одна попытка переписать вызов.
- **Смена схемы БД** — версия схемы хранится в таблице `meta` и
  проверяется до применения схемы; при расхождении база пересобирается
  сама. Каталог засевается одной транзакцией: несколько экземпляров
  на Vercel стартуют одновременно и не видят его полузаполненным.

## Правило подтверждения

Ключевое требование кейса: состав корзины не меняется без явного
согласия клиента. Это не строчка в промпте, а инвариант на сервере.

1. Модель не может добавить товар сама. `propose_add` только записывает
   предложение со статусом `pending` и возвращает `proposalId`; корзина
   не трогается.
2. Подтверждение приходит одним из двух путей, и **решение принимает
   сервер, а не модель**:
   - **кнопка «Да»** — `POST /api/confirm` идёт из интерфейса напрямую,
     минуя модель; подделать этот вызов модель не может, потому что
     в нём не участвует;
   - **текст** — модель вправе вызвать `confirm_add`, но сервер исполнит
     его только после трёх проверок. Текст реплики клиента сервер
     сохраняет сам, до обращения к модели.
3. Три проверки текстового пути:
   - **предложение создано в предыдущем ходу** — иначе модель в одном
     ответе предложила бы и сама подтвердила, подставив под проверку
     ту же фразу клиента;
   - **реплика — явное согласие.** Вопросы («а можно добавить?»),
     условия («если есть на складе, добавь») и отрицания согласием
     не считаются; по-русски и по-казахски. Сомнительное — отказ;
   - **реплика не называет другой товар.** «Добавь 027004» — новая
     просьба, а не согласие на висящее предложение про другой артикул.
     Эту дыру нашли на живом демо: модель попыталась подтвердить старое
     предложение на просьбу о новом товаре.
4. Предложение одноразовое: условный `UPDATE … WHERE status='pending'`,
   гонкой двух запросов его не обойти.
5. Количество не больше доступного остатка. Если запрошено больше —
   добавляется доступное, и агент обязан об этом сказать.
6. Спецификация из файла проходит через ту же функцию `consumeProposal`.
   Второго пути изменения корзины в приложении нет.

Всё перечисленное покрыто `npm run smoke`, включая отрицательные случаи.

## Данные

Каталог — **боевая выгрузка из API партнёра**, не выдумка:

```
GET https://ekt.kz/api/products?page=N       список
GET https://ekt.kz/api/products/detail?id=N  карточка с характеристиками и складами
```

`scripts/seed-from-api.ts` ходит туда один раз и пишет `data/catalog.json`,
который лежит в репозитории. В рантайме сеть к ekt.kz не нужна: приложение
читает SQLite. Демонстрация не зависит ни от чужого API, ни от Wi-Fi.

Срез: 300 позиций. Характеристики берутся из `properties` карточки
(номинальный ток, число полюсов, напряжение, отключающая способность),
сопутствующие товары — из `properties.RECOMMEND`, собственных
рекомендаций партнёра. Изначально мы читали это поле как список
аналогов; проверка на данных показала, что все связи ведут из
автоматов и УЗО на клеммы, то есть это допродажа, а не замена.
Аналоги подбираются по разделу каталога, типу, бренду и цене.

### Что пришлось учесть в реальных данных

**Не все склады торговые.** В `stores[]` вперемешку городские склады и
служебные: «Брак MEGALIGHT», «Востановленный продукт», «перемещение»,
«Образцы Отдел Закупа», «Витрина ТЗ». Их остаток не считается доступным —
показать брак как наличие значит соврать клиенту. Поле `quantity` верхнего
уровня суммирует все склады, включая служебные, поэтому доступный остаток
пересчитывается по отфильтрованному списку.

**Описание противоречит характеристикам.** У товара id 515291 в названии
и описании «160А», а в `properties.NOMINALNYY_TOK` — «250 А». Источником
чисел объявлены только `properties`; описание показывается как текст и
никогда не служит источником характеристик. Это же зафиксировано
в системном промпте.

**Грязные имена и артикулы.** Названия встречаются с префиксом `***`
и продублированным артикулом; поле `article` бывает служебным
(`200300285_`), а настоящий артикул поставщика лежит в
`properties.ARTIKULPOSTAVSHCHIKA`. Чистка делается на этапе выгрузки,
оригинал сохраняется в `rawName`.

**Кириллица и латиница вперемешку.** В каталоге есть и «16А», и «25A»
латиницей, и «3P», и артикул «404029х» с русской «х». Встроенный
`LOWER()` в SQLite понимает только латиницу, а `LIKE` для кириллицы
чувствителен к регистру: «узо» не находило «УЗО». Поэтому текст для
поиска готовится при засеве средствами JS: нижний регистр, ё → е,
латинские буквы-двойники — в кириллицу. Плюс синонимы (УЗО ↔ ВДТ,
автомат ↔ АВ, дифавтомат ↔ АВДТ) и бонус за совпадение с типом изделия:
«автомат 16А» ставит автоматы выше боксов для автоматов.

### Что синтетическое

- **Сертификаты.** В API их нет, а требование кейса есть. Проставлены
  примерно трети позиций, детерминированно по артикулу, с флагом
  `demo: true`. Интерфейс и агент помечают такой сертификат как
  демонстрационный. Выдавать придуманный сертификат за настоящий нельзя.

Всё остальное — реальные данные партнёра. Артикулы, названия, цены,
характеристики, остатки и рекомендации — из API. **Условия покупки**
(`data/terms.json`) — с публичных страниц ekt.kz (`/about/howto`,
`/about/faq`, `/about/contacts`): оплата для физлиц и юрлиц, тарифы
доставки по Алматы, порог бесплатной доставки по стране, города
самовывоза, гарантия, возврат, контакты. Источник и дата сверки
записаны в самом файле.

## Вложения

Раздел 5 ТЗ: вход — не только текст, но и файлы.

**Спецификация** (`.xlsx`, `.xlsm`, `.csv`, `.tsv`, `.txt`, `.docx`)
разбирается своим кодом, без внешних библиотек. Готовый пакет для xlsx
на npm тянет известные уязвимости, а разбирать предстоит файл, который
прислал кто угодно. Формат — zip с XML внутри, и нужная его часть
читается средствами Node: `zlib` умеет `inflateRaw`, остальное — разбор
заголовков. Из файла берутся только значения ячеек и текст: ни формулы,
ни макросы, ни внешние ссылки не исполняются.

**PDF и фото накладной** читает модель отдельным вызовом и возвращает
строки «артикул — количество»; дальше они идут тем же путём, что и таблица.
Фото модель сначала классифицирует: изделие или документ.

Артикулы сопоставляются с каталогом, найденное собирается в одно
предложение на несколько позиций. Ненайденные строки показываются
отдельным блоком — молча терять позиции из спецификации нельзя.
Подтверждение при этом обычное: предложение проходит через ту же
функцию, что и добавление одного товара.

**Фото товара** читается отдельным одноразовым вызовом модели, вне
агентного цикла: картинка не попадает в поток сообщений и не трогает
стриминг с ретраями. Сравнения изображений нет намеренно — в каталоге
электротехника, где модульные автоматы внешне неотличимы, визуальное
сходство почти не несёт сигнала. Зато на фото читается текст: артикул,
бренд, номинал. Модель возвращает короткий JSON, дальше работает
обычный поиск по каталогу.

## Сопутствующие товары, казахский язык, менеджер

**Сопутствующие.** После подтверждения одной позиции сервер сам
прикладывает до двух сопутствующих товаров из рекомендаций партнёра —
и в ответ модели, и в ответ кнопки «Да». Агент предлагает их одной
фразой с обоснованием, интерфейс — подсказками. В корзину они сами
не попадают: это новое предложение и новое подтверждение.

**Казахский.** Агент отвечает на языке клиента. Язык определяет
**сервер**, а не модель: правило в промпте живая модель игнорировала,
отвечая на казахские реплики по-русски, — промпт и каталог на русском
и перетягивают. Сервер смотрит на буквы, которых нет в русском алфавите
(ә ғ қ ң ө ұ ү һ і), и добавляет на ход явную инструкцию. Названия
и характеристики товаров не переводятся. Интерфейс переключается RU / KZ.

Правило подтверждения работает и на казахском: «иә», «жарайды»,
«қосыңыз» — согласие; «жоқ», «керек емес», «қоспа» — отказ. Вопрос
с частицей «ма/ме» («қосуға бола ма») согласием не считается, даже
без знака вопроса.

**Менеджер.** Крупная партия, претензия или возврат, доставка не по
Алматы, прямая просьба позвать человека — агент даёт реальные контакты
из условий покупки и не обещает обратного звонка. В интерфейсе есть
кнопка «Связаться с менеджером».

## Безопасность и приватность

ТЗ требует учесть приватность клиента и защиту от несанкционированного
изменения корзины. Что сделано:

- **Ссылка на корзину — только для чтения.** В ней случайный токен, а не
  идентификатор сессии: сессия даёт право менять корзину через чат,
  а ссылкой клиент делится. По токену сессию не восстановить.
  Идентификатор сессии создаётся через `crypto.randomUUID()`.
- **Платёжные данные не хранятся.** Номер карты (с проверкой Луна), CVV
  и IBAN вырезаются из реплики до всего остального — в модель, журнал
  сервера и историю, которую видит модель, попадает метка. Лента чата
  сохраняется в браузер клиента тоже уже с меткой. Агент говорит клиенту,
  что в чате платёжные данные не нужны. В журнал дополнительно
  не пишутся телефон, email и ИИН.
- **Журнал сервера наружу не отдаётся.** Он общий для всех сессий.
- **Лимиты**: 20 сообщений и 6 файлов в минуту с адреса, реплика до
  2000 символов. Лимитер в памяти экземпляра — защита от одного
  назойливого клиента, не от распределённой атаки; для прода нужен WAF.
- **Встраивание во фрейм** разрешено только нам и ekt.kz
  (`frame-ancestors`): иначе чужая страница может накрыть кнопку «Да»
  прозрачным фреймом.
- **Вложения** не исполняются: из xlsx и docx берутся только значения
  ячеек и текст, без формул, макросов и внешних ссылок.

### База на Vercel

На serverless у каждой функции свой `/tmp`. С файловой SQLite чат,
подтверждение и страница корзины попадали в разные базы, и страница
корзины оказывалась пустой — это проверено на проде. Поэтому публичная
версия работает на Turso (удалённый libSQL): переменные подставляет
интеграция Turso в Vercel, код тот же. С ноутбука процесс один,
и файловой базы достаточно.

## Встраивание в сайт

Одна строка на любой странице, независимо от платформы сайта:

```html
<script src="https://hackalem10.vercel.app/embed.js" async></script>
```

Скрипт рисует кнопку и панель с iframe на `/embed`. Стили изолированы
дважды — shadow DOM и самим iframe, — поэтому ни сайт не ломает чат, ни
чат сайт. Связь с родительской страницей идёт через `postMessage` с
проверкой источника и origin с обеих сторон; по каналу ходят только
служебные сообщения — готовность, высота, закрытие. Данные корзины
и диалога через него не передаются.

- [`/demo-site`](https://hackalem10.vercel.app/demo-site) — сторонняя
  витрина с другим оформлением и подключённым виджетом.
- [`/try`](https://hackalem10.vercel.app/try) — закладка для браузера:
  откройте ekt.kz, нажмите закладку — виджет появится на живом сайте
  партнёра. Сам сайт при этом не меняется: виджет видит только тот,
  кто нажал закладку.

## Ограничения

### По требованиям кейса

- агент **не оформляет заказ** — последний шаг это ссылка на корзину;
- **не запрашивает и не хранит платёжные данные**;
- **не меняет корзину** без явного подтверждения;
- **не сообщает недостоверных данных** о цене и наличии: все числа
  приходят из инструментов, модель их не придумывает и не пересчитывает;
- если данных нет — говорит, что не нашёл, и предлагает связаться
  с менеджером. Выдумывать артикулы запрещено.

### Ограничения прототипа

- **Каталог — срез из 300 позиций и снимок на момент выгрузки.** Цены
  и остатки не обновляются в реальном времени; в проде — периодическая
  синхронизация через тот же API.
- **Корзина своя, а не корзина Bitrix.** Для настоящей интеграции нужен
  API корзины сайта; сейчас ссылка ведёт на нашу страницу корзины.
- **Сертификаты синтетические** и помечены как демонстрационные.
- **История диалога — в браузере, в пределах сессии.** Для авторизованных
  клиентов id должен приходить с сервера Bitrix с подписью: верить
  идентификатору из браузера нельзя.
- **Лимитер запросов — в памяти экземпляра.** Для прода — WAF или
  лимитер на Redis.

## Как делали: Claude и Codex

Условие хакатона — использовать Codex. Роли разделены в
[AGENTS.md](AGENTS.md): архитектура, контракты инструментов, правила
поведения агента, приёмочные критерии и системный промпт — одна зона;
реализация кода — Codex.

Каждая задача Codex — отдельная постановка в [docs/codex/](docs/codex)
(01–08): какие файлы менять, что трогать нельзя, чем проверить результат.
Каждый результат проверялся прогоном, а не по отчёту. Грабли, на которые
наступили за день, собраны в конце `AGENTS.md`: от `\b`, который
не видит кириллицу, до базы, которая на Vercel у каждой функции своя.

- [docs/codex/HANDOVER.md](docs/codex/HANDOVER.md) — состояние проекта,
  инварианты и безопасная процедура деплоя;
- [docs/DEFENSE.md](docs/DEFENSE.md) — ответы на вопросы жюри.
