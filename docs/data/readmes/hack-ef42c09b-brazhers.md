# Money Graph — объяснимый анализ транзакционной сети

Инструмент для AML-аналитика банка: по обезличенным переводам назначает каждому узлу структурную роль, выделяет сообщества и формирует очередь проверки с числовыми обоснованиями. В браузере можно найти полный `gid`, увидеть прямых плательщиков и получателей, суммы, количество переводов, правило роли и состав приоритета.

Результаты — гипотезы для проверки по наблюдаемому графу. Имена, возраст, доход и другие отсутствующие атрибуты клиента не добавляются. `role_score` показывает заданную силу правила, а не вероятность правонарушения.

Инструкция и сценарий выступления: [HOWTO.md](HOWTO.md). Текущая проверка и исправления: [FINAL_CHECK.md](FINAL_CHECK.md). Предыдущий аудит: [AUDIT_REPORT.md](AUDIT_REPORT.md), [SECURITY.md](SECURITY.md).

## Запуск одной командой

Нужен **Python 3.10 или новее**. Для предоставленных Markdown-таблиц достаточно стандартной библиотеки. Команды выполняются в текущем репозитории `C:\hackalemai\submission`. Одна команда генерирует результаты; следующие независимо проверяют их, запускают тесты и открывают локальный сервер:


После запуска сервера откройте [http://127.0.0.1:8765/](http://127.0.0.1:8765/); остановка — Ctrl+C. В текущем приватном репозитории таблицы `data/nodes.md`, `data/edges.md`, `data/transactions.md` и результаты `out/` **отслеживаются Git** и уже присутствуют. Запуск пайплайна пересоздает результаты без ручных промежуточных действий; если `out/` отсутствует, каталог создается автоматически. ## Вход из Parquet

Для Parquet нужна одна прямая зависимость: **`pyarrow==25.0.1`**, закрепленная в `requirements.txt`. Однократная подготовка окружения:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Поместите разрешенные `nodes.parquet`, `edges.parquet`, `transactions.parquet` в `parquet_data/`. Полный пересчет выполняется одной командой:

```powershell
.venv\Scripts\python.exe pipeline.py --data parquet_data --out parquet_out
```

Загрузчик предпочитает полный набор Markdown, если в каталоге есть все три `.md`; иначе использует полный набор Parquet. Смешанный набор форматов не объединяется. Отдельный каталог устраняет неоднозначность выбора.

При предыдущем аудите путь Parquet проверен на локально преобразованных копиях **всех** предоставленных Markdown-строк. Оригинальные Parquet-файлы организаторов отсутствовали. Результаты преобразованного набора совпали с Markdown. pandas не требуется: его нативная библиотека тогда была заблокирована Windows Application Control, поэтому загрузчик использует Arrow напрямую. Политика Windows не изменялась. Команды установки выше относятся к отдельной подготовке Parquet; текущий Markdown-запуск и стандартные тесты установки пакетов не требуют. Пути `.venv` относятся к окружению, созданному в текущем каталоге репозитория.

`load_tables`, `normalize_tables` и `validate_inputs` в `pipeline.py` проверяют точный состав колонок, int64-идентификаторы без преобразования из float, глубины и согласованность seed с глубиной 0. Для Parquet проверяются типы: идентификаторы и `n_tx` — int64, глубины — знаковые целые, суммы — float64, seed — bool, дата — календарная дата либо timestamp без часового пояса ровно в полночь.

Чрезмерные значения, способные переполнить расчет, отвергаются. Неизвестные клиентские колонки не принимаются.

Оборот — **365 890 012.01 KZT**; максимальная разница суммы транзакций и ребра — `5.820766091346741e-11 KZT`. ## Метрики и точные правила ролей

`in_deg/out_deg` — число разных плательщиков/получателей; `in_tx/out_tx` — количество отдельных переводов; `in_kzt/out_kzt` — наблюдаемые суммы. Денежные суммы для правил накапливаются через `Decimal(str(amount))`; `pass_through` получается делением этих Decimal-сумм с единственным преобразованием результата в float. Это сохраняет бизнес-границы доли `0.50`, `0.70` и `1.30` без предварительного двоичного округления накопленных сумм. Если входящая сумма нулевая, доля отсутствует. Эта доля не является полным балансом счета.

PageRank следует направлению «плательщик → получатель» с весом `sum_kzt`, затуханием **0.85**, пределом **200 итераций** и остановкой при сумме абсолютных изменений меньше `1e-12`. Betweenness рассчитывается методом Brandes с Dijkstra по направленному графу: длина ребра **`1 / log(1 + sum_kzt)`**, нормировка **`(N-1)*(N-2)`**. Крупный перевод получает меньшую условную длину; это модель структурной связи, не время прохождения денег.

Квантили вычисляются заново. В отсортированных `N` значениях позиция равна `(N-1)*q`; между соседями применяется линейная интерполяция. Точные пороги текущего `analysis_summary.json`:

| Порог | Значение |
|---|---:|
| P75(`in_deg`) | `1.0` |
| P90(`in_deg`) | `2.0` |
| P75(`out_deg`) | `1.0` |
| P90(`out_deg`) | `3.0` |
| P75 положительных betweenness | `9.738917745675346e-05` |
| P75 PageRank по всем узлам | `0.00046046328200250765` |

Для betweenness берутся положительные значения, поскольку множество нулей скрывает различия между посредниками. Нижняя граница степени — `max(1, квантиль)`, чтобы нулевой квантиль сам по себе не создавал сигнал. Константы доли пересылки и силы правил — заданные эвристики; они не подгоняются под конкретные `gid`.

Правила в `build_features` (`pipeline.py:596`) применяются **сверху вниз; первое совпадение завершает выбор**:

| № | Роль и точное условие | `role_score` |
|---|---|---:|
| 1 | `terminal`: `out_deg == 0` и `depth == 4` | `0.45` |
| 2 | `terminal`: `out_deg == 0` и `in_deg > 0`; после правила 1 глубина меньше 4 | `0.82` для не-seed; `0.50` для seed |
| 3 | `coordinator`: `in_deg >= max(1, P75(in_deg))`, `out_deg >= max(1, P75(out_deg))`, `betweenness > 0` и `betweenness >= P75(положительных betweenness)` | `0.76` |
| 4 | `consolidator`, не-seed: `in_deg >= max(1, P90(in_deg))`, доля пересылки существует и `< 0.50` | `0.72` |
| 5 | `consolidator`, seed: `in_deg >= max(1, P90(in_deg))` и `pagerank >= P75(pagerank)` | `0.62` |
| 6 | `transit`, не-seed: `in_deg >= max(1, P75(in_deg))`, доля пересылки существует и `0.70 <= pass_through <= 1.30` | `0.68` |
| 7 | `distributor`: `out_deg >= max(1, P90(out_deg))` | `0.66` |
| 8 | `peripheral`: ни одно предыдущее правило не сработало | `0.50` |

У правила 5 наличие исходящего ребра следует из порядка терминальных правил. Для seed накопление — более слабая гипотеза по степени и PageRank, поскольку доля пересылки искажена неполными входящими. Изолированный seed получает `peripheral`: наблюдений о потоках нет.

`evidence` содержит реальные числа и оговорки seed/глубины 4, максимум **200 символов**. Повторные переводы учитываются в `in_tx/out_tx` и объяснении; самостоятельного порога по их количеству для назначения роли нет. В правилах счетный сигнал задается числом разных контрагентов, денежный — долей пересылки и взвешенными метриками. Множество операций одного плательщика не приравнивается к множеству независимых плательщиков.

Распределение: `consolidator` — **88**, `transit` — **92**, `distributor` — **85**, `terminal` — **1 535**, `coordinator` — **147**, `peripheral` — **301**. Среди терминальных **444** имеют score `0.45` из-за границы четвертого шага. Все значения `role_score` — фиксированная сила правила, **не калиброванная вероятность**.

## Кластеры и гипотезы

Многоуровневый **Louvain** работает на ненаправленной проекции с весом `sum_kzt`, разрешением **1** и генератором перестановок **seed 41**; встречные веса суммируются. Пределы реализации — **20 уровней**, **100 проходов на уровень**. После Louvain каждое сообщество разбивается на компоненты связности собственного индуцированного подграфа: путь через узлы другого сообщества не делает его связным. Затем применяется прежняя нумерация по убыванию размера и минимальному `gid`. Сообщество группирует связанные потоки, его состав сам по себе не доказывает единую организацию. Изолированные узлы остаются отдельными сообществами; при изменении данных номера могут измениться.

`make_cluster_rows` (`pipeline.py:731`) считает `sum_kzt_internal` по исходным **направленным** ребрам с обоими концами внутри сообщества. `top_gids` содержит до пяти участников по полному приоритету; при равенстве выбирается меньший `gid`. Число структурных сигналов — сумма числа `consolidator`, `coordinator`, `distributor` и `transit`.

Текст `hypothesis` выбирается по составу в таком порядке:

1. Есть seed и consolidator/coordinator — связь seed с накоплением или координацией.
2. Есть consolidator/coordinator — накопление или координация в наблюдаемой сети.
3. Есть distributor — веерное распределение.
4. Есть transit — пересылка средств.
5. Иначе — фрагмент без выраженного сигнала.

Каждый текст начинается с `Hypothesis`, содержит **число seed / число узлов**, число структурных сигналов и измеренный внутренний оборот, завершаясь предложением проверить транзакции. Оборот в тексте округлен до целого KZT; числовая колонка сохраняет расчетное значение. Глобальная оптимальность разбиения не заявляется.

## Формула приоритета

`build_features` (`pipeline.py:562`) использует процентильные ранги:

```text
priority_score = 0.30 * rank(pagerank)
               + 0.25 * rank(in_deg)
               + 0.25 * rank(betweenness)
               + 0.10 * rank(out_deg)
               + 0.10 * rank(seed_reach)
```

Для `N > 1` ранг — средняя позиция среди равных значений, считая с нуля, деленная на `N-1`. Равные значения получают одинаковый ранг; для единственного узла он равен `0.5`. Ранги лежат в `[0,1]`, веса суммируются в 1. Формула объединяет значимость получателя, число связей, посредничество и близость к seed без сложения исходных величин разных шкал.

`seed_reach` — число разных seed на расстоянии **не более двух шагов в ненаправленном соседстве**. Seed учитывает себя на расстоянии 0 (`seed_reach_within_two_hops`, `pipeline.py:404`). Это близость в графе, не число направленных денежных маршрутов.

Сортировка — по полному приоритету по убыванию, затем числовому `gid` по возрастанию. CSV хранит шесть знаков после запятой: визуально одинаковые оценки могут иметь разные полные значения. `why` включает приоритет и объяснение роли. `role_score` и номер кластера в формулу не входят.

## Ограничения и масштабирование

Отсутствуют межбанковские переводы, входящие из-за границ выборки, суммы ниже 5 000 KZT и продолжение обхода после глубины 4. Полный баланс, последовательность прохождения конкретных денег и дробление ниже порога установить нельзя. `terminal` до четвертого шага означает отсутствие захваченного исходящего потока в этой выгрузке.

Размеченных истинных ролей нет: accuracy, полнота обнаружения и вероятность роли не оценены. Фиксированные scores не калиброваны. Квантили степени на разреженном графе могут быть малы; порядок правил может скрывать вторую подходящую роль. Месячная доля пересылки не подтверждает быстрый транзит. Seed-правило консолидации — более слабый структурный признак, без утверждения об остатках денег.

Даты и минимальная сумма привязаны к июлю 2026 и этому контракту; для другого периода требуется осознанная настройка кода. Временные паттерны, циклы, удаление узлов и внешние сведения сейчас не рассчитываются. Номера кластеров нельзя сравнивать между снимками без сопоставления. Весь граф хранится в памяти и HTML. Многопользовательский публичный сервис с разграничением доступа не реализован.

При росте до **примерно 1 млн узлов** точная betweenness по всем источникам станет узким местом. Потребуются графовая БД или другое хранилище с индексами, разбиение по компонентам/периодам, приближенная betweenness по выборке источников и PageRank на подходящем вычислительном движке. Обновления следует считать для затронутых областей; глобальные квантили — версионировать по снимкам. Интерфейс должен запрашивать ограниченное соседство и сводки сообществ вместо полного графа в HTML. Эти изменения описаны как план, не заявлены реализованными.
