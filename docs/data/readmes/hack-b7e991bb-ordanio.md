# Прогноз выработки ВЭС: агент на архивных прогнозах погоды

Команда Ordanio, HackAlem AI, Астана, 23.09.2026. Задача «Agentic AI для прогнозирования выработки ВЭС»
(владелец задачи: Самрук-Казына), трек «Энергетика».

Развёрнутая демонстрационная версия: https://hackathon.ordanio.com (Docker на сервере в Амстердаме;
на сервере включены необязательные OpenAI-функции и фоновый ролик). Воспроизводимый сценарий проверки
описан для репозитория ниже.

## Назначение

Ветростанция должна каждый день заранее сообщать, какую мощность дадут её турбины завтра
и послезавтра по часам: ошибка прогноза стоит денег на балансирующем рынке. Проект отвечает
на вопрос «какую нормализованную мощность выдадут две турбины по часам на два следующих календарных
дня», если известен только прогноз погоды, и делает это сам для каждой даты выпуска с 31 января
по 28 февраля 2026; выпуск условно выполняется в 23:59.

Вход: история работы двух турбин (10-минутные замеры с 11.03.2023 по 31.01.2026, выданы
организаторами, `data/raw/`) и архивные прогнозы погоды Open-Meteo по координатам турбин.
Выход: для каждого дня выпуска почасовой прогноз на 48 часов по каждой турбине с коридором
неопределённости (p10, p50, p90), журнал агента с анализом дня, файлы CSV.

## Что реализовано

- Модель прогнозирования по историческим данным турбин: три квантильные модели градиентного
  бустинга (scikit-learn), обученные на парах «прогноз погоды на этот час → фактическая выработка».
  Признаки только из прогноза погоды и календаря, замеры турбины в признаки не входят.
- Самостоятельное получение прогнозов погоды по координатам турбин из открытого источника
  Open-Meteo (без ключа и регистрации), с кэшем ответов в репозитории.
- Почасовой прогноз на 48 часов по двум турбинам с коридором p10–p90.
- Agentic-цикл на каждый день выпуска: архивный прогноз погоды по принятой реконструкции доступности → признаки → модель → CSV →
  анализ (сравнение с прогнозом предыдущего дня, часы низкой уверенности, экстремальный ветер,
  ошибка за вчера при наличии факта) → сводка в журнал → следующий день с пересчётом.
- Воспроизведение «как в прошлом» на 31.01–28.02.2026 одной командой: 29 прогнозов и общий журнал.
- Проверка модели на январе 2026, который в обучение не входил: те же веса модели и то же основное
  упреждение погоды 48/72 ч, что у февральского агента, против трёх точек отсчёта; отчёт с числами
  `model/artifacts/report.md`. Агент дополнительно применяет правило обнуления при прогнозном ветре
  выше 25 м/с; в январской и декабрьской проверках таких часов не было (максимум прогнозного ветра
  на 100 м 12,2 и 14,0 м/с), поэтому оно их результат не меняет.
- Веб-страница: при открытии сразу последний готовый прогноз и карточка с метриками проверки;
  выбор даты, кнопка, лента шагов агента с временем, графики с интервалом p10–p90 по турбинам,
  панель «Что изменилось при пересчёте» (вчерашний прогноз с упреждением 48 ч против сегодняшнего
  с 24 ч на одни и те же часы, пересчитанные часы подсвечены), таблица, CSV, прогон всего февраля,
  панель проверки на январе и декабре, вопросы агенту (при наличии ключа OpenAI), выгрузка всех
  прогнозов одним CSV (`/api/forecasts.csv`) и журнала файлом (`/api/journal.md`).
- LLM-аналитик (OpenAI, опционально): сводка дня по числам анализа и ответы на вопросы через
  инструменты (прогноз на дату, погода, сравнение запусков, метрики проверки). Модельная сводка
  строится для одного дня (кнопка или `--date`), при прогоне всего периода сводки шаблонные,
  чтобы прогон занимал секунды. Без ключа цикл и страница работают полностью, сводка собирается
  по шаблону, чат отключён с надписью.
- Тест сценария `pytest`, печатает PASS. Docker-запуск одной командой.

## Основной сценарий

1. Пользователь выбирает дату выпуска D (31.01.2026 … 28.02.2026) и нажимает «Сформировать прогноз».
2. Агент получает из Open-Meteo прогноз погоды на часы D+1 00:00 … D+2 23:00, взятый с упреждением:
   в основном (строгом) режиме для каждого часа D+1 значение, предсказанное за 48 часов до него
   (`previous_day2`), для каждого часа D+2 за 72 часа (`previous_day3`); наибольшее вычисленное номинальное
   `weather_run_time` равно D−1 23:00, момент выпуска принят как 23:59 дня D. В файле прогноза у каждой строки
   стоят `issue_timestamp`, `weather_lead_hours` и `weather_run_time`, агент проверяет, что
   `weather_run_time` не позже момента выпуска. Сравнительный режим `WEATHER_STRICT=0` берёт
   упреждение 24 и 48 часов (`previous_day1`/`previous_day2`).
3. Агент собирает признаки и запускает модель.
4. Агент записывает 96 строк (48 часов × 2 турбины) в `output/forecasts/forecast_<D>.csv`.
5. Агент анализирует результат: сумма нормализованной мощности по часам за каждые сутки (нормализованная
   мощность × час), изменения к прогнозу предыдущего дня на те же часы (это и есть пересчёт при
   обновлении входных данных: вчера эти часы шли с упреждением 72 ч, сегодня 48 ч), пары час–турбина низкой
   уверенности (флаг `confidence`), часы с ветром выше 25 м/с (гипотеза штатной остановки),
   ошибка за вчера по факту, если факт есть (январь).
6. Агент пишет сводку дня в `output/journal.md` и `output/runs/<D>.json`, затем переходит к D+1.

## Архитектура

```
данные турбин (10 мин)  ──►  model/prepare  ──►  часовые ряды, фильтр простоев
Open-Meteo, архив и previous-runs ──►  model/weather (кэш data/weather_cache) ──►  model/features ──► model/train
                                                                                              │
                                                                                              ▼
день D ──► agent: погода на D ──► признаки ──► model/predict (p10/p50/p90) ──► CSV ──► анализ ──► журнал ──► D+1
                                                                                              │
web/app (FastAPI + одна страница) ◄───────────────────────────────────────────────────────────┘
```

- `common/config.py` — координаты, пути, период, часовой пояс.
- `data/raw/` — данные организаторов (источник в `data/raw/ИСТОЧНИК.md`); `data/weather_cache/` —
  ответы Open-Meteo, чтобы расчёт воспроизводился из кэша после установки зависимостей.
- `model/` — подготовка данных, погода, признаки, обучение, предсказание; `model/artifacts/` —
  обученные модели, метрики, отчёт и таблица проверки.
- `agent/` — инструменты цикла, суточный запуск, прогон по периоду, LLM-аналитик.
- `web/` — API и одна HTML-страница без сборки и внешних библиотек (график в SVG).
- `tests/` — проверочный сценарий; `examples/` — примеры выходных файлов; `docs/` — контракт модулей,
  журнал экспериментов, текст ТЗ организаторов.

Что детерминировано, а что делает LLM. Погода, признаки, модель, файлы, правила анализа и журнал
по шаблону работают без ключа и не зависят от доступности Open-Meteo: кэш ответов лежит в репозитории
и используется при `WEATHER_OFFLINE=1` или при ошибке сети;
на проверенном окружении при одинаковых весах модели, погодном кэше, режиме и дате значения p10/p50/p90
воспроизводятся (29 дней за секунды на ноутбуке, без обучения и без загрузки погоды). Сравнение
с предыдущим выпуском и флаг `confidence` зависят от наличия предыдущего выпуска в `output/`, поэтому
одиночный запуск и та же дата внутри последовательного прогона имеют одинаковые квантили, но могут
отличаться полями анализа; для сравнения с `examples/` используется полный последовательный прогон
в свежей копии репозитория. Побайтовое совпадение времени выполнения шагов и LLM-текстов не заявляется;
прогон в Linux-контейнере Docker отличается от прогона на macOS в небольшой доле строк при тех же весах,
см. «Ограничения».
Модель OpenAI используется только для человеческой сводки дня по числам анализа и для ответов
на вопросы через инструменты; она не может изменить прогноз.

Подробный контракт функций и колонок: `docs/architecture.md`.

## Как устроена модель и что показала проверка

Модель учится на прогнозе, а не на измеренном ветре: в день выпуска замеров за завтра ещё нет,
и модель, обученная на точном ветре, ошибается сильнее на прогнозном. Обучающая выборка:
архив свежих прогнозов с 2023 года плюс история прогнозов за сутки и за двое суток с марта 2024.
Один и тот же час факта входит в выборку до трёх раз с разными версиями прогноза (свежий, суточной
и двухсуточной давности), поэтому строк обучения 107 417 при 48 767 часах факта по двум турбинам;
январь 2026 в обучение не входил. 15 признаков: ветер на 10 и 100 м,
порывы, направление, температура, давление, час, месяц, турбина, давность прогноза, куб и сглаженный
ветер. Три модели `HistGradientBoostingRegressor(loss="quantile")` на квантили 0.1, 0.5, 0.9.

Проверка на январе 2026 повторяет работу агента в основном (строгом) режиме, упреждение 48/72 ч:
31 дата выпуска (с 31.12.2025 по 30.01.2026), 2 914 записей «выпуск, целевой час, турбина» с фактом;
уникальных часов по двум турбинам 1 481,
почти каждый час проверен дважды, как день 1 и как день 2, поэтому записи не независимы.
Точки отсчёта считаются на тех же записях: persistence берёт для даты выпуска D факт дня D
в тот же час (для дня 2 тоже факт дня D, а не D+1), кривая мощности берёт тот же прогноз ветра.
Ошибки в шкале нормализованной мощности 0…1; MAE и RMSE усреднены по всем записям, то есть по обеим турбинам
и обоим горизонтам вместе, срезы по горизонту и по турбине лежат в `metrics.json`.

| Январь 2026, режим 48/72 (основной) | Модель MAE | RMSE | Факт внутри p10–p90 | Кривая мощности MAE | Persistence MAE |
|---|---|---|---|---|---|
| Все 48 ч | 0.160 | 0.240 | 82.6 % | 0.177 | 0.365 |
| День 1 (упреждение погоды 48 ч) | 0.156 | — | — | 0.168 | — |
| День 2 (упреждение погоды 72 ч) | 0.165 | — | — | 0.185 | — |

Третья точка отсчёта, климатология (константа, медиана выработки по обучению 0.235): MAE 0.272.
Сравнительный режим 24/48 (`WEATHER_STRICT=0`, `model/artifacts_lead24/`) на том же январе:
модель 0.144, RMSE 0.218, покрытие 85.3 %, кривая 0.158, persistence 0.365; по горизонтам модель
0.135 и 0.154 против кривой 0.149 и 0.168. Лишние сутки упреждения стоят модели около 0.016 MAE.

На январской валидации в основном режиме MAE модели ниже на 9,2 % относительно кривой «ветер → мощность»
(0,160 против 0,177) и в 2,3 раза ниже правила «завтра как сегодня» (0,365); выигрыш держится на обоих
горизонтах. Веса модели одни и те же в обоих режимах (md5 в `metrics.json`, поле `weights_md5`),
обучение шло на архиве свежих прогнозов и на previous_day1/day2, упреждение 72 ч в обучении не
представлено, проверка на нём идёт «как есть».
Январь использовался и для выбора версии модели (`docs/experiments.md`), поэтому это валидация,
а не независимый тест. Дополнительная ретроспективная проверка сделана на декабре 2025 с отсечкой
обучения 30.11.2025: та же конфигурация без изменений, даты выпуска 30.11 … 30.12, 2 912 записей,
1 480 пар турбина–час, тот же основной режим 48/72. Декабрьская модель на декабрьских ответах не училась, но конфигурация
выбиралась по январю моделями, обученными по 31.12, то есть декабрь входил в их обучающие данные;
полностью нетронутым внешним тестом это назвать нельзя, поэтому и не называем.
В декабре ошибки прогноза мощности выше, чем в январе: MAE кривой мощности 0,215 против 0,177. Сами по себе
эти метрики не устанавливают причину различия между месяцами. Модель сохраняет меньшую MAE относительно
всех трёх точек отсчёта:

| Декабрь 2025, режим 48/72, ретроспективная проверка | Модель | Кривая мощности | Persistence | Климатология |
|---|---|---|---|---|
| MAE | 0.206 | 0.215 | 0.376 | 0.346 |
| RMSE | 0.300 | 0.317 | 0.491 | — |
| Факт внутри p10–p90 | 76.5 % | 69.9 % | — | — |
| День 1 / День 2, MAE | 0.197 / 0.215 | 0.204 / 0.225 | — | — |

В сравнительном режиме 24/48 декабрь даёт модель 0.196, кривая 0.206 (`model/artifacts_dec2025_lead24/`).
Числа и отчёты: `model/artifacts_dec2025/metrics.json`, `report.md`.
Коридор: интервал между оценками квантилей 0,1 и 0,9; наблюдаемое покрытие в основном режиме на январе
82,6 % при средней ширине 0,55 в шкале нормализованной мощности, на декабре 76,5 % при ширине 0,56; у кривой мощности
78,2 % и 69,9 %. Покрытие меняется между месяцами, стабильная калибровка на 80 % не подтверждена;
широкий интервал покрывает факт легко, поэтому ширина указана рядом с покрытием. Снижение MAE
относительно кривой: 9,2 % в январе и около 4 % в декабре, это положительный результат на двух
месяцах, а не доказательство устойчивого выигрыша во всех сезонах. Флаг `confidence` в файле прогноза
это эвристика по ширине интервала (порог: 75-й процентиль ширины по январской проверке того режима,
чьи артефакты лежат в `model/artifacts/`) и по изменению к вчерашнему прогнозу, а не вероятность.
Фильтр неполных часов и простоев применён и к обучению, и к проверке: в январе он убрал 7 из
1 488 пар турбина–час; метрики без фильтра лежат в блоке `validation_unfiltered` в `metrics.json`
каждой папки проверки и отличаются от отфильтрованных в третьем знаке (в режиме 24/48: 0,1436
против 0,1440).
Что пробовали и что не помогло: `docs/experiments.md`. Полный отчёт с фильтром данных,
самопроверкой выравнивания по времени и параметрами: `model/artifacts/report.md`.

## Технологии

Python 3.12, pandas, numpy, scikit-learn, httpx, joblib, FastAPI, uvicorn, python-dotenv, openai, pytest.
Одна HTML-страница без сборки. Docker. Источник погоды: Open-Meteo (Historical Forecast API
и Previous Runs API). LLM: OpenAI API, опционально.

## Установка

Получите репозиторий через доступ, предоставленный организаторами; после клонирования перейдите
в папку проекта. Все команды ниже выполняются из корня репозитория.

```
git clone https://github.com/BAITC-Hacks/hack-b7e991bb-ordanio.git repo
cd repo
```

Два пути: Docker (рекомендуется, локальный Python не нужен) или локальный запуск (Python 3.12,

## Ограничения

Известные ограничения проекта, честно по факту:

- Фактической выработки за февраль 2026 в предоставленных данных нет. Качество оценено на январской
  валидации и дополнительной декабрьской ретроспективной проверке; для февральских дней ошибка по факту
  не вычисляется, агент пишет «ошибка за вчера: нет факта».
- Агент использует архивные прогнозные значения погоды с фиксированным упреждением относительно каждого
  целевого часа: 48/72 ч в основном режиме и 24/48 ч в сравнительном. Повторный расчёт выполняется раз
  в сутки для следующей даты выпуска, внутрисуточные обновления в этом сценарии не используются.
- Часовой пояс данных принят как местное время; Казахстан перевёл часы на UTC+5 в марте 2024,
  самопроверка выравнивания (`model/artifacts/report.md`) показывает нулевой целый сдвиг в обоих
  периодах, но дробная часть часа не исправляется.
- Номинальное покрытие интервала p10–p90 составляет 80 %. Наблюдаемое покрытие в основном режиме
  82,6 % в январе и 76,5 % в декабре при средней ширине 0,55 и 0,56 в шкале нормализованной мощности;
  стабильная калибровка на 80 % не подтверждена. Суммы почасовых p10 и p90 в журнале не являются
  границами 80-процентного интервала суточной выработки.
- Доступность погоды на момент выпуска. Поле `weather_run_time` вычислено как целевой час минус
  упреждение; это номинальный порядок во времени, а не метка публикации от провайдера (Previous Runs
  API отдаёт значения по фиксированному упреждению и не сообщает время публикации конкретного прогона).
  Момент выпуска принят как 23:59 дня D. Основной режим (по умолчанию) берёт упреждение 48 и 72 часа
  (`previous_day2`/`previous_day3`): наибольшее вычисленное номинальное `weather_run_time` равно D−1 23:00, при задержке
  публикации у глобальных моделей до 6 часов он доступен к D 05:00, за 19 часов до выпуска. Это
  консервативная реконструкция доступности при явно заданном допущении о задержке публикации,
  а не подтверждение фактического времени публикации каждого значения: Previous Runs API его не
  сообщает. Сравнительный режим `WEATHER_STRICT=0` (упреждение 24/48, bash: `WEATHER_STRICT=0 python
  -m model.train --artifacts-dir model/artifacts_lead24`; PowerShell: `$env:WEATHER_STRICT="0"`
  отдельной строкой) точнее на 0,016 MAE, но часть его значений для последних часов суток могла
  стать доступна уже в первые часы D+1; он оставлен как эксперимент с этой подписью.
- Время в данных турбин это начало 10-минутного интервала, часовое значение это среднее шести
  интервалов, `target_time` это начало часа; `lead_hours` считается от 00:00 дня выпуска.
- Обнуление при ветре выше 25 м/с это гипотеза о штатной остановке по типовому порогу, параметры
  этих турбин неизвестны; такие часы помечаются `confidence=low` с пометкой в `note`, чтобы интервал
  [0; 0] не читался как уверенность; правило действует только в агенте, в проверке на январе
  не применялось (в январе 2026 таких часов в прогнозе не было).
- Ранняя остановка бустинга использует случайную внутреннюю выборку 10 % обучающих примеров, поэтому
  разные версии прогноза одного и того же часа могут оказаться по обе стороны этого разбиения; это
  ограничение внутреннего выбора сложности модели (числа деревьев), а не утечка проверочных месяцев:
  январь и декабрь в обучение соответствующих моделей не входили.
- Момент выпуска 23:59 и последний интервал факта: замер 23:50 описывает интервал 23:50–00:00,
  который к 23:59 ещё не завершён; persistence в проверке берёт полный час дня выпуска, то есть
  допускает доступность последнего часа к моменту выпуска. На прогноз модели это не влияет, на
  точку отсчёта persistence влияет в пределах одного часа из 24.
- `lead_hours` в CSV это календарное смещение от 00:00 дня выпуска (24 … 71), а не упреждение от
  момента выпуска 23:59; упреждение погоды указано отдельно в `weather_lead_hours`.
- Переобучение и совпадение md5 моделей проверены на macOS Apple Silicon в указанном окружении;
  на Windows и других процессорах этим протоколом не подтверждены. Округлённые метрики служат ориентиром
  для сравнения, побайтовое совпадение между платформами не заявляется: прогон февраля в Linux-контейнере
  Docker при тех же весах (md5 совпадает) отличается от прогона на macOS в 106 строках из 2 784, обычно
  на 0,005–0,01, десять значений на 0,05–0,085, в двух строках сменился флаг `confidence`; переобучение
  на декабре в контейнере дало MAE 0,204 против 0,206 на macOS. По нашей оценке, причина в разных сборках
  numpy и scikit-learn: значение признака у порога разбиения дерева уходит в соседний лист. Файлы
  `examples/` получены на macOS, сравнивайте их с прогоном той же платформы; объёмы, даты, упреждения
  и порядок величин совпадают на обеих.
- Последние даты выпуска (27 и 28 февраля) прогнозируют также 1 и 2 марта: февральский набор
  выделяется по `target_time`, происхождение каждой строки видно по `issue_date` и `weather_run_time`.
- Мощность представлена в нормализованной шкале 0…1, предоставленной организаторами. Параметры
  нормализации и номинальная мощность турбин не подтверждены, поэтому значения не переводятся в МВт
  и МВт·ч; MAE это ошибка в шкале нормализованной мощности, суммы по часам выражены в единицах
  нормализованной мощности × час.
- Координаты турбин взяты из ссылок в ТЗ; параметры турбин (высота ступицы, номинал) неизвестны,
  поэтому выработка нормирована так же, как в данных.
- Из обучающего набора исключены 149 часов вероятного простоя и 120 неполных часов; фильтрация
  применяется также к проверке, объёмы исключений и метрики без фильтра приведены в отчётах;
  ремонтные графики неизвестны.
- LLM-сводка дня и чат требуют ключ OpenAI; шаблонная сводка и основной цикл доступны без ключа,
  при ошибке OpenAI агент продолжает основной расчёт.

(Anthropic, модели Fable и Opus) под руководством участника; задача, архитектура, приёмка и решения
по методике за участником. Сторонние библиотеки перечислены в `requirements.txt` с версиями
(лицензии BSD, MIT, Apache 2.0). Данные турбин принадлежат владельцу задачи и выданы для хакатона.
Погодные данные Open-Meteo, CC BY 4.0. Фоновый ролик заставки на развёрнутой версии: Pexels,
видео 4404136 «Windmills in the farmland», лицензия Pexels (свободное использование, без указания
автора), в репозиторий не входит, подключается переменной `HERO_VIDEO_URL`. Шрифт IBM Plex, OFL,
через Google Fonts с системным запасным. Ранее написанного кода, шаблонов и чужих решений в проекте нет.
