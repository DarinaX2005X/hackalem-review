# TwinTurbo.ai

**Почасовой прогноз нормализованной мощности двух ветровых турбин на 24 или 48 часов с честной неопределённостью, последовательной проверкой качества и полным происхождением данных.**

TwinTurbo.ai объединяет реальную историю SCADA, архивные выпуски NOAA GFS, отдельные кривые мощности турбин, online bias-коррекцию, Q10/Q50/Q90, версионирование выпусков и Streamlit-интерфейс. Главный критерий выбора модели — минимальный MAE на будущих относительно обучения данных. Более сложная модель включается только после доказанного улучшения.

> Продукт называется **TwinTurbo.ai**. Совместимое имя Python-пакета и CLI — `windoracle`, поэтому штатные команды имеют вид `python -m windoracle ...`. Исходники находятся в `src/TwinTurbo.ai/`; это не два разных проекта.

## Что уже реализовано

- импорт двух исходных CSV, аудит качества и почасовая агрегация;
- подтверждённый фиксированный часовой пояс исходных меток **UTC+05:00** (`Etc/GMT-5`), семантика начала интервала и задержка поступления факта 15 минут;
- выбор только такого погодного выпуска, который был доступен к `origin_time` (`available_at <= origin_time`);
- реальный архив NOAA GFS, локальный кэш, аудит покрытия и SHA-256 происхождения;
- ежедневный выпуск в 23:00 местного времени, то есть в 18:00 UTC, на 24/48 часов;
- отдельная forecast-space power curve для каждой турбины;
- mean и persistence baselines, Ridge, опциональный boosting и ensemble;
- последовательная временная проверка без перемешивания прошлого и будущего;
- bias-коррекция только по уже созревшим ошибкам;
- Q10/Q50/Q90, pinball loss, покрытие и ширина интервала;
- неизменяемые версии модели, bias и прогнозных выпусков;
- SQLite/JSON/CSV, проверка checksum, replay и журнал действий агентов;
- Streamlit-интерфейс: 24/48 часов, сравнение выпусков, доступный факт, КИУМ, MAE, типы отклонений, рекомендации и ветровая карта;
- отдельный синтетический fixture-режим для мгновенной демонстрации без сети.

Путь одного прогноза:

```text
SCADA CSV (+05) ──> почасовые as-of наблюдения ─┐
                                                 ├─> power curve ─> bias ─> Q10/Q50/Q90
архивный NOAA GFS ─> допустимый погодный run ───┘                         │
                                                                          v
                                                SQLite + JSON/CSV + Streamlit
```

Модель не скачивает погоду и не читает сырой CSV. Это делает интеграционный слой, а predictor получает уже разрешённый `AsOfSnapshot`. UI также не пересчитывает прогноз: он работает через `ForecastService`.

## Что проверено локально

Главный результат находится в [кратком отчёте](reports/january-model-comparison.md) и полном [JSON с provenance](reports/january-model-comparison.json). Проверка использует 39 реальных выпусков GFS: 8 для предъянварской настройки и 31 для последовательного январского backtest. Полезная сетевая нагрузка архива — 2 000 847 617 байт.

| Проверка | Строк | MAE | Решение |
| --- | ---: | ---: | --- |
| Mean baseline, весь январь | 2 928 | 0.3023227 | База сравнения |
| Power curve, весь январь | 2 928 | **0.2265555** | Включена: skill к mean baseline **25.06%** |
| Mean baseline, пиковые часы `fact >= 0.8` | 456 | 0.5690665 | Диагностика |
| Power curve, те же пиковые часы | 456 | **0.2522542** | Улучшение **55.67%** |
| Power curve, нетронутый период 16–31 января | 1 488 | 0.2190094 | База для bias |
| Power curve + bias, тот же период | 1 488 | **0.1952489** | Финальный выбранный вариант |
| Ridge, тот же период | 1 488 | 0.3707068 | Отключён: MAE хуже |

Bias уменьшил MAE power curve на отложенном периоде примерно на 10.85%. Ridge не прошёл ворота качества; Ridge+bias также не победил. Ensemble отключён, потому что добавлять ещё одну степень свободы без независимого улучшения было бы необоснованно. В production выбран не самый сложный, а реально лучший из проверенных вариантов: **power curve + bias**.

MAE здесь измеряется в нормализованной мощности от 0 до 1, а не в МВт и не является «процентом точности». UI дополнительно показывает RMSE, среднюю знаковую ошибку, долю недопрогноза, перепрогноза и долю попаданий в нейтральный коридор ±0.05.

### Неопределённость

На отложенном периоде 16–31 января:

- Q10/Q50/Q90 доступны для 100% из 1 488 оценённых строк;
- фактическое покрытие Q10–Q90 — **0.76747** при целевом 0.80;
- средняя ширина Q10–Q90 — **0.51440** нормализованной мощности.

Покрытие немного ниже цели, и это показывается как есть. До накопления 30 зрелых ошибок для пары «турбина × группа горизонта» квантили равны `null`, а статус содержит `interval:insufficient_history`. При устаревшем состоянии bias интервалы также не выдумываются. Так модель буквально сообщает, когда данных для уверенного диапазона недостаточно.

## КИУМ, точность и способы отклонения

КИУМ (коэффициент использования установленной мощности, capacity factor) для равных часовых интервалов вычисляется как среднее `power_norm`:

```text
КИУМ = sum(power_norm) / N
```

Интерфейс показывает прогнозный КИУМ выбранного горизонта и фактический КИУМ только по уже доступным измерениям. Для физической энергии в МВт·ч необходима подтверждённая номинальная мощность каждой турбины. Пока `rated_power_mw: null`, TwinTurbo.ai корректно оставляет МВт·ч пустыми и не подменяет неизвестный номинал предположением. Станционный КИУМ при разных номиналах должен быть взвешен по установленной мощности.

Знак ошибки принят как `prediction - actual`:

- **недопрогноз** — ошибка меньше `-0.05`: фактическая мощность выше ожидаемой;
- **перепрогноз** — ошибка больше `+0.05`: фактическая мощность ниже ожидаемой;
- **нейтральная зона** — абсолютная ошибка не больше 0.05;
- **bias** — средняя знаковая ошибка, а **MAE** — средний модуль ошибки.

Причины отклонений система не придумывает. По имеющимся данным можно доказать только само отклонение, его направление, длительность и связь с прогнозом погоды. Обледенение, curtailment, отказ датчика или поломка требуют отдельных эксплуатационных сигналов.

## Рекомендации оператору и ремонту

Блок «Оперативная аналитика» формирует только проверяемые подсказки поддержки решения:

- при широком Q10–Q90 предлагает предусмотреть резерв или гибкость графика;
- при ожидаемой мощности не ниже 0.90 напоминает проверить сетевые ограничения и готовность приёма мощности;
- при устойчивом перепрогнозе предлагает проверить доступность установки, журнал ограничений, качество датчиков и состояние оборудования;
- при отсутствии интервалов предупреждает не использовать одно число как гарантированный диспетчерский график.

Это **не команда автоматически повысить или понизить уставку** и не диагноз «деталь скоро сломается». В датасете нет паспортных ограничений, аварийных кодов, вибрации, температур подшипников и редуктора, токов генератора, положения pitch/yaw, данных об обледенении и диспетчерском ограничении. Без них конкретная рекомендация «заменить редуктор» была бы выдумкой.

Практический следующий уровень для predictive maintenance:

1. подключить SCADA alarms/events и журнал ремонтов;
2. добавить vibration, bearing/gearbox temperature, generator current, pitch/yaw и icing-сигналы;
3. задать паспортные пределы и регламент производителя;
4. проверить правила на исторических отказах;
5. только после этого выводить вероятный узел, срочность осмотра и основание рекомендации.

До такой интеграции TwinTurbo.ai рекомендует **что проверить**, но не утверждает, **что именно сломано**.

## Ветровая карта

Streamlit показывает обе турбины на карте по их координатам и прикрепляет к точкам доступные скорость, направление ветра и температуру из сохранённого погодного снимка выпуска. Размер маркера отражает скорость ветра; выбранная турбина выделяется в интерфейсе.

Это точечная погодная карта, а не CFD-модель и не непрерывное поле ветра. Разрешение GFS — 0.25°, поэтому близкие турбины могут попадать в одну ячейку и иметь одинаковый внешний прогноз. Карта не доказывает wake-эффект, влияние рельефа или шероховатости. Для такой детализации нужны локальная мачта/LiDAR, цифровая модель рельефа и downscaling. У старого выпуска без `manifest.weather_values` карта честно сообщает, что погодные точки отсутствуют.

## Запуск от clone до работающей системы

### 1. Требования

- Git;
- Python 3.11+; для Windows и нативного ecCodes рекомендуется Python 3.13;
- около 3 ГБ свободного места для полного январского GFS-кэша;
- интернет только для установки зависимостей и первой загрузки NOAA GFS.

### 2. Клонирование и окружение

```bash
git clone <URL_РЕПОЗИТОРИЯ>
cd hack-a9db1b13-chachmechanics
python -m venv .venv
```

Windows PowerShell:

```powershell
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps -e .
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m eccodes selfcheck
```

Linux/macOS:

```bash
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -r requirements.lock
.venv/bin/python -m pip install --no-deps -e .
.venv/bin/python -m pip check
.venv/bin/python -m eccodes selfcheck
```

### 3. Мгновенный просмотр

Без сети, GFS и базы:

```bash
python -m frontend.preview --port 8765
```

Открыть <http://127.0.0.1:8765>. Это явно маркированный синтетический fixture, предназначенный для проверки интерфейса, а не качества прогноза.

Полный Streamlit UI:

```bash
python -m streamlit run app.py
```

Он также открывается в fixture-режиме, но уже показывает оперативный блок, КИУМ, отклонения, рекомендации и карту.

### 4. Проверка конфигурации и импорт реальных CSV

В репозитории используются короткие стабильные имена:

```text
data/raw/turbine_1.csv
data/raw/turbine_2.csv
configs/site.yaml
```

Ключевой фрагмент `configs/site.yaml`:

```yaml
site:
  timezone: Etc/GMT-5       # фиксированный UTC+05; знак в Etc/GMT инвертирован
  timestamp_semantics: interval_start
  time_basis: confirmed
  observation_delay_minutes: 15
forecast:
  issue_local_time: '23:00' # 18:00 UTC
  horizon_hours: 48
```

Импорт:

```bash
python -m windoracle ingest \
  --config configs/site.yaml \
  --turbine-1 data/raw/turbine_1.csv \
  --turbine-2 data/raw/turbine_2.csv \
  --output reports/ingest-utc-plus05.json
```

В PowerShell обратные слеши можно убрать и выполнить команду одной строкой.

### 5. Bootstrap реального GFS

Один проверочный выпуск:

```bash
python -m windoracle weather fetch --config configs/site.yaml \
  --origin 2026-01-01T18:00:00Z \
  --run 2026-01-01T12:00:00Z \
  --progress
```

Все 39 выпусков, использованные для предъянварской калибровки и январской проверки:

```bash
python -m windoracle weather fetch --config configs/site.yaml \
  --start 2025-12-24 --end 2026-01-31 \
  --max-runs 39 --max-download-mb 2600 --progress \
  --output reports/weather-january-bootstrap.json
```

Команда идемпотентна относительно валидного кэша: уже сохранённые объекты повторно используются. Доступность run всё равно перепроверяется для каждого `origin_time`.

### 6. Полное воспроизведение январского выбора модели

После импорта и загрузки GFS:

```bash
python scripts/reproduce_january.py --config configs/site.yaml
```

Скрипт заново строит только допустимые as-of снимки, настраивает кривую до января, последовательно сравнивает baseline/power curve/bias/Ridge, применяет строгие ворота MAE и записывает:

- `reports/january-model-comparison.json` — полный машиночитаемый отчёт;
- `reports/january-model-comparison.md` — краткую сводку;
- `artifacts/models/february-production.json` — выбранную модель;
- `artifacts/bias/february-production-bias.json` — состояние коррекции.

Проверка не использует январский факт раньше его реального `available_at`. Полный JSON содержит временные границы, гиперпараметры, GFS run IDs и хэши, версии состояния Critic и SHA-256 исходного кода эксперимента.

### 7. Проверка базового predictor через штатный CLI

PowerShell:

```powershell
$env:TWINTURBO_MODEL_ARTIFACT = 'artifacts/models/february-production.json'
python -m windoracle predict `
  --config configs/site.yaml `
  --origin 2026-01-30T18:00:00Z `
  --predictor windoracle.models.registry:load_predictor `
  --mode replay `
  --output outputs/forecast
python -m windoracle verify --input outputs/forecast
python -m windoracle export --input outputs/forecast --output outputs/forecast.csv
```

Linux/macOS:

```bash
export TWINTURBO_MODEL_ARTIFACT=artifacts/models/february-production.json
python -m windoracle predict \
  --config configs/site.yaml \
  --origin 2026-01-30T18:00:00Z \
  --predictor windoracle.models.registry:load_predictor \
  --mode replay \
  --output outputs/forecast
python -m windoracle verify --input outputs/forecast
python -m windoracle export --input outputs/forecast --output outputs/forecast.csv
```

Один штатный 48-часовой выпуск для двух турбин содержит 96 строк. Артефакт модели проверяется по checksum; случайной или молчаливой fallback-модели нет. Эта команда проверяет точечную power curve: общий `predict` намеренно не угадывает, какое состояние bias загрузить. Полная выбранная цепочка **power curve + конкретный versioned bias** запускается следующим offline-скриптом, где оба артефакта переданы явно.

### 8. Февральский replay 1–28 февраля

Целевой сценарий — ежедневный выпуск в 23:00 UTC+05 с горизонтом 48 часов. Для целей 1–28 февраля нужны origin от `2026-01-31T18:00:00Z` до `2026-02-27T18:00:00Z`.

Сначала загрузить допустимые GFS-выпуски:

```bash
python -m windoracle weather fetch --config configs/site.yaml \
  --start 2026-02-01 --end 2026-02-28 \
  --max-runs 28 --max-download-mb 2600 --progress \
  --output reports/weather-february-bootstrap.json
```

Затем выполнить offline-генерацию уже по кэшу и замороженным артефактам:

```bash
python scripts/generate_february.py \
  --config configs/site.yaml \
  --model artifacts/models/february-production.json \
  --bias artifacts/bias/february-production-bias.json \
  --output outputs/replay-february
python -m windoracle verify --input outputs/replay-february
```

`generate_february.py` не скачивает погоду и не читает CSV: он использует импортированный SQLite, проверенный GFS-кэш и неизменяемые модель/bias. Если bias становится старше разрешённого окна, точечный прогноз остаётся базовым, Q10/Q50/Q90 становятся `null`, а статус явно сообщает об устаревшей истории.

**Статус:** февральский replay является обязательным следующим артефактом сдачи, но в README не объявляется завершённым, пока каталог `outputs/replay-february` не сгенерирован, не прошёл `verify` и не открыт через UI.

### 9. Запуск UI на реальном сервисе

PowerShell:

```powershell
$env:TWINTURBO_CONFIG = 'configs/site.yaml'
$env:TWINTURBO_MODEL_ARTIFACT = 'artifacts/models/february-production.json'
$env:TWINTURBO_PREDICTOR = 'windoracle.models.registry:load_predictor'
python -m streamlit run app.py
```

В интерфейсе переключиться из **Демо** в **Проверка на истории**. `ForecastService` предоставляет каталог выпусков, новый расчёт, сравнение, доступный факт, журнал и экспорт. Сгенерированные февральские выпуски уже содержат применённый versioned bias и отображаются без пересчёта. Новый расчёт через стандартную UI-фабрику использует подключённый predictor без автоматического выбора bias; для online-обновления bias нужна сервисная фабрика, которая передаёт явно выбранное допустимое состояние в `create_forecast`. Без модели просмотр сохранённых выпусков доступен, а новый расчёт отключён.

## Что хранится в Git и почему

Чтобы проверяющий действительно мог клонировать, установить и запустить проект, в репозиторий должны входить:

- оба исходных CSV под стабильными именами `data/raw/turbine_1.csv` и `turbine_2.csv`;
- подтверждённый `configs/site.yaml` без секретов;
- исходный код, lock-файл зависимостей и тесты;
- выбранные JSON-артефакты модели и bias;
- полный январский отчёт и маленькие отчёты загрузки GFS;
- проверенные финальные прогнозы/экспорт для показа;
- синтетические fixtures, всегда явно помеченные как `synthetic`.

Не следует коммитить:

- `.venv`/`venv`, `__pycache__` и кэши тестов;
- временную SQLite, которая детерминированно восстанавливается командой `ingest`;
- весь `data/weather`: текущий рабочий GFS-кэш занимает около 2.2 ГБ и содержит тысячи производных объектов;
- временные файлы и незавершённые выгрузки.

Большой GFS-кэш не является скрытой зависимостью: команда bootstrap, run IDs, метаданные, размеры и хэши публикуются. Его загрузка из NOAA воспроизводима, а хранение в обычном Git резко утяжелило бы каждый clone. Если организаторы требуют полностью offline-архив, правильный вариант — приложить версионированный ZIP к GitHub Release или объектному хранилищу с SHA-256, а не помещать 2.2 ГБ в историю Git.

`.gitignore` нужен именно для машинных окружений и восстанавливаемых тяжёлых данных; он не должен исключать CSV, конфигурацию, production-артефакты, отчёт и финальные результаты. Пустые `.gitkeep` для работы системы не нужны.

## Деплой: Render или Vercel

### Что готово, а что только настроено

Локальный Streamlit, общий Python-сервис, модельные артефакты и команды запуска проверены. Публичный URL пока не заявляется: ниже приведена **готовая конфигурация деплоя**, которую ещё нужно выполнить и проверить в облаке.

Для текущей архитектуры проще и надёжнее **один Render Web Service**: Streamlit и Python backend уже работают одним процессом.

Рекомендуемые команды Render:

```text
Build: pip install -r requirements.lock && pip install --no-deps -e .
Start: streamlit run app.py --server.address 0.0.0.0 --server.port $PORT
```

Для fixture-демо база данных не нужна. Для реальных выпусков и истории SQLite обязательна как текущее хранилище проекта. На Render файловая система сервиса по умолчанию эфемерна, поэтому для одного экземпляра нужен persistent disk и пути `storage.database`/`weather.cache_dir` под его mount point, например `/var/data/twinturbo.sqlite` и `/var/data/weather`. Это соответствует [официальной документации Render о persistent disks](https://render.com/docs/disks).

SQLite подходит для демо и одного экземпляра. Для нескольких реплик и production-нагрузки разумно добавить отдельный адаптер хранилища для PostgreSQL; сейчас такой адаптер не заявлен реализованным.

**Vercel не нужен для текущего репозитория.** Его можно использовать позже только для отдельно собранного статического/Next.js frontend, который обращается к Render API. Сейчас интерфейс — Streamlit, а Vercel Python Runtime строится вокруг функций-запросов, имеет read-only filesystem кроме временного `/tmp` и ограничения на bundle/runtime; см. [официальное описание Vercel runtimes](https://vercel.com/docs/functions/runtimes). Разделение на Vercel + Render добавит CORS, авторизацию и второй деплой, не улучшив конкурсное демо.

### Чек-лист деплоя

1. Сначала добиться локального `pytest -q` и `eccodes selfcheck`.
2. Сгенерировать и проверить `outputs/replay-february`.
3. Для простого публичного показа развернуть fixture/готовые неизменяемые результаты на Render без online-загрузки GFS.
4. Для новых расчётов подключить persistent disk и положить на него SQLite/GFS-кэш.
5. Задать `TWINTURBO_CONFIG`, `TWINTURBO_MODEL_ARTIFACT`, `TWINTURBO_PREDICTOR`.
6. Проверить в браузере прогноз, факт, Q10/Q50/Q90, КИУМ, отклонения, карту, рекомендации, сравнение выпусков и CSV.
7. Только после этого публиковать URL как рабочий деплой.

## Честные ограничения

- Номинальная мощность турбин пока не подтверждена, поэтому физические МВт и МВт·ч не выводятся.
- GFS 0.25° не моделирует микрорельеф, шероховатость и взаимное затенение двух близких турбин.
- Покрытие Q10–Q90 на отложенном январе 76.75%, а не ровно целевые 80%.
- Рекомендации — поддержка решения, а не удалённое управление и не автоматический диагноз оборудования.
- Fixture-режим синтетический и не доказывает качество реальной модели.
- Публичный деплой считается готовым только после публикации URL и сквозной проверки на развёрнутом окружении.
- Февральский результат считается готовым только после генерации, `verify` и проверки в интерфейсе; наличие обученного артефакта само по себе этого не доказывает.
