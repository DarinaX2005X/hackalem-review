# Tessera — рабочее место менеджера закупок

Проект хакатона **HACKALEM AI** по кейсу ТОО «Электрокомплект»: подготовка обоснованных заказов для пополнения склада.

> **Статус на 23.09.2026:** реализованы демонстрационный интерфейс, серверная модель данных, XLSX-импорт, детерминированные прогноз/пополнение и фоновые задачи Trigger.dev. Перед публикацией коммита `8979ed6` прошли **215 тестов**, TypeScript, ESLint и production-сборка. Интерфейс пока не подключён к серверному расчётному сценарию; живые облачные интеграции не проверены. Демо работает на синтетических данных без аккаунтов внешних сервисов.

Старый маршрут `/workspace` сохранён для совместимости; основной адрес — `/`.

**Быстрый маршрут для жюри:** [установка](#7-установка-и-запуск) → `/` → [сценарии проверки](#8-как-проверить-решение).

## 1. Название проекта

**Tessera** — рабочее название решения для поддержки менеджера закупок. Исходный кейс и требования партнёра: [techtask/TECHTASK.md](techtask/TECHTASK.md).

## 2. Какую проблему решаем и для кого

Менеджеру закупок приходится сводить продажи, остатки, товары в пути и условия поставщиков из нескольких Excel-файлов. Простое усреднение продаж может завысить потребность из-за разового крупного заказа или занизить её из-за периода отсутствия товара.

Tessera проектируется как единое рабочее место: проверить качество исходных данных, получить объяснимую рекомендацию по каждому артикулу, сгруппировать позиции по поставщикам и оставить окончательное решение человеку. Целевая аудитория — менеджеры закупок и специалисты по планированию складских запасов. Экономия времени и точность прогноза пока не измерялись.

| **Детерминированный расчёт** | Прогноз с сезонностью, устойчивым трендом, stockout-коррекцией и обработкой разовых продаж; заказ с учётом свободного остатка, поставок в пути, срока поставки, периода пересмотра и страховки. Количества и числовое обоснование рассчитываются без ИИ. |

| **ИИ и статусы** | Серверные адаптеры OpenAI/NVIDIA с проверкой ответов и шаблонным резервным объяснением; компоненты доступа/публикации статусов Liveblocks и контроллер обновлений. Их подключение к реальному расчётному сценарию не завершено. |

Это **частичная реализация**, а не заявление о выполнении всех требований кейса. Подробный статус: [трекер прогресса](context/progress-tracker.md).

## 4. Как работает решение

### Пользовательский сценарий

Целевой путь: **файлы → проверка и сопоставление → версия данных → расчёт → рекомендации по поставщикам → правки менеджера → утверждение → экспорт**.

Сейчас доступны три отдельных способа проверки:

1. **Интерфейс:** открыть готовый синтетический результат, изучить обоснования, изменить количество с причиной, проверить поставщиков и утвердить локальный снимок. Кнопка расчёта имитирует этапы и использует заранее подготовленные рекомендации.
2. **Импорт:** передать локальный XLSX и manifest в CLI. Проверяются структура и контрольная сумма; результат — `ready`, `needs_mapping` или `invalid` и диагностический отчёт. CLI не записывает данные в БД и не отправляет файлы внешним сервисам.
3. **Серверный расчёт:** выполнить `npm run test:jobs`. Синтетический интеграционный тест публикует набор в настоящую временную PostgreSQL, создаёт диагностический запуск, выполняет детерминированные этапы и читает сохранённые рекомендации. Повтор не создаёт дубликаты. Это проверка серверных сервисов, не браузерного пути или живого Trigger.

Серверный путь импорта: сессия Clerk → проект владельца → подписанный PUT → загрузка в S3 → `finalize` → сохранённые попытка и намерение отправки → `validate-import` → отчёт и, при успешной проверке, версия данных. Расчёт запускается **отдельным явным запросом**; импорт сам его не запускает.

### Принцип объяснимости

Количества определяет детерминированный алгоритм, **не LLM**. Ядро прогноза отделяет регулярный спрос от разовых продаж, учитывает подтверждённую экспозицию, интервалы отсутствия товара, сезонность и устойчивый тренд. Неизвестные данные не превращаются в нули; ограничения отражаются в предупреждениях и полноте результата.

Ядро пополнения считает потребность на срок поставки и период пересмотра, добавляет прогноз страховки, вычитает свободный остаток и допустимые поставки в пути, затем округляет вверх до разрешённого шага. Исходные вклады сохраняются в обосновании. Методика и ограничения: [прогноз](lib/domain/forecast/README.md), [пополнение](lib/domain/replenishment/README.md).

В существующих ИИ-адаптерах модель выбирает ссылки на разрешённые факты и предупреждения. Приложение проверяет ссылки и формирует текст из исходных фактов. При ошибке провайдера используется шаблонное объяснение; модель не утверждает и не отправляет заказ.

## 6. Архитектура проекта

```text
Браузер / ──→ демо-данные и локальная проверка заказа
                      (пока отдельно от серверного API)

HTTP /api/* ──→ Clerk + проверка владельца + валидация
                ├─→ PostgreSQL: попытки, версии данных, запуски, dispatch
                └─→ приватное S3: загрузка исходных файлов

Сохранённый dispatch ──→ Trigger.dev
  ├─→ validate-import ──→ S3 → проверка/нормализация → приватный отчёт
  │                                              └─→ атомарная версия в PostgreSQL
  └─→ calculate-procurement ──→ прогноз → пополнение → рекомендации в PostgreSQL

Восстановитель ──→ повтор недоставленных намерений и подтверждение отмен
HTTP /api/runs/* ──→ сохранённые состояния и рекомендации PostgreSQL

Локальный XLSX + manifest ──→ CLI → отчёт без записи в БД
ИИ-адаптеры и Liveblocks ──→ отдельные модули; сквозное подключение ожидается
```

## 7. Установка и запуск

### Требования

- Git, **Node.js 24** и npm. Локальная сборка ранее проверялась на **Node.js 24.19.0/macOS arm64**; другие окружения требуют отдельной проверки.
- Интернет для установки пакетов; приложение использует `next/font/google`, поэтому загрузка шрифтов при сборке также может требовать сети.
- Для демо и CLI не нужны PostgreSQL, S3, Clerk или платные AI-сервисы. Тесты БД самостоятельно запускают временный PostgreSQL.

### Шаг 1. Получить код

```bash
git clone --branch 01-agent https://github.com/BAITC-Hacks/hack-86eb72c7-tessera.git tessera
cd tessera
npm ci
```

### Шаг 2. Проверить зафиксированные зависимости

Зависимости данных, импорта и Trigger закреплены в `package.json` и `package-lock.json`: достаточно `npm ci`, дополнительных установок `--no-save` нет. Если политика npm блокирует install scripts, для локальных PostgreSQL-тестов после просмотра скрипта восстановите штатные ссылки пакета:

```bash
(cd node_modules/@embedded-postgres/linux-x64 && node scripts/hydrate-symlinks.js)
```

Это настройка Linux x64 тестового пакета, не создание облачной базы данных.

### Шаг 3. Настроить окружение и открыть демо

Команды приведены для Bash. Существующий файл с ключами не перезаписывается:

```bash
test -f .env.local || cp .env.example .env.local
npm run dev
```

Открыть **[http://localhost:3000/](http://localhost:3000/)** для синтетического демо. Для своего проекта настройте Clerk/PostgreSQL/S3, войдите, откройте `/projects`, затем `/?projectId=UUID`. Для демо внешние ключи оставьте пустыми. Не выполняйте вызовы OpenAI без отдельного разрешения пользователя.

Проверка production-сборки и запуск сервера (Webpack проверен в окружении B; стандартный Turbopack ранее ограничивался запуском процессов/портов):

```bash
npx next build --webpack
npm start
```

### Локальный запуск в Docker

Docker Desktop должен быть запущен. Файлы `.env.local` и `.env.docker` исключены из Git и Docker-образа. Для новой копии один раз создайте отдельный пароль локальной базы; существующие файлы не перезаписываются:

```bash
python3 - <<'PY'
from pathlib import Path
import secrets
local = Path('.env.local')
if not local.exists():
    local.write_text(Path('.env.example').read_text())
    local.chmod(0o600)
docker = Path('.env.docker')
if not docker.exists():
    docker.write_text('TESSERA_DB_PASSWORD=' + secrets.token_hex(24) + '\nTESSERA_PORT=3000\n')
    docker.chmod(0o600)
PY
docker compose -p tessera-local --env-file .env.local --env-file .env.docker up --build -d
```

Открыть **[http://localhost:3000/](http://localhost:3000/)**. Compose ждёт готовности PostgreSQL18, применяет миграции отдельным контейнером, затем запускает Next.js от пользователя `node`. Порт сайта опубликован только на127.0.0.1, порт БД наружу не опубликован. Данные БД сохраняются в отдельном томе. Если3000 занят, измените только `TESSERA_PORT` в `.env.docker`.

Clerk без ключей остаётся недоступным; синтетическое демо работает. Только публичный `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` передаётся при сборке, секреты — во время запуска. После изменения публичного ключа повторите команду с `--build`. Этот запуск сам по себе не разворачивает workers Trigger.dev, S3 или Clerk и не разрешает вызовы OpenAI.

```bash
docker compose -p tessera-local --env-file .env.local --env-file .env.docker ps -a
docker compose -p tessera-local --env-file .env.local --env-file .env.docker stop
```

Остановка сохраняет базу; не удаляйте том при обычном перезапуске.

Исходники партнёра в этой локальной копии сохранены в исключённом из Git каталоге `.agent-loop/source-data`: оба ZIP и все 12 Excel-книг, 14 листов. Контрольные суммы всех файлов проверены также внутри контейнера. Compose подключает каталог только для чтения как `/app/local-source-data`; в образ и публичные файлы сайта эти данные не входят. В новой копии репозитория исходники нужно передать отдельно.

Состояние набора — **`preserved_unmapped`**: сохранение файлов не является публикацией данных для расчёта. В локальной БД пока нет проектов, импортов и версий набора. Сопоставление полей, проверка бизнес-семантики и полный путь импорта ещё не выполнены. Детальная сверка: [инвентаризация данных](context/data-inventory.md).

### Серверные интеграции вне Docker

Для работы API проектов заполните Clerk-ключи, задайте `DATABASE_URL` доступной PostgreSQL и примените миграции **до** работы с API:

```bash
node --env-file=.env.local --conditions=react-server --import tsx scripts/migrate-data-model.ts
```

Миграции не выполняются автоматически при сборке. Проверки БД проведены на PostgreSQL 18.4. Для импорта через HTTP дополнительно нужны приватный bucket, настройки S3 и разрешённый CORS для вашего приложения; облачная конфигурация здесь не разворачивается.

| Переменные из `.env.example` | Назначение |
| --- | --- |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY` | Вход и проверенная серверная сессия |
| `NEXT_PUBLIC_CLERK_*_URL` | Маршруты входа/регистрации и возврата; для перехода после входа можно задать fallback `/` |
| `DATABASE_URL` | Строка подключения PostgreSQL |
| `S3_BUCKET`, `S3_REGION` | Хранилище загрузок; обязательны для API импорта |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Пара серверных ключей; если оба отсутствуют, SDK использует стандартную цепочку учётных данных окружения |
| `S3_ENDPOINT` | Необязательный endpoint; совместимость конкретного S3-совместимого сервиса отдельно не проверена |
| `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` | Настройка адаптера; допустимый базовый адрес в коде — `https://api.openai.com/v1` |
| `NVIDIA_API_KEY`, `NVIDIA_MODEL`, `NVIDIA_BASE_URL` | Настройка адаптера; допустимый адрес — `https://integrate.api.nvidia.com/v1` |
| `LIVEBLOCKS_SECRET_KEY` | Серверный адаптер Liveblocks |
| `TRIGGER_SECRET_KEY`, `TRIGGER_PROJECT_REF` | Серверный доступ Trigger и идентификатор проекта для задач |
| `RUN_CURSOR_SECRET` | Отдельный стабильный секрет подписи курсоров API расчётов, не менее 32 символов |

Одного заполнения переменных AI/Liveblocks/Trigger недостаточно для подключения их к демо. OpenAI live-вызовы сейчас запрещены. Секреты храните только в окружении или `.env.local`, не в Git и не в клиентских `NEXT_PUBLIC_*` переменных.

```bash
node --env-file=.env.local node_modules/trigger.dev/dist/esm/index.js dev
# Развёртывание — только в заранее настроенном аккаунте и среде:
# node --env-file=.env.local node_modules/trigger.dev/dist/esm/index.js deploy
```

Команды выше обращаются напрямую к локальному CLI установленной версии. Для развёрнутых задач задайте серверные секреты в среде Trigger отдельно; локальная `.env.local` сама по себе не настраивает облако. Не передавайте секреты через аргументы команд или Git.

Восстановитель обрабатывает одну ограниченную партию и завершается:

```bash
node --env-file=.env.local --conditions=react-server --import tsx scripts/recover-dispatch.ts
# При уже настроенном окружении: npm run jobs:recover
```

Запускайте его при старте и регулярно отдельным планировщиком, например раз в минуту. Это **не автоматический перерасчёт**: процесс доставляет уже сохранённые намерения и подтверждает отмену. Без планировщика нельзя полагаться на восстановление после остановки HTTP. Детали: [отправка и отмена](lib/server/dispatch-README.md).

Начальные лимиты для синтетической проверки: 600 секунд на задачу, по 2 параллельных выполнения каждой очереди, до 3 попыток задачи и до 5 попыток отправки. Импорт ограничен 8 уникальными объектами и 100 MiB суммарно, при 25 MiB на объект и дополнительных пределах парсера. Это не согласованная промышленная политика.

## 8. Как проверить решение

### Сценарий А: рабочее место менеджера без ключей

1. Откройте `/`: начальное состояние — **«Расчёт готов»**. На широком экране поставщик выбирается слева от таблицы, на телефоне — селектором; четыре иконки внизу открывают закупки, данные, историю и параметры. На экране обозначено: **«Демо»**.
2. Проверьте две группы поставщиков и раскройте обоснование позиции: показаны спрос, сезонность, тренд, отсутствие товара, остатки и товары в пути. Это демонстрационные показатели, не результат расчёта по вашему файлу.
3. Измените количество в колонке **«К заказу»** с учётом шага позиции, заполните **«Причина правки»**, нажмите **«Сохранить»**. Исходная рекомендация остаётся отдельной.
4. Отметьте **«Проверено»** у каждого поставщика. Нажмите **«Утвердить»**, затем **«Подтвердить»**.
5. Откройте **«Предпросмотр заказа»**. Ожидается предпросмотр утверждённых строк с вашими правками, без скачивания и отправки.
6. Обновите страницу: правки сбросятся. Через **«Параметры → Сценарий просмотра»** можно отдельно проверить состояния «Ошибки данных», «Связь потеряна» и «ИИ-пояснение недоступно».

### Сценарий Б: настоящий разбор синтетического XLSX

В новом терминале из корня репозитория:

```bash
DEMO_DIR=$(mktemp -d)
node --conditions=react-server --import tsx scripts/generate-import-fixture.ts "$DEMO_DIR"
node --conditions=react-server --import tsx scripts/import-dataset.ts \
  --manifest "$DEMO_DIR/manifest.json" \
  "20000000-0000-4000-8000-000000000001=$DEMO_DIR/synthetic.xlsx"
```

Ожидаемый результат: `status: "ready"`, `checkedRows: 37`, `acceptedRows: 37`, `rejectedRows: 0`, `unresolvedRows: 0`, код выхода `0`.

Создаётся книга с 12 ролями источников: артикул `000123`, обычные продажи и крупная разовая продажа, месячная история, остаток 0, поставка в пути, явный интервал отсутствия товара, сезонные индексы и справочники. Контрольная сумма рассчитывается для сгенерированного файла.

**Это dry-run:** отчёт доказывает работу парсера и нормализации, но не точность прогноза, не сохранение в БД и не публикацию полного набора. В частности, материальная ведомость принимается в диагностический черновик, но ещё не поддерживается SQL-публикацией. `ready` здесь означает структурную проверку, не готовность всех алгоритмов.

## 9. Данные и интеграции

### Источники данных

Поддерживаемые роли manifest: продажи по операциям, месячные продажи, остатки, поставки в пути, интервалы отсутствия товара, поставщики, сроки поставки, категории, прогноз прироста, сезонность, сопоставление товаров и материальная ведомость.

В текущем checkout используются **синтетические данные** из `lib/procurement/mock-workspace.ts` и генератора `scripts/generate-import-fixture.ts`. Они независимы друг от друга. Исходные XLSX/ZIP партнёра не входят в публикуемую версию; [инвентаризация](context/data-inventory.md) — исследовательский документ, не доказательство поддержки всех реальных файлов.

Артикулы сохраняются как строки с ведущими нулями; отсутствие данных не подменяется нулём. Формулы и макросы не исполняются, внешние связи и опасные архивные структуры отклоняются. Политика обезличивания реальных клиентских данных требует отдельного согласования: синтетические `anon_*` не подтверждают анонимность чужой выгрузки. Не загружайте персональные данные в демонстрацию.

### HTTP API

Все маршруты требуют проверенную сессию и доступ владельца. Ответы имеют форму `{ data: ... }` либо `{ error: { code, message, requestId, ... } }`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/projects`, `POST /api/projects` | Список и создание проектов |
| `GET /api/projects/:projectId`, `PATCH /api/projects/:projectId` | Чтение, переименование, архивирование |
| `GET /api/projects/:projectId/imports`, `POST /api/projects/:projectId/imports` | Список импортов, создание попытки и подписанной загрузки |
| `GET /api/projects/:projectId/imports/:importId` | Состояние попытки |
| `POST /api/projects/:projectId/imports/:importId/finalize` | Фиксация manifest и намерения фоновой проверки; новая работа — `202`, повтор — `200` |
| `POST /api/projects/:projectId/imports/:importId/attempts` | Исправленный manifest и новая фоновая попытка без изменения предыдущей |
| `GET /api/projects/:projectId/datasets` | Список опубликованных версий |
| `POST /api/projects/:projectId/runs` | Создание расчёта: `202`; повтор того же ключа/тела — `200`, конфликт — `409` |
| `GET /api/projects/:projectId/runs` | История запусков с подписанным курсором |
| `GET /api/runs/:runId` | Сохранённые статус, этапы, конфигурация, предупреждения и полнота |
| `POST /api/runs/:runId/cancel` | Отмена незавершённого расчёта; без тела запроса |
| `GET /api/runs/:runId/recommendations` | Рекомендации после успеха; до него — `409`; курсор, `limit`, `supplierId`, `q`, `urgency` |

Схемы запросов: [проекты и импорт](lib/contracts/project-data.ts), [расчёты](lib/contracts/runs.ts). Создание расчёта требует `datasetVersionId`, `scope`, `configuration` и `idempotencyKey`. Конфигурация включает явные политики прогноза/пополнения и `parametersHash`; алгоритм этой версии — `1`. Диагностический запуск не разрешает утверждение; готовность набора не означает полноту всех требований. Лимит исходного файла — **25 MiB**, подписанной ссылки — **300 секунд**. Для браузерного PUT необходимо передавать требуемые подписанные заголовки; завершающий HTTP-запрос не заменяет проверку содержимого импортёром.

## 10. Ограничения текущей версии

- **UI ещё не связан со сквозным сценарием:** прогноз, пополнение и серверные задачи реализованы; демонстрационный интерфейс пока не читает их через API. Облачная проверка и интеграция UI остаются отдельными этапами.
- **Нет производственного утверждения/экспорта:** демо хранит правки в памяти, не скачивает файл и не отправляет заказ. Коннектор 1С и совместимый формат обмена не подтверждены. Автоматическая отправка поставщику не входит в объём решения.
- **Импорт неполон:** реализован XLSX, но не CSV и не внешний ZIP с несколькими книгами. Не завершены числовая сверка месячной/транзакционной истории, полный путь конверсий единиц и разрешение конфликтов приоритетов. SQL-публикация отклоняет материальную ведомость и частичные месяцы, а не молча теряет данные.
- **API подготовки требует доработки:** начальное несопоставленное описание источника требует согласования. Финализация сохраняет намерение фонового импорта; отчёт попытки читается из приватного S3 после проверки владельца. Вызовы S3 при подготовке загрузки пока удерживают транзакционную блокировку; нет уборки просроченных загрузок и распределённого ограничения частоты запросов.
- **Восстановление после длительного сбоя БД:** если PostgreSQL недоступен до завершения обработчика `onFailure`, операция может остаться незавершённой в БД и требует отдельной сверки; восстановитель dispatch не сверяет терминальное состояние Trigger.
- **Интеграции не приняты в облаке:** реальные Trigger/S3/RDS/Clerk/Liveblocks/AI и передача данных партнёра отдельно не проверены. Модели, бюджет, права передачи и сроки хранения требуют настройки и согласования.
- **Поставка ещё интегрируется:** зависимости закреплены в package/lock; metadata snapshot Drizzle после SQL-миграций 0001/0002 ещё не обновлён. Используйте отслеживаемые SQL-миграции, не автоматическую генерацию изменений схемы.
- **Аудит зависимостей:** при проверке установки 23.09.2026 npm сообщил о 19 уязвимостях: 12 moderate, 6 high, 1 critical; high/critical находятся в транзитивном дереве CLI Trigger (включая tar/ws/deepmerge-ts). Их разбор и совместимое обновление зависимостей остаются отдельной задачей перед эксплуатацией; автоматический `audit fix --force` не применялся.

Следующие шаги — закрыть пробелы импорта/API, подключить детерминированное ядро и фоновые задачи, затем связать интерфейс с сохранёнными результатами. Полный план: [context/feature-specs/00-build-plan.md](context/feature-specs/00-build-plan.md).
