# KaiBridge AI

MVP для HackAlem AI / AI Sana Hackathon: бизнес описывает проблему, уточняет её через интервью, проверяет предложенную карточку и публикует задачу. Студенты отправляют предложения, бизнес вручную выбирает команду. Readiness Score показывает полноту карточки и считается Python-кодом, а не моделью.

Архитектура: React + Vite → FastAPI → SQLite. Общий AIWorkflow выполняет проверку схем и цитат, сохраняет анализ/предложение отдельно и применяет карточку только после подтверждения человека. Через один интерфейс подключается либо локальный DemoAIProvider, либо настоящий OpenAIProvider (Responses API + Structured Outputs). Аккаунты, роли и серверные cookie-сессии относятся к этапу 5A; demo AI не изменяет права доступа. backend/agent.py и backend/tools.py остаются неиспользуемыми заготовками.

Актуальный путь независимой проверки — quick-start и сценарий DEMO ниже. Разделы этапов 1–4 дальше в README сохраняют историю: их старые Swagger/PowerShell-примеры без cookie и Origin не являются актуальной инструкцией запуска.

В свежем клоне .env.example включает **AI_PROVIDER=demo**, а OPENAI_API_KEY пуст. OpenAI account, подписка и API-ключ для этого сценария не нужны. Если корневой `.env` уже существует, не перезаписывайте его: установите в нём `AI_PROVIDER=demo` вручную. Переменные окружения процесса имеют приоритет над `.env`; убедитесь, что они не задают другой provider.

## Два режима AI

**1. DEMO MODE — независимая техническая проверка**

```dotenv
AI_PROVIDER=demo
OPENAI_API_KEY=
```

Это локальный deterministic provider: одни и те же входные данные дают одинаковые вопросы и содержимое предложения. Он не делает сетевых AI-запросов, не требует OpenAI account/API key и **не является реальным LLM inference**. Позволяет проверить весь workflow: draft → analysis → questions → answers → card proposal → source validation → human confirmation → readiness. UUID записей анализа/предложения создаются сервером заново и не обязаны совпадать.

Provider использует текст draft только как исходный контекст, а не пытается понимать его смысл. Вопросы построены по фиксированным категориям и содержат фрагмент текущего описания. Ответ бизнеса переносится целиком в соответствующее поле с точной цитатой и source_id. Неотвеченные поля остаются неизвестными; название и отрасль заполняются человеком. Текст длиннее лимита поля не обрезается с потерей смысла: контекст можно уточнить ответом на соответствующий вопрос.

На странице виден баннер «Демонстрационный AI-режим» с пояснением об отсутствии LLM. Это симуляция для проверки интеграции и человеческого подтверждения, а не доказательство качества настоящего AI или автоматическая гарантия допуска организаторами.

**2. OPENAI MODE — настоящая интеграция**

```dotenv
AI_PROVIDER=openai
OPENAI_API_KEY=your_key_here
OPENAI_MODEL=gpt-5.4-mini
```

Замените `your_key_here` своим действующим серверным ключом только в корневом `.env`. Здесь выполняются настоящие запросы через OpenAI Responses API с Pydantic Structured Outputs; требуется доступ к модели и API-биллинг. Ключ не помещается во frontend или Git. Реальные вызовы могут тарифицироваться.

Режим выбирается явно. Если AI_PROVIDER нигде не задан, сохраняется прежний режим **openai**, а не demo. При отсутствии ключа/модели или ошибке OpenAI остаётся прежний ручной fallback; **скрытого переключения OpenAI → demo нет**. Неизвестный AI_PROVIDER останавливает запуск с понятной ошибкой. После изменения режима перезапустите backend и обновите страницу. Для незавершённого интервью заново выполните анализ: demo не переинтерпретирует вопросы, сохранённые другим provider.

## Этап 1: API задач

Работает без OpenAI и API-ключа. Сервис сохраняет только введённые сведения, ничего не извлекает и не придумывает из черновика. Поле draft хранит исходное описание; структурированные поля заполняются явно через API.

| Метод | Адрес | Назначение |
|---|---|---|
| POST | /challenges | Создать черновик, HTTP 201 |
| GET | /challenges/{id} | Получить карточку и актуальный рейтинг |
| PATCH | /challenges/{id} | Частично изменить карточку и пересчитать рейтинг |
| POST | /challenges/{id}/readiness | Пересчитать рейтинг сохранённой карточки |
| GET | /health | Прежний health check |

Ответ карточки содержит id, draft, все структурированные поля, published=false, readiness_score, readiness_level, breakdown, missing_information и recommendations. Ответ пересчёта содержит только рейтинг, уровень, разбивку, недостающие поля и рекомендации.

При создании обязателен непустой draft (до 20 000 символов). Остальные текстовые поля необязательны и ограничены 10 000 символами каждое. Пробелы по краям удаляются. PATCH меняет только переданные поля; пустая строка очищает структурированное поле. Пустой PATCH, null, неверные типы, неизвестные поля и попытки задать id/published/рейтинг возвращают 422. Некорректный UUID — 422, отсутствующая задача — 404, ошибка SQLite — 503. Валидация сообщает проблемное поле в detail.

Создание и редактирование не публикуют задачу: даже 100 баллов не меняют published. Для публикации добавлен отдельный endpoint этапа 3. Рейтинг всегда вычисляется из сохранённых полей и не хранится отдельным устаревающим значением.

### Правила рейтинга

| Критерий | Баллы |
|---|---|
| context + need | 10 + 10 |
| data_and_materials | 20 |
| expected_result | 15 |
| success_criteria | 15 |
| constraints | 10 |
| users | 10 |
| contact + interaction_format | 5 + 5 |

Каждое непустое поле получает указанный вес целиком. Пустое поле получает 0. title, industry и исходный draft на баллы не влияют. Явное описание отсутствия данных или ограничений считается предоставленной информацией. Это оценка заполненности, а не качества, истинности или реализуемости задачи: произвольный непустой текст тоже получает баллы.

Уровни: 0–39 Draft; 40–69 Working; 70–89 Ready; 90–100 Priority. breakdown содержит score и max_score для семи критериев. missing_information перечисляет пустые оцениваемые поля, recommendations объясняет, что добавить и сколько баллов это даст.

### Ручная проверка

Запустите backend командой выше и откройте http://127.0.0.1:8000/docs. Либо выполните в PowerShell:

```powershell
$base = 'http://127.0.0.1:8000'
Invoke-RestMethod "$base/health"
$body = @{draft='We want to improve customer support'} | ConvertTo-Json
$challenge = Invoke-RestMethod "$base/challenges" -Method Post -ContentType 'application/json' -Body $body
$challenge # score=0, level=Draft, published=False
$edit = @{context='Online shop'; need='Reduce repetitive questions'; data_and_materials='FAQ and anonymized support tickets'} | ConvertTo-Json
Invoke-RestMethod "$base/challenges/$($challenge.id)" -Method Patch -ContentType 'application/json' -Body $edit
# score=40, level=Working
Invoke-RestMethod "$base/challenges/$($challenge.id)/readiness" -Method Post
Invoke-RestMethod "$base/challenges/$($challenge.id)"
```

После перезапуска backend GET с тем же id должен вернуть сохранённую карточку. Для проверки снижения баллов отправьте PATCH с {"context":""}: результат — 30, Draft.

База и служебные файлы SQLite исключены из Git. Частичные обновления выполняются в транзакции; подключения закрываются после запроса. ORM и миграции пока не нужны.

## Этап 2: AI-анализ и предложенная карточка

Весь workflow доступен через Swagger; frontend не менялся. Слово card-proposals означает предложения полей карточки от AI, а не заявки студенческих команд.

### Настройки OpenAI

Проверенный установленный SDK: openai==3.19.0. Используется официальный Responses API, client.responses.parse(text_format=PydanticModel), строгий Structured Output. Документация: https://developers.openai.com/api/docs/guides/structured-outputs

Установите зависимости:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Для настоящего OpenAI в корневом .env задайте AI_PROVIDER=openai, OPENAI_API_KEY и OPENAI_MODEL. Актуальный .env.example включает demo и пример модели gpt-5.4-mini, но не содержит настоящего ключа. Не перезаписывайте существующий .env командой копирования, если в нём есть ваши настройки.

```dotenv
AI_PROVIDER=openai
OPENAI_API_KEY=your_key_here
OPENAI_MODEL=gpt-5.4-mini
```

Замените your_key_here своим ключом. OpenAIProvider не подставляет модель в коде: она берётся из настройки OPENAI_MODEL. Без ключа ИЛИ модели в режиме openai AI endpoint вернёт fallback/not_configured. Переменные окружения процесса имеют приоритет над .env. Секрет читается только backend; префикс VITE_ использовать нельзя. /health возвращает только статус и имя provider, без секретов. .env не изменялся при реализации.

Один запрос анализа или построения карточки делает один запрос OpenAI: timeout 30 секунд, автоматические повторы выключены, store=false. SDK-клиент закрывается после запроса. Реальные вызовы могут тарифицироваться; automated tests используют mock и не вызывают OpenAI.

### Новые endpoints

| Метод | Путь | Назначение |
|---|---|---|
| POST | /challenges/{id}/analysis | Анализ draft, известные сведения, недостающие категории, минимум 3 вопроса |
| POST | /challenges/{id}/card-proposals | Ответы на вопросы → отдельное AI-предложение карточки |
| GET | /challenges/{id}/card-proposals/{proposal_id} | Просмотр предложения и исходной карточки |
| POST | /challenges/{id}/card-proposals/{proposal_id}/confirm | Подтверждение с необязательными ручными правками |

Анализ и построение возвращают HTTP 200 со status=ok либо status=fallback. При fallback доступны code, message и manual_edit_available=true; фиктивных AI-карточек или вопросов не генерируется. Коды: not_configured, unavailable, invalid_output. При ошибке остаются доступны PATCH и readiness этапа 1. Нет анализа/предложения для этой задачи — 404, неверный запрос — 422, устаревшее или повторное подтверждение — 409.

Анализ содержит known_information, evidence, missing_information и questions с id (q1, q2, …), field, kind и text. Для неизвестной категории kind=missing; когда категорий не хватает меньше трёх, модель должна спрашивать только ещё не описанные детали (kind=detail), не повторять известные факты. Дубликаты вопросов и вопросы kind=missing о найденных полях отклоняются. missing_information вычисляется backend по извлечённым полям девяти обязательных категорий.

### Ручная проверка с настоящим ключом

1. Запустите backend и откройте http://127.0.0.1:8000/docs.
2. Создайте Challenge через POST /challenges с непустым draft и сохраните id.
3. Выполните POST /challenges/{id}/analysis (без body). При status=ok сохраните analysis_id и прочитайте вопросы.
4. Ответьте на вопросы через POST /challenges/{id}/card-proposals. Подставьте настоящий analysis_id, соответствующие question_id и ваши ответы:

```json
{
  "analysis_id": "UUID из ответа анализа",
  "answers": [
    {"question_id": "q1", "text": "Ответ бизнеса на первый вопрос"},
    {"question_id": "q2", "text": "Ответ бизнеса на второй вопрос"},
    {"question_id": "q3", "text": "Ответ бизнеса на третий вопрос"}
  ]
}
```

Можно ответить на часть вопросов, но минимум на один. Неизвестные поля остаются пустыми. Суммарный размер ответов — до 30 000 символов.

5. Получите proposal_id. Просмотрите proposed_card, current_card и evidence. GET Challenge до подтверждения должен вернуть прежние данные и рейтинг. Предложение хранится отдельно и доступно после перезапуска.
6. Для принятия отправьте POST /challenges/{id}/card-proposals/{proposal_id}/confirm:

```json
{
  "confirmed": true,
  "edits": {
    "title": "Название, подтверждённое бизнесом"
  }
}
```

edits можно опустить или передать пустой объект. В него входят только поля карточки; пустая строка очищает поле. Ручные правки — новые сведения самого пользователя, поэтому они не ограничены цитатами AI. Значения null, draft, published и readiness_score в edits запрещены.

7. Confirm заменяет ВСЕ структурированные поля на просмотренную proposed_card с вашими edits. Пустые поля предложения тоже применяются: сравните с current_card перед подтверждением, чтобы сохранить нужные прежние сведения через edits. Исходный draft сохраняется. Backend пересчитывает readiness прежним scoring engine; published не меняется (для неопубликованной задачи остаётся false). GET Challenge показывает итог.
8. Если Challenge изменился после анализа (включая ручной PATCH), повторите анализ и построение предложения: устаревшее предложение не перезапишет новые данные. Повторный confirm возвращает 409.

### Защита от выдуманных сведений и ограничения

- Каждое непустое AI-поле — точная цитата с source_id из draft или конкретного answer:qN. Backend проверяет наличие цитаты именно в указанном источнике. Текст вопроса не является источником фактов.
- Неизвестные поля возвращаются как null в ответе модели и как пустые строки в proposed_card. Произвольный текст не разбирается регулярными выражениями.
- Некорректная схема, выдуманная цитата, отказ модели или незавершённый ответ дают явный fallback. Challenge не изменяется.
- AI не получает инструментов записи в БД, публикации или выбора команды. Scoring не передаётся модели.
- Цитирование не доказывает правильность смыслового отнесения фразы к полю. Ошибки интерпретации, неполное извлечение и неудачные вопросы возможны: просмотр и ручное подтверждение обязательны. В MVP нет свободного перефразирования и придуманного заголовка, поэтому title/industry часто остаются пустыми.
- При очень полном draft требование трёх вопросов реализуется вопросами о дополнительных неуказанных деталях. Их полезность зависит от модели.
- Используются две таблицы SQLite: исходные challenges и отдельная ai_workflows с анализами, ответами и предложениями. Добавление таблицы не меняет существующие Challenge. Подтверждение и отметка confirmed выполняются одной транзакцией. Автоматического удаления старых workflow пока нет.
- Авторизации, rate limiting и UI workflow пока нет. Реальные вызовы OpenAI проверены отдельно при ручном сценарии с gpt-5.4-mini. API-ключ хранится только локально в .env.

## Этап 3: публикация, каталог и студенческие предложения

Frontend и AI workflow не изменены. Регистрации, ролей и проверки прав нет: Business/Student — логические сценарии. Использовать локально для MVP; любой клиент API технически может выполнить ручное действие.

### Публикация и каталог

- POST /challenges/{id}/publish с JSON {"confirmed":true} публикует существующую карточку. Подтверждение обязательно; false, строка "true" и отсутствующий body дают 422.
- Любой score, включая 0, допустим. Публикация не меняет поля или рейтинг. Повторная публикация идемпотентна: 200 и та же карточка.
- AI analysis, card-proposals, confirm и обычный PATCH не меняют флаг публикации. Уже опубликованная карточка остаётся опубликованной после редактирования; изменения сразу видны в каталоге. Снятие с публикации в этом этапе не реализовано.
- GET /challenges возвращает массив только опубликованных карточек, включая низкорейтинговые. Сортировка: score по убыванию, затем id по возрастанию при равенстве.
- Необязательные query-параметры industry и readiness_level комбинируются через AND. Industry — полное совпадение без учёта регистра и внешних пробелов; readiness_level — Draft, Working, Ready или Priority (неизвестное значение даёт 422).
- Рейтинг вычисляется текущим scoring engine при чтении. Для небольшого MVP фильтрация и сортировка выполняются в Python; пагинации и полнотекстового поиска нет.

### Student Proposal

POST /challenges/{id}/proposals создаёт заявку команды (201). В отличие от AI /card-proposals, это отдельная сущность и таблица student_proposals.

```json
{
  "team_name": "Student Team",
  "skills": "Python, React",
  "solution_idea": "Помощник для подготовки ответов по FAQ",
  "plan": "Изучить FAQ, сделать прототип, проверить на тестовых вопросах",
  "estimated_time": "5 часов",
  "prototype_url": "https://example.com/demo"
}
```

Все текстовые поля, кроме prototype_url, обязательны и не могут состоять из пробелов. skills — строка. prototype_url можно опустить или передать null; разрешены HTTP/HTTPS URL. Ссылка не открывается и не загружается сервером. id, challenge_id и status задаёт backend, при создании status=pending. Попытка передать status в запросе даёт 422.

Для unpublished Challenge отправка запрещена (409). Отсутствующая задача — 404. GET /challenges/{id}/proposals возвращает все её заявки в порядке поступления; пустой список допустим. Заявка связана с Challenge внешним ключом SQLite.

### Ручные решения бизнеса

- POST /challenges/{challenge_id}/proposals/{proposal_id}/accept (без body): pending → accepted.
- POST /challenges/{challenge_id}/proposals/{proposal_id}/reject (без body): pending → rejected.
- Повтор того же решения возвращает 200 и текущее состояние.
- accepted → rejected и rejected → accepted запрещены (409).
- Предложение от другой задачи или неизвестный proposal_id — 404.
- Только одна accepted-заявка на Challenge. Попытка принять другую — 409. Ограничение защищено транзакцией BEGIN IMMEDIATE и уникальным частичным индексом SQLite, включая конкурентные запросы.
- Остальные pending остаются pending, их можно вручную отклонить. Новые заявки после выбора команды разрешены и остаются pending; принимать их нельзя, пока уже есть accepted. Отмена выбора не реализована.
- AI не вызывается при публикации, отправке студенческой заявки или решении бизнеса.

### SQLite migration

При старте старая таблица challenges с CHECK (published = 0) атомарно перестраивается в таблицу с CHECK (published IN (0, 1)). Сохраняются id, payload и published, таблица ai_workflows не удаляется. Добавляется student_proposals. Повторный запуск не перестраивает уже обновлённую схему. На каждом подключении включён foreign_keys. Новых зависимостей нет.

### Ручной сценарий через Swagger

1. Создайте draft и пройдите AI analysis → card-proposals → confirm по инструкции этапа 2. Проверьте score и published=false.
2. Вызовите POST /challenges/{id}/publish с {"confirmed":true}. Ожидайте published=true и прежний score.
3. GET /challenges: карточка видна в каталоге. Проверьте фильтры industry и readiness_level.
4. Отправьте заявку командой POST /challenges/{id}/proposals с JSON выше. Сохраните её id.
5. Получите список GET /challenges/{id}/proposals: заявка pending.
6. POST /challenges/{id}/proposals/{proposal_id}/accept: accepted. Альтернативный сценарий — reject для другой pending-заявки.
7. Проверьте запрет принятия второй команды (409) и повтор того же accept (200).

Отдельный ручной прогон выполнен на временном Uvicorn-сервере и отдельной SQLite с настоящим OpenAI: draft → анализ (10 вопросов) → AI-предложение → ручные правки/confirm → score 100 → publish → отфильтрованный каталог → student proposal → accept. До confirm Challenge оставался неизменным. /health возвращал ok. Рабочая карточка пользователя не использовалась; временный сервер остановлен.

Полный automated suite: 55 тестов (40 прежних + 15 новых), включая миграцию с сохранением данных и конкурентный accept. Автотесты не делают платных AI-вызовов.

Backend-ограничения этапа 3: нет авторизации, пагинации, снятия публикации, отмены принятия команды, уведомлений и UI этих сценариев. Смысловые неточности вопросов AI из этапа 2 требуют ручной проверки; новый AI workflow не добавлялся.

## Этап 5A: аккаунты, роли и демонстрационный статус проверки

Новых Python/npm-зависимостей нет. User содержит id, name, уникальный нормализованный email, password_hash, role (student/business), verification_status, created_at и необязательные university / company_name / position / company_industry / company_website. Поля другой роли не сохраняются. Роль задаётся при регистрации; статус всегда unverified. Передать owner_id, чужую роль в действии или verification_status для повышения прав нельзя.

### Authentication

| Метод | Путь | Поведение |
|---|---|---|
| POST | /auth/register | Создать аккаунт, 201; отдельный login обязателен |
| POST | /auth/login | Проверить пароль, выдать новую cookie-сессию |
| GET | /auth/me | Текущий профиль без password_hash либо 401 |
| POST | /auth/logout | Удалить серверную сессию и cookie, 204 |
| POST | /auth/request-verification | unverified → pending, без автоматического подтверждения |

Пароли хешируются PBKDF2-HMAC-SHA256: 600 000 итераций и индивидуальная случайная соль. Сессия — случайный 256-битный токен; в SQLite хранится только SHA-256 токена, user_id и срок действия 12 часов. Cookie kaibridge_session имеет HttpOnly, SameSite=Lax, Path=/, без Domain. Повторный login меняет токен и отзывает предыдущую сессию данного браузера; logout отзывает её сразу. Права и статус читаются из БД на каждый запрос.

Все POST/PUT/PATCH/DELETE требуют точный Origin из FRONTEND_ORIGIN, включая login/logout; отсутствие Origin тоже даёт 403. Для API-клиента явно передавайте `Origin: http://localhost:5173` и сохраняйте полученную cookie. Это защита от браузерного CSRF, а не замена авторизации. CORS разрешает credentials только этому origin. Auth-ответы имеют Cache-Control: no-store; ошибки валидации не возвращают входные значения, включая пароль.

Секрет подписи не требуется: токены непрозрачные и серверные. Секреты и токены не хранятся в frontend/localStorage. Там остаётся только ID последней задачи с отдельным ключом для каждого пользователя и несекретная отметка незавершённого расчёта. Выход очищает текущий ID и приватные формы.

### Verification и права

`unverified → pending` выполняет пользователь. Повтор запроса при pending/verified не меняет статус; rejected остаётся rejected. В 5A rejected предусмотрен моделью, но отдельного процесса отказа и апелляции нет. `pending → verified` доступен только локальной demo-команде ниже; публичного endpoint для назначения verified нет. Это **не проверка личности, документов, email или компании**.

| Действие | Условия на backend |
|---|---|
| Каталог и опубликованная карточка | Публично |
| Создать черновик | Вход с ролью business, подтверждение пока не нужно |
| Читать черновик, редактировать, AI-анализ/предложение/confirm, читать отклики | Только business-владелец |
| Публиковать, принять/отклонить отклик | verified business-владелец |
| Изменять уже опубликованную карточку | verified business-владелец |
| Отправить отклик | verified student; задача опубликована и имеет владельца |

Новый Challenge получает owner_id из сессии, Student Proposal — student_id из сессии. Business A не может редактировать задачи или решать по откликам Business B. Ручное подтверждение AI-карточки и отдельное согласие на публикацию сохранены; скоринг не менялся.

### Миграция и старые задачи

При старте добавляются users/auth_sessions и nullable-ссылки challenges.owner_id, student_proposals.student_id. Старые payload, id, published, AI history и статусы предложений сохраняются. Повторная инициализация безопасна. Старым записям никто автоматически не назначается.

Опубликованные задачи без owner остаются в каталоге только для чтения; новые отклики и управление запрещены (409). Старые черновики и AI history не становятся публичными. Для восстановления управления оператор локально назначает конкретную старую задачу существующему бизнес-аккаунту:

```powershell
.\.venv\Scripts\python.exe -m backend.demo_identity assign-legacy --challenge-id ID --business-email owner@example.com --demo
```

Команда не может заменить уже назначенного владельца и не принимает student. Сначала убедитесь, что выбраны нужные задача и email. Для другой БД укажите `--database PATH` перед `assign-legacy` или `verify`. Назначение владельца не изменяет содержание и предложения. Старые student_id остаются NULL, поскольку достоверно связать прежние отклики с новыми аккаунтами нельзя.

3. Нажмите «Запросить проверку»: статус «На проверке». Только для тестового аккаунта выполните из корня:

```powershell
.\.venv\Scripts\python.exe -m backend.demo_identity verify --email owner@example.com --demo
```

4. Нажмите «Обновить статус», проверьте «Подтверждён». Опубликуйте задачу с отдельным согласием.
5. Выйдите, зарегистрируйте student с другим email. Откройте задачу: отправка до подтверждения запрещена. Запросите проверку, выполните ту же demo-команду для студенческого email, обновите статус. Отправьте предложение.
6. Выйдите, войдите прежним business, найдите свою задачу в каталоге и нажмите «Управлять задачей». Примите/отклоните отклик вручную. Другой business не получает эту кнопку и получает 403 при прямом запросе к API.
7. После logout /auth/me возвращает 401. Обновление страницы восстанавливает действующую cookie-сессию. Не переключайте бизнес и студента в одном аккаунте: это разные роли и разные аккаунты.

В локальном HTTP demo AUTH_COOKIE_SECURE=false. Для HTTPS-развёртывания нужен AUTH_COOKIE_SECURE=true и корректный FRONTEND_ORIGIN; frontend/API должны иметь совместимые same-site адреса. До публичного запуска нужны HTTPS, ограничение частоты login/register/AI, реальное управление verification, восстановление доступа и эксплуатационная защита БД/резервных копий. Email при регистрации не подтверждается, поэтому он не доказывает личность. Большой профиль, email delivery, OAuth, Student ID/OCR/Vision, внешняя проверка компаний, MFA и admin panel не реализованы в 5A.

Backend suite 5A: 79 тестов (55 прежних + 24 новых). Auth-fixtures минимально адаптированы для 43 прежних тестов: 10 API, 18 AI workflow, 1 fallback provider, 14 publication; исходные проверки поведения сохранены. Остальные 12 тестов не менялись. Добавлены проверки ролей, владельца, session expiry/logout, Origin, паролей/валидации и legacy migration. AI-вызовы в тестах подменены, реальный ключ не используется.

Frontend lint и production build проходят. Browser QA 5A выполнен в headless Edge на экранах 1366×900 и 390×844, с отдельной SQLite и детерминированной подменой только AI-provider: регистрация Business/Student → запрет до verification → запрос pending → локальный demo verify → публикация с согласием → два студенческих отклика → ручные Accept/Reject. Проверены logout, восстановление сессии и своей задачи после reload, HttpOnly cookie, отсутствие токена в localStorage, прокрутка мобильной формы и переключение роли. Ошибок JavaScript/CORS не обнаружено; 401 от /auth/me для гостя ожидаем. Реальные AI-запросы в проверке 5A не выполнялись.

Сравнение рабочей БД до/после миграции подтвердило сохранность всех прежних 9 Challenges, 13 AI workflow и 5 Student Proposals без изменения содержимого или статусов; foreign_key_check не выявил ошибок. Тестовые аккаунты браузерной проверки находятся только в отдельной временной БД, а не в рабочем каталоге.
