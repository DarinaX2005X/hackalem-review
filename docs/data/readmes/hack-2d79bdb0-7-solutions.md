# 7-Solutions — пополнение склада

Рабочий прототип для кейса «Автоматический расчёт заказов поставщикам для пополнения склада», ТОО «Электрокомплект». HackAlem AI, 23 сентября 2026. Команда: Мадияр и Асанали.

Приложение читает предоставленные ZIP с Excel, формирует объяснимые рекомендации для IEK и Systeme Electric, позволяет уточнить остаток и количество, утверждает заказ и выгружает CSV для Excel. Данные обрабатываются локально; внешние AI API не вызываются. Прогноз — воспроизводимая статистическая модель. Codex использован при разработке.

## Запуск

Требуется Python 3.11 или новее и openpyxl 3.1.x.

```sh
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python server.py
```

Открыть http://127.0.0.1:8765. На исходном компьютере можно запустить `run.cmd`: он использует готовый Python из среды Codex, если тот доступен. Альтернативный порт: `python server.py --port 8766`.

Код работает без сети после установки зависимости. Сервер слушает только localhost. Это локальный прототип, с локальными аккаунтами, не облачный production-сервис; не следует открывать его напрямую в интернет.

## Данные

В интерфейсе загрузить оба архива `Systeme electric.zip` и `IEK.zip`. Они читаются в памяти, без извлечения путей ZIP на диск. Лимит загрузки — 40 МБ; суммарного распакованного размера Excel — 150 МБ. Импорт ZIP обновляет соответствующего поставщика. JSON заменяет весь набор.

Также доступен импорт из командной строки:

```sh
python importer.py "Systeme electric.zip" "IEK.zip"
```

CLI-результат хранится в `data/dataset.json`. При первом чтении сервер переносит этот набор в SQLite. После появления базы импортировать новые ZIP/JSON через интерфейс; простое изменение старого JSON не заменяет актуальную базу. В локальной сборке для команды данные уже загружены. Исходный архив для передачи кода и Git исключают коммерческие данные, базу аккаунтов, сессии и утверждённые заказы. После клонирования импортировать данные заново либо открыть «Демо-сценарии».

Проверенные входы: 12 файлов, 3 908 уникальных пар поставщик–код 1С, 248 467 положительных строк расходных накладных. 724 позиции Systeme Electric и 3 184 позиции IEK. Это объединение справочников, поэтому не у каждого товара есть все источники.

### Особенности источников

* Основные продажи в динамике положительные. Отрицательные записи не превращаются в положительный спрос; они уже влияют на нетто-продажи месячных отчётов. Обнаружение выбросов работает по положительным накладным.
* Код 1С и артикул поставщика хранятся строками. Соединение выполняется по коду 1С в рамках поставщика; начальные нули и подчёркивания сохраняются.
* Пустые продажи в месячной форме 1С трактуются как 0. Это допущение формата. Пустые остатки остаются неизвестными.
* У Systeme Electric в отчёте товаров в пути есть свободный остаток на 22.09.2026 и поступление 24.09.2026. Колонка «Заказ» не используется как предсказание.
* У IEK доступны месячные начальные остатки, а не подтверждённый свободный остаток на 22 сентября. Для утверждения нужен ручной актуальный остаток или нормализованный импорт.
* «MOQ» у Systeme содержит кратность, у IEK — минимально разрешённую отгрузку. Минимум и кратность не подменяют друг друга. Для IEK кратность по умолчанию 1 учётная единица, пока не передано иное.
* Позиции с закупкой бухтами и учётом метрами блокируются до согласования единиц. В нормализованном JSON нужно привести все количества к одной учётной единице и установить `unit_review: false`.
* В динамике нет ID клиента. Проверка регулярности покупок одного клиента работает только при передаче обезличенного `customer_id` в нормализованном JSON.
* Месячные остатки не позволяют точно восстановить дни stockout. Такие периоды не выдумываются: компенсация применяется при наличии `stockout_days`. Демо содержит подтверждённые синтетические периоды.
* Категории в исходном отчёте Systeme присутствуют как коды без расшифровки. Множитель страхового запаса задаёт менеджер через «Политику категорий». Значение по умолчанию 1; бизнес-смысл кодов не придумывается.

## Сверка месячных продаж с динамикой (DATA-1)

При импорте ZIP создаётся диагностический отчёт `meta.reconciliation`, отдельно по поставщикам. Он также доступен в существующем `GET /api/status`. Для отдельного локального файла:

```sh
python importer.py "Systeme electric.zip" "IEK.zip" --reconciliation-output data/reconciliation.json
```

Строка отчёта соответствует паре код 1С–месяц внутри поставщика; артикул добавляется из справочника, если известен. Сохраняются ведущие нули и подчёркивания. Поля `invoice_positive`, `invoice_negative`, `other_positive`, `other_negative` показывают суммы количеств со своими знаками отдельно для расходных накладных и остальных документов. `dynamics_net` — сумма этих четырёх полей; `delta = dynamics_net − monthly_sales`. Положительная delta означает превышение суммы динамики над месячной формой. Допуск совпадения — 0.000001 учётной единицы.

Статусы: `matched` — арифметическое совпадение; `difference` — расхождение; `missing_monthly` — нет месяца в месячной форме; `missing_dynamics` — нет строк динамики для кода/месяца. Отсутствие строк не подменяется нулём. Пустая ячейка месячной формы по существующему правилу импорта считается нулём. Коды только из динамики также попадают в отчёт, но не становятся новыми рекомендациями. `skipped_rows` считает строки динамики с кодом, но нераспознанной датой/количеством, а также слишком короткие строки. Заголовки и строки без кода не считаются движениями.

Это проверка арифметики, а не подтверждение сопоставимости: назначение прочих документов, единицы, набор складов и полноту периодов нужно сверить с владельцем данных. `partial_month` отмечает месяц даты расчёта (23.09.2026) и будущие месяцы; даже для прошлых месяцев полнота не гарантирована. Неизвестные причины расхождений не угадываются. Отчёт не меняет прогноз и правила утверждения; положительные расходные накладные по-прежнему отдельно используются для поиска выбросов.

Отчёт не содержит имён клиентов, номеров документов, названий товаров или складов. Коды и количества остаются коммерческими данными: хранить файл локально в исключённой из Git папке `data/`, не добавлять его в PR. Сверка реализована для партнёрских ZIP; нормализованный JSON этим отчётом не проверяется. Проверки используют синтетические Excel; для реальной сверки нужны исходные `Systeme electric.zip` и `IEK.zip`.

## Методология

1. **Выбросы.** Строки объединяются по дате, накладной и, при наличии, клиенту. При минимум восьми накладных порог равен `max(5 × медиана, медиана + 6 × 1.4826 × MAD, 1)`. Из исключительной накладной вычитается часть выше медианы обычного заказа. Крупные покупки одного известного клиента на трёх и более отдельных датах сохраняются. Без ID клиента доступны только эвристики по накладным. Обнаружение не является доказательством разового характера покупки.
2. **Сезонность.** Каждый полный год нормализуется к своему среднемесячному уровню. Используется смесь сезонности товара (65%) и поставщика (35%). При отсутствии полного года используется сезонность поставщика. Для поставщика берутся полные 2024–2025 годы. Сезонность выручки поставщика является приближением сезонности количества; доли и цена могут меняться.
3. **Базовый спрос.** Последние шесть полных месяцев очищаются от избыточной части накладных; количества переводятся в дневной спрос и делятся на сезонный индекс. Среднее даёт базовый дневной уровень. Текущий неполный месяц не входит в обучение.
4. **Stockout.** При известных днях отсутствия спрос восстанавливается из скорости продаж в дни наличия. Для полностью пустого месяца используется устойчивый сезонный базовый уровень. Добавленный спрос явно показан в карточке. Без этих данных компенсация не применяется, что отмечено в интерфейсе.
5. **Рост.** При трёх и более сопоставимых месяцах вычисляется медиана отношения к прошлому году. Текущий уровень уже учтён в базе, поэтому исторический рост экстраполируется только на горизонт планирования. Если передан отдельный прогноз прироста (в исходном отчёте Systeme — «Кэф. Роста»), применяется он. Менеджер может задать дополнительный процент. Это разные источники, не дважды применённый один коэффициент.
6. **Горизонт.** Срок новой поставки + период между заказами. Дневной спрос суммируется по календарю с сезонностью каждого месяца горизонта. Страховой запас = текущая дневная скорость × заданные дни × множитель категории.
7. **Поставки.** Вычитаются только положительные поставки с ожидаемой датой от даты расчёта до конца горизонта. Просроченные поступления не считаются доступными автоматически. Риск дефицита рассчитывается по дням с учётом дат поступлений: поздняя большая поставка не скрывает ранний дефицит.
8. **Количество.** `max(0, прогноз + страховой запас − свободный остаток − поступления в срок)`. Положительная потребность доводится до минимума партии и округляется вверх по кратности.

По умолчанию: дата 23.09.2026, срок поставки 30 дней, период заказов 14 дней, страховой запас 14 дней. Это допущения для демо; договорные сроки не представлены. Общие параметры действуют на текущий расчёт всех поставщиков. Для разных условий можно рассчитывать и утверждать поставщиков поочерёдно.

Неизвестный остаток для предварительной оценки принимается равным 0, но утверждение блокируется. Остаток на начало месяца отмечается как предварительный. Неизвестная кратность, несогласованные единицы и история менее трёх из последних шести месяцев также блокируют утверждение.

## Нормализованный JSON

Пример доступен на странице «Источники и качество» или `GET /api/template`. Это синтетический набор; перед загрузкой заменить поля своими обезличенными данными. Пример минимальной позиции:

```json
{
  "items": [{
    "id": "IEK:SKU-001",
    "supplier": "IEK",
    "code": "SKU-001",
    "sku": "SUPPLIER-001",
    "name": "Товар",
    "unit": "шт",
    "category": "1",
    "sales": {"2026-03": 90, "2026-04": 100, "2026-05": 50, "2026-06": 110, "2026-07": 120, "2026-08": 130},
    "stock": 20,
    "stock_kind": "current",
    "stock_date": "2026-09-23",
    "stockout_days": {"2026-05": 15},
    "growth_forecast": 0.1,
    "pack": 5,
    "minimum": 10,
    "inbound": [{"eta": "2026-10-01", "quantity": 30}],
    "transactions": []
  }]
}
```

`growth_forecast` — доля прироста (0.1 = +10%), `seasonality` — необязательный массив из 12 индексов. `transactions` содержит `date` (YYYY-MM-DD), `document`, положительное `quantity`, необязательный обезличенный `customer_id`. Суммы транзакций и месячная история должны относиться к одному периметру. Нормализованный импорт не публикует данные и не отправляет их третьим сторонам.

## Утверждение и экспорт

Открыть карточку товара → при необходимости подтвердить свободный остаток и пересчитать → изменить количество с соблюдением партии → «Выбрать в заказ» → «Утвердить и выгрузить» → ввести ответственного. На сервере повторно проверяются ограничения. Изменение параметров сбрасывает выбранные позиции; импорт инвалидирует предыдущие расчёты.

Снимок утверждения хранится в SQLite `data/app.sqlite3`, в личной истории пользователя, включая параметры, рекомендации и ручные количества. CSV — UTF-8 с BOM, разделитель `;`, строки сгруппированы по поставщикам. Обозначение `demo`/`real` включено в экспорт. Ячейки с формульными префиксами экранируются. Автоматической отправки поставщикам нет. Совместимость с конкретной обработкой импорта в 1С ещё нужно согласовать с владельцем кейса.

## План Б: проверка устойчивости заказа

`scenario.py` и `POST /api/scenario` принимают ID существующего расчёта, ID товара и `shock: {delay_days, demand_pct}`. Допустимы целая задержка 0–60 дней и прирост спроса 0–200%. Симуляция не меняет исходные рекомендации, выбранные количества или утверждения; устаревший расчёт возвращает 409. Дневной прогноз передаётся из движка без округления, сумма совпадает с прогнозом на горизонт.

- Каждый день: поступление в начале дня → расход прогнозного спроса → неотрицательный остаток. Непокрытый спрос учитывается как потерянные продажи и не переносится в долг. Это допущение, не доказанные потерянные продажи.
- Обычный план включает все будущие известные поступления и рекомендуемый новый заказ на день `lead_days`, даже если заказ ещё не утверждён. Задержка сдвигает их все; просроченные поступления не возвращаются в расчёт.
- Горизонт равен сроку поставки плюс периоду между заказами. Поступления за его пределами не скрывают дефицит внутри горизонта.
- План Б: дополнительная партия в объёме всего непокрытого спроса горизонта, округлённая вверх с учётом минимума и кратности. Предполагается поступление до расхода в первый день дефицита. Показываем остаток в конце, чтобы не скрывать возможный избыток. Это не оптимизация стоимости и не разделение уже рекомендуемого заказа.
- При блокировках исходных данных показывается только предварительная симуляция, без предложения количества срочной закупки. Если остаток неизвестен, для предварительного графика он равен нулю.
- Доступность срочной партии, её срок и стоимость менеджер согласует отдельно. Результат не оценивает вероятность события, не обещает экономию и ничего не отправляет поставщику.

Раздел «Источники и качество» также показывает сводку сверки Асанали: совпадения, расхождения, отсутствующие пары и пропущенные строки. Для ранее импортированного набора повторно импортировать ZIP, чтобы получить новую метаинформацию.

## Аккаунты и база данных

Открыть приложение → «Создать аккаунт» → имя, email и пароль от 8 символов. Это аккаунт локального приложения, не GitHub. Email служит логином; проверка письмом и восстановление пароля ещё не реализованы. Не использовать здесь важный пароль от другого сервиса.

`data/app.sqlite3` создаётся автоматически. Таблицы: `users`, `sessions`, `documents` (общий набор, расчёты и утверждённые заказы), `login_failures`. Пароли хранятся как PBKDF2-HMAC-SHA256 (600 000 итераций, случайная соль). Сессионный токен хранится в БД в виде SHA-256; браузер получает HttpOnly, SameSite=Strict cookie на 12 часов. Запросы изменений требуют CSRF-токен сессии; проверяются Host и Origin. После пяти неудачных входов для одного email действует ограничение на 15 минут. Сервер по-прежнему доступен только на localhost; для внешнего размещения нужны HTTPS, Secure cookie, приглашения/роли, отдельные пространства и эксплуатационная настройка.

**Границы доступа:** импортируемый набор товаров общий для локальной команды; зарегистрированный пользователь может его обновлять. Расчёты и заказы принадлежат создавшему их аккаунту. Чужое утверждение/скачивание блокируется сервером. Последние 15 расчётов каждого пользователя сохраняются в БД; импорт нового набора инвалидирует все старые расчёты. История показывает последние 100 собственных заказов и позволяет повторно скачать CSV. Перезапуск сервера сохраняет пользователей, сессии, набор и заказы.

Прежние `data/order-*.json` остаются на диске, но автоматически не назначаются новым аккаунтам: их владельцев исходная версия не сохраняла. Новые заказы записываются в SQLite. Для резервной копии после остановки сервера сохранить папку `data/`; не добавлять её в Git. SQLite не синхронизирует данные между компьютерами.

Маршруты: `POST /api/auth/register`, `/api/auth/login`, `/api/auth/logout`; `GET /api/auth/me`, `/api/orders`. Остальные `/api/*` требуют сессию. `GET /api/status` возвращает пользовательский CSRF-токен после входа. `storage.py` отвечает за SQLite и локальные аккаунты; `static/auth.js` — за формы и историю.
