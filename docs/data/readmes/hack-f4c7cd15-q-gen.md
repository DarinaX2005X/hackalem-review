## 🤖 AML Graph Copilot — Автономный ИИ-агент финансовой разведки

Архитектура ИИ-агента комплаенс-офицера с поддержкой OpenAI / NVIDIA NIM Tool-Calling:
- **Инструменты агента:**
  1. `get_node_info(gid)` — возвращает финансовый профиль узла: роль, входящие/исходящие суммы в ₸, число связей, удалённость от seed и числовое обоснование (`evidence`).
  2. `find_common_recipients(gids)` — находит общие узлы назначения для списка клиентов (выявление теневых казначеев и аккумуляторов средств).
  3. `get_cluster_summary(cluster_id)` — формирует аналитическую сводку по ячейке Louvain, внутренний оборот и проверяемую гипотезу.
- **Токен и конфигурация:**
  - Токен по умолчанию: `FGCSBZ39VF5NLAFF`.
  - Поддержка `OPENAI_API_KEY` и `OPENAI_BASE_URL` (например, `https://integrate.api.nvidia.com/v1` для NVIDIA NIM `meta/llama-3.1-70b-instruct`).
  - **100% SLA Отказоустойчивость:** гибридный движок со встроенным детерминированным локальным анализатором графа (мгновенный аналитический ответ без зависаний даже при отсутствии интернета на ноутбуке жюри).
- **Интерфейсы взаимодействия:**
  - **CLI / Python модуль:** `python agent.py`
  - **Streamlit:** 4-я вкладка `with st.tab("🤖 AI-Ассистент"): ...` (`streamlit run app.py` или `python app.py`)
  - **REST API:** `POST /api/copilot/ask`, `GET /api/copilot/tools`, `GET /api/copilot/examples`
  - **Интерактивный веб-интерфейс:** `http://127.0.0.1:8765/copilot` с чипами типовых вопросов и переходом из карточки клиента
- **Тесты:** `python finanse/test_agent.py` (9/9 успешно).

## Запуск в PowerShell

### SQLite-база, созданная на Python

Готовый файл: `database/bank.sqlite3`. Таблицы: `nodes` (2 248 клиентов),
`edges` (3 119 связей), `transactions` (4 840 операций).
Представления: `daily_turnover` — обороты по дням; `client_turnover` — обороты клиентов.
Примеры запросов сохранены в `database_queries.sql`.

Создание из Parquet: `python create_database.py`. Нужна библиотека DuckDB из
`requirements.txt` для импорта. Для работы с готовой SQLite достаточно стандартного Python:

```python
import sqlite3

with sqlite3.connect("file:database/bank.sqlite3?mode=ro", uri=True) as db:
    for row in db.execute("SELECT date, n_tx, sum_kzt FROM daily_turnover ORDER BY date"):
        print(row)
```

Деньги хранятся целыми тиынами в `amount_tiyn`; `sum_kzt` вычисляется для отображения.
При импорте суммы округляются до тиына и сверяются с агрегатами рёбер точно.
`transaction_id` — локальный номер строки: в исходных данных ID операции отсутствует.
Одинаковые операции сохраняются. Включены внешние ключи и индексы по клиентам и датам.
При записи из других программ нужно выполнить `PRAGMA foreign_keys=ON` для их соединения.
Существующую БД скрипт не перезаписывает: для нового импорта укажите другое имя через `--db`.
Это отдельная SQLite-база; существующие `analyze.py`, `db_analytics.py` и дашборд пока
используют прежнюю DuckDB. Сервер для открытия SQLite не нужен.

### Высокопроизводительный REST API на FastAPI для фронтенда

Для независимой и параллельной разработки современного фронтенда (React, Next.js, Vite, Vue, мобильные приложения) проект оснащен полноценным асинхронным REST API на **FastAPI**:

- **Автоматическая интерактивная документация OpenAPI / Swagger UI**: `http://127.0.0.1:8000/docs`
- **Интерактивная ReDoc документация**: `http://127.0.0.1:8000/redoc`
- **Поддержка CORS**: настроена для любых фронтенд-серверов разработки (`localhost:5173`, `localhost:3000` и др.)
- **Быстродействие**: in-memory индексация графа и транзакций обеспечивает время ответа эндпоинтов < 5-15 мс (заголовок `X-Process-Time-Ms`).
- **Спецификация моделей**: все ответы и запросы строго типизированы через Pydantic v2.

## Методика и ограничения

Роли назначаются последовательными, явными правилами в `classify`:
граница и изоляты → peripheral; 5+ входящих и 5+ исходящих контрагентов,
достижимость от ≥2 других seed за ≤4 шага и соседи из ≥2 внешних групп → coordinator;
5+ исходящих и минимум вдвое больше входящих → distributor;
у не-seed 3+ входящих и минимум вдвое больше исходящих, выход ≤50% входа → consolidator;
у не-seed отношение выхода ко входу 0,7–1,3 и временное сопоставление ≥50% входа → transit;
не-seed с входом, без выхода, не на границе → terminal; остальные → peripheral.
Порядок правил важен. Названия описывают структуру, не личность и не доказанную деятельность.
`role_score` — заданная сила правила, не обученная вероятность: изоляты 0,30, граница 0,20,
coordinator/consolidator 0,75, distributor 0,80, transit 0,65, terminal 0,55, остальные 0,40.
`role_stability` — доля совпадений роли при s=0,8/1/1,2. Пороги степеней и их отношения
умножаются на s; граница выхода consolidator = 0,5/s; диапазон transit = 1±0,3/s,
временная доля ≥0,5s. Числа seed и внешних групп фиксированы. Это проверка чувствительности,
не статистический доверительный интервал.

`priority_score` = 0,25 × L(вход+выход) + 0,20 × L(число связей)
+ 0,20 × L(число других seed с путём ≤4 шага до узла)
+ 0,15 × L(число внешних групп соседей) + 0,10 × fast_share + 0,10 × участие в цикле.
L(x)=log(1+x)/log(1+max(x)) по набору; при max=0 вклад 0.
Временной вклад отключён для seed и границы. Веса — открытые эвристики.
`priority_evidence` и `top_nodes.why` раскрывают каждый вклад. Это важность проверки,
не оценка мошенничества.
При изменении набора приоритеты пересчитываются и не сравнимы напрямую с прошлым запуском.

PageRank направленный и взвешенный по сумме. Louvain использует неориентированную
проекцию с суммированием встречных переводов; random seed=42.
Циклы определены через сильносвязные компоненты и петли; наличие цикла не доказывает
возврат именно тех же денег во времени. Временные признаки: число активных дней и
доля входящих/исходящих операций в самый активный день, без восстановления последовательности внутри дня.

У seed входящие неполны, поэтому роли на основе отношения входа/выхода для них отключены.
444 клиента на границе не объявляются конечными: peripheral с низкой силой правила и
объяснением неопределённости. У остальных terminal означает лишь отсутствие выхода
в этой выборке и периоде. Нулевой вход: pass_through=0 как техническое заполнение,
а pass_through_defined=false; интерфейс показывает «не определён».
CSV лучше импортировать с типом gid «текст», чтобы Excel не округлил длинные номера.

## Масштабирование

Это локальный прототип, а не распределённая Big Data-система. SQL-агрегации выполняются
в DuckDB с лимитом памяти 1 GB, но граф NetworkX и JSON интерфейса целиком находятся в памяти.
Для миллионов рёбер нужны отдельный сервер запросов с пагинацией и графовая обработка
по разделам/распределённым алгоритмом; Parquet можно разделять по дате, агрегации выполнять
в ClickHouse/Spark. Для текущих 4 840 транзакций этот уровень инфраструктуры не требуется.

Проверены суммы и количества транзакций по каждой паре, ссылки на клиентов, уникальность,
валидность значений, полнота выгрузки, точность gid, нормировка PageRank и обработка границы.
Полное ТЗ прочитано; обязательные схемы выгрузок проверяются автоматически.

## Дополнительные аналитические функции

**Сценарий 1–2 дня.** Входящие и исходящие суммы агрегируются по клиенту и дню.
Вход расходуется по FIFO только на выход следующего или второго дня. Вход текущего дня
добавляется после выхода: порядок внутри дня неизвестен. Каждая сумма сопоставляется
не более одного раза. Это возможное распределение сумм, не доказанная трассировка
тех же денег. Остатки и внешние операции неизвестны, последние два дня месяца обрезаны.
Результат: `out/temporal_matches.csv`; `fast_share` — доля всего наблюдаемого входа в сценарии.

**Гипотезы кластеров.** Доля крупнейшего отправителя ≥50% внутреннего оборота →
гипотеза распределения; иначе доля крупнейшего получателя ≥50% → сбора; иначе смешанная сеть.
Указаны обе доли и доля внутреннего оборота во всех связанных с группой переводах.
Назначение платежей неизвестно.

**Устойчивость сети.** Удаление топ-1/5/10 из неориентированной проекции сравнивается
с 30 случайными наборами того же размера, seed=42. Сохраняются изоляты.
Показаны медиана/диапазон крупнейшей компоненты, количество компонент и изолятов.
Случайное сравнение включает изоляты и не контролирует степень/оборот удаляемых клиентов.
Это изменение структуры наблюдаемого графа, не прогноз адаптации реальных участников.
Крупнейшая компонента: 1 877 → 1 782 / 1 631 / 1 448; случайные медианы 1 876 / 1 872 / 1 864.

**Карточки и защита.** Роль, вклад в приоритет, устойчивость порогов, временные окна,
направленные связи с цветом роли/группы и рекомендация следующего запроса данных.
`out/DEMO.md` содержит пятиминутный сценарий и 3 gid, выбранных алгоритмом.

Для миллиона узлов также потребуется обрабатывать временные события по разделам клиентов,
заменить обход от каждого seed пакетным распространением битовых множеств и загружать
соседей в интерфейс по запросу. Текущая версия хранит эти данные в памяти.
35 слабосвязных компонент с изолятами; 16 без 19 изолятов. Вне крупнейшей — 371 клиент,
из них 352 участвуют в рёбрах. Это уточняет разные способы подсчёта в ТЗ.

## Главный экран и поиск цепочек

`/` — обзор и навигация; `/analytics` — клиенты и граф; `/routes` — поиск между двумя gid.
Главный экран показывает показатели выборки и 12 крупнейших связей ведущего клиента.
Это фрагмент исходного графа, а не декоративная иллюстрация.

Поиск использует операции SQLite (`database/bank.sqlite3`) только для чтения.
`run.py` создаёт эту БД из Parquet, если её ещё нет; существующую не перезаписывает.
При замене исходных данных SQLite необходимо отдельно пересоздать из того же набора.
Алгоритм BFS перебирает состояния (клиент, дата прихода), сохраняет разные даты прихода
и возвращает одну кратчайшую по числу операций последовательность. Направление сохранено.
Каждая следующая дата строго позже предыдущей, пауза не больше выбранного порога;
все операции попадают в заданный период. Допустимы повторные клиенты в разные даты.
Лимит — 8 операций и 50 000 состояний. При достижении лимита интерфейс сообщает
о неполном поиске, а не об отсутствии цепочки. В памяти находятся операции выборки;
для больших объёмов нужна индексация и выборка соседей по клиенту и диапазону дат.

Суммы на шагах показываются отдельно, они не обязаны совпадать. Минимум сумм операций
не означает сумму, дошедшую по всей цепочке: атрибуция одних и тех же денег неизвестна.
Переводы одного дня исключены из последовательных шагов из-за отсутствия точного времени.
Кнопка примера выбирает из данных пару с хронологической цепочкой через посредника,
без прямого ребра между выбранными клиентами; gid не зашиты в коде.
Нажатие на участника цепочки открывает его карточку в аналитике.

Для демонстрации: главная → «Найти цепочку» → «Подставить пример из данных» → «Найти цепочку».
На текущей выборке показаны два перевода по 500 000 ₸ от 30 и 31 июля через транзитного клиента.
