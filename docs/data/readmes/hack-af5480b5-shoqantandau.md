# Заказы поставщикам — HACKALEM AI

**Объяснимое пополнение склада из выгрузок 1С для ТОО «Электрокомплект» (ekt.kz).** Продукт помогает менеджеру закупа определить, что заказать, в каком количестве и почему. На выходе — рекомендации по поставщикам, риск дефицита, возможность ручной правки, утверждение и Excel с заказом.

Ручное сведение таблиц замедляет закупки. При этом крупная разовая продажа завышает регулярную потребность, отсутствие товара скрывает спрос, а уже заказанная партия может приехать слишком поздно. Сервис учитывает эти ситуации в одном расчёте и показывает основания каждого решения.

**Основной путь:** Excel → проверка и объединение данных → прогноз → рекомендации → решение менеджера → экспорт. Числа вычисляет статистический алгоритм. Дополнительный AI-агент выбирает инструменты анализа, сравнивает сценарии и объясняет результаты. Автоматической отправки заказов поставщику нет.

> Для проверки используйте ветку **`main`**. Основной сценарий работает без API-ключей, доступа к 1С и внешней базы. В комплекте 12 реальных файлов партнёра и 6 синтетических файлов. Дата исходных данных — **22.09.2026**. Публичная версия не развёрнута; ниже дан самостоятельный локальный запуск.

### Windows — рекомендуемый путь

**Шаг 1. Получите код.** Если установлен Git:

```powershell
git clone --branch main https://github.com/BAITC-Hacks/hack-af5480b5-shoqantandau.git
cd hack-af5480b5-shoqantandau
```

Без Git: на странице репозитория выберите `main` → **Code → Download ZIP**, распакуйте архив и откройте PowerShell в папке, где лежат `manage.py` и `requirements.txt`. Не запускайте команды внутри ZIP или на уровень выше этой папки.

**Шаг 2. Проверьте Python и создайте отдельное окружение.**

```powershell
py -3.12 --version
py -3.12 -m venv .venv
```

Ожидается `Python 3.12.x`. Если команда `py` отсутствует, но `python --version` показывает **3.12.x**, вместо второй команды выполните `python -m venv .venv`. Если обе команды отсутствуют, завершите установку Python и заново откройте терминал.

**Шаг 3. Установите зависимости и создайте базу.** Выполняйте команды по порядку; при ошибке не переходите к следующей.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe manage.py migrate --noinput
.\.venv\Scripts\python.exe manage.py check
```

Ожидается `No broken requirements found`, у миграций — `OK`, у проверки Django — `System check identified no issues`. Миграции сами создают `db.sqlite3`, роли и демо-пользователей. `createsuperuser`, импорт базы и ручное заполнение таблиц не нужны.

**Шаг 4. Запустите приложение.**

```powershell
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Дождитесь `Starting development server at http://127.0.0.1:8000/` и откройте **[http://127.0.0.1:8000/](http://127.0.0.1:8000/)**. Терминал должен оставаться открытым. Остановка — `Ctrl+C`. Для следующего запуска достаточно последней команды из корня проекта; расчёты и решения сохраняются.

Активация окружения через `Activate.ps1` не требуется: все команды явно используют его Python. Это поддерживаемый [способ работы с venv](https://docs.python.org/3.12/library/venv.html#how-venvs-work). Установка пакетов выполняется в `.venv`, системный Python не изменяется.

В репозитории также есть `start.ps1`: `powershell -File .\start.ps1` создаёт окружение, устанавливает пакеты, выполняет миграции и запускает сервер. Если политика PowerShell запрещает сценарии, используйте ручные команды выше — менять системную политику для проверки проекта не нужно.

## 2. Первый заказ — маршрут проверки жюри

### Основной сценарий без API, около 5 минут

1. Войдите менеджером. На странице **«Заказы»** выберите **«Все поставщики»**, оставьте стандартные настройки и нажмите **«Рассчитать заказ»**. Первое чтение Excel может занять до полуминуты; дождитесь результата.
2. Откройте вкладку **IEK**, найдите код **`030201020_`**. Для неизменённых исходных файлов рекомендация — **107 шт.** Откройте **«Почему столько?»**: видны основания расчёта. Текст без ключа помечается как шаблонный; числа всё равно вычислены алгоритмом.
3. Измените поле **«Заказать»** со 107 на **108**, сохраните количество кнопкой **«Сохранить количества»**. Отметьте строку галочкой и нажмите **«Утвердить»**. У этого товара кратность равна 1; у других она может отличаться.
4. Нажмите **«Скачать заказ для 1С»**. В Excel должна появиться выбранная позиция с количеством **108** и обоснованием. Основная кнопка выгружает утверждённые положительные количества активного поставщика. Через соседнее меню доступен отдельный экспорт **«Все рекомендации (черновик)»**.
5. Измените утверждённое количество ещё раз и сохраните. Утверждение сбросится: изменённый заказ нужно подтвердить заново. Неутверждённая строка не попадёт в основной экспорт.
6. Откройте **«Как считается»**, выберите IEK и тот же код. Меняйте входы и наблюдайте пересчёт по таблице ниже. Эта страница проверяет сценарии и не меняет сохранённый заказ.
7. Откройте **«Точность»** для проверки прогноза на истории. Затем выйдите через меню пользователя и войдите наблюдателем: кнопки расчёта, правки и утверждения недоступны; сервер также проверяет права.

**Что подтверждает сценарий:** обработку входных файлов, расчёт, объяснение, участие человека, контроль прав и получение выходного артефакта. Числа ниже получены из данных; в коде нет подстановки готового ответа для этих артикулов.

## Методика

### Подготовка

Ключ объединения — строковый код 1С с сохранением ведущих нулей. Спрос берётся из месячного отчёта; накладные используются для поиска крупных покупок. Их суммы существенно расходятся с месячными отчётами — предупреждение видно в интерфейсе. Отрицательные месячные продажи обрезаются до нуля; модуль отрицательных строк накладных используется только для выявления аномалий. Смысл знаков требует подтверждения партнёра.

База — последние 12 полных месяцев; для роста используются 24 месяца. Незавершённый месяц и будущие значения не входят в сезонный профиль поставщика. Товарам без продаж за окно спрос автоматически не придумывается.

### Исключение выбросов

Строки одного товара группируются по накладной. При наличии обезличенного `client_id` накладные одного клиента за день объединяются. Выброс одновременно превышает:

- максимум из медианы + `5 × max(1, 1.4826 × MAD)` и трёх медиан;
- 1,5 медианы положительных месячных продаж;
- 40% объёма месяца в накладных.

Из месячного спроса вычитается превышение над обычной покупкой. Второй фильтр сглаживает месячные всплески без крупной накладной: после снятия сезонности порог равен максимуму из `медиана + 5 × 1.4826 × MAD` и четырёх медиан. Даты и величины корректировки сохраняются в объяснении.

### Сезонность, категории, рост

Профили поставщика и группы — отношение продаж к центрированной скользящей средней. Профиль товара — средние очищенные продажи по месяцам года при достаточной истории. Вес товара — 2, категории — 1, поставщика — 1; отсутствующие профили исключаются, итог нормируется к среднему 1.

У SE используется переданная «Категория 2026» (`SE-1`, `SE-2` и т.д.). Для остальных позиций группа выводится из первых четырёх цифр кода 1С. Коды категорий не интерпретируются как заданные уровни сервиса.

Рост — ограниченное отношение последних 12 месяцев к предыдущим 12 на уровне товара, группы и поставщика. Плановый процент заменяет исторический рост. Учитывается возраст базы и длина будущего горизонта. −100% даёт нулевой прогноз.

### Упущенный спрос

Без точных периодов stockout предполагается по неположительному остатку на начало текущего или следующего месяца. Ожидаемый спрос оценивается по месяцам с наличием с учётом сезона. При точных датах добавляется ожидаемый спрос за отсутствующие дни; пересечения периодов учитываются один раз.

Длительное отсутствие (6 месяцев подряд) и `!!!` требуют ручной проверки. Для `!!!` принято консервативное, **не подтверждённое партнёром допущение**: автоматическое предложение равно нулю, расчётная потребность видна в объяснении, менеджер может задать заказ вручную. Политика не зависит от переключателя stockout.

### Заказ и срочность

```text
H = срок поставки L + период между заказами R
F = сумма прогнозного дневного спроса за H дней
SS = z × max(1.4826 × MAD, sqrt(базовый спрос)) × sqrt(H / 30)
Потребность = max(0, F + SS − свободный остаток − поставки в горизонте)
Заказ = округление потребности вверх до кратности
```

Деление месячной базы на 30 — приближение. Страховой запас охватывает весь период защиты при периодическом заказе; `z=1.65` не доказывает достигнутый уровень сервиса 95%.

Каждая партия сохраняет дату. Партии вне горизонта и просроченные партии не уменьшают заказ. Неизвестная дата явно помечается и в сценарии заменяется сроком поставки. Риск дефицита проверяется по дням с поступлениями в их даты. Позиция может быть срочной при нулевом заказе: товар уже в пути, но придёт после исчерпания остатка. В таком случае нужны ускорение или перемещение.

Для первого запуска загружать ничего не нужно. В дальнейшем администратор может заменить файл через «Данные из 1С». Используйте структуру соответствующего файла из `data/demo/`: парсеры настроены на эти выгрузки 1С, произвольный Excel с другими заголовками не является поддерживаемым форматом. Некорректная загрузка откатывается. Загрузки приоритетнее демо-файлов и лежат в `data/uploads/`.

Дополнительно поддерживаются:

- `stock_current.xlsx`: **Код 1с, Свободный остаток, Дата**. Уникальные коды, неотрицательные количества, дата совпадает с датой расчёта. Точные остатки заменяют оценку совпавших позиций.
- `stockouts.xlsx`: **Код 1с, Начало, Конец**. Даты включительны. Для перечисленных товаров периоды приоритетнее месячной оценки; за их пределами известный stockout равен нулю. Для остальных сохраняется оценка.
- Столбец `client_id` в накладных: только обезличенный ID, без персональных данных.

В исходных файлах нет ID клиентов и точных периодов stockout. Накладная не выдаётся за идентификатор клиента. Покупки одного клиента в разные дни остаются отдельными наблюдениями.

## Проверка прогноза на истории

Каждый месяц марта–августа 2026 прогнозируется по предшествующей истории. Товары без прогноза учитываются с нулевым предсказанием. База сравнения — среднее за предыдущие 12 месяцев, **не воспроизведение реального процесса Excel компании**.

Результаты на исходных файлах после учёта переданных категорий SE:

| Поставщик и единица | WAPE сервиса | WAPE среднего | Смещение сервиса |
|---|---:|---:|---:|
| IEK, штуки | 36,0% | 36,6% | +0,6% |
| IEK, метры | 59,0% | 63,0% | +8,6% |
| IEK, упаковки | 49,8% | 56,8% | +14,5% |
| SE, штуки | 27,8% | 28,4% | −16,1% |

`WAPE = Σ|прогноз − факт| / Σфакт`; при нулевом факте метрика не определена. Разные единицы не смешиваются. У SE сохраняется систематическое занижение; страховой запас не гарантирует его исправление.

Продажи ограничены наличием, включают разовые сделки; исторического справочника товаров нет. Бэктест оценивает наблюдаемые продажи, а не скрытый спрос, излишки или фактическую экономию. Разница сумм двух рекомендаций — расчётная оценка. Шесть месяцев не гарантируют будущую точность.

## 4. AI-агент — необязательное подключение

**Для расчёта, утверждения, экспорта и всех 63 тестов ключ не нужен.** Для живого диалога на странице `/agent/` нужен собственный ключ OpenAI API с доступом к `gpt-5-mini`, доступ к `api.openai.com` и средства/кредиты в API-проекте. Подписка ChatGPT сама по себе не подключает API к приложению.

Агент понимает вопрос, выбирает разрешённые инструменты и получает результат Python-алгоритма. Реализованы поиск товара, обзор дефицита и избытка, подробный расчёт, изменение условий и сравнение сезонов. Под ответом — ссылки на карточки, дата данных, оценка расхода, вызванные инструменты; для сценария отдельно показаны числа алгоритма.

### Подключение без ключа в истории команд

Из корня проекта в PowerShell запустите команду и вставьте ключ в скрытый запрос:

```powershell
.\.venv\Scripts\python.exe -c "from getpass import getpass; from pathlib import Path; key = getpass('OpenAI API key: ').strip(); assert key, 'Empty key'; Path('.openai-key').write_text(key, encoding='utf-8'); print('Key saved locally')"
```

На Linux/macOS используйте тот же аргумент `-c`, заменив путь к Python на `.venv/bin/python`. Файл `.openai-key` уже исключён из Git. Он читается при запросе: после сохранения обновите страницу агента, должна появиться отметка **«Ключ подключён»**. Эта отметка подтверждает наличие ключа; доступ к API проверяется первым вопросом.

Другой вариант — переменная окружения `OPENAI_API_KEY` в процессе сервера. При изменении окружения перезапустите сервер. Приоритет: переменная окружения → `OPENAI_API_KEY` в `local_constants.py` → `.openai-key`. Не публикуйте ключи, не вставляйте их в README и не пересылайте в чат. В клоне и ZIP ключей нет.

### Проверка агента

Войдите менеджером, откройте **«AI-агент»**, выберите **ТехноСезон**:

1. «Проверь риски дефицита. Где нужна закупка, а где достаточно ускорить уже заказанный товар?»
2. «Для товара 3301002_ сравни срок поставки 30 дней вместо 20». Ожидаются **192 → 228**, разница **+36**.
3. «А если на складе будет 100 штук при том же сроке 30 дней?» Ожидаются **132**, разница с предыдущим сценарием **−96**, со стандартным — **−60**.
4. «Сравни вентилятор 1101001_ и конвектор 2201001_ в январе и июле».

Кнопки примеров заполняют вопрос; отправка — **«Спросить агента»**. Ответ обычно занимает 10–40 секунд, при проблемах сети возможен более долгий ответ или сообщение об ошибке. Формулировки могут меняться; числа проверяйте по карточке алгоритма. **«Новый диалог»** и смена поставщика очищают контекст, последние 6 сообщений сохраняются в серверной сессии.

### Границы полномочий и расходов

- Агент не меняет остатки, не создаёт, не утверждает и не отправляет заказы. Он рассчитывает текущие файлы со стандартными настройками; ручные правки сохранённого заказа не учитываются.
- В OpenAI идут вопрос, короткий контекст и агрегаты выбранных товаров. Исходные Excel, клиентские ID и локальный ключ в ответ не передаются. Коммерческую передачу реальных агрегатов следует согласовать с владельцем данных; для демонстрации есть синтетический поставщик.
- Используется Responses API и фиксированный набор проверяемых функций. Произвольный код, SQL и внешние действия модели недоступны. `store=false` не следует трактовать как гарантию нулевого хранения провайдером.
- Локальный бюджет агента **$5** хранится в SQLite; перед вопросом резервируется **$0.10**. Максимум 4 обращения к модели и 6 исполняемых инструментов на вопрос. При неизвестном результате сетевого запроса резерв остаётся учтённым.
- Расход — оценка по токенам, без скидки за кэш. Это **не баланс аккаунта OpenAI** и не ограничение расходов других приложений. Отдельная старая кнопка AI-объяснения строки не входит в этот бюджет.
- При отсутствии ключа или ошибке API чат сообщает об этом. Шаблонный ответ не выдаётся за ответ агента. Обычный расчёт продолжает работать.

Подробности реализации и параметров — [docs/AGENT.md](docs/AGENT.md), `procurement/agent_config.py`.

## 7. Архитектура и техническая реализация

```text
18 XLSX / загрузки администратора
    → loaders.py: проверка, нормализация, объединение по коду 1С
    → engine.py: очистка спроса → сезон/рост → потребность → даты поставок/MOQ
    → services.py: атомарное сохранение расчёта в SQLite
    → Django: таблица → ручная правка → утверждение → XLSX

Вопрос менеджера → OpenAI → разрешённый инструмент → тот же engine.py
                         ← числа и источники       ←
                    → объяснение и проверяемый сценарий
```

| Компонент | Ответственность |
|---|---|
| `constants.py`, `supply/settings.py` | Настройки данных и приложения |
| `procurement/loaders.py` | Парсеры выгрузок, текущие остатки, категории, кэш |
| `procurement/engine.py` | Детерминированный прогноз и расчёт заказа |
| `procurement/services.py`, `models.py` | Запуск, строки заказа, решения и авторы |
| `procurement/forms.py`, `views.py` | Валидация, права, сценарии, загрузка, экспорт |
| `procurement/backtest.py` | Последовательная проверка на истории |
| `procurement/agent*.py` | Инструменты, ограниченный цикл OpenAI, бюджет, HTTP-интерфейс |
| `procurement/templates/`, `static/` | Django HTML, Bootstrap, JavaScript, SVG-графики |
| `procurement/migrations/` | Воспроизводимая схема и демо-роли |
| `procurement/tests.py`, `test_regressions.py`, `test_synthetic.py`, `test_agent.py` | Автоматические проверки |
| `docs/` | Сценарий защиты, синтетические данные и инструкция агента |

Стек: **Django 5.2.17, pandas 3.0.1, NumPy 2.3.5, openpyxl 3.1.5, python-calamine 0.8.2, SQLite**, Bootstrap и Bootstrap Icons. Полный список с точными версиями — `requirements.txt`. Сборки frontend нет. Bootstrap и иконки локальные; веб-шрифт Google Fonts необязателен, при отсутствии сети используется запасной шрифт. При разработке использовались AI-помощники; функциональность проверяется кодом, входами и тестами.

### Надёжность и безопасность

- Все рабочие страницы требуют входа; операции расчёта, правки, утверждения, экспорта и загрузки проверяют права на сервере. Изменения через POST защищены CSRF.
- Ввод проверяется сервером: сроки и период 1–365 дней, годовой прирост −100…300%, конечные неотрицательные остатки и поставки, кратность заказанного количества.
- Сохранение расчёта атомарно. Ошибка не оставляет частичного заказа. Некорректная загрузка откатывается.
- Правка утверждённой строки сбрасывает её утверждение и старое AI-объяснение. В основной экспорт входят утверждённые положительные количества; черновик выгружается явно отдельно.
- Строки из Excel записываются в экспорт как текст, без исполнения формул. Ответы агента выводятся как текст, без выполнения HTML.
- Агент ограничен выбранным поставщиком и разрешёнными функциями, не имеет инструментов отправки заказа. Ключ остаётся на сервере; ошибки API не показывают сырые ответы провайдера.
- Сохраняются автор и время последнего решения. Полного неизменяемого журнала всех предыдущих решений пока нет.

Локальная конфигурация содержит известные демо-пароли, демонстрационный `SECRET_KEY`, включённые `DEBUG` и демо-вход. **Не публикуйте её как есть в интернете.** Для публичной эксплуатации потребуются замена секретов и паролей, отключение демо-входа/DEBUG, HTTPS, рабочий сервер, конфигурация статики, резервирование, общий ограничитель запросов и проверка доступа к данным. Это отдельный этап; см. [официальный checklist Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).

| Симптом | Что проверить / сделать |

| `no such table`, сообщение о неприменённых миграциях | Из корня проекта выполнить команду `manage.py migrate --noinput` через Python `.venv` |
| Порт 8000 занят | Запустить `manage.py runserver 127.0.0.1:8001` и открыть `http://127.0.0.1:8001/` |
| Страница не открывается | Проверить вывод терминала; сервер должен работать. Открывать `http`, не `https`. Использовать `127.0.0.1`, не адрес другой машины |
| `DisallowedHost` | Для локальной проверки использовать `127.0.0.1` или `localhost`; они разрешены в конфигурации |
| Нет файлов / ошибка Excel | Проверить 18 `.xlsx` в трёх папках `data/demo`. Убедиться, что загруженная замена соответствует структуре исходной выгрузки |
| Числа отличаются от README | Проверить поставщика, стандартные настройки, `data/uploads`, локальные переопределения и ручные правки. Для эталона использовать свежую копию |
| Не виден товар с заказом 0 | Включить фильтр **«Весь список»** |
| Скачать заказ не удаётся | Отметить строку, нажать **«Утвердить»**, убедиться, что количество положительное и после этого не было правки; либо выбрать экспорт черновика |
| «Ключ подключён», но AI не отвечает | Проверить права/кредиты API-проекта, доступ к модели и сеть. Наличие ключа не доказывает его действительность. Ошибки 401/403/429 поясняются в интерфейсе |
| Ключ положен в `.env`, агент его не видит | `.env` не загружается. Использовать `.openai-key`, окружение процесса или `local_constants.py` |
| Локальный лимит агента исчерпан | Обычные расчёты доступны. Не путать этот лимит с балансом OpenAI; бюджет настраивается отдельно в `agent_config.py` |

Если ошибка остаётся, сохраните текст ошибки без секретов, версию Python, ОС и точную команду. Эти сведения позволят воспроизвести сбой; не пересылайте `.openai-key` или содержимое локальных настроек с ключами.

## 9. Известные ограничения

- Остаток IEK оценён без поступлений текущего месяца. Для коммерческого заказа нужна точная ведомость; её загрузка поддерживается. У позиций SE, отсутствующих в сводке, также используется оценка.
- В реальных исходниках нет клиентских ID и точных периодов отсутствия. Накладная не подменяет клиента. Группировка по обезличенному клиенту за день проверяется на синтетических данных; покупки в разные дни остаются отдельными.
- Один склад Алматы; межскладская оптимизация отсутствует. Метры автоматически не переводятся в бухты. MOQ трактуется как кратность — это требуется согласовать с поставщиком.
- Значение категорий и пометки `!!!`, возвраты и знаки количеств требуют уточнения у партнёра. Срок SE 40 дней — настройка; срок IEK из открытых заказов может быть нерепрезентативен.
- Новые товары без истории не прогнозируются автоматически. Месячные остатки не дают точных внутримесячных периодов отсутствия. Денежная сезонность зависит также от цен и ассортимента.
- Бэктест измеряет ошибку наблюдаемых продаж; фактическое сокращение дефицита и затрат пока не измерено. Синтетические примеры показывают поведение алгоритма, а не бизнес-эффект.
- Excel содержит код 1С, артикул, количество, единицу, кратность, срочность и обоснование. **Импорт в конкретную конфигурацию 1С не проверен**, API-интеграции и отправки поставщику нет, несмотря на краткое название кнопки экспорта.
- AI может ошибаться в формулировках; числовые результаты доступны отдельно. Для нескольких процессов нужен общий ограничитель одновременных запросов; текущий предназначен для локальной демонстрации.

## 10. Ценность и развитие после хакатона

Продукт объединяет подготовку заказа и его проверку в одном рабочем процессе. Отличие от простого среднего — совместный учёт разовых покупок, скрытого спроса при отсутствии, сезонности, роста, дат партий и кратности. Особенно показателен нулевой заказ с высоким риском: закупать ещё не требуется, но уже заказанное нужно ускорить. Агент позволяет исследовать эти причины обычным языком, используя тот же расчётный код.

Польза, которую предстоит измерить в пилоте: время подготовки заказа, доля дефицита, дни запаса, избыточный запас и упущенные продажи. Денежная экономия сейчас не заявляется как достигнутая.

| Этап | Что нужно сделать | Критерий успеха |
|---|---|---|
| Подготовка пилота | Согласовать справочники, категории, MOQ, единицы, сроки; получить ежедневные остатки и поступления | Проверенная полнота источников и согласованные правила расчёта |
| Пилот с закупщиком | Сравнивать рекомендации и фактические решения на сопоставимых группах | Изменение времени работы, дефицита и дней запаса без ухудшения доступности |
| Интеграция | Проверить формат с конкретной 1С, автоматизировать обмен и резервирование | Повторяемый импорт/экспорт и отслеживаемые решения |
| Масштабирование | Несколько складов, дополнительные адаптеры поставщиков, PostgreSQL/фоновые задания при росте нагрузки | Измеренные время расчёта, устойчивость и изоляция доступа |

Новый поставщик сейчас подключается через адаптер данных и `SUPPLIERS`; универсального мастера добавления организаций нет. Следующий этап — подтвердить качество источников и эффект на ограниченном пилоте, затем расширять автоматизацию.
