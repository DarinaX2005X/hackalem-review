# EventMatch KZ

MVP для хакатона Hack Alem AI: сервис подбирает event-подрядчиков в Казахстане.
Организатор указывает город, дату, тип мероприятия, категорию подрядчика и
бюджет (по желанию ещё длительность и язык). Сервис возвращает до трёх
подходящих подрядчиков из датасета на 66 профилей. У каждого есть объяснение
«почему этот», построенное на конкретных совпадениях по бюджету, формату и
описанию, а не на общих фразах. Если никто не подходит, сервис объясняет почему.

```text
Браузер ──► Next.js (frontend/, :3000) ──/api/*──► FastAPI (backend/, :8000) ──► OpenAI
                                                    └─ датасет в памяти: backend/data/hackathon-dataset.csv
```

## Как устроен подбор

Код пайплайна: [backend/main.py](backend/main.py), эндпоинт `POST /api/recommend`.

1. **Жёсткий фильтр, этап 1: город + категория.** Остаются профили, у которых
   город совпадает с запрошенным, а в списке категорий есть запрошенная
   (сравнение без учёта регистра). Если таких нет, ответ `no_category`.
   Число прошедших профилей возвращается в `total_candidates`, это размер
   пула **до** остальных фильтров.
2. **Жёсткий фильтр, этап 2: доступность.** Из пула отсеиваются подрядчики,
   у которых формат мероприятия не в `event_formats`, `price_from_kzt` выше
   бюджета или дата мероприятия входит в `busy_dates`. Если указаны язык и
   длительность, отсеиваются также те, кто не говорит на этом языке или у кого
   `max_hours` меньше нужного. Если не остался никто, ответ `no_match`, а в
   `message` перечислены причины со счётчиками, например «не подходит формат
   мероприятия — 2». Если отсеян хотя бы один профиль, причины дописываются в
   `message` и при `ok`, сколько бы карточек ни вернулось. Счётчики считаются
   по причинам, а не по людям: профиль, не прошедший два фильтра, учитывается
   в обоих, поэтому сумма может быть больше числа отсеянных. К причине
   «заняты на выбранную дату» добавляется ближайшая дата после выбранной (до
   2026-12-31), в которую свободен хотя бы один из занятых. Остальные фильтры
   для этой даты не проверяются, поэтому в тексте прямо сказано: «не
   гарантирует совпадение по остальным критериям».
3. **Детерминированный скор без цены.** При старте backend одним пакетным
   запросом получает embeddings (`text-embedding-3-small`) для описаний всех
   профилей и для всех пар «категория + формат» из датасета. Скор равен
   косинусной близости описания к паре «категория + формат» из запроса,
   приведённой к шкале 0…1, плюс 0.10, если язык указан и совпадает. **Цена в
   скоре не участвует:** она уже проверена фильтром. Сортировка идёт по
   убыванию скора, при равенстве по `id`. Берутся первые три.
4. **Сортировка тройки по цене.** Выбранные три карточки выводятся по
   возрастанию `price_from_kzt`, при равной цене по `id`.
5. **LLM только переписывает готовые факты.** Для каждой карточки backend сам
   считает факты: цену, бюджет, запас бюджета в %, совпадение формата и языка,
   длительность и фрагмент описания. Фрагмент получается так: описание
   разбивается на предложения. Если язык в запросе не указан, из него убираются
   предложения, где упоминаются языки («язык…», «двуязыч…» или языки
   подрядчика). Оставшееся склеивается и обрезается до 850 символов. Эти факты
   уходят в `gpt-4o-mini` с `temperature=0` и инструкцией использовать только
   их. Backend заранее составляет первую фразу, например
   `Формат «свадьба» совпадает; цена от 650000 ₸ укладывается в бюджет 1000000 ₸.`,
   и модель должна скопировать её дословно. Если в запросе указаны язык или
   длительность, первая фраза подтверждает и их в виде
   `…; язык «<язык>» совпадает; запрошенные N ч укладываются в лимит M ч.`
   (при пустом `max_hours`: «ограничение по часам в профиле не указано»).
   Второе предложение модель
   добавляет, только если в описании есть конкретная деталь. Ответ
   запрашивается в виде JSON с ключом `explanation`. Ответ проверяется:
   - он должен начинаться ровно с этой первой фразы;
   - если язык в запросе не указан, в нём не должно быть упоминаний языка.

   Если проверка не пройдена, JSON не разобрался или вызов упал (таймаут 5.5 с,
   без повторов), берётся шаблонное объяснение `factual_fallback`: это та же
   первая фраза без второго предложения. Три карточки объясняются параллельно.
6. **Кэш.** Объяснения хранятся в памяти процесса по ключу
   `(id подрядчика, sha256 от JSON запроса с отсортированными ключами)`.
   Одинаковый запрос сразу получает те же тексты, а параллельные одинаковые
   запросы вызывают LLM один раз. В кэш попадают только ответы LLM, прошедшие
   проверку. Шаблон `factual_fallback` не кэшируется, поэтому после разового
   сбоя повтор того же запроса снова обращается к модели. Кэш сбрасывается при
   перезапуске backend.

Без `OPENAI_API_KEY` backend тоже работает: фильтры действуют как обычно,
семантический скор равен 0 (порядок решают бонус за язык и `id`), а
`explanation` содержит `заглушка`.

## Запуск

Нужны Python 3.10+ (проверено на 3.14) и Node.js 20.9+ (проверено на 24).
Команды для PowerShell. Backend и frontend запускаются в разных терминалах из
корня репозитория.

### Backend (FastAPI, порт 8000)

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env      # затем впишите ключ: OPENAI_API_KEY=sk-...
.\.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000
```

- Датасет `backend/data/hackathon-dataset.csv` уже лежит в репозитории и
  читается один раз при старте.
- `.env` читается только при старте. После смены ключа backend нужно
  перезапустить.
- Swagger: http://127.0.0.1:8000/docs
- На macOS/Linux вместо `.\.venv\Scripts\python.exe` используйте `.venv/bin/python`.

### Frontend (Next.js, порт 3000)

```powershell
cd frontend
npm install
npm run dev
```

Откройте http://localhost:3000. Next.js проксирует `/api/*` на backend, так
что проблем с CORS нет. Адрес backend задаётся в `frontend/.env.local`
(образец: [frontend/.env.example](frontend/.env.example)):

```dotenv
# адрес backend (это значение по умолчанию)
BACKEND_URL=http://localhost:8000
# true: мок-данные без backend и переключатель ответов в шапке
NEXT_PUBLIC_USE_MOCKS=false
```

### 3. Без результата: объяснение, почему никто не подошёл

В Астане 2 видеографа, но оба не работают с юбилеями. Статус `no_match`,
`total_candidates = 2`, `message`: «В городе Астана есть 2 подрядчиков
категории Видеограф, но никто не прошёл фильтры: не подходит формат
мероприятия — 2».

**Что показывает:** пустой результат не выглядит как ошибка или пустой экран.
Жёлтая панель «Никто не подошёл» называет конкретную причину. Она визуально
отличается от голубой панели `no_category`, которую можно увидеть так: Астана,
Ресторан. Ответ: «В городе Астана нет подрядчиков категории Ресторан»,
`total_candidates = 0`.

### Как проверить, что объяснения пишет LLM

Если вызов модели не удался, backend подставляет шаблон: только первую фразу,
например `Формат «свадьба» совпадает; цена от 650000 ₸ укладывается в бюджет 1000000 ₸.`
Без ключа приходит `заглушка`. В прогоне выше у всех 7 карточек есть второе
предложение с деталью из описания, которого нет ни в шаблоне, ни в заглушке:
это ответы `gpt-4o-mini`. Обратное не работает: если в описании нет конкретной
детали, модель тоже возвращает одну первую фразу, и по тексту такой ответ от
шаблона не отличить.

## Ограничения

- Повторяемость текста внутри одного запуска гарантирует кэш. Между
  перезапусками её обеспечивает `temperature=0`, но побайтовое совпадение
  ответа модели не гарантировано. Порядок карточек от LLM не зависит.
- Embeddings считаются при старте. Если OpenAI недоступен в этот момент,
  семантический скор до перезапуска равен 0.
- Датасет читается при старте. Базы данных, бронирования и обновления профилей
  на лету нет.
- Категория выбирается из 17 значений датасета: backend требует точного
  совпадения названия.
