# Stockwise — помощник закупщика для пополнения склада

Stockwise помогает менеджеру закупок перейти от редкого ручного расчёта в Excel к воспроизводимым рекомендациям по заказам поставщикам. Сервис анализирует продажи и доступные запасы, отделяет разовые крупные сделки от регулярного спроса, учитывает периоды отсутствия товара и показывает, почему предлагает заказать именно такое количество. Цель — уменьшить одновременно дефицит и избыточные остатки.

> Статус MVP: backend и Next.js-интерфейс связаны через API и JWT-сессию. Импорт, расчёт, принятие рекомендаций, заказ и XLSX-экспорт доступны в рабочем сценарии. При этом первая таблица на главной странице показывает отдельный встроенный набор `/api/v1/procurement/recommendations`, а результаты нового расчёта — в секции ниже. Ограничения интерфейса перечислены в конце README.

## Для кого и что реализовано

Основной пользователь — закупщик. Он загружает данные, запускает расчёт, изучает объяснения, при необходимости меняет количество и принимает рекомендации. Из принятых строк формируются черновики заказов по поставщику и складу. Администратор просматривает и утверждает заказ; закупщик после этого скачивает XLSX для учётной системы. Заказ **не отправляется поставщику автоматически**.

Backend поддерживает:

- импорт `.xlsx` с валидацией, защитой от повторной загрузки и запретом явных персональных данных клиентов;
- два режима истории спроса: транзакции и помесячные продажи;
- обработку возвратов, разовых крупных продаж, stockout, устойчивого роста и сезонности;
- учёт текущего остатка, товара в пути, материальной потребности, срока поставки, страхового запаса, MOQ и кратности упаковки;
- сохранение прогнозов, аномалий, компонентов формулы, уровня риска дефицита и помесячных трендов;
- фильтрацию и пагинацию рекомендаций, ручную корректировку с причиной и контролем версии, явное принятие;
- создание черновиков, утверждение только администратором и экспорт утверждённого заказа в XLSX с checksum;
- локальные аккаунты сотрудников, Argon2-хеширование паролей и короткоживущие JWT. Публичной регистрации нет.

Дополнительные AI-подсказки для интерфейса используют OpenAI `gpt-4o-mini`, если задан ключ; без него доступен детерминированный fallback. Расчёт рекомендуемого количества не зависит от LLM.

## Как работает расчёт

```text
Excel → проверка и импорт → очистка истории спроса → прогноз
      → учёт запасов и условий поставщика → рекомендация с объяснением
      → корректировка и принятие закупщиком → черновик
      → утверждение администратором → XLSX для ручного импорта в 1С
```

Для каждого артикула и склада сервис строит регулярный спрос по истории. Разовые крупные продажи помечаются как аномалии и не раздувают базовую потребность; возвраты учитываются отдельно. При stockout фактические нулевые продажи не считаются нулевым спросом. Прогноз учитывает рост и коэффициенты сезонности. Затем из потребности на горизонт планирования со страховым запасом вычитаются доступный остаток и ожидаемые поступления, добавляется материальная потребность; положительный результат округляется по MOQ и кратности поставщика. Результат сопровождается формулой и сохранёнными исходными компонентами. Подробные параметры и HTTP-контракт — в [docs/http_api.md](docs/http_api.md).

## Технологии и архитектура

| Компонент | Технологии и назначение |
|---|---|
| Frontend | Next.js 15, React 19, TypeScript, Tailwind CSS, TanStack Query, Zustand, Zod; BFF с HttpOnly JWT-cookie |
| API и аналитика | Python, FastAPI, Pydantic, Pandas, NumPy/SciPy, Openpyxl |
| Данные | PostgreSQL 16, SQLAlchemy 2, Alembic; SQLite — только в части автоматических тестов |
| Авторизация | JWT (`PyJWT`), Argon2; роли `buyer` и `admin` |
| AI-подсказки | Опциональный OpenAI API (`gpt-4o-mini`) и fallback без ключа |

Backend организован в три слоя DDD: `backend/domain` содержит сущности и правила расчёта, `backend/application` — сценарии и порты репозиториев, `backend/infrastructure` — FastAPI, PostgreSQL-адаптеры, Excel и внешние сервисы. `frontend/` — отдельное Next.js-приложение. Миграции запускаются явно: API не создаёт таблицы при старте.

## Установка и запуск локально

Ниже команды для PowerShell на Windows. Нужны Python 3.11+, Node.js 20+ с npm и Docker с Compose. Команды выполняются из корня репозитория; для macOS/Linux замените путь к `.venv/Scripts/python.exe` на `.venv/bin/python`.

1. Подготовьте окружение. Скопируйте `.env.example` в `.env`, задайте локальный адрес базы и **замените** пример `JWT_SECRET` случайным секретом. Примерный секрет из шаблона намеренно не принимается. `.env` не коммитьте.

   ```powershell
   Copy-Item .env.example .env
   python -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

   В `.env` укажите, например:

   ```dotenv
   DATABASE_URL=postgresql+psycopg://postgres:postgres@localhost:5432/procurement
   JWT_SECRET=<сгенерированный_случайный_секрет>
   ```

   `OPENAI_API_KEY` необязателен. URL с `localhost` предназначен для backend, запускаемого на компьютере, а не внутри контейнера.

2. Запустите PostgreSQL и установите зависимости backend:

   ```powershell
   docker compose up -d db
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
   .\.venv\Scripts\python.exe -m alembic upgrade head
   ```

3. Создайте первого администратора и запустите API. Команда создания попросит пароль без отображения; повторно пользователя с тем же именем не создавайте.

   ```powershell
   .\.venv\Scripts\python.exe -m backend.infrastructure.bootstrap_admin --username admin@example.com
   .\.venv\Scripts\python.exe -m uvicorn backend.infrastructure.api.main:app --reload
   ```

   API: `http://localhost:8000`; проверка готовности: `/health` и `/health/db`; схема API: `/openapi.json`, Swagger UI: `/docs`. Для доступа к рабочим маршрутам нужен заголовок `Authorization: Bearer <access_token>`. Вход — `POST /api/auth/login`; администратор создаёт закупщика через `POST /api/auth/users`. Подробности — в [docs/authentication.md](docs/authentication.md).

4. Создайте аккаунт закупщика через `POST /api/auth/users` с токеном администратора. Публичной регистрации и отдельного экрана создания сотрудников нет. Например, выполните в новом PowerShell-терминале (подставьте пароли, заданные вами):

   ```powershell
   $login = @{ username = 'admin@example.com'; password = '<пароль_админа>' } | ConvertTo-Json
   $admin = Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/auth/login -ContentType 'application/json' -Body $login
   $buyer = @{ username = 'buyer@example.com'; display_name = 'Закупщик'; password = '<пароль_от_12_символов>' } | ConvertTo-Json
   Invoke-RestMethod -Method Post -Uri http://localhost:8000/api/auth/users -ContentType 'application/json' -Headers @{ Authorization = "Bearer $($admin.access_token)" } -Body $buyer
   ```

5. В другом терминале запустите интерфейс:

   ```powershell
   Copy-Item frontend/.env.example frontend/.env.local
   cd frontend
   npm ci
   npm run dev
   ```

   Откройте `http://localhost:3000` и войдите как закупщик. Next.js обращается к FastAPI через собственный `/api`-прокси и хранит JWT в HttpOnly cookie. `SERVER_API_URL` из `frontend/.env.local` должен указывать на FastAPI, доступный процессу Next.js.

## Как проверить решение жюри

1. Откройте `http://localhost:3000` под закупщиком. Загрузите `.xlsx` с продажами и условиями поставщика, нажмите «Пересчитать потребность», откройте секцию «Результат расчёта», скорректируйте количество с причиной и примите рекомендацию. Сформируйте заказ и сохраните его UUID. Выйдите, войдите администратором, откройте `/orders`, найдите заказ по UUID и утвердите. Снова войдите закупщиком и скачайте XLSX с экрана заказа. Первая таблица «Рекомендации закупок» на главной странице — встроенный серверный набор; именно секция «Результат расчёта» отражает загруженные файлы.
2. Отдельно запустите настоящий сквозной тест backend из корня проекта:

   ```powershell
   .\.venv\Scripts\python.exe -m unittest discover -s tests -p test_api_end_to_end_smoke.py -v
   .\.venv\Scripts\python.exe -m unittest discover -s tests -p test_auth_api.py -v
   ```

   Первый тест сам создаёт небольшие Excel-файлы, импортирует продажи и условия поставщика, запускает расчёт, проверяет прогноз и объяснение, меняет и принимает рекомендацию, создаёт заказ, проверяет запрет утверждения закупщиком, утверждает его администратором и скачивает XLSX. Он работает во временной SQLite-базе и подставляет тестовые роли; второй отдельно проверяет реальный JWT-вход, права и отклонение недействительных токенов. Для полного набора тестов: `.\.venv\Scripts\python.exe -m unittest discover -s tests -v`.
3. Для ручной проверки на PostgreSQL после локального запуска войдите через `POST /api/auth/login`, создайте закупщика, загрузите `.xlsx` через `POST /api/imports`, запустите `POST /api/calculation-runs`, получите рекомендации по `GET /api/calculation-runs/{id}/recommendations`, откройте объяснение, примите рекомендацию и создайте заказ через `POST /api/orders`. Администратор утверждает его через `POST /api/orders/{id}/approve`, после чего закупщик создаёт и скачивает экспорт через `POST`/`GET /api/orders/{id}/export`. Для начала достаточно столбцов `Дата`, `Артикул`, `Склад`, `Количество` в истории продаж и `Артикул`, `Поставщик`, `MOQ` в условиях поставщика. Файл должен содержать обезличенные сведения о клиентах.

## Данные и интеграции

API принимает `.xlsx` для продаж, помесячных продаж, остатков, периодов stockout, товаров в пути, сезонности, условий поставщиков, прогноза роста и материальной потребности. Полный список типов импорта: `sales`, `monthly_sales`, `inventory`, `stockout`, `in_transit`, `seasonality`, `supplier_terms`, `growth`, `material_requirements`. Исходные файлы партнёра не включены в репозиторий; для разработки и тестов используются синтетические данные. Клиентские идентификаторы должны быть заранее обезличены; явные персональные колонки импорт отклоняет.

XLSX для 1С — **проектный шаблон**, а не универсальный формат обмена. На стороне конкретной 1С нужно настроить сопоставление справочников; контрольный пример и поля находятся в [docs/excel-order-export.md](docs/excel-order-export.md). Отправки поставщику или записи в 1С по API нет.

## Ограничения текущей версии

- Первая таблица главной страницы использует отдельный встроенный набор `/api/v1/procurement/recommendations`, не связанный с загруженными файлами. В таблице результатов расчёта backend пока возвращает UUID товара и поставщика без названий и цен. Списка всех заказов и выбора произвольного подмножества рекомендаций для заказа нет: заказ ищут по UUID, а создание берёт все принятые рекомендации запуска.
- Алгоритм опирается на качество и полноту загруженных данных. Периоды без продаж и без подтверждённого stockout нельзя трактовать как доказанный нулевой спрос; прогноз не является гарантией продаж.
- Проверка формата анонимного ID не доказывает обезличивание: это обязанность источника данных.
- Шаблон XLSX требует настройки импорта под конфигурацию 1С. Заказы не отправляются поставщику автоматически.
- Для production нужны HTTPS, секреты вне `.env`, ограничение частоты попыток входа, процедуры восстановления доступа и отдельная проверка на предоставленном партнёром полном наборе данных.
