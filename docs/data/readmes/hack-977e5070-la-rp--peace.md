# la(rp)-peace — агент анализа реорганизации

## Проблема

При реорганизации подразделений кто-то должен вручную сопоставить старые и новые
оргструктуры, положения о подразделениях и приложения к приказам — и убедиться, что по
дороге ничего не сломалось. Типичные риски:

- **потеря функций** — подразделение упразднили, а часть его обязанностей никому не передали;
- **дублирование** — одну и ту же функцию закрепили за двумя подразделениями;
- **пересечение зон ответственности** — разные подразделения делают разные вещи с одним
  объектом, а кто главный — не написано;
- **конфликт интересов** — одно подразделение и исполняет, и само себя контролирует.

Документы большие, формулировки меняются, пункты перенумеровываются. Вручную это долго и
легко пропустить.

## Как это решает софт

Пользователь загружает документ «до» и документ «после», нажимает «Начать анализ» и
через несколько минут получает список того, что изменилось, и список рисков — с цитатой из
пункта документа под каждым выводом. Дальше — по пунктам задачи.

### 1. Какие подразделения реорганизованы, сохранились, созданы

Агент читает оба документа, извлекает из них подразделения и должности (с иерархией) и
сопоставляет два списка. Если приказ прямо говорит «образовать… путём слияния»,
«преобразовать», «упразднить» — статус берётся из приказа, и этот пункт становится
источником. Если прямого указания нет — по совпадению названия и содержания. Для каждого
упразднённого подразделения определяется правопреемник — это нужно для следующего шага.

*Что видит пользователь:* экран «Изменения → Визуал» — слева подразделения «до», справа
«после», между ними карточки: сохранено / преобразовано / упразднено / создано.

### 2. Потеря функций

Агент извлекает из каждого положения, что закреплено за каждым подразделением: функции,
обязанности, права, с условиями и сроками. Затем для каждой функции «до» ищет её в «после» —
по смыслу, а не по номеру пункта и не по совпадению слов: сначала ближайшие кандидаты по
эмбеддингам, потом модель проверяет, та ли это функция. Если она нашлась у того же
подразделения или его правопреемника — сохранена; у другого — перенесена; не нашлась ни у
кого — **потеря**.

Отсутствие доказывается не пустотой, а тем, где искали: к каждой потере приложена область
поиска, порог и ближайшие кандидаты со сходством. Удалённый пункт сам по себе потерей не
считается — функцию могли переписать другими словами или перенести в другой документ.

*Что видит пользователь:* в «Визуале» потеря помечена «∅ не закреплено»; на странице
«Анализ → Потеря функций» — карточка с цепочкой: была у такого-то (цитата) → подразделение
упразднено (цитата из приказа) → у правопреемника не найдена (что проверено).

### 3. Дублирование и конфликт интересов

Функции подразделений в «после» сравниваются между собой попарно.

- **Дублирование** — две функции разных подразделений похожи выше порога, и модель
  подтверждает, что это одна и та же работа без разграничения ролей.
- **Конфликт интересов** — у одного подразделения две функции над одним объектом из
  несовместимой пары: исполняет / контролирует, закупает / принимает, готовит отчёт /
  утверждает отчёт. Отдельно отмечается случай, когда контрольная функция переехала из
  независимого подразделения к исполнителю.
- **Пересечение зон** — разные подразделения, один объект, разные действия (согласует /
  устанавливает сроки), порядок взаимодействия не описан.

*Что видит пользователь:* страница «Анализ» с подстраницами Потеря функций · Дублирование ·
Конфликт интересов · Пересечение зон. У каждой находки — уверенность (high / medium / low)
и её основание.

### 4. Источник под каждым выводом

Каждая находка содержит хотя бы одну цитату с указанием документа и пункта. Цитата должна
дословно входить в текст этого пункта — это проверяет код, а не модель; находка без
подтверждённой цитаты отбрасывается. В цепочке доказательств факты (с цитатами) отделены от
рассуждений агента, и рассуждения так и помечены.

*Что видит пользователь:* клик по карточке открывает панель доказательств: вывод → как
получен → шаги с цитатами → что проверено → уверенность. Клик по цитате открывает
«Изменения → Word» — две редакции рядом, как diff, — на нужном пункте с подсветкой.

### 5. Аналитическое заключение

*Что видит пользователь:* сверху каждой страницы результатов — сводка: изменённые блоки и
счётчики по типам (сохранено, перенесено, потеряно, дублирование, конфликт…), кнопка
«Показать полную аналитику» с полным списком выводов. У каждого вывода — «Подтвердить» /
«Отклонить»: выводы рекомендательные, решение принимает человек, отметки сохраняются и
считаются в сводке («Проверено сотрудником: N из M»). «Скачать PDF» — печатная версия.
В «Чате» можно спросить «Что изменилось?», «Какие функции потеряны?» — агент отвечает
только по пунктам загруженных документов, со ссылками; если ответа в них нет, говорит об этом.

### Опционально

- **Соответствие внешним требованиям.** На экране загрузки есть зона «НПА и регулирующие
  документы». Загруженные документы попадают в блок «Нормативная база» панели доказательств
  и используются только если пользователь их загрузил — агент не ходит за законами сам.
- **Сравнение с другими операторами.** Зона «Документы других операторов» — их структуры
  сопоставляются с преобразованными и созданными подразделениями тем же механизмом.
- **Рекомендации по перераспределению функций** — в текущем объёме не делаются; выводы
  агента — это список рисков с доказательствами, а не готовое решение.

## Запуск

Нужны [uv](https://docs.astral.sh/uv/), Node.js 20+ и ключ OpenAI.

```bash
cp .env.example .env            # OPENAI_API_KEY, OPENAI_MODEL
uv sync
uv run uvicorn la_rp_peace.api.app:create_app --factory --reload   # :8000, /docs
```

Всё одной командой — соберёт интерфейс и отдаст его вместе с API на :8000:

```bash
uv run python -m la_rp_peace.serve
```

Принимаются Word, PDF, Excel. База — `data/larp.sqlite3`. Контрольные документы —
[`test_data/`](test_data/), снимок базы с разобранными документами — [`snapshots/`](snapshots/).

Через API:

```bash
curl -F set=before -F "file=@test_data/Положение_о_внутреннем_аудите_редакция_8_обезличено.docx" http://localhost:8000/api/documents
curl -F set=after  -F "file=@test_data/Положение_о_внутреннем_аудите_редакция_9_обезличено.docx" http://localhost:8000/api/documents
curl -X POST http://localhost:8000/api/comparisons -H 'Content-Type: application/json' -d '{"before_ids":[1],"after_ids":[2]}'
curl http://localhost:8000/api/comparisons/1          # status: done → result
```

## Как устроено

SvelteKit (интерфейс) + FastAPI и SQLite (сервер) + OpenAI (модель и эмбеддинги).
Этапы обработки по [`methodology/`](methodology/): разбор документа
([`ingestion/`](src/la_rp_peace/ingestion)) → подразделения
([`entities/`](src/la_rp_peace/entities)) → функции
([`activities/`](src/la_rp_peace/activities)) → коллизии и каскад внутри документа
([`collisions/`](src/la_rp_peace/collisions), [`cascade/`](src/la_rp_peace/cascade)) →
сопоставление «до → после» ([`comparison/`](src/la_rp_peace/comparison)) → проверка цитат
([`sources.py`](src/la_rp_peace/sources.py), [`verification.py`](src/la_rp_peace/verification.py)).

ТЗ и макеты — [`docs/spec/`](docs/spec/README.md); устройство и контракт API —
[`.agents/backend.md`](.agents/backend.md), [`.agents/frontend.md`](.agents/frontend.md).
