**Кого из 2248 клиентов AML-аналитику смотреть первым и почему — роли, кластеры и
ранжированный список с обоснованием в числах, одной командой из транзакционной сети.**

### [→ Живое демо: zhetysu-team.kz](https://zhetysu-team.kz)

Открывается без регистрации и без наших аккаунтов.

## 2. Краткое описание: какую проблему решает и для кого

**Для кого.** AML-аналитик подразделения финансового мониторинга банка второго уровня.

**Проблема.** От правоохранительных органов аналитик получает только нижний уровень
цепочки — 81 клиента, получавшего деньги, связанные с незаконным оборотом. Кто эти
деньги собирает, через кого прогоняет и у кого они оседают, приходится восстанавливать
вручную: часы работы на один узел, четыре колена переводов, 2248 клиентов в сети и
никакого ранжирования.

**Что даёт решение.** Одной командой из трёх `.parquet` строится граф, каждому из 2248
узлов присваивается роль по формальному правилу с порогом, сеть делится на кластеры,
и аналитик получает ранжированный список «кого смотреть первым и почему» — с
обоснованием в числах по каждому узлу и схемой сети в браузере.

### Методическое ядро: почему «нет исходящих» не значит «деньги осели»

Граф собран обходом от 81 seed по исходящим переводам на 4 колена, поэтому у 444 узлов
последнего колена исходящих нет по построению. Наивное `out_deg == 0 ⇒ terminal` дало бы
444 ложных «конечных получателя». Узлы разделены по наблюдаемости (`terminal_status`):

| Статус | Узлов | Смысл |
|---|---|---|
| `observed_sink` | 1091 | деньги пришли и остались; исходящие проверены обходом |
| `observed_forwarder` | 694 | деньги пришли и ушли дальше |
| `unknown_truncated` | 444 | 4-е колено, исходящие никто не выгружал |
| `no_edges` | 19 | seed без единого ребра в выгрузке |

Для обрезанных роль по отсутствию рёбер не назначается — работает модель `terminal_p`
с высоким порогом (подробности и цифры — в таблице ниже). Вторая ловушка — заниженный
вход у seed: правила транзита и осаждения по доле пропуска (R3a, R3b, R3d, R4b) к seed
не применяются, а seed с исходящими без других признаков получает `transit` с
уверенностью 0.55.

### Чем решение отличается от «пайплайн + три CSV»

| Что | Как подтверждается |
|---|---|
| **Ловушка обрыва на 4-м колене учтена моделью, а не правилом `out_deg == 0`.** 444 узла без исходящих — артефакт обхода. Для них считается `terminal_p` логистической регрессией на 10 признаках входящего профиля, обученной на коленах 1–3 | переносимость проверена на невиданном колене: обучение на коленах 1–2, проверка на колене 3 — AUC 0.64 против 0.73 на своей выборке. Поэтому порог высокий: `terminal` получают 86 из 444, остальные 358 честно остаются `peripheral`. Отчёт — `out/censoring_report.json` |
| **Пороги посчитаны из распределений данных, а не заданы руками** | в коде (`pipeline/config.py`) заданы только уровни квантилей; числовые значения порогов считаются на прогоне и выгружаются с формулировкой в `out/thresholds.json` |
| **`rule_id` у каждого узла** — по любому gid видно, какое из 12 правил сработало | колонка `rule_id` в `out/nodes_roles.csv`, таблица правил — раздел 4 |
| **Собственное ранжирование проверено изъятием** | изъятие топ-20 по нашему приоритету отрезает 9,4% оборота, изъятие 20 случайных узлов (20 повторов) — 1,7%, в 5,7 раза меньше. Кривые для N = 0…50 — `out/robustness_report.json` |
| **Вопрос словами без выдуманных цифр** | ответ считается по графу детерминированно (`ask.py`); языковая модель, если ключ задан, только переформулирует готовый текст. Без ключа работает полностью |
| **Результат воспроизводим бит в бит** | два прогона дают одинаковые `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`; Louvain и случайная база изъятия — с `seed=42` |

### Соответствие обязательным требованиям ТЗ (раздел 7)

| № | Требование ТЗ | Где выполнено | Как проверить |
|---|---|---|---|
| 1 | Один запуск от `.parquet` до трёх выгрузок, < 5 минут | `pipeline/run.py` | шаг 1 раздела 8: ~15 с |
| 2 | Роль, `role_score`, `evidence` у всех 2248 узлов | `out/nodes_roles.csv` | шаг 2 раздела 8 |
| 3 | Формальное правило с порогом для каждой роли | `pipeline/roles.py`, `out/thresholds.json`, колонка `rule_id` | шаг 3 раздела 8 |
| 4 | Кластеры: размер, число seed, оборот, гипотеза | `out/clusters.csv` | шаг 2 раздела 8 |
| 5 | Топ-лист ≥ 20 узлов с обоснованием + схема сети | `out/top_nodes.csv` (30 строк), `web/` | шаги 2 и 4 раздела 8 |

Пайплайн сам проверяет эти требования в конце каждого прогона (функция `verify` в
`pipeline/run.py`, 17 проверок) и завершается с кодом 1, если хоть одна не прошла.

## 3. Что реализовано

| Функция | Что именно |
|---|---|
| **Воспроизводимый пайплайн** | одна команда от сырых `.parquet` до выгрузок, без ручных шагов, ~15 секунд |
| **Роль у каждого из 2248 узлов** | роль из словаря ТЗ, `role_score`, `cluster_id`, `priority_score`, `evidence` (до 200 символов, всегда с числами) и `rule_id`. Итог: terminal 1260, peripheral 483, transit 381, distributor 54, consolidator 43, coordinator 27 |
| **12 правил с порогами из квантилей** | таблица правил — раздел 4 |
| **Отделение конечных получателей от обрезанных обходом** | модель `terminal_p` — раздел 2, «Методическое ядро» |
| **Кластеризация** | Louvain, 72 кластера (71 сообщество и кластер `-1` для 19 seed без рёбер); по каждому размер, число seed, внутренний оборот, состав по ролям, оборот наружу и внутрь, гипотеза |
| **Топ-лист приоритетов** | 30 узлов; в колонке `why` — какие факты подняли узел и в какие верхние проценты графа он попал |
| **Временные паттерны** | по отдельным транзакциям: сквозной транзит за двое суток — 233 узла, синхронный сбор (3+ плательщика в один день) — 38, дробление — 74; входят в `evidence`, в приоритет и выгружаются колонками |
| **Возвратные потоки** | взаимные пары A→B и B→A (`mutual_pair`, 266 узлов), направленные циклы длиной до 6 (`in_cycle`, 303 узла) |
| **Оценка устойчивости сети** | изъятие топ-N против случайных N в пайплайне и ползунок изъятия с пересчётом компонент в интерфейсе |
| **Вопросы словами** | `POST /api/ask` и вкладка вопросов: «кого смотреть первым», «кто собирает деньги с X и Y», «куда уходят деньги от X», «откуда деньги у X», «покажи координаторов», «какие есть кластеры», карточка узла по gid |
| **Веб-интерфейс** | схема сети с направлением потоков и цветом ролей, поиск по gid, досье узла, очередь проверки, сообщества, границы данных, изъятие узлов, вопросы; светлая и тёмная темы, адаптив под телефон |
| **Раскладка схемы в пайплайне** | seed в центре, колена кольцами наружу, кластеры клиньями; координаты одинаковы при каждом прогоне |

## 4. Как работает решение: от входных данных до результата

```text
3 × .parquet ──► граф ──► признаки узла ──► модель обрыва ──► правила ролей ──► кластеры
                                                                                  │
         веб-интерфейс ◄── graph.json ◄── выгрузки CSV ◄── приоритет и топ-лист ◄─┘
```

1. **Загрузка и проверка данных** (`data.py`): 2248 узлов, 3119 рёбер, 4840 транзакций.
   Суммы рёбер сверяются с транзакциями; при битых данных прогон останавливается
   с понятным сообщением.
2. **Граф и признаки** (`graphbuild.py`, `features.py`): направленный взвешенный граф,
   степени, обороты, доля пропуска `pass_through = out_kzt / in_kzt`, PageRank,
   betweenness, HITS, точки сочленения, циклы, достижимость вниз по потоку.
3. **Модель обрыва** (`censoring.py`): вероятность `terminal_p` для 444 узлов 4-го колена.
4. **Временные паттерны** (`patterns.py`): по датам транзакций.
5. **Роли** (`roles.py`): правила применяются в фиксированном порядке, первое
   сработавшее побеждает. Значения порогов на этих данных:

| Правило | Роль | Условие | Узлов |
|---|---|---|---|
| R0 | peripheral | нет ни одного ребра в выгрузке | 19 |
| R1 | distributor | `out_deg >= 11` (квантиль 0.975) | 54 |
| R2 | consolidator | `in_deg >= 4` (квантиль 0.975) и (`out_deg <= max(2, in_deg/2)` или `pass_through <= 0.5`) | 43 |
| R3a | transit | `0.8 <= pass_through <= 1.2` | 67 |
| R3b | transit | `pass_through > 1.2` — отдал больше, чем получил: приток извне выборки | 249 |
| R3c | transit | seed с исходящими: вход у seed занижен, роль по исходящему профилю | 40 |
| R3d | transit | ≥60% исходящей суммы ушло в пределах 2 суток и `pass_through >= 0.6` | 25 |
| R4a | terminal | исходящих нет, и они проверены обходом (`depth <= 3`) | 1069 |
| R4b | terminal | дальше уходит ≤26% полученного (квантиль 0.2) — сумма осела | 105 |
| R4c | terminal | обрезан 4-м коленом и `terminal_p >= 0.70` | 86 |
| R5 | peripheral | смешанный профиль ниже всех порогов | 464 |
| R6 | coordinator | ≥2 плательщика-сборщика (`in_deg >= 4`) или ≥2 seed-плательщика, `in_kzt` в верхних 5% (614 тыс. KZT), не seed | 27 |

6. **Кластеры** (`clusters.py`): Louvain на неориентированной проекции, вес — сумма,
   гипотеза собирается из состава кластера.
7. **Приоритет** (`priority.py`): взвешенная сумма перцентилей — объём потока 0.25,
   число плательщиков 0.18, позиция в сети 0.14, связь с seed 0.12, роль 0.12,
   временные паттерны 0.10, осевшая сумма 0.09. Скор seed умножен на 0.5: их следствие
   уже знает, инструмент нужен, чтобы показать невидимую часть сети.
8. **Выгрузки и самопроверка** (`export.py`, `run.py`).

Пример строки `out/top_nodes.csv` (ранг 1, gid `100000003115284100`, `coordinator`):
«вход 2.2 млн KZT от 8 плательщиков (seed: 2); выход 517 тыс. KZT на 2 получателей;
осело 1.6 млн KZT; 7 плательщиков в один день…»

Полное описание метода — [`pipeline/METHOD.md`](pipeline/METHOD.md); схема решения —
[`docs/solution-map.md`](docs/solution-map.md) и [`docs/solution-map.svg`](docs/solution-map.svg).

## 6. Архитектура

```text
case/data/*.parquet          исходные данные организаторов (только чтение)
        │
        ▼
pipeline/                    ядро анализа, запуск: python -m pipeline.run
  config.py                  уровни квантилей и веса приоритета в одном месте
  data.py                    загрузка и проверки консистентности
  graphbuild.py              направленный взвешенный граф
  features.py                признаки узла: степени, обороты, пропуск, посредничество, циклы
  censoring.py               модель terminal_p для узлов, обрезанных обходом
  patterns.py                временные паттерны: сквозной транзит, синхронный сбор, дробление
  roles.py                   12 правил с порогами, rule_id у каждого узла
  clusters.py                сообщества и гипотезы по ним
  priority.py                приоритет проверки и топ-лист
  layout.py                  координаты узлов для схемы
  robustness.py              изъятие топ-N против случайных N
  fmt.py                     форматирование чисел в обоснованиях
  export.py                  выгрузки
  run.py                     единая точка входа и самопроверка
        │
        ▼
out/                         результат (закоммичен, пересоздаётся пайплайном)
  nodes_roles.csv            2248 строк: схема ТЗ + rule_id и признаки, на которых построены правила
  clusters.csv               72 кластера
  top_nodes.csv              30 узлов
  graph.json                 узлы, рёбра, кластеры, топ-лист для интерфейса одним файлом
  thresholds.json            значение и формулировка каждого порога
  censoring_report.json      модель terminal_p: коэффициенты, AUC, калибровка
  robustness_report.json     кривые изъятия топ-N и случайных N
        │
        ▼
server.py  ──►  web/         интерфейс читает /out/graph.json
   │
```

Ядро и интерфейс связаны **только** через `out/graph.json`; контракт — [`docs/spec.md`](docs/spec.md).
Сервер отдаёт: `/` — интерфейс, `/out/...` — выгрузки, `POST /api/ask` — вопросы,
`GET /api/health` — наличие выгрузок.

### Масштабирование до ~1 млн узлов

На таком объёме реализация не проверялась. Ниже — что изменится, по замеренному
профилю прогона на 2248 узлах (~14 с): 57% времени — признаки узла, 30% — оценка
устойчивости, остальное — меньше секунды на этап.

- **Правила ролей и пороги не меняются.** Они заданы квантилями распределений и
  переносятся на любой объём без ручной настройки; модель `terminal_p` переобучается
  на самих данных за один проход.
- **Betweenness** — самая дорогая метрика (2,2 с сейчас, O(V·E)). Заменяется
  приближённым расчётом по выборке источников (`k`-sample в networkx) или igraph.
- **Построчные признаки** (временные паттерны, концентрация входящих) переносятся
  на групповые операции polars или DuckDB без изменения смысла.
- **Кластеризация** — Louvain/Leiden на igraph вместо networkx.
- **Поиск циклов** (сейчас 0,1 с) растёт экспоненциально с плотностью — на большой
  сети запускается только на подграфе кандидатов: топ по приоритету и их соседи.
- **Оценка устойчивости** — на подграфе топ-узлов и по разреженной сетке N.
- **Хранение и интерфейс** — выгрузки в parquet вместо CSV; браузер показывает не весь
  граф, а окрестность выбранного узла или кластера, подгружаемую с сервера.

Подробный разбор — `pipeline/METHOD.md`, раздел «Масштабирование до ~1 млн узлов».

## 7. Установка и запуск

Нужен Python 3.10 или новее с модулем `venv` (в Ubuntu: пакет `python3-venv`).

```bash
git clone https://github.com/BAITC-Hacks/hack-f6676a41-zhetysu.git
cd hack-f6676a41-zhetysu
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pipeline.run --data case/data --out out
.venv/bin/python server.py --port 3300
```

Пятая команда считает роли и пишет выгрузки в `out/`. Шестая поднимает интерфейс на
http://127.0.0.1:3300 и занимает терминал (остановка — Ctrl+C); команды раздела 8
выполняйте во втором терминале из той же папки.

**Переменные окружения: обязательных нет.** Единственная необязательная —
`OPENAI_API_KEY`: с ней ответы на вопросы переписываются связным языком, без неё
отдаётся тот же ответ шаблоном, цифры и состав не меняются. Ключ можно экспортировать
в окружение или записать в `.env` по образцу [`.env.example`](.env.example) —
`server.py` прочитает файл при запуске.

## 8. Как проверить решение

Около минуты, без наших аккаунтов и ключей. Команды выполняются из корня репозитория
после раздела 7.

**Шаг 1. Пайплайн.**

```bash
.venv/bin/python -m pipeline.run --data case/data --out out
```

## 10. Ограничения

- **Роли — гипотезы для проверки, а не вывод о виновности.** `evidence` описывает
  наблюдаемое поведение счёта, и только его.
- **Размеченных ролей в данных нет**, поэтому точность измерить нельзя. Проверяема
  обоснованность: у каждого правила порог из распределения, у каждого узла `rule_id`.
- **Модель `terminal_p` переносится хуже, чем работает на своей выборке** — AUC 0.64
  на невиданном колене против 0.73. Поэтому 358 обрезанных узлов остаются `peripheral`,
  хотя часть из них, вероятно, конечные получатели (модель ожидает 266 из 444).
- **Входящие потоки видны не полностью** — граф собран по исходящим переводам: полный
  баланс узла недостижим: 354 узла отдают больше, чем по данным получили (`pass_through > 1`),
ровно как указано в ТЗ.
- **Дробление ниже 5 000 KZT невидимо** — такие транзакции в выгрузку не попали.
- **Louvain теряет направление рёбер** на шаге кластеризации.
- **Кластер `-1`** — 19 seed без единого ребра: сообщество для них не определить,
  они собраны в отдельную строку `clusters.csv`.
- **Только внутрибанковские переводы за июль 2026** — выводы за эти рамки не переносятся.
- **Нет аутентификации и разграничения прав** — это демонстрационный прототип.
- **Граф в миллион узлов не проверялся** — план изменений в разделе 6.
