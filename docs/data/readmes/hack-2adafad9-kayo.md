# Samal — прогноз выработки ВЭС

Агентная система прогнозирования для «Самрук-Казына», разработанная в рамках HackAlem AI.

Почасовой прогноз выработки двух ветротурбин на 24–48 часов вперёд. Система сама забирает прогноз
погоды по координатам площадки, готовит признаки, считает выработку, проверяет себя против базовых
линий и объясняет результат. Тестовый период — февраль 2026.

Прогноз выпускается ежедневно в **23:00 UTC на следующие 1–48 часов**. Для восстановления прошлого
используется консервативный архив погоды day2/day3 с запасом до выпуска не менее суток.
**Допущение:** задержка публикации погодных прогнозов не превышала 24 часа. Архив не содержит
исторических времён публикации, поэтому точную доступность каждого запуска доказать нельзя.

Площадка: ВЭС в Шелекском коридоре, Алматинская область, 43.645150 / 78.535604.

```bash

cd hack-2adafad9-kayo
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt

python checks/final_acceptance.py
```

Проверенная среда — Python 3.12. Зависимости устанавливаются через интернет; после установки
полный архивный прогон работает без сети и без API-ключей. Погодные кеши и часовой срез турбин
включены в репозиторий. Исходные десятиминутные CSV нужны только для пересборки часового кеша.

Одна команда делает всё: собирает часовые данные турбин, снимает кривые мощности, обучает модель,
проверяет агентный цикл на отложенном окне и прокручивает его по графику из условия — выпуски
30 и 31 января, 1 февраля и далее каждый день до 27 февраля, каждый на следующие 24–48 часов.
Прогноз на февраль — это ровно то, что выпустил агент в эти дни.

### Экономический сценарий

После почасового графика показана **сценарная цена ошибки**. Пользователь задаёт номинал одной
турбины и условную цену ошибки; исходные 2,5 МВт и 12 000 ₸/МВт·ч — допущения, а не данные ВЭС.
Расчёт: `nMAE × число турбин × номинал × часы периода × цена ошибки`. При исходных параметрах
и округлённых метриках дашборда: 15,35 млн ₸ для базы, 7,22 млн ₸ для агента, разница 8,13 млн ₸.
Это перенос средней ошибки валидации на масштаб 28 дней, **не измеренная экономия февраля**,
не выручка и не прибыль. Реальные договоры могут рассчитывать небаланс иначе.

Ожидаемая выработка по P50 при том же номинале — около 1 620,5 МВт·ч: суммируются часы обеих
турбин только на горизонте 24 ч; 48 ч не добавляется второй раз. Денежный сценарий всегда относится
ко всему периоду, даже если почасовая таблица экспортируется только для одного выпуска.

Условие кейса не назначает обязательную денежную метрику или конкретную формулу ошибки.
Обязательный результат — почасовой прогноз двух турбин и работающий агентный цикл. Для оценки
качества мы выбрали nMAE, nRMSE, смещение, улучшение против базовой линии и покрытие P10–P90;
денежный сценарий поясняет применимость решения, оцениваемую жюри отдельно.

Ещё два режима:

```bash
python -m windagent.run --forecast   # живой выпуск на ближайшие 24–48 часов по свежей погоде (нужна сеть)
python -m windagent.run --export     # пересобрать web/data.json без выгрузок в forecasts/
```

Время полного прогона: около минуты на ноутбуке (обучение, валидация модели и агентного цикла на
93 выпусках, прокрутка февраля на 29 выпусках, все выгрузки). Модель — HistGradientBoosting из
scikit-learn, считает на CPU.

### Языковая модель

Объяснение для диспетчера пишет языковая модель. Ключ кладётся в файл `.env` в корне (он в
`.gitignore`):

```
OPENAI_API_KEY=sk-...
# LLM_PROVIDER=nvidia и NVIDIA_API_KEY=nvapi-... — NVIDIA NIM
# LLM_MODEL=gpt-6-sol — другая модель
```

По умолчанию — `gpt-6-luna`. **Без ключа система работает полностью**: прогноз, проверки и журнал
не зависят от языковой модели, объяснение собирается шаблоном из тех же чисел (статус «шаблон» в
журнале). Проверить ключ: `python checks/llm_ping.py`.

## Архитектура

```text
1. Погода: Open-Meteo Previous Runs
                 |
2. Подготовка: часовая сетка, признаки, отбраковка простоев
                 |
3. Модель: кривая мощности + бустинг, P10/P50/P90
                 |
4. Прогноз на 24–48 часов
                 |
5. Анализ: сравнение с базовыми линиями
                 |
6. Пересчёт при новом прогоне погоды
       /                         \
Рефлексия по доступному факту       Шлюз качества: откат, если хуже базы
                 |
Объяснение результата; запись каждого шага в журнал
```

Где что считается:

- **Числа считает код.** Кривая мощности, бустинг, метрики, интервалы — обычный Python, без языковой
  модели. Это принципиально: прогноз выработки не должен зависеть от того, что «подумала» LLM.
- **Языковая модель объясняет.** Читает готовые цифры и пишет разбор для диспетчера: что ждёт
  станцию, где риск ошибки. Ни одна цифра прогноза от неё не зависит.
- **Решение о пересчёте.** Когда выходит новый прогон погоды, агент сравнивает его с прошлым на
  перекрывающихся часах: если ветер сдвинулся меньше чем на 1 м/с, оставляет прежний прогноз и пишет
  «пересчёт не нужен», иначе считает заново.
- **Рефлексия.** Перед публикацией агент сверяет свою медиану с фактом последних 14 суток и снимает
  систематическое смещение, если оно больше двух стандартных ошибок.
- **Шлюз качества стоит между расчётом и публикацией.** Если на последних 14 днях с фактом решение
  проигрывает прогнозу «как вчера», агент публикует чистую кривую мощности и пишет откат в журнал.
- **Отказы не валят цикл.** Нет сети или данных — запись `error` в журнале и понятная причина.

Провайдер языковой модели переключается переменной окружения: OpenAI или NVIDIA NIM
(`https://integrate.api.nvidia.com/v1`, тот же клиент, меняется адрес и ключ).

## Данные

| Источник | Что берём |
| --- | --- |
| CSV турбин (даны организаторами) | скорость ветра, нормализованная мощность, температура; шаг 10 минут, 11.03.2023 — 31.01.2026 |
| Open-Meteo Previous Runs API | архивные прогнозы: ветер и направление на 100 м, ветер на 10 м, температура, давление |

Обработка данных турбин:

- часовое усреднение с подсчётом числа замеров в часе — неполные часы в обучение не идут;
- **метки времени в файлах местные, а не UTC.** Сдвиг определён по взаимной корреляции измеренного
  ветра с прогнозным: 6 часов до перехода Казахстана на единый пояс и 5 после. Без этой поправки
  прогноз и факт разъезжаются на несколько часов, и любая метрика теряет смысл;
- **«ноль» в данных записан как 0.01**, мощность квантована до сотых — приводим к настоящему нулю;
- **часы простоя** (мощность ≈ 0 при рабочем ветре, около 1,5 % времени, серии до 47 часов) помечены
  отдельно: это ограничения выдачи, а не физика. В обучение они не идут и в основную метрику тоже,
  но показаны отдельной строкой — прятать их было бы нечестно.

Базовая погодная модель названа явно — ICON (`icon_seamless`). Запрос без модели («best match»)
отдаёт Open-Meteo на выбор, и 1 октября 2025 он сам переключился с ICON на другую модель: обучение
шло бы на одной, февраль — на другой.

Архив прогнозов погоды — ICON, GFS и ECMWF, включая отдельные day3-кеши — лежит в репозитории
(`data/weather/*.parquet`), поэтому архивный прогон воспроизводится без интернета.

Турбины стоят в 338 м друг от друга и попадают в одну ячейку любой погодной сетки, поэтому погода
запрашивается один раз, а различия между машинами модель ловит признаком турбины.

## Почему не historical-forecast-api

Очевидный кандидат на «архив прогнозов» у Open-Meteo — `historical-forecast-api`. Для этого кейса он
не годится, и это главная ловушка задания.

Этот эндпоинт склеивает непрерывный ряд из **первых часов каждого прогона** (горизонт 0–3 часа). То
есть каждое значение там — это почти факт: прогноз, выпущенный час-два назад, знает текущую погоду.
Модель, обученная на таком входе, показывает отличные метрики на валидации и разваливается, когда ей
дают настоящий прогноз на сутки вперёд, — а именно так её и будут использовать.

У **Previous Runs API** тоже есть важное ограничение: `_previous_dayN` задаёт возраст относительно
**целевого часа**, а не один запуск модели на момент ежедневного выпуска. Если в полночь объявить
выпуск и взять day1 на весь следующий день, поздние часы будут опираться на погоду позже выпуска.

Поэтому `windagent/asof.py` использует следующий фиксированный протокол:

| Параметр | Следующие сутки | Вторые сутки |
| --- | --- | --- |
| Выпуск | 23:00 UTC | тот же выпуск |
| Фактический горизонт | 1–24 ч | 25–48 ч |
| Погодный архив | previous_day2 | previous_day3 |
| Возраст относительно целевого часа | 48 ч | 72 ч |
| Запас reference time до выпуска | 24–47 ч | 24–47 ч |

Доступность предполагает задержку публикации ≤24 ч. Это смесь значений с фиксированным возрастом,
**не реконструкция единственного метеорологического запуска**. Для строгой реконструкции нужны
архивы отдельных запусков с временем фактической публикации. Семантика источника:
[Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api),
[Single Runs API](https://open-meteo.com/en/docs/single-runs-api).

Проверка `python checks/asof_weather.py` сравнивает значения с day2/day3-кешами, проверяет запас
до выпуска, закрытый час персистентности и live-окно 1–48 ч. JSON сохраняет описание допущения
в `forecast_protocol`; CSV — временные метки, необходимые для независимой проверки.

## Модель и метрики

Четыре слоя:

0. **Ансамбль погодных моделей** — к базовому ICON добавлены среднее и разброс по ICON, GFS и ECMWF,
   каждая со своими прогнозами day2/day3. Среднее и разброс между моделями используются как
   признаки; сам по себе разброс не является калиброванной вероятностью ошибки.
   Сглаживание ветра по соседним часам считается внутри блока выпуска — один горизонт, одни сутки, —
   то есть ровно по тому, что агент видит в день выпуска.
1. **Кривая мощности** — эмпирическая, по бинам прогнозной скорости, отдельно для каждой турбины и
   каждого горизонта. Строится на прогнозной, а не измеренной скорости: прогноз сглажен относительно
   показаний анемометра, и кривая, снятая с измерений, дала бы систематическое смещение.
2. **Градиентный бустинг на остаток** — учит то, что физика не объясняет: систематические ошибки
   прогноза погоды, плотность воздуха, направление, сезон, час. Отдельные квантильные модели дают
   коридор P10–P90, поверх — конформная калибровка на отложенном срезе, чтобы покрытие соответствовало
   заявленному.
3. **Рефлексия агента** — перед публикацией агент сверяет свою медиану с фактом последних 14 суток по
   каждой турбине и снимает смещение, если оно больше двух стандартных ошибок, то есть отличимо от
   шума; иначе пишет в журнал «в пределах шума, поправка не нужна». Сдвигается только медиана внутри
   коридора. Зимой модель систематически завышает, и рефлексия это ловит: строка «наше
   решение» против «модели без агента» в таблице ниже, замер — `checks/reflect_eval.py`.

Валидация — отложенное окно **ноябрь 2025 — январь 2026**: модель этих данных не видела, а зима —
тот же режим, что и в феврале. Февраль 2026 проверить нечем: в выданных данных его нет, это режим
поставки, а не теста.

«Наше решение» измерено тем же агентным циклом, который выпускает февраль, и в том же режиме: факт
обрывается в начале каждого месяца валидации, как в феврале он кончается 31 января, и агент переносит
поправку смещения по последним 14 суткам известного факта (если ему не больше 30 суток). Замер
`checks/stale_reflect.py`. Рядом — та же модель без агента и лестница
базовых линий: климатология по месяцу и часу, персистентность («как сутки назад»), их смесь и
эмпирическая кривая мощности. Часы без простоев. **Персистентность получает ежедневный факт**,
а агент в режиме поставки — только факт до начала месяца: базовая линия имеет больше информации.
Сравнение при одинаковой доступности входов — агент против модели без агента и кривой мощности.

| Модель | nMAE 24 ч | nMAE 48 ч | Скилл 24 ч | Скилл 48 ч |
| --- | --- | --- | --- | --- |
| **Наше решение (агентный цикл, режим поставки)** | **0,179** | **0,193** | **0,53** | **0,50** |
| Агент при ежедневном факте | 0,180 | 0,193 | 0,53 | 0,50 |
| Модель без агента | 0,192 | 0,208 | 0,50 | 0,46 |
| Кривая мощности | 0,193 | 0,210 | 0,49 | 0,46 |

| Климатология | 0,331 | 0,331 | 0,13 | 0,14 |
| Персистентность | 0,381 | 0,386 | 0 | 0 |

nMAE — средняя ошибка в долях номинала: 0,179 значит, что прогноз в среднем ошибается на 17,9 %
мощности турбины. Скилл — относительное снижение MAE против персистентности: 0,53 — примерно на 53 %.

Покрытие коридора P10–P90: **79,4 %** при средней ширине **0,522** (цель — 80 %).
Достигается конформной калибровкой: квантильные модели учатся без прошлой зимы (ноябрь 2024 —
февраль 2025), а на ней оценивается конформный отступ — отдельно на пару «турбина × горизонт»,
потому что у 48 ч разброс шире. Цели калибровочного окна исключены и из обучения квантилей, и из
кривой мощности. Обучение заканчивается 30.10.2025 в 22:00 UTC — до первого выпуска валидации.
Старые эксперименты с соседними окнами относятся к предыдущему протоколу; их числа здесь не используются.

### Как мы поймали утечку у себя

Прежняя версия показывала nMAE 0,156. Независимое ревью нашло, что сглаживание ветра по соседним
часам считалось по строкам таблицы, где соседями одного часа были горизонты 0, 24 и 48 — и в признак
для суточного прогноза подмешивался ноукаст. Теперь окна считаются внутри блока выпуска одной функцией
для обучения и для агента, и признаки поставки совпадают с обучающими до нуля
(`checks/agent_cycle.py`). Затем проверка расписания нашла вторую проблему: возраст day1/day2
ошибочно трактовался как доступность всего суточного выпуска. Исправлены погодные источники,
момент выпуска, граница обучения и доступность базовой линии; метрики пересчитаны целиком.
Прежние 0,164/0,179 не относятся к текущему протоколу и не используются в итоговой оценке.

Метрики нормированы на установленную мощность, поэтому читаются как доля от номинала.

## Ограничения

- **Февраль 2026 проверить нечем.** В выданных данных его нет, поэтому качество на нём заявлять
  нельзя — мы показываем метрики на отложенном окне и явно об этом пишем.
- Часы ограничения выдачи исключены из основной метрики: предсказать решение диспетчера по погоде
  невозможно, но их доля и влияние показаны отдельно.
- Прогноз даётся в долях от номинала, как в исходных данных. Экономический блок на дашборде —
  оценка порядка величин на **допущениях**: мощность турбины 2,5 МВт и штраф за небаланс
  12 000 ₸/МВт·ч — не тарифы станции.
- Покрытие коридора 79,4 % — измерение на валидации, не гарантия для февраля или другой площадки.
- Календарные границы февральской выгрузки заданы в UTC; `time_local` показывает сдвиг +5 ч.
- Времена фактической публикации архивных погодных запусков отсутствуют: используется запас 24 ч
  и допущение о задержке, а не доказательство доступности каждого отдельного запуска.
- Одна площадка и одна ячейка погодной сетки: на парк из десятков турбин решение переносится, но
  потребует учёта затенения между машинами.
- Горизонт ограничен глубиной архива Previous Runs — с 17.02.2024.
- Live использует свежую погоду, а обучение — консервативный day2/day3-архив. Качество live
  отдельным бэктестом не подтверждено; приведённые метрики относятся к архивному протоколу.

## Подключение к действующей ВЭС

Собственник может использовать решение как основу для пилота вместе со своей ИТ-командой или
интегратором. Точка подключения — система мониторинга станции (SCADA), её база или регулярная
выгрузка. На первом этапе достаточно доступа к измерениям для чтения; система формирует прогноз,
а решение о плане поставки принимает диспетчер.

### Что потребуется от станции

| Данные или доступ | Для чего нужны |
| --- | --- |
| Идентификаторы, координаты и номинальная мощность каждой турбины | привязать измерения и погоду, переводить доли номинала в МВт |
| История и новые измерения активной мощности с временными метками, единицами и часовым поясом | обучить модель на площадке, проверять ошибки и корректировать смещение |
| Статусы работы, простои и ограничения выдачи, если доступны | отличать недостаток ветра от остановки или ограничения оборудования |
| Описание API, структуры базы или формата выгрузки | разработать адаптер конкретной системы мониторинга |
| Условия расчёта небаланса и реальные параметры станции | заменить демонстрационный денежный сценарий расчётом по договору |
| Сервер и доступ к источнику прогноза погоды | выполнять расчёт регулярно и сохранять выпуски |

Для другой ВЭС потребуется обучение и отдельная валидация на её истории. Качество на двух турбинах
этого кейса не доказывает такую же точность на новой площадке.

### Как данные используются в работе

1. Сервис получает измерения станции и новый прогноз погоды, проверяет время, пропуски и единицы.
2. Агент рассчитывает почасовые P10/P50/P90 на следующие 48 часов и записывает причины пересчёта.
3. Диспетчер использует P50 как ориентир для плана выработки, а диапазон — для оценки
   неопределённости отдельных часов. Мощность в МВт получается умножением нормированного прогноза
   на номинал турбины; почасовые значения позволяют оценить энергию в МВт·ч.
4. После поступления факта сравниваются прогноз и измерения: nMAE, nRMSE, смещение, улучшение
   относительно базовой линии и покрытие диапазона. Эти показатели оценивают качество системы.
5. Планировщик и собственник получают отчёт Excel/PDF. Денежный эффект оценивается по реальным
   условиям договора; заявка на рынок формируется отдельным процессом.

### Что уже автоматизировано, а что нужно добавить

| Возможность | Состояние прототипа |
| --- | --- |
| Получение погоды, подготовка признаков, расчёт, анализ и решение о пересчёте | выполняются программно после запуска команды |
| Восстановление февральских выпусков и отчётов | `python -m windagent.run --backtest` |
| Разовый расчёт по свежей погоде | `python -m windagent.run --forecast`; результат выводится в консоль |
| Запуск каждый день без человека | нужно настроить планировщик на сервере; в репозитории он не настроен |
| Получение свежей телеметрии SCADA | нужно реализовать адаптер станции; сейчас используется исторический часовой кеш |
| Непрерывное обновление дашборда живыми выпусками | нужно добавить сохранение live-результата и обновление данных страницы |
| Передача прогноза в систему планирования станции | нужно согласовать формат и реализовать интеграцию |
| Отправка рыночных заявок и управление оборудованием | в прототипе отсутствуют |

**Обновление страницы не запускает прогноз.** Сейчас дашборд показывает рассчитанные февральские
выпуски. Для постоянной эксплуатации к существующему расчётному циклу нужно добавить расписание,
приём новых измерений, хранение выпусков, контроль сбоев и отображение времени последнего
успешного расчёта. Приёмка live-режима должна включать сетевую проверку источников и накопление
ошибок на новых фактических данных; архивные метрики её не заменяют.
