# 🚀 AI Sana Challenge Hub

> AI-платформа, которая превращает сырую бизнес-проблему в структурированную, измеримую и готовую к работе задачу для студенческих команд.

Проект разработан в рамках **HackAlem / AI Sana Challenge**.

---

## 🎯 Что решает проект

У бизнеса может быть реальная проблема, но не готовое техническое задание.

Например:

> «Хотим с помощью ИИ уменьшить очереди в нашей клинике».

Такого описания недостаточно, чтобы студенческая команда сразу начала работу:

- непонятно, где именно возникает проблема;
- неизвестно, кто будет пользоваться решением;
- неизвестно, какие данные доступны;
- не определены ограничения;
- отсутствует измеримый ожидаемый результат;
- отсутствуют критерии успеха.

**AI Sana Challenge Hub** помогает бизнесу пройти путь от такой идеи до полноценной карточки задачи.

---

# 💡 Как работает решение

Основной пользовательский сценарий:

```text
Бизнес описывает проблему
        ↓
OpenAI анализирует описание
        ↓
Определяет недостающую информацию
        ↓
Генерирует ≥ 3 уточняющих вопросов
        ↓
Бизнес отвечает
        ↓
AI формирует структурированную карточку
        ↓
Бизнес проверяет и редактирует её
        ↓
Человек подтверждает карточку
        ↓
Рассчитывается Readiness Score 0–100
        ↓
Задача публикуется
        ↓
Попадает в каталог
        ↓
Студенческие команды предлагают решения
        ↓
Бизнес сравнивает предложения
        ↓
Accept / Reject
        ↓
Для принятой команды можно подготовить план пилота
```

AI помогает структурировать информацию, но **не принимает финальные решения вместо человека**.

- увидеть Readiness Score;
- увидеть недостающую информацию;

# 🤖 Где используется AI

В проекте используется **реальный OpenAI API**.

AI применяется там, где требуется работа с естественным языком и неполной информацией.

### 1. Анализ первоначального описания

AI определяет, какой информации недостаточно.

Например:

```text
Хотим автоматизировать работу склада.
```

Система может определить отсутствие:

```text
users
data_and_materials
constraints
success_criteria
expected_result
```

---

### 2. Уточняющие вопросы

AI генерирует минимум три различных вопроса.

Например:

```text
Кто будет основным пользователем системы?

Какие данные о работе склада уже доступны?

По каким показателям будет измеряться успех решения?
```

Backend дополнительно проверяет, чтобы вопросы действительно отличались друг от друга.

---

### 3. Формирование Task Card

После получения ответов AI структурирует предоставленные сведения.

AI **не должен придумывать отсутствующие факты**.

---

### 4. AI Review

Для уже сформированной карточки AI может найти:

- расплывчатые формулировки;
- пропущенные сведения;
- потенциальные противоречия;
- места, которые стоит дополнительно уточнить.

---

### 5. Proposal Coach

AI помогает студенческой команде подготовить:

- идею решения;
- план реализации;
- вопросы бизнесу.

При этом AI самостоятельно не назначает:

- название команды;
- сроки;
- prototype URL.

Финальное предложение отправляет человек.

---

### 6. Pilot Assistant

После ручного принятия команды AI может предложить:

- этапы пилота;
- открытые вопросы.

Фактические данные пилота берутся обычной логикой приложения из карточки задачи и предложения команды.

# 🛡 Защита от выдуманных AI-фактов

При генерации карточки AI возвращает:

```text
значение
+
дословную цитату-источник
```

Backend принимает значение только если:

1. AI предоставил цитату;
2. цитата действительно присутствует в первоначальном описании или ответах пользователя;
3. значение прошло проверку.

Если подтверждения нет:

```text
field = null
```

Тексты самих AI-вопросов **не считаются источниками фактов**.

После генерации карточку всё равно проверяет человек.

> Механизм снижает риск выдуманных фактов, но окончательная смысловая проверка остаётся за пользователем.

# 🧠 Structured Outputs

Backend не пытается разбирать произвольный текст LLM.

Используются:

- OpenAI Structured Outputs;
- `AsyncOpenAI.responses.parse`;
- Pydantic.

Пример AI-ответа:

```json
{
  "missing_fields": [
    "users",
    "data_and_materials",
    "success_criteria"
  ],
  "questions": [
    "Кто будет пользоваться решением?",
    "Какие данные уже доступны?",
    "Как будет измеряться успех?"
  ]
}
```

Это позволяет backend работать с предсказуемой структурой данных.

# 🔐 OpenAI

Конфигурация находится в:

```text
backend/app/core/config.py
```

Используются environment variables:

```env
OPENAI_API_KEY=
OPENAI_MODEL=gpt-4.1-mini
```

API key:

- хранится только локально;
- не передаётся frontend;
- не хранится в исходном коде;
- не должен попадать в Git;
- не выводится в логи.

OpenAI-запросы выполняются с:

```text
store=False
```

При ошибке API или невалидном ответе выполняется одна повторная попытка.

Если запрос всё равно не выполнен, пользователь получает понятную ошибку и может продолжить заполнение карточки вручную.

Скрытого mock AI fallback в рабочем приложении нет.

# 🏆 Readiness Score

Каждая задача получает рейтинг готовности:

```text
0 ───────────────────────────────── 100
```

Он показывает **насколько задача заполнена и готова к работе со студенческой командой**.

Он не оценивает:

- ценность компании;
- коммерческий потенциал;
- качество идеи;
- достоверность предоставленных данных.

---

## Формула

| Критерий | Баллы |
|---|---:|
| Контекст | 10 |
| Потребность | 10 |
| Данные и материалы | 20 |
| Ожидаемый результат | 15 |
| Критерии успеха | 15 |
| Ограничения | 10 |
| Пользователи | 10 |
| Контакт + формат взаимодействия | 10 |
| **Всего** | **100** |

Рейтинг вычисляется **обычной Python business logic**.

LLM рейтинг не определяет.

Backend возвращает:

```json
{
  "score": 75,
  "level": "ready",
  "missing": [],
  "improvements": []
}
```

---

## Уровни

| Score | Level |
|---:|---|
| 0–39 | `draft` |
| 40–69 | `working` |
| 70–89 | `ready` |
| 90–100 | `priority` |

Низкий рейтинг **не запрещает публикацию**.

# 🎮 Геймификация

Пользователь видит:

- текущий score;
- уровень;
- недостающие сведения;
- рекомендации;
- изменение рейтинга после редактирования.

Логика:

```text
Более полная задача
        ↓
Выше Readiness Score
        ↓
Выше уровень готовности
        ↓
Выше позиция в каталоге
```

Это мотивирует бизнес улучшать качество постановки задачи.


# 🧪 Pilot Plan

После принятия предложения бизнес может подготовить план пилота.

Документ содержит:

- цель;
- ожидаемый результат;
- критерии успеха;
- данные;
- ограничения;
- обязанности сторон;
- сроки;
- этапы;
- открытые вопросы.

Фактические поля копируются обычной Python-логикой.

AI предлагает только:

```text
этапы
+
открытые вопросы
```

---

## Правила Pilot Plan

AI-генерация сама ничего не сохраняет.

Сохранение ручных изменений снимает подтверждение.

Если исходная задача или предложение изменились:

```text
Pilot → outdated
```

Перед подтверждением должны быть заполнены обязательные поля и существовать хотя бы один этап.

Для отклонённой команды нельзя сохранить или подтвердить pilot.

Подтверждение бизнеса не означает автоматического согласия команды.

# 🚀 Быстрый запуск на Windows

Для текущего development environment предусмотрен автоматический PowerShell-скрипт.

Из корня проекта:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-local.ps1
```

Скрипт:

1. запускает локальный PostgreSQL;
2. задаёт `DATABASE_URL`;
3. применяет Alembic migrations;
4. запускает seed;
5. запускает FastAPI;
6. запускает frontend;
7. ожидает готовности сервисов.

После запуска:

### Frontend

```text
http://localhost:5173
```

### Backend / Swagger

```text
http://127.0.0.1:8000/docs
```

### Local PostgreSQL

```text
127.0.0.1:55432
```
