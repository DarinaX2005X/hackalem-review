# Career Quest

**AI-навигатор развития сотрудника для HackAlem AI × Halyk Bank**

Career Quest превращает разрозненные HR-активности в понятную карьерную траекторию. Сотрудник видит, какие навыки отделяют его от следующего грейда, получает 1–3 доступных шага с проверяемым объяснением и сразу видит модельный эффект выполнения. HR получает агрегированный срез по дефицитам компетенций и участию — без публичных рейтингов сотрудников.

Решение работает на синтетическом стартовом наборе и поддерживает загрузку дополнительных профилей жюри. Внешняя LLM опциональна: без API-ключей приложение использует прозрачный локальный ранжировщик.

## Краткое описание

Обычный каталог обучения отвечает на вопрос «что доступно?», но не объясняет сотруднику, зачем ему конкретная активность. Career Quest связывает четыре контекста:

- текущий грейд и требования следующего уровня;
- фактические разрывы по навыкам;
- историю завершений, пропусков и отказов;
- доступность, prerequisites и ожидаемый прирост от активности.

Результат — не рекомендация по минимальному навыку, а следующий реалистичный шаг к карьерной цели с доказательствами, на которых он выбран.

## Что реализовано

| Требование ТЗ | Реализация в Career Quest |
| --- | --- |
| Профиль и карьерная траектория | Роль, грейд, следующая веха, долгосрочная цель, подтверждённые и модельные уровни навыков, история и обязательные активности. |
| 1–3 рекомендации | Сервер отбирает только доступные добровольные активности, сокращающие разрыв до ближайшей или долгосрочной цели. |
| Объяснимость минимум по трём факторам | Карточка показывает цель, текущий/требуемый/ожидаемый уровень навыка, историю похожих активностей, доступность и место в локальном рейтинге. |
| Обновление прогресса | «Отметить пройденным» применяет <code>gain</code> с учётом <code>max_level</code>, пересчитывает траекторию и рекомендации. Демо-отметку можно отменить. |
| HR-view | Карта дефицитов, сотрудники с разрывом без доступного шага, сотрудники без цели и статистика участия по активностям. |
| Загрузка проверочных профилей | HR может предварительно проверить и атомарно импортировать JSON профилей и CSV истории в схеме стартового набора. |
| Разграничение ролей | В демо сотрудник видит только выбранный профиль; импорт и агрегаты доступны роли HR. Границы демо-авторизации явно обозначены ниже. |
| Запуск одной командой | Приложение и PostgreSQL поднимаются через Docker Compose; схема и стартовые данные загружаются автоматически. |

## Установка и запуск

Потребуется Docker Desktop с запущенным Linux engine.

~~~powershell
Copy-Item .env.example .env
docker compose up --build -d
~~~

После запуска:

- приложение — [http://localhost:8000](http://localhost:8000);
- health check — [http://localhost:8000/api/health](http://localhost:8000/api/health);
- OpenAPI — [http://localhost:8000/docs](http://localhost:8000/docs).

Первый старт создаёт таблицы PostgreSQL и загружает <code>data/</code>: 200 профилей, 40 событий, 60 навыков и 2 743 записи истории. Повторный запуск не дублирует данные.

Проверить состояние контейнеров:

~~~powershell
docker compose ps
docker compose logs app --tail 100
~~~

Остановить приложение без удаления данных:

~~~powershell
docker compose down
~~~

PostgreSQL хранится в Docker volume <code>postgres_data</code>. Команда <code>docker compose down -v</code> удалит volume вместе с импортами и смоделированными завершениями — используйте её только для полного сброса демо.

Приложение по умолчанию привязано к <code>127.0.0.1</code>. При конфликте порта измените <code>APP_PORT</code> в <code>.env</code>.

## Как проверить решение

1. Откройте «Моя траектория» и выберите <code>E0028</code> либо произвольный профиль. Покажите текущий грейд, следующую веху, покрытие требований и историю.
2. Перейдите к рекомендациям. В каждой карточке видны разрыв, прогнозируемый прирост, влияние истории и доступность. Если подходящего курса нет, система честно объяснит ограничение и сформирует конкретный запрос HR по главному разрыву или карьерной цели. Копирование запроса не изменяет навыки.
3. Для самостоятельной активности нажмите «Отметить пройденным». Демо-отметка сохраняется датой среза, а прогресс и рекомендации пересчитываются. Очную или онлайн-активность можно отметить только после состоявшейся сессии; созданную в приложении отметку можно отменить в истории.
4. Переключитесь на роль HR и покажите карту дефицитов, разрывы без шага, профили без цели и участие по активностям.
5. В разделе «Импорт данных» загрузите проверочный JSON/CSV: сначала «Проверить файлы», затем «Загрузить набор». Импорт не изменяет исходные файлы и выполняется атомарно.

> «Отметить пройденным» создаёт обратимую демо-запись. Исходная история датасета при этом не изменяется и не удаляется.

## Как работает решение

Основной пользовательский сценарий:

1. Платформа получает профиль сотрудника, текущий грейд, уровни навыков и историю участия из PostgreSQL.
2. Доменный модуль определяет следующую карьерную веху и рассчитывает разрывы между текущими и требуемыми уровнями.
3. Каталог фильтруется по роли, грейду, prerequisites, датам сессий и уже выполненным активностям; оставшиеся варианты получают многофакторную оценку.
4. Если настроен AI-провайдер, он переупорядочивает только допустимых кандидатов. Сервер проверяет ответ модели и при любой ошибке использует локальный рейтинг.
5. Сотрудник получает 1–3 шага с объяснением цели, разрыва, ожидаемого прироста, истории и доступности. Если курса нет, система показывает причину и готовит запрос для HR без обращения к OpenAI.
6. После демо-отметки выполнения модельный прогресс и рекомендации пересчитываются. HR видит агрегированные дефициты и статистику участия.

~~~mermaid
flowchart LR
    A[Профиль и история] --> B[Цель и разрывы навыков]
    C[Каталог активностей] --> D[Фильтр доступности]
    B --> D
    D --> E[Прозрачный локальный score]
    E --> F{LLM настроена?}
    F -- нет или timeout --> G[Детерминированный Top 1–3]
    F -- да --> H[LLM rerank допустимых кандидатов]
    H --> I[Проверка ID, фактов и локального Top 3]
    I -- ответ валиден --> J[Объяснимые рекомендации]
    I -- ответ невалиден --> G
    G --> J
    J --> K[Модельное выполнение]
    K --> B
~~~

### 1. Расчёт траектории

Ближайшая веха — следующий грейд в текущей роли. Если следующего грейда нет, используется только явно заданная и валидная карьерная цель; система не придумывает направление развития. Прогресс считается по требованиям целевого профиля:

~~~text
coverage = Σ min(модельный уровень, требуемый уровень) / Σ требуемых уровней
~~~

Исходные <code>employees.skills</code> остаются подтверждённой оценкой. Завершения после <code>last_review_date</code> образуют отдельный модельный уровень. Прирост ограничивается диапазоном 0–5 и значением <code>max_level</code> активности.

### 2. Фильтр допустимости

До обращения к LLM сервер исключает:

- обязательные мероприятия — они показываются отдельно;
- активности не для текущей роли или грейда;
- шаги с невыполненными prerequisites;
- уже завершённые неповторяемые активности;
- активности в процессе или без будущей сессии;
- шаги, которые не сокращают ни одного разрыва до цели.

Поэтому внешняя модель не может предложить несуществующую или недоступную активность.

### 3. Многофакторный рейтинг

Для каждого допустимого кандидата локальный слой учитывает:

- величину закрываемого разрыва и повышенный вес критичных навыков;
- вклад в ближайшую и долгосрочную цель;
- завершения активностей того же типа;
- пропуски, прерывания и отказы по тем же навыкам;
- длительность активности.

Шаг по критичному разрыву включается в контекст LLM, но критичность сама по себе не отменяет штрафы за пропуски и отказы. Первый выбор LLM обязан входить в локальный Top 3; если локальный лидер закрывает критичный разрыв, этот приоритет сохраняется. Правила повторно проверяются сервером.

### 4. Роль LLM и fail-safe

LLM не генерирует каталог и не рассчитывает уровни. Она только выбирает и переупорядочивает заранее проверенных кандидатов. Ответ принимается, если:

- содержит только известные <code>event_id</code>;
- ссылается минимум на три разрешённых фактора и факты из серверного контекста;
- ставит первым один из локальных Top 3 и сохраняет критичный приоритет локального лидера.

При отсутствии ключа, таймауте, сетевой ошибке или невалидном ответе автоматически используется детерминированный Top 1–3. Результат кэшируется на пять минут и инвалидируется после импорта или выполнения активности.

### Что означает источник рекомендации в интерфейсе

- **«AI · OpenAI»** — OpenAI ответил, после чего сервер проверил выбранные <code>event_id</code>, подтверждающие факты и соблюдение правил ранжирования и только затем принял результат. Список допустимых курсов и расчёт их пользы до обращения к модели формирует код платформы: OpenAI не создаёт активности и не изменяет уровни навыков.
- **«Анализ данных»** — для сотрудника не нашлось подходящих курсов. Система локально объясняет причину и показывает запасной шаг — готовый запрос к HR по главному разрыву или карьерной цели. В этом сценарии запрос к OpenAI не отправляется, а копирование текста не влияет на прогресс.

## Архитектура проекта

Frontend собран в статические файлы и раздаётся тем же FastAPI-приложением, что обслуживает API. FastAPI получает профиль и историю из PostgreSQL, передаёт их в независимый доменный модуль, а при наличии допустимых кандидатов может вызвать настроенный AI-провайдер для rerank. Любой ответ модели проходит серверную проверку; при ошибке используется локальный результат.

Основной поток запроса:

~~~text
Browser → FastAPI → domain rules → PostgreSQL
                    └→ optional LLM rerank → validator → fallback
~~~

Ключевые модули:

~~~text
backend/
├── main.py          # API, роли, импорт и раздача собранного frontend
├── domain.py        # траектория, фильтр, scoring и объяснения
├── ai_provider.py   # OpenAI/NVIDIA, schema validation и fallback
├── analytics.py     # HR-агрегаты
├── ingestion.py     # парсинг и валидация JSON/CSV
├── database.py      # доступ к PostgreSQL и первичная загрузка
└── schema.sql       # схема БД
frontend/src/        # React/TypeScript интерфейс
data/                # синтетический стартовый набор
tests/               # предметные и acceptance-тесты
~~~

## Данные и интеграции

Стартовый синтетический набор хранится локально в каталоге <code>data/</code> и содержит:

- <code>employees.json</code> — 200 профилей сотрудников;
- <code>events.json</code> — 40 HR-активностей и правила прироста навыков;
- <code>skills.json</code> — 60 навыков, шкалу уровней и требования профилей;
- <code>activity_history.csv</code> — 2 743 записи истории за 24 месяца.

После первого запуска данные загружаются в PostgreSQL. Дополнительные профили и историю можно импортировать через HR-интерфейс. Из внешних интеграций реализованы опциональные OpenAI Responses API и NVIDIA NIM Chat Completions; при отсутствии ключей решение полностью работает на локальном детерминированном алгоритме.

### Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| <code>APP_PORT</code> | <code>8000</code> | Локальный порт веб-приложения. |
| <code>POSTGRES_DB</code> | <code>careerquest</code> | Имя БД PostgreSQL. |
| <code>POSTGRES_USER</code> | <code>careerquest</code> | Пользователь PostgreSQL. |
| <code>POSTGRES_PASSWORD</code> | <code>careerquest</code> | Пароль локальной демо-БД. |
| <code>DEMO_MODE</code> | <code>true</code> | Включает локальный переключатель ролей и профилей. |
| <code>AI_PROVIDER</code> | <code>auto</code> | <code>auto</code>, <code>openai</code>, <code>nvidia</code> или <code>off</code>. |
| <code>OPENAI_API_KEY</code> | — | Ключ OpenAI; для запуска не обязателен. |
| <code>OPENAI_MODEL</code> | <code>gpt-4.1-mini</code> | Доступная аккаунту модель Responses API. |
| <code>NVIDIA_API_KEY</code> | — | Ключ NVIDIA NIM; для запуска не обязателен. |
| <code>NVIDIA_MODEL</code> | <code>meta/llama-3.3-70b-instruct</code> | Доступная модель NVIDIA NIM. |
| <code>AI_TIMEOUT_SECONDS</code> | <code>7.5</code> | Общий бюджет внешнего AI; остаётся внутри лимита ТЗ в 10 секунд. |

Режимы <code>AI_PROVIDER</code>:

- <code>auto</code> — OpenAI → NVIDIA → локальный fallback;
- <code>openai</code> или <code>nvidia</code> — выбранный провайдер → локальный fallback;
- <code>off</code> — только детерминированное ранжирование.

Ключи не нужны для локального демо. Не коммитьте <code>.env</code>: файл исключён через <code>.gitignore</code>. Во внешний AI передаются целевая роль, агрегированные разрывы и обезличенные кандидаты — без имени сотрудника и сырой истории.

### Импорт проверочных данных

Импорт доступен в HR-режиме и принимает файлы до 3 МБ:

- <code>employees.json</code>: один профиль, массив профилей, объект <code>{ "employees": [...] }</code> или полный формат стартового файла;
- <code>activity_history.csv</code>: CSV с теми же колонками, что в <code>data/activity_history.csv</code>.

Минимальный пример профиля:

~~~json
{
  "employee_id": "JURY_001",
  "full_name": "Test Employee",
  "department": "Backend Development",
  "role": "Backend Engineer",
  "grade": "Middle",
  "manager_id": null,
  "hire_date": "2023-01-01",
  "tenure_months": 44,
  "work_format": "hybrid",
  "preferred_language": "ru",
  "career_goal": {
    "target_role": "Backend Engineer",
    "target_grade": "Senior"
  },
  "skills": {
    "SK_PYTHON": 3,
    "SK_SYSTEM_DESIGN": 2,
    "SK_PUBLIC_SPEAKING": 2
  },
  "last_review_date": "2026-09-01"
}
~~~

CSV-заголовок:

~~~csv
record_id,employee_id,event_id,date,due_date,status,completion_pct,score,feedback_rating,assigned_by
~~~

Preview проверяет уникальность ID, существование ролей, грейдов, навыков и событий, диапазоны значений и ссылки истории на сотрудников. Commit выполняется одной транзакцией. Повторная загрузка тех же файлов определяется по хэшу и не создаёт дубликаты; исходный batch удалить нельзя.

## Ограничения текущей версии

- Данные стартового набора синтетические; приложение не отправляет репозиторий или данные куда-либо автоматически.
- HR-view содержит агрегаты и рабочие списки, но не публичный рейтинг результативности сотрудников.
- Обязательные процессы отделены от добровольных рекомендаций и не используются как игровая механика.
- <code>DEMO_MODE</code> и заголовки — только имитация ролей для защиты, не корпоративная авторизация.
- Перед работой с реальными данными необходимы SSO/RBAC, аудит доступа, управление согласиями, секрет-хранилище и согласованная политика передачи данных внешнему AI.
- Дата расчёта фиксирована метаданными набора (<code>2026-10-01</code>), поэтому демо воспроизводимо и не зависит от часов компьютера.
- Для self-paced активности историческая дата может означать назначение, а не завершение. Неоднозначные записи до последней оценки не повышают уровень автоматически.
- Процент покрытия показывает соответствие требованиям профиля, а не вероятность повышения сотрудника.
- Контент каталога в стартовом наборе на английском; интерфейс текущей версии — на русском.

## Deployed-версия

Публичная deployed-версия в репозитории не указана. После локального запуска приложение доступно по адресу [http://localhost:8000](http://localhost:8000).

## Возможности развития

- SSO и корпоративная матрица ролей;
- согласованный каталог на русском и казахском языках;
- обратная связь сотрудника для learning-to-rank;
- календарь, мессенджер и напоминания по добровольному opt-in;
- конструктор активностей и симуляция карьерных сценариев для HR;
- мониторинг качества рекомендаций, fairness и drift;
- командные и менторские механики без публичного соревнования сотрудников.
