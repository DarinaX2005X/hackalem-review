# Agentic AI для прогноза выработки ВЭС

Команда «Во имя Омниссии!», HackAlem AI, кейс «Agentic AI для прогнозирования выработки ВЭС».

Система сама строит почасовой прогноз выработки ветроэлектростанции из двух турбин на следующие 24–48 часов:
берёт архивный прогноз погоды, известный на момент прогноза, прогоняет ML-модель, проверяет результат,
сравнивает с предыдущим прогнозом и пишет отчёт для диспетчера. Каждый шаг агента виден в журнале.

## Какую проблему решает и для кого

Ветроэлектростанция заранее сообщает энергосистеме, сколько электроэнергии выдаст по часам, и платит за отклонения
от заявленного. Ветер изменчив, поэтому нужен точный прогноз с оценкой неопределённости и предупреждениями о рисках.
Пользователь — диспетчер станции: утром он видит прогноз на завтра и послезавтра, интервал уверенности, риски
(обледенение, резкий спад) и может спросить агента на естественном языке.

## Что реализовано

- **Прогноз выработки** на сутки D+1 и D+2 от выпуска в день D в 12:00 местного времени: 48 часов, основной прогноз
  и интервал P10–P90, мощность в долях номинала. Обе турбины.
- **Честный backtest по ТЗ:** выпуски 31.01–26.02.2026 покрывают весь февраль. Каждый прогноз использует только
  прогнозы погоды, опубликованные до момента выпуска; время выпуска погоды (`weatherIssuedAt`) есть в каждом ответе
  и всегда не позже момента прогноза. Модель обучена только на данных по 31.01.2026.
- **Цикл агента** (`POST /api/forecast/run`), 6 шагов:
  1. погода у турбины — прогон Open-Meteo, опубликованный до момента прогноза; недоступен → берётся более старый;
  2. прогноз ML — при сбое повтор, каждая попытка в журнале;
  3. проверка — 48 часов подряд, значения 0..1, прогноз внутри P10–P90, погода не из будущего; иначе прогноз отклоняется;
  4. сравнение с предыдущим выпуском — насколько изменился прогноз тех же суток после обновления погоды;
  5. отчёт для диспетчера от LLM с **самопроверкой**: каждое время и процент из текста должны быть в данных,
     иначе отчёт отклоняется и собирается по шаблону;
  6. сохранение — прогноз и журнал шагов в `data/cycles/`.
- **Журнал агента** (`GET /api/agent-log`): шаги, статусы, время выпуска использованных данных.
- **Чат с агентом** (`POST /api/agent/chat`): LLM сама вызывает инструменты — прогноз, версии прогноза, погода, метрики —
  и отвечает только по их данным.
- **Предупреждения:** риск обледенения, штормовое отключение, резкий рост/спад выработки, расхождение погодных моделей.
- **Метрики качества** на отложенном тесте (январь 2026) с двумя бейзлайнами.
- **Веб-интерфейс:** карта турбин, график прогноза с интервалом, сводка и предупреждения, версии прогноза, журнал агента,
  метрики, чат.
- **Результаты backtest в репозитории:** `data/cycles/` — циклы агента за все даты выпуска для обеих турбин, с отчётами LLM.

## Результаты

Факта за февраль 2026 в выданных данных нет (датасет заканчивается 31.01.2026), поэтому точность измерена
на **отложенном тесте — январе 2026**: отдельная модель, обученная по 31.12.2025, прогнозирует январь тем же
способом (выпуск в 12:00, сутки D+1 и D+2). Ошибки — в процентах номинальной мощности, сутки D+1:

| Турбина | MAE | RMSE | Смещение | Покрытие P10–P90 | Бейзлайн «мощность как в момент прогноза» | Бейзлайн «кривая мощности без ML» |
|---|---|---|---|---|---|---|
| t1 | **17.3 %** | 23.6 % | +6.0 п.п. | 83.9 % | 35.9 % | 24.2 % |
| t2 | **18.2 %** | 24.8 % | +7.6 п.п. | 82.5 % | 35.9 % | 24.9 % |

На сутках D+2 MAE — 17.8 % и 18.5 %. Модель точнее бейзлайна «как в момент прогноза» примерно в 2 раза
и бейзлайна «кривая мощности без ML» на 7 п.п. Подробности обучения — [ML/TRAINING.md](ML/TRAINING.md).

**Backtest февраля** (`data/cycles/`): 27 выпусков (31.01–26.02) × 2 турбины = **54 цикла агента, все успешны**.
Все 54 отчёта написала LLM и прошли самопроверку; ни один прогноз не использует погоду, опубликованную позже
момента прогноза; в 26 циклах агент зафиксировал существенное изменение прогноза после обновления погоды.

## Как работает решение

```
выпуск в день D, 12:00 местного
        │
        ├─ ML-сервис: архивные прогнозы ECMWF + GFS + ICON (опубликованы ≤ D 12:00)
        │             → признаки → LightGBM → 48 ч, P10/P50/P90 + автоматический анализ
        │
        ├─ бэкенд-агент: погода у турбины (ECMWF IFS) → проверка → сравнение с выпуском D−1
        │                → отчёт LLM с самопроверкой → сохранение
        │
        └─ интерфейс: график, интервал, предупреждения, журнал шагов агента, метрики, чат
```

Пользовательский сценарий: диспетчер выбирает дату (например, 10.02) и турбину → видит прогноз на 11 и 12 февраля
с интервалом и предупреждениями → открывает журнал и видит, какие данные взял агент и когда они были опубликованы →
нажимает «Пересчитать» и наблюдает шаги агента вживую → спрашивает в чате «будет ли 11 февраля риск обледенения?».

## Технологии

| Часть | Технологии |
|---|---|
| Бэкенд и агент | Kotlin 2.3, Spring Boot 4.1, Spring AI 2.0 (tool calling), Jackson 3, springdoc (Swagger), Java 17 |
| LLM | Ollama, `qwen3:8b` — локально, без внешних API-ключей |
| ML | Python 3.12, FastAPI, LightGBM (среднее и квантили P10/P50/P90), scikit-learn (изотоническая кривая мощности), pandas |
| Фронтенд | React 19, TypeScript, Vite, Recharts, Leaflet |
| Запуск | Docker, Docker Compose, nginx |
| Разработка | AI-агенты Claude Code и Codex; контекст проекта для них — [AGENTS.md](AGENTS.md) |

## Архитектура

```
Браузер ──► frontend (React, nginx :3000) ──/api──► backend (Spring Boot :8080)
                                                     ├─ REST API, Swagger
                                                     ├─ цикл агента и чат (Spring AI) ──► ollama :11434 (qwen3:8b)
                                                     ├─ клиент погоды ──► Open-Meteo Single Runs API (+ кэш data/weather-cache)
                                                     ├─ метрики (отложенный тест ML + SCADA)
                                                     └─ хранилище циклов data/cycles/
                                                            │
                                                            ▼ POST /v1/forecast, GET /v1/evaluation
                                                     ML (FastAPI :8000): модели, кэш погоды Previous Runs, SCADA
```

- Контракт фронт ↔ бэкенд: [backend/src/main/resources/static/openapi.yaml](backend/src/main/resources/static/openapi.yaml).
- Контракт бэкенд ↔ ML: [contracts/ml-service.openapi.yaml](contracts/ml-service.openapi.yaml).
- LLM никогда не считает числа сама: ML-модель считает прогноз, код — сводки и выводы, LLM только выбирает
  инструменты и пересказывает готовые данные.
- Подробно: [docs/architecture.md](docs/architecture.md).

## Установка и запуск

Нужен Docker с Docker Compose. Docker должно быть выделено **не меньше 8 ГБ памяти** (Docker Desktop → Settings →
Resources): LLM `qwen3:8b` с контекстом занимает около 6.5 ГБ. Если памяти меньше — возьмите модель поменьше:
`OLLAMA_MODEL=qwen3:4b docker compose up --build` (около 3 ГБ, ответы проще).

```bash
git clone https://github.com/BAITC-Hacks/hack-cb6a2678-team.git
cd hack-cb6a2678-team
docker compose up --build
```

Первый запуск: сборка образов — несколько минут, загрузка LLM `qwen3:8b` — около 5 ГБ.
Когда сервисы поднимутся:

- интерфейс — http://localhost:3000
- API и Swagger — http://localhost:8080/swagger-ui.html
- ML-сервис — http://localhost:8000/docs

**Без LLM** (быстрее и без 5 ГБ): `docker compose up --build ml backend frontend`. Прогнозы, журналы
и отчёты из сохранённого backtest работают; чат с агентом недоступен, новые циклы пишут отчёт по шаблону.

Ollama в Docker на macOS работает только на CPU и отвечает медленно. Быстрее — нативный Ollama на хосте:

```bash
ollama serve & ollama pull qwen3:8b
OLLAMA_BASE_URL=http://host.docker.internal:11434 docker compose up --build ml backend frontend
```

## Как проверить решение

1. **Прогноз и честность данных.** Откройте http://localhost:3000, выберите дату 10.02 и турбину t1, или:

   ```bash
   curl 'http://localhost:8080/api/forecast?turbineId=t1&date=2026-02-10'
   ```

   `forecastIssuedAt` = `2026-02-10T07:00:00Z` (12:00 местного), точки — сутки 11 и 12 февраля,
   `weatherIssuedAt` раньше `forecastIssuedAt`.

2. **Журнал агента** за этот выпуск (из сохранённого backtest):

   ```bash
   curl 'http://localhost:8080/api/agent-log?date=2026-02-10&turbineId=t1'
   ```

3. **Цикл агента вживую:** кнопка «Пересчитать» в интерфейсе или

   ```bash
   curl -X POST http://localhost:8080/api/forecast/run -H 'Content-Type: application/json' \
        -d '{"turbineId":"t2","date":"2026-02-14"}'
   # повторять, пока status = running:
   curl 'http://localhost:8080/api/agent-log?date=2026-02-14&turbineId=t2'
   ```

4. **Метрики:** `curl http://localhost:8080/api/metrics` — таблица из раздела «Результаты».

5. **Чат с агентом** (нужна LLM):

   ```bash
   curl -X POST http://localhost:8080/api/agent/chat -H 'Content-Type: application/json' \
        -d '{"message":"Какая ожидается выработка t1 на 11 февраля 2026? Есть ли риск обледенения?"}'
   ```

   В ответе — текст и `toolCalls`: какие инструменты вызвал агент.

6. **Повторить весь backtest** (нужны запущенные сервисы; ~10 минут с LLM):

   ```bash
   python3 scripts/backtest.py
   ```

7. **Тесты:** `cd backend && ./gradlew test` (без сети, ML и LLM); `cd ML && python -m pytest tests`.

## Данные и интеграции

| Источник | Для чего |
|---|---|
| Датасет организаторов: SCADA двух турбин, 10-минутные данные 11.03.2023–31.01.2026 (`ML/data/raw/`) | Обучение модели, факт для метрик и бейзлайна |
| Координаты турбин из ТЗ: t1 43.645150, 78.535604; t2 43.643198, 78.538828 | Погода, карта |
| Open-Meteo **Previous Runs API**: архивные прогнозы ECMWF IFS 0.25°, GFS, ICON (кэш в `ML/data/cache/`) | Вход ML-модели. Режим `strict`: для суток D+k берётся прогноз, сделанный не менее чем за k+1 суток |
| Open-Meteo **Single Runs API**: конкретные прогоны ECMWF IFS HRES 9 км (кэш в `data/weather-cache/`) | Погода у турбины для агента: предупреждения, чат. Берётся последний прогон, опубликованный до момента прогноза (задержка публикации — 7 ч с запасом) |
| Ollama, `qwen3:8b` | LLM агента (локально) |

Всё, что нужно для воспроизведения, лежит в репозитории: модели, кэши погоды, датасет, результаты backtest.
API-ключи не нужны.

## Ограничения

- **Факта за февраль 2026 нет в данных**, поэтому точность февральских прогнозов мы проверить не можем — она оценена
  на отложенном январе.
- Модель в среднем **завышает выработку на 6–8 п.п.** номинала; калибровка на декабре уменьшила смещение, но не убрала.
- **Версии прогноза — раз в сутки.** Архив Previous Runs хранит прогнозы с шагом в сутки заблаговременности,
  поэтому внутридневные пересчёты по каждому прогону погоды не сделаны; «повторный расчёт при обновлении данных» —
  это прогноз тех же суток из следующего выпуска.
- **Два источника погоды:** ML обучена на ансамбле Previous Runs, агент для предупреждений использует прогоны ECMWF
  HRES — ветер и температура в них могут немного отличаться.
- **Часовой пояс SCADA** организаторы не указали; ML выбрала UTC+5 по ошибке на валидации (ноябрь–декабрь 2025).
- Турбины в 300 м друг от друга попадают в одну ячейку погодных моделей — погода для них одинаковая.
- **LLM в Docker требует ~6.5 ГБ памяти**; при нехватке процесс модели убивается — чат отвечает 503, а циклы агента
  пишут отчёт по шаблону (прогнозы, журналы и сохранённый backtest работают без LLM).
- **LLM локальная и небольшая (8B):** отчёты фактически точные (самопроверка), но стилистически простые;
  ответы в чате — 5–60 секунд, в Docker на macOS дольше.
- Предупреждение об обледенении — эвристика по температуре и влажности, без данных о подогреве лопастей.
- Установленная мощность турбин неизвестна, поэтому прогноз — в долях номинала, а не в МВт·ч.
