## 1. Название

**Ainalym — финансовая операционная система для торгового бизнеса. Агенты ведут коммерческий цикл. Вы принимаете решения.**
*Ainalym is a financial operations OS for trading businesses. Agents run the commercial cycle. You decide.*

«Ainalym» по-казахски — «полный круг». Первая вертикаль — кейс «Автоматический расчёт заказов поставщикам для пополнения склада»: агенты считают, что и сколько заказать у каждого поставщика, по всем источникам данных компании, объясняют каждое число, а утверждает заказ только менеджер по закупу.

## 2. Проблема и для кого

**Для кого.** Менеджер отдела закупок дистрибьютора электротехники (партнёр — ТОО «Электрокомплект», поставщики IEK и System Electric, склад Алматы). Второй пользователь — финансовый руководитель: ему важно, сколько денег заказ заморозит и когда они уйдут поставщику.

**Проблема.** Сейчас потребность считается вручную в Excel, редко и не в реальном времени. Итог — излишки по одним позициям и дефицит по другим одновременно, а разовые крупные продажи (в том числе одному клиенту) раздувают «среднее» и тянут закупку вверх. Пример на данных партнёра — [`docs/FINANCIAL_EXAMPLE.md`](docs/FINANCIAL_EXAMPLE.md) (появляется вместе с документами соавтора).

**Ценность.** Меньше денег в лишнем запасе, меньше дефицита и упущенных продаж, регулярная закупка по объяснимому расчёту.

**Почему сейчас.** 10 февраля 2026 года на расширенном заседании правительства президент поставил задачу оптимизировать таможенные процедуры с помощью цифровых подходов и искусственного интеллекта без потери контроля. Ainalym не заменяет государственные системы - он готовит для них согласованные данные и делает официальный импорт понятным процессом для предпринимателя: от заказа поставщику до принятого на склад товара и итоговой себестоимости в учёте.

## 4. Как это работает: от входных данных до результата

Основной сценарий как поток данных:

1. **Данные** — выгрузки партнёра (история продаж по документам, помесячные продажи и остатки, товар в пути, кратность/MOQ, сезонность) → таблицы SQLite (`sales_line`, `sales_month`, `stock_month`, `in_transit`, `sku`, `season_index`).
2. **Расчёт** — менеджер запускает расчёт по поставщику или категории (или новое событие ленты — день продаж, снимок остатков, изменение товара в пути — запускает пересчёт затронутых артикулов агентом). Движок по каждому артикулу: очищает ряд от разовых заказов (M4) → восстанавливает спрос в месяцы без товара (M3) → строит прогноз с сезонностью и ростом (M2) → считает потребность за вычетом остатка и товара в пути (M1).
3. **Рекомендации** — список, сгруппированный по поставщикам, с количеством, срочностью и обоснованием по каждой строке (M5).
4. **Проверка и утверждение** — менеджер корректирует количество (исходная рекомендация сохраняется), утверждает заказ поставщику в очереди решений; утверждение привязано к версии. Автоматической отправки поставщику нет.
5. **Записи** — каждое действие агента и решение человека пишется в журнал (`agent_action`, `approval`); утверждённый заказ создаёт обязательства (предоплата 30 % при утверждении, остаток к сроку поставки).
6. **Результат** — черновик заказа поставщику, файл для 1С в форме документа «Заказ поставщику» (xlsx/csv, ключ — «Номенклатура.Код», код 1С), подготовленное письмо поставщику (не отправляется), деньги: сколько заморожено по поставщикам и когда уйдут платежи.

### Методика расчёта

Реализация — `computeNeed` в `src/domain/engine.ts` (детерминированно, количества и деньги — `decimal.js`); запуск по поставщику/категории — `runCalculation` в `src/domain/apply.ts`; параметры поставщика — `src/domain/params.ts`. Обозначения: L — срок поставки (IEK 40 дн, SE 50 дн), R — период пересмотра (30 дн).

1. **Источники (M1).** По артикулу: помесячные продажи (`sales_month`), строки документов продаж (`sales_line`, расходные накладные и события ленты), текущий остаток на 22.09.2026 (`sku.on_hand_qty`, если снимку не больше 31 дня; иначе последний известный остаток на начало месяца из `stock_month` — он обязателен), товар в пути со сроком прибытия в горизонте (`in_transit`), утверждённые ещё не полученные заказы в горизонте, сезонный индекс поставщика (`season_index`) и правило заказа. Товар в пути без даты считается доступным в горизонте. Товар в пути IEK с датой в заголовке колонки («поступление до dd.mm.yyyy») учитывается, только если приходит в пределах L + R. Если нет истории продаж у артикула, который продавался, или нет известного остатка, расчёт по этому артикулу не выполняется и называет причину («не рассчитано: …»), а остальные артикулы считаются дальше. Артикул без продаж за период получает потребность 0 с пометкой «Нет продаж за период». Категория — фильтр запуска (`scope.category`).
2. **Регулярный ряд.** Строки документов группируются по (номер документа, месяц); разовые документы исключаются по порогу, рассчитанному без проверяемого документа (алгоритм ниже). Месяц = `qty_regular`, а если его нет — число из помесячного отчёта (`qty_file`) минус исключённые документы; события ленты (дни продаж, документы жюри) добавляются к своему месяцу. Средний уровень спроса считается только по завершённым месяцам, начиная с `first_sale_ym`: неполный текущий месяц и нули до начала продаж в среднее не входят.
3. **Упущенный спрос (M3).** Подтверждённый месяц дефицита (`stockout_kind=observed`): известный остаток на начало равен 0, а в двух из трёх предыдущих месяцев были продажи. При неизвестном остатке и такой же истории продаж месяц помечается `stockout_kind=inferred`: это предположение, а не наблюдаемый ноль. Оба вида помечаются `stockout=1` и не входят в базовый спрос; отрицательный известный остаток дефицитом не считается. **Базовый спрос = среднее по месяцам без помеченного дефицита**. Обоснование показывает фактический и скорректированный спрос одного артикула и различает подтверждённые и предполагаемые месяцы.
4. **Сезонность (M2).** Индекс календарного месяца: собственный (среднее продаж месяца / базовый спрос), если у артикула ≥ 12 месяцев с продажами без дефицита; иначе индекс поставщика (выручка 2024–2025, нормирована к среднему 1).
5. **Рост (M2).** Продажи последних 6 месяцев / те же 6 месяцев год назад (месяцы дефицита заменены базовым спросом), в пределах ±50 %; если истории не хватает — 1.
6. **Прогноз.** Сумма по дням горизонта L + R: базовый спрос × рост × индекс месяца / 30; разбивка по месяцам — `monthly_forecast`.
7. **Страховой запас.** z × σ_мес / √30 × √L, σ_мес — стандартное отклонение месяцев без дефицита; z = 1,28 при уровне сервиса 90 % (1,645 — 95 %, 2,33 — 99 %).
8. **Потребность (M1).** raw = max(0, прогноз + страховой запас − остаток − товар в пути − утверждённые заказы). Для IEK ненулевая рекомендация = max(ceil(raw), минимум); для SE — ceil(raw / кратность) × кратность.
9. **Срочность.** Покрытие = (остаток + в пути + утверждённые заказы) / (базовый спрос × рост / 30) дней: < L — «критично», < L + R — «скоро», иначе «планово»; рекомендация 0 — «не требуется».
10. **Обоснование (M5).** `rationale_ru` показывает фактический и скорректированный спрос, прогноз, запас, остаток, датированный товар в пути, утверждённые заказы, потребность и правило заказа в единице `sku.unit`, а также наблюдаемые и предполагаемые месяцы дефицита и исключённые разовые документы. `components` сохраняет числа и источники.
11. **Деньги.** Сумма заказа = Σ количество × себестоимость («СС реал», только SE); строки без себестоимости (IEK) не превращаются в 0 — считается их число («Себестоимость не задана»).

Пример (SE `300200745_`, розетка 2-я IP54 Alas Profi 54 белая; расчёт 23.09.2026 на `main` @ `9b01fcb`), обоснование дословно: «фактические продажи 75.906 шт/мес; спрос с учётом дефицита 75.906 шт/мес; сезонность артикула, рост ×0.789; прогноз на 80 дн 193.023 + запас 73.33 − остаток 23 − в пути 120 − утверждённый заказ 0 шт = потребность 126 шт (кратность 6 шт). Ожидаемые поставки: 120 шт прибудет до 11.11». Проверка: 193,023 + 73,33 − 23 − 120 = 123,353 → вверх до кратности 6 → 126; срочность «скоро». Разбор по шагам — `docs/METHODOLOGY_RU.md`.

Если провайдер AI недоступен или вернул ошибку, пограничные решения принимаются по правилам («Правила без LLM»), и это отмечено в результате; расчёт потребности от AI не зависит.

### Ответ поставщика

Когда поставщик отвечает на заказ (например, «Отгрузим 60 %, остальное через 3 недели» — событие ленты `WE-046`, `src/ai/supplier-reply.ts`), агент распознаёт ответ как частичную отгрузку или задержку и готовит предложение: разделить заказ на две поставки (`supplier_split`) или ускорить (`supplier_expedite`). Предложение ждёт решения менеджера в «Проверке»; после утверждения обязательства 30 % / 70 % пересчитываются для каждой части. Всё остаётся черновиком — поставщику ничего не отправляется.

### Алгоритм исключения выбросов

1. Единица анализа — документ продажи в месяце: строки одного документа по артикулу суммируются.
2. Порог каждого документа = **max(20 единиц, min(3 × медиана месячных продаж, 5 × p95 количества в документе))**. p95 считается по суммам документов без проверяемого документа (leave-one-out); при менее шести документах вместо p95 берётся медиана остальных документов. `npm run etl` сохраняет справочный p95 по суммам документов, а расчёт порога использует текущие документы, включая новые события.
3. Документ с количеством > порога — **разовый крупный заказ**: он не входит в регулярный ряд, попадает в `components.outliers_excluded` (номер, месяц, количество, порог) и в текст обоснования («исключены разовые документы: …»).
4. Решение по документу фиксируется в `outlier_doc`: `excluded` — исключать, `kept` — вернуть в расчёт; пограничные документы воркер отправляет на типизированное решение (`one_off_order`) или менеджеру (`outlier_review`); в режиме «Правила без LLM» — детерминированное правило.
5. Крупные продажи одному клиенту: в выгрузках нет идентификатора клиента (только номера документов), поэтому такая продажа ловится на уровне документа.
6. Пример (эталон `oneoff`, IEK `010500008_` ВА47-29 25А): медиана месяца 14 502 шт, p95 документа 144 шт → порог max(20, min(43 506, 720)) = 720 шт; исключены 14 документов от 807 до 7 488 шт, в том числе `20000099834` на 7 488 шт; добавленный жюри документ на 5 000 шт тоже исключается, регулярный спрос меняется на 0,00 % (`node scripts/scenario.mjs`, строка M4). Если крупный документ — регулярный оптовый клиент, менеджер возвращает его в расчёт (`kept`).

### Модели

Задачи распределяются по классам. Рассуждения — разбор событий и ответов поставщиков, черновики писем и сводок расчёта — идут в модель OpenAI для рассуждений (`OPENAI_REASONING_MODEL`); быстрые задачи — метки намерения, короткие подсказки — в быструю модель (`OPENAI_FAST_MODEL`); голосовой помощник — в OpenAI Realtime (`gpt-realtime-2.1`). Хостинг-демо работает с моделью рассуждений `gpt-5.5`, быстрой моделью `gpt-5.4-mini` и `gpt-realtime-2.1`. Если переменные не заданы, код берёт `gpt-5-mini` и `gpt-4o-mini`. Без ключей всё работает в локальном режиме правил («Локальный режим»). Расчёт потребности (M1–M5) от моделей не зависит.

## 6. Архитектура

```
fixtures/partner/*.xlsx ──npm run etl──▶ SQLite (src/db/schema.sql)
                                            │
лента событий (world_event) ──▶ воркер агентов (src/ai/worker.ts) ──▶ журнал (agent_run, agent_action)
                                            │
                     расчётный движок (src/domain/engine.ts: M4 → M3 → M2 → M1)

      рекомендации по поставщикам (M5) ──▶ очередь решений (proposal) ──▶ утверждение человека (approval)
                                            │

```
По контракту все записи идут через API route handlers Next.js (`src/app/api/**`), ключи провайдеров — только на сервере. Стрелки описывают контракт; что уже работает — `docs/TASK_MAP.md`.

Ответ поставщика «Отгрузим 60 %, остальное через 3 недели» теперь становится решением агента: он выделяет долю, срок и затронутые позиции, создаёт в очереди предложение разделить заказ или ускорить поставку, а в ленте пишет понятное последствие. В демо это событие идёт после прежних 45; повтор по источнику не создаёт второе предложение. Только утверждение менеджера делит заказ и его платежи 30 % / 70 % на две части. Письма поставщику остаются черновиками и не отправляются автоматически.

## Документы

Подробно — [`docs/DOCUMENTS_RU.md`](docs/DOCUMENTS_RU.md). Сервис принимает счёт поставщика (загрузка файла или демонстрационный пример), сверяет его с заказом по коду 1С, артикулу и названию, а после акта приёмки — трёхсторонне (заказ · счёт · приёмка). По маршруту поставщика (внутри РК, ЕАЭС, третьи страны) он показывает пакет документов: что есть, чего не хватает, где расхождение. IEK и Systeme Electric по умолчанию идут маршрутом ЕАЭС (уточняется у менеджера): заявление о ввозе (форма 328.00), НДС при импорте 12 % (форма 320.00), статистическая форма; декларация на товары для ЕАЭС не нужна. Черновики, которые готовит агент (например, форма 328.00), помечены «Черновик подготовлен агентом — не отправлен». Подключения к «Кеден», ЭСФ или 1С нет: сервис ничего не подаёт и не отправляет.

Проверка за минуту (после `npm run demo:reset` и `npm run dev`; наблюдение 12:02Z на `main` @ `4de3022`, без ключей):

```sh
curl -sS -X POST http://localhost:3000/api/documents -H 'Content-Type: application/json' -d '{"fixture":"iek_invoice_demo.xlsx"}'
# в ответе .document.po_id — заказ, с которым сопоставлен счёт (дальше <po_id>)
curl -sS 'http://localhost:3000/api/documents?po_id=<po_id>'
curl -sS http://localhost:3000/api/orders/<po_id>/package
```

Демонстрационный счёт привязывается к заказу `PO-DEMO-IEK-DOCUMENTS` (10 строк; создаётся при первой загрузке), если нет заказа, который покрывает те же строки; `GET /api/documents` без `po_id` показывает весь входящий список. Ожидается: документ `extraction_mode: deterministic`, состояние `discrepancy`; сверка — 10 строк совпали, 2 расхождения (`010300001_` — количество 60 против 100, `010300002_` — цена), сумма счёта 354 750,00 против заказа 392 500,00 KZT; пакет — маршрут `eaeu` («задан по умолчанию, уточните у менеджера»), счёт `discrepancy`, форма 328.00 `draft`, остальные пункты `missing`. Счёт демонстрационный: 10 реальных кодов каталога IEK, цены и количества условные (`fixtures/PROVENANCE.md`).
