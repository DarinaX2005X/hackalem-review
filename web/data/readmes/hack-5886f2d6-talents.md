# Поток — граф денежных переводов

**Кого из 2248 клиентов проверять первым и почему?** «Поток» помогает AML-аналитику банка восстановить наблюдаемую структуру переводов: увидеть возможные роли клиентов, сообщества, приоритеты проверки и следующие действия.

Проект команды **TALENTS** для HackAlem AI. Решение работает локально: **Parquet → Python → C++ → веб-интерфейс и три CSV**. Каждая роль — гипотеза для проверки человеком, каждый балл сопровождается объяснением.

Кейс: «Граф денег: восстановление финансовой структуры организованной группы по транзакционной сети».

**Итоговая поставка:** C++ **1.3.0**, **2248 клиентов**, **3119 направленных связей**, **4840 переводов**, **88 кластеров**, **топ-20**. Полный рассчитанный пакет находится в [frontend/public/data](frontend/public/data/).

## Проблема и пользовательский сценарий

Основной пользователь — AML-аналитик / специалист финансового мониторинга банка. По списку исходных клиентов и выгрузке переводов ему нужно определить, какие связи и клиентов исследовать первыми, и объяснить свой выбор.

1. Аналитик передаёт три Parquet-файла пайплайну через локальную папку.
2. Одна команда проверяет данные, строит граф, выделяет сообщества и вызывает C++.
3. Аналитик открывает очередь проверки, находит клиента по `gid`, рассматривает входящие и исходящие связи.
4. Карточка показывает гипотезу роли, причины приоритета, ограничения данных и 1–3 следующих действия: например, запросить продолжение исходящих за границей обхода.
5. Аналитик сравнивает структурные сценарии исключения top-N и сохраняет три CSV того же расчёта для дальнейшей проверки.

Загрузка Parquet выполняется через CLI; интерфейс читает подготовленный пакет. Запросы в банк или правоохранительные органы автоматически не отправляются.

## Установка и полный пересчёт

Для расчёта нужны **Python 3.12, CMake ≥3.16 и C++17-компилятор** (GCC/Clang/MSVC). `nlohmann/json` включён в репозиторий. GPU, платные API, база данных, `.env` и ключи не требуются.

Все следующие команды выполняются **из корня репозитория**. Установка и сборка выполняются заранее и не входят в замер пакетного расчёта.

### 1. Python-зависимости

Windows / PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\Activate.ps1
```

Если политика PowerShell запрещает активацию, вместо `python` в дальнейших командах используйте `.\.venv\Scripts\python.exe`.

Linux / macOS:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
source .venv/bin/activate
```

Версии зависимостей закреплены в [requirements.txt](requirements.txt); для установки нужен доступ к PyPI либо заранее подготовленные пакеты.

### 2. C++-ядро

```sh
cmake -S engine -B engine/build -DCMAKE_BUILD_TYPE=Release
cmake --build engine/build --config Release --parallel 2
```

На Windows есть альтернативный скрипт, который находит инструменты в PATH или установленном CLion:

```powershell
powershell -ExecutionPolicy Bypass -File engine/build.ps1
```

Пути бинарника: MinGW/Ninja — `engine/build/engine.exe`, Visual Studio — `engine/build/Release/engine.exe`, Linux/macOS — `engine/build/engine`. Пайплайн автоматически проверяет эти пути. Подробности — [engine/README.md](engine/README.md).

### 3. Одна команда от сырых данных до результата

```sh
python pipeline.py
```

Вход по умолчанию: `TechTask/data(1)/data`. Выход: `out/` — три CSV, `input.json`, `result.json`, `graph.json`, отчёт проверки и manifest. Успех: код завершения `0`, сообщение `status: complete`; ожидаются 2248 узлов, 3119 рёбер, 88 кластеров и 20 строк топа.

Чтобы **пересчитать и проверить пакет для интерфейса**, используйте вместо предыдущей команды:

```sh
python prepare_ui_data.py
```

Она выполняет весь пайплайн, обновляет `frontend/public/data/` и дополнительно проверяет результат, исходные файлы и использованный бинарник. Ожидаются `complete` и `passed`. После успеха запустите `npm run dev` в папке `frontend` или нажмите «Обновить файлы» в открытом UI.

На Windows перед пересчётом остановите Vite через `Ctrl+C`: ранее наблюдалась блокировка файла. Публикация повторяет временные ошибки Windows 5/32/33 с общим бюджетом до 3 секунд; постоянная ошибка остаётся ошибкой. Для `npm run preview` после пересчёта требуется новая `npm run build`, поскольку preview читает копию из `dist/data`.

Другой вход, выход или конфигурация:

```sh
python pipeline.py --data "TechTask/data(1)/data" --core engine/build/engine.exe --out out
python pipeline.py --core-config overrides.json --top 50 --out out-custom
```

Замените путь бинарника для своей системы. Конфигурация по умолчанию — [engine/config/default.json](engine/config/default.json); для данной выгрузки сохраняйте `max_depth=4`. Указанный в `--core-config` файл должен существовать.

## Правила ролей и приоритета

Правила применяются ко всем клиентам одинаково. Самопереводы сохраняются в исходных данных, но исключаются из признаков ролей и приоритета.

Обозначения: `I/O` — наблюдаемые входящие/исходящие суммы без самопереводов; `D_in/D_out` — число разных внешних отправителей/получателей; `V=max(I,O)`; `P` — число уникальных внешних контрагентов; `S` — число других seed, из которых клиент достижим по направлению рёбер; `B` — число внешних кластеров среди его непосредственных контрагентов.

`Q(X)` — доля положительных значений признака по всему графу, не превышающих X. Для нуля Q=0. `sat(x,t)=min(1,x/t)`. Seed не засчитывается сам себе даже при цикле.

### Выбор основной роли

Первое сработавшее правило в таблице определяет основную роль; остальные сохраняются в `role_candidates`.

| Порядок | Роль | Условие по умолчанию |
|---:|---|---|
| 1 | `coordinator` — структурно связующий узел | `S≥3`, `B≥2`, `D_in≥2`, `D_out≥2`, `Q(V)≥0.75` |
| 2 | `consolidator` — признаки сбора средств | `D_in≥3`, `D_in>D_out`, `I>0`, `Q(I)≥0.5` |
| 3 | `distributor` — признаки распределения | `D_out≥5`, `D_out>D_in`, `O>0`, `Q(O)≥0.5` |
| 4 | `transit` — признаки транзита | Не seed, `depth<4`, обе степени положительны, `I>0`, `0.8≤O/I≤1.2` |
| 5 | `terminal` — гипотеза конечного получателя в выгрузке | Не seed, `depth<4`, `D_in>0`, `I>0`, исходящая степень **включая петли** равна 0 |
| 6 | `peripheral` — недостаточно признаков | Ни одно предыдущее правило не выполнено |

На `depth=4` отключены `terminal` и `transit`; у seed не используется отношение входящих/исходящих для этих ролей. `peripheral` не означает отсутствие риска, а `coordinator` не устанавливает организатора группы.

### Оценки и объяснения

`role_score ∈ [0,1]` — **сила соответствия эвристическому правилу, не калиброванная вероятность**. Она зависит от числа контрагентов, достижимости, перцентилей сумм и близости входа/выхода для транзита. Поправка на качество наблюдения: ×0.8 для границы обхода и ×0.85 для seed; при обоих условиях применяются оба множителя. Точные формулы для всех ролей находятся в [спецификации ядра](engine/README.md#сила-соответствия-роли).

`priority_score ∈ [0,1]` рассчитывается отдельно от роли:

```text
priority = 0.35 × sat(S, 5)
         + 0.30 × Q(V)
         + 0.20 × Q(P)
         + 0.15 × sat(B, 3)
```

Топ сортируется по неокруглённому приоритету, при равенстве — по возрастанию **числового** `gid`. `evidence` объясняет роль, `why` — очередь проверки, `priority_breakdown` хранит вклад каждого сигнала. `next_actions` задаёт 1–3 следующих проверки с учётом недостающих наблюдений. Пороговые значения и веса сохраняются в `meta.config` каждого расчёта.

### Кластеризация

Louvain применяется к **неориентированной взвешенной проекции**: вес пары равен сумме переводов в двух направлениях. Петли исключаются только из проекции, изолированные клиенты получают отдельные кластеры. `seed=42`, `resolution=1.0`, порядок данных фиксирован. Исходный граф, признаки ролей и достижимость сохраняют направление переводов.

Внутренний оборот кластера считается по исходным направленным рёбрам один раз, включая петли. Лидеры — до пяти клиентов по приоритету; `hypothesis` описывает возможное назначение по составу ролей и ограничениям данных. Кластер не является доказанной организованной группой.

## Измеренная польза и отличие подхода

Отбор учитывает не только объём, но и связь нескольких исходных клиентов, внешние кластеры и число контрагентов. Пользователь получает объяснение каждого выбора и может сравнить его с простой альтернативой.

**Эксперимент на всех 2248 клиентах:** при одинаковом N виртуально исключили выбранные узлы и их связи. Исходная крупнейшая слабая компонента — 1877 клиентов.

| N | Крупнейшая компонента после отбора по приоритету | После отбора по объёму |
|---:|---:|---:|
| 1 | 1782 | 1782 |
| 3 | 1655 | 1705 |
| 5 | 1561 | 1620 |
| 10 | **1420** | **1502** |

Для N=10 наш отбор уменьшает крупнейшую компоненту на **457 клиентов**, выбор по объёму — на **375**: разница **82 клиента** при одинаковом числе выбранных карточек. Одновременно выбор по объёму охватывает больше прошлых операций: **103,37 млн KZT против 88,06 млн KZT**. Преимущество по одной метрике не переносится автоматически на другую.

Все восемь сценариев и baseline независимо сверены с Python/NetworkX. Повторить сравнение:

```sh
python engine/tests/benchmark_benefit.py --engine engine/build/engine.exe --require-engine-resilience --runs 5
```

Вновь используйте путь бинарника своей системы. Полная [методика, таблица, охват seed и ограничения](docs/EVIDENCE.md).

**Граница вывода:** это структурный эксперимент на неполной наблюдаемой сети. Роли, баллы и кластеры после исключения не пересчитываются. Направление игнорируется только для слабой связности; суммы и рёбра сохраняют направления. Исключение в модели не доказывает прекращение переводов, а прошлый оборот не является предотвращённым ущербом. Новизна продукта — сочетание объяснимой очереди, учёта неполноты и проверяемого сравнения стратегий; мировой новизны графовых алгоритмов не заявляем.

| Аналитическое ядро | C++17, STL, CMake, nlohmann/json 3.12.0 | Направленная достижимость, роли, приоритет, объяснения, следующие действия, устойчивость |

| Проверки | pytest, Python unittest, Node test runner/tsx, JSON Schema, независимый NetworkX | Контракты, крайние случаи, согласованность данных и интеграция |

Версии Python закреплены в [requirements.txt](requirements.txt), версии frontend — в [package-lock.json](frontend/package-lock.json). Код, лицензии и происхождение компонентов раскрыты в [THIRD_PARTY.md](THIRD_PARTY.md).

```mermaid
flowchart LR
    A["3 исходных Parquet"] --> B["Python: проверки и метрики"]
    B --> C["Louvain: кластеры"]
    C --> D["input.json"]
    D --> E["C++: роли, приоритет, объяснения, устойчивость"]
    E --> F["result.json"]
    F --> G["Python: валидация и экспорт"]
    G --> H["3 CSV + graph.json + manifest"]
    H --> I["React: граф и очередь проверки"]
```

Python вызывает `engine input.json result.json`. В JSON `gid`, `src`, `dst` — строки канонического int64; соединение результатов идёт по `gid`, без преобразования в JavaScript Number. UI отображает рассчитанные значения и не пересчитывает роли. Контракты: [Python/UI](CONTRACT.md), [C++](engine/CONTRACT.md), [устойчивость](team/RESILIENCE_CONTRACT.md).

Публикация пишет manifest последним, но не является атомарной заменой всего каталога. UI сверяет SHA-256 graph и трёх CSV, а также повторно читает manifest; несогласованный пакет отклоняется. Два процесса с одним `--out` одновременно запускать нельзя. JSON/CSV опубликованного пакета отмечены в `.gitattributes` для сохранения байтов и целостного разрешения конфликтов.

**AI и внешние сервисы.** Все три участника использовали OpenAI Codex как AI-агента при разработке, тестировании и подготовке документации. В работающем продукте используются графовые алгоритмы и открытые эвристики; обученная ML-модель и внешний LLM API не используются. Данные клиентов не обогащаются внешними источниками, облачный кластер и API-ключи не нужны.

## Данные, интеграции и выходные файлы

Предоставленные организаторами обезличенные данные находятся в `TechTask/data(1)/data/`, исходный стартер — в `TechTask/starter(1)/starter/`, Word-ТЗ — в [TechTask](TechTask/). Python развивает функции загрузки, построения графа и базовых метрик из стартера в модуле `hackalem/data.py`. Обязательные проверки: уникальность gid и направленных пар, концы рёбер, типы, глубины, конечность сумм, точное число транзакций и суммы по каждой паре с допуском 0,01 KZT.

| Источник | Строк | Поля |
|---|---:|---|
| `nodes.parquet` | 2248 | `gid, depth, is_seed` |
| `edges.parquet` | 3119 | `src, dst, sum_kzt, n_tx, depth` |
| `transactions.parquet` | 4840 | `src, dst, date, sum_kzt` |

Период — июль 2026; 81 seed; обход только по исходящим переводам на четыре колена; только внутрибанковские операции от 5000 KZT. Все узлы, включая 19 изолированных seed, включены до добавления рёбер. Поэтому полный граф содержит **35 слабых компонент: 16 с рёбрами и 19 одиночных**, а не только 16 компонент из описания связанной части. 88 Louvain-кластеров — другой вид разбиения.

Схемы обязательных CSV фиксированы:

| Файл | Строк данных | Колонки в порядке выгрузки |
|---|---:|---|
| [nodes_roles.csv](frontend/public/data/nodes_roles.csv) | 2248 | `gid, role, role_score, cluster_id, priority_score, evidence` |
| [clusters.csv](frontend/public/data/clusters.csv) | 88 | `cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis` |
| [top_nodes.csv](frontend/public/data/top_nodes.csv) | 20 | `rank, gid, role, priority_score, why` |

CSV: UTF-8, разделитель — запятая; `top_gids` — JSON-массив строк внутри ячейки. В CSV gid записан точным десятичным int64 без `.0`; при чтении сохраняйте его строкой или int64, не float. `evidence` и `why` — непустые объяснения до 200 Unicode-символов. Для каждого клиента ровно одна основная роль, обе оценки в диапазоне 0–1.

Дополнительные артефакты: `input.json` — вход ядра; `result.json` — его исходный ответ; `graph.json` — данные UI; `validation.json` — проверка исходных данных; `run_manifest.json` — конфигурация, версии, времена и SHA-256 исходников, бинарника и артефактов. Локальные логи `core.*.log` не включены в Git. Данные и синтетические gid предоставлены для хакатона; команда не заявляет авторство датасета.

## Ограничения

- У 444 клиентов `depth=4`: исходящие за границей выгрузки неизвестны. Входящие seed неполны; полные балансы, другие банки, другие периоды и суммы ниже порога недоступны.
- Нет размеченных ролей. `role_score` не является проверенной вероятностью, accuracy/precision/recall не измерены. Достижимость не устанавливает хронологию и происхождение конкретных денег.
- Временной транзит за 1–2 дня, автоматический поиск повторяющихся маршрутов/циклов, отдельная ML-детекция аномалий и чат-ассистент не реализованы. Даты транзакций загружаются, но не используются для подтверждения сквозного движения средств.
- Экономия рабочего времени AML-аналитика не измерена. Автоматические проверки и браузерная приёмка описаны в отчётах; [замер с человеком](team/USABILITY_CHECK.md) и новое подтверждение сохранения трёх CSV на диск пока не получены.
- Текущая версия рассчитана на пакетную локальную обработку. Нет потокового сервиса, авторизации пользователей и промышленной банковской интеграции; JSON и граф находятся в памяти. Большой JS-бандл даёт предупреждение Vite при сборке.
- Синтетические файлы `examples/` используются в тестах и не заменяют полную поставку. Явный режим `python pipeline.py --demo --out out-demo` запускает отдельную Python-эвристику с меткой demo; автоматического переключения на неё при ошибке C++ нет.

## Развитие и масштабирование до 1 млн узлов

Текущая сложность направленной достижимости при N клиентах, M рёбрах и S seed — `O(S·(N+M))`. Новый блок устойчивости добавляет `O(N log N + 9·(N+M))`. Точные ограничения памяти и сортировок — в [описании ядра](engine/README.md#производительность-и-масштабирование).

| Ограничение текущей версии | Следующий технический шаг | Как проверять результат |
|---|---|---|
| Parquet/JSON и Python-граф целиком в памяти | Потоковая агрегация Arrow/DuckDB, компактные CSR-массивы и обмен Arrow/Parquet | Время и пиковая RAM на 100 тыс. и 1 млн узлов |
| Отдельный BFS для каждого seed | Битовые наборы достижимости по конденсации сильно связных компонент; при необходимости приближения | Совпадение с точным эталоном на контрольных графах, цена памяти |
| Все узлы загружаются в браузер | Серверная выдача окрестностей, агрегаты сообществ, уровни детализации | Время открытия карточки и объём ответа |
| Эвристики без разметки | Проверка гипотез предметными экспертами, временные признаки, версионирование правил | Размеченная выборка, ошибки и время решения задач аналитика |
| Локальный инструмент | Контроль доступа, аудит действий и подключение к разрешённым банковским выгрузкам | Пилот с AML-командой и проверка требований организации |

Это план развития; миллион узлов и промышленный пилот ещё не испытывались. Предельное время пять минут на новом масштабе требует отдельного подтверждения.
