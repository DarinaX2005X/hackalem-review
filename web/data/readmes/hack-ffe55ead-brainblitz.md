# Аким на 5 часов

Учебный AI-симулятор управления городским бюджетом.

**100 условных единиц → 5 решений → последствия для районов → AI-разбор → пересмотр решения.**

Пользователь выбирает городские инициативы, распределяет ограниченный бюджет и получает **Astana Quality of Life Score**: итоговую оценку сценария с изменениями показателей районов, сохраняющимися проблемами и объяснением компромиссов.

Например, перенос одной школы из Есиля в Нуру при одинаковых расходах повышает Score с **53,83 до 55,07** и уменьшает число критических показателей с двух до одного. При этом средняя оценка города немного снижается — симулятор помогает понять, почему итог всё равно улучшился.

**Статус:** реализован локальный MVP с интерфейсом, математической моделью, серверной валидацией и OpenAI-интеграцией. Зафиксированные проверки: **285 Python-тестов и 12 браузерных тестов**. Живые AI-разборы сценариев A/B проверены отдельно; сведения о версиях и границах проверок приведены ниже.

**Перед финальной сдачей остаётся закрыть расхождение в правиле направлений и провести полную репетицию защиты.**

## Проблема и пользователь

Транспорт, озеленение, социальная инфраструктура, безопасность и городские сервисы конкурируют за один бюджет. Решение может улучшить среднее значение по городу, но оставить критические потребности отдельного района нерешёнными.

Симулятор позволяет исследовать такие ситуации в коротком воспроизводимом упражнении: выбрать меры, увидеть последствия, прочитать объяснение и проверить другую комбинацию.

Основная учебная аудитория — студенты и слушатели программ городского управления, урбанистики и экономики. Преподаватель может использовать приложение для обсуждения бюджетных решений; управленец или аналитик — для знакомства с учебной моделью компромиссов.

Польза текущего продукта:

- одинаковые исходные условия позволяют сопоставлять решения;
- ограничения проверяются автоматически;
- последствия видны по отдельным районам и показателям;
- AI объясняет конкретный рассчитанный сценарий;
- повторная попытка позволяет проверить собственную гипотезу.

**Границы применения:** данные синтетические, стоимости и эффекты условные. Astana Quality of Life Score — учебный индекс, а не официальный показатель или прогноз развития Астаны. Образовательная эффективность, спрос и готовность организаций использовать продукт пока не подтверждены исследованием.

## Основной сценарий

1. Открыть исходные показатели пяти районов и базовый Score **52,56**.
2. Выбрать ровно пять мероприятий и районы для локальных мер.
3. Проверить стоимость и остаток бюджета **100**.
4. Получить понятную причину отказа, если набор нарушает правила.
5. Рассчитать итоговый Score, изменения районов и критические показатели.
6. Получить AI-разбор сильных сторон, рисков и основного компромисса.
7. Изменить решение и повторить расчёт.

При изменении выбора предыдущий результат помечается как устаревший. Запоздалый ответ старой попытки не подменяет результат новой.

## Данные и правила

Источник модели — предоставленный для задачи документ «Датасет районов». Машиночитаемые данные находятся в:

- [data/districts.json](data/districts.json) — районы, исходные показатели, веса и доли населения;
- [data/measures.json](data/measures.json) — мероприятия, цены, эффекты, лаги, конфликты и синергии.

Сервер проверяет целостность данных при запуске и использует неизменяемую конфигурацию. Каждая попытка рассчитывается от исходного состояния: эффекты предыдущих запросов не накапливаются.

| Параметр | Значение |
| --- | --- |
| Бюджет | 100 условных единиц для всех пользователей |
| Районы | Есиль, Алматы, Сарыарка, Байконур, Нура |
| Направления | Транспорт, экология/озеленение, соцсфера, безопасность, сервисы |
| Показатели | 10; от 0 до 100, больше — лучше |
| Каталог | 14 мероприятий |
| Горизонт | 8 кварталов |
| Число решений | Ровно 5 |
| Остаток бюджета | Отображается, бонуса к Score не даёт |

Сервер применяет следующие правила:

1. Стоимость набора не превышает 100.
2. Выбрано ровно пять мероприятий.
3. Каждое мероприятие встречается не более одного раза.
4. Для районной меры указан существующий район.
5. Для городской меры район отсутствует или равен `null`; эффект действует на все районы.
6. В текущей версии выбрана ровно одна мера каждого из пяти направлений.
7. Несовместимые мероприятия запрещены.
8. Порядок решений не влияет на результат.
9. Невалидный набор возвращает причину отказа без Score.

**Известное расхождение требований.** Исходный документ допускает не более двух мероприятий одного направления. Текущие API и интерфейс реализуют более строгое правило: по одной мере каждого из пяти направлений.

Поэтому исходные примеры стоимостью **95** и **61**, содержащие по две меры одного направления, сейчас отклоняются с `CATEGORY_COVERAGE`. Перед окончательной сдачей необходимо подтвердить допустимость ужесточения у организаторов либо согласованно обновить правила, интерфейс, контракт и тесты. Полное соответствие исходному правилу пока не заявляется.

### Несовместимости и синергии

| Несовместимые меры | Ограничение |
| --- | --- |
| M1 и M3 | Запрещены вместе независимо от района |
| M4 и M7 | Запрещены в одном районе |
| M5 и M13 | Запрещены в одном районе |

| Пара с синергией | Фиксированный бонус |
| --- | --- |
| M1 + M2 | T1 +2 в районе M1 |
| M10 + M12 | B1 +2 в районе M10 |
| M5 + M6 | E2 +2 в районе M5 |

Бонусы синергий не масштабируются лагом. При текущем правиле категорий пары M1+M2 и M5+M6 недоступны через API; они сохранены в исходной модели и проверяются отдельно на уровне расчётных функций.

## Расчёт Score

Расчёт выполняется Python-кодом по фиксированной модели:

```text
realized_effect = full_effect × (8 − lag) / 8

new_indicator =
    clip(initial_indicator + sum(realized_effects) + synergies, 0, 100)

district_score = sum(weight × new_indicator)

city_average = sum(population_share × district_score)

critical_count =
    число пар «район × показатель» со значением строго меньше 40

Score = 0.7 × city_average + 0.3 × min(district_score) − critical_count
```

Формула учитывает средний результат города, положение слабейшего района и количество критических дефицитов.

| Показатель | T1 | T2 | E1 | E2 | S1 | S2 | B1 | B2 | C1 | C2 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Вес | 0.10 | 0.10 | 0.09 | 0.11 | 0.11 | 0.11 | 0.09 | 0.09 | 0.10 | 0.10 |

| Район | Доля населения | Исходная оценка |
| --- | --- | --- |
| Есиль | 0.27 | 62.99 |
| Алматы | 0.24 | 57.06 |
| Сарыарка | 0.20 | 54.65 |
| Байконур | 0.13 | 56.63 |
| Нура | 0.16 | 49.18 |

Базовое среднее — **56.8624**, слабейший район — **Нура**, критических показателей — **2**.

**Базовый Score: 52.55768**, отображение в интерфейсе — **52,56**.

Особенности расчёта:

- ограничение показателей диапазоном 0–100 применяется один раз, после суммирования эффектов и синергий;
- значение ровно 40 не является критическим;
- промежуточные результаты не округляются;
- итоговый Score дополнительно не ограничивается диапазоном 0–100;
- интерфейс округляет числа только для отображения;
- транспортные и экологические показатели уже приведены к шкале «больше — лучше» и повторно не инвертируются.

## Архитектура и роль AI

**Backend:** Python, FastAPI, Pydantic, `httpx`.  
**Frontend:** HTML, CSS и JavaScript без обязательных внешних CDN.  
**Данные:** версионируемые JSON-файлы.

Один FastAPI-процесс обслуживает интерфейс и API. Для локального MVP не требуются база данных и авторизация.

```text
Выбор пользователя
        │
        ▼
/api/simulate → проверка правил → Python-расчёт → числа в интерфейсе
        │
        └─ после успешного расчёта:
           /api/analyze → повторная проверка и расчёт
                        → OpenAI → проверка ответа → объяснение
```

**Python отвечает за числа:** стоимость, допустимость набора, эффекты, изменения показателей и Score. Клиент передаёт только ID выбранных мероприятий и районов.

**AI отвечает за интерпретацию:** итог, сильные стороны, сохраняющиеся проблемы, компромисс и вопрос для следующей попытки. AI получает результат текущего расчёта; история попыток и автоматический поиск оптимального сценария не реализованы.

Используется **OpenAI Responses API** со Structured Outputs. Модель задаётся через `AI_MODEL`; значения по умолчанию нет. Для зафиксированной живой приёмки использована `gpt-4.1`.

Сервер проверяет:

- структуру и допустимые поля ответа;
- ограничения длины;
- существование ссылок на факты в результате расчёта;
- корректность формата ответа провайдера.

Числовые поля итогового ответа формируются сервером. AI не может заменить Score собственным числом.

Проверка структуры и ссылок не гарантирует правильную интерпретацию. Ключевые выводы живых A/B проверены вручную; качество на широком наборе сценариев ещё предстоит оценить.

При отказе, timeout или некорректном ответе AI интерфейс сохраняет рассчитанные показатели и показывает статус недоступности. Общий предел ожидания по умолчанию — 12 секунд, автоматических повторов нет.

### API и состояние реализации

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/config` | Бюджет, районы, каталог, правила, версии и базовый Score |
| POST | `/api/simulate` | Валидация и расчёт сценария |
| POST | `/api/analyze` | Повторная проверка и расчёт, затем AI-разбор |
| GET | `/health` | Проверка доступности приложения |

Оба POST принимают один формат:

```json
{
  "selections": [
    {"measure_id": "M1", "district_id": "esil"},
    {"measure_id": "M4", "district_id": "saryarka"},
    {"measure_id": "M7", "district_id": "nura"},
    {"measure_id": "M10", "district_id": "esil"},
    {"measure_id": "M12", "district_id": null}
  ]
}
```

Ответ `/api/simulate` содержит `SimulationResult`: версии, нормализованные решения, стоимость, остаток, Score до/после, районные изменения, критические показатели, эффекты и синергии.

Невалидный запрос получает HTTP 422:

```json
{
  "detail": [
    {
      "code": "BUDGET_EXCEEDED",
      "message": "Стоимость решений 107 превышает бюджет 100 на 7 единиц.",
      "path": ["selections"],
      "context": {
        "budget": 100,
        "total_cost": 107,
        "over_by": 7
      }
    }
  ]
}
```

Возвращается одна первая ошибка. Score отсутствует, провайдер AI не вызывается.

Недоступность AI для допустимого набора возвращается отдельно: HTTP 200, `status="unavailable"`, причина в `unavailable_reason`. Математический результат при этом сохраняется.

Полные схемы и порядок проверок описаны в [API-контракте](docs/api-contract.md).

## Запуск и конфигурация

Для воспроизведения на Windows рекомендуется **Python 3.12**: чистая установка проверена с CPython **3.12.14**. AI-адаптер использует возможности Python 3.11 и новее.

Нужен современный браузер. Node.js требуется только для дополнительных браузерных тестов, но не для запуска приложения.

### Получение проекта

При первом запуске:

```sh
git clone --branch main https://github.com/BAITC-Hacks/hack-ffe55ead-brainblitz.git
cd hack-ffe55ead-brainblitz
```

Для приватного репозитория необходим доступ через GitHub. Следующие команды выполняются из корня проекта.

### Windows — установка и запуск без AI

В PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check

$env:AI_ENABLED = 'false'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

### macOS / Linux — установка и запуск без AI

В bash или zsh:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check

AI_ENABLED=false .venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

После запуска:

- [Приложение](http://127.0.0.1:8000/) — интерфейс с реальными расчётами.
- [Документация API](http://127.0.0.1:8000/docs) — интерактивные запросы.
- [Конфигурация](http://127.0.0.1:8000/api/config) — исходные данные и правила.
- [Проверка сервера](http://127.0.0.1:8000/health) — `{"status":"ok"}`.

Открывайте приложение **без `?demo=1`**. Сервер одновременно обслуживает frontend и backend; отдельная сборка интерфейса не нужна. Остановка сервера — `Ctrl+C`.

Без AI доступны все математические расчёты. Успешный `/health` подтверждает работу приложения, но не доступ к OpenAI.

| `AI_ENABLED` | `true` включает AI, `false` явно отключает; по умолчанию `true` |
| `AI_API_KEY` | Секретный ключ, доступный только backend |
| `AI_MODEL` | Обязательный ID модели; значения по умолчанию нет |
| `AI_BASE_URL` | По умолчанию `https://api.openai.com/v1` |
| `AI_TIMEOUT_SECONDS` | Общий предел ожидания; по умолчанию `12` |

**Настройки читаются при запуске сервера. После их изменения сервер нужно перезапустить. Файл `.env` автоматически не загружается.**

На Windows остановите предыдущий сервер и выполните в том же PowerShell:

```powershell
$env:AI_ENABLED = 'true'
$env:AI_MODEL = 'gpt-4.1'
$env:AI_BASE_URL = 'https://api.openai.com/v1'
$env:AI_TIMEOUT_SECONDS = '12'

$aiSecret = Read-Host 'OpenAI API key' -AsSecureString
$aiKeyPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($aiSecret)

try {
    $env:AI_API_KEY =
        [Runtime.InteropServices.Marshal]::PtrToStringBSTR($aiKeyPointer)
} finally {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($aiKeyPointer)
    $aiSecret.Dispose()
    Remove-Variable aiSecret, aiKeyPointer
}

.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`gpt-4.1` использовалась в зафиксированной приёмке. Доступ к ней необходимо проверить для своего ключа.

На macOS / Linux создайте локальный `.env` по образцу [.env.example](.env.example), заполните `AI_API_KEY`, `AI_MODEL` и установите `AI_ENABLED=true`. Затем загрузите свой файл в том же терминале:

```sh
set -a
source .env
set +a

.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

`source` выполняет содержимое файла как команды оболочки: используйте только собственный доверенный `.env`.

Ключи не передаются браузеру и не должны попадать в Git. `.env` исключён из репозитория. После `git pull` настройки другого участника команды автоматически не появляются.

Адаптер использует `/responses` и Structured Outputs. Совместимости провайдера только с Chat Completions недостаточно. Подробности — в [инструкции AI](docs/ai.md).

### Если AI не работает

| Симптом | Что проверить |
| --- | --- |
| `not_configured` | Установлены ли `AI_API_KEY` и `AI_MODEL` в окружении процесса сервера; перезапущен ли сервер |
| `disabled` | Значение `AI_ENABLED`; для живого разбора требуется `true` |
| `provider_error` | Ключ, доступ к модели, адрес API и соединение |
| `rate_limited` | Доступную квоту и лимиты провайдера |
| `timeout` | Доступность провайдера и установленное время ожидания |
| `invalid_response` | Совместимость модели и результат проверки структуры/ссылок |
| HTTP 404 на `/api/analyze` | Версию локального кода и процесс, запущенный на выбранном порту |

Режим `?demo=1` использует заранее подготовленные примеры контракта. Полный демонстрационный ответ доступен для B; этот режим не подтверждает работу backend или живого AI.

Перед выступлением запустите приложение на презентационном ноутбуке, проверьте AI и откройте интерфейс без `?demo=1`.

| Время | Действие | Что показать |
| --- | --- | --- |
| 0–10 сек. | Объяснить исходную проблему | Бюджет 100; критические S1=38 и S2=35 в Нуре |

Сравнение A/B объясняет выступающий. Приложение показывает текущую попытку относительно исходного города и пока не хранит историю результатов.

## После хакатона

Первый шаг — пилотное занятие с преподавателем и небольшой группой пользователей.

План проверки пользы:

- предложить сопоставимые задания до и после упражнения;
- оценить, насколько участники объясняют средний результат, положение слабейшего района и критические проблемы;
- собрать трудности использования и ошибки понимания;
- отдельно сравнить работу с AI-разбором и без него.

После подтверждения пользы можно развивать историю попыток, задания преподавателя, новые учебные кейсы и проверенные рекомендации альтернатив.

Для публичного сервиса дополнительно потребуются управление доступом, ограничения AI-запросов, контроль расходов, мониторинг и нагрузочная проверка. Интеграция реальных городских данных потребует отдельной проверки их качества, прав использования и обоснованности модели.

Потенциальные заказчики — образовательные программы и организации, проводящие обучение городскому управлению. Это гипотеза развития; внедрения и платящие клиенты пока не заявляются.
