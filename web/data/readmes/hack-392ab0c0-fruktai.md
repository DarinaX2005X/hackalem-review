# FruktAI — интегрированный предфинальный MVP

Ветка `main` содержит интегрированную версию: frontend команды, FastAPI,
детерминированный workflow и SQLite. Интеграционная ветка — `test-main`.
Пользователь открывает таблицу рекомендаций, видит причины и историю продаж,
загружает собственные данные, изменяет остаток / товар в пути, получает пересчёт
и экспортирует CSV/XLSX из сохранённого расчёта после проверки.

Число заказа рассчитывает алгоритм:

```text
ceil(max(0, forecast_demand + safety_stock - on_hand - in_transit))
```

OpenAI может добавить пояснение. Ошибка OpenAI не отменяет расчёт.
Все экранные рекомендации загружаются из API. Файл mock используется только тестами.

## Frontend: рабочее место принятия решений

Интерфейс построен вокруг **последовательного раскрытия информации**:
менеджер сначала оценивает ситуацию на дашборде, затем выбирает позиции
в таблице и открывает детали только для проверки конкретного решения.
Обзор, закупочная очередь и сводка поставщиков решают разные задачи,
поэтому не дублируют один и тот же экран.

- **Контрактное взаимодействие.** Типизированный клиент получает данные
  по [единому API-контракту](docs/API_CONTRACT.md); представление отделено
  от сетевых запросов и серверной бизнес-логики.
- **Единое управление состоянием.** [useWorkspace](frontend/src/hooks/useWorkspace.ts)
  координирует загрузку, фильтры, выбор позиций и сценарные поправки.
  Устаревший ответ запроса не заменяет более свежий результат.
- **Проверка гипотез через what-if.** Изменение остатка или количества в пути
  запускает настоящий серверный пересчёт. Значения «до / после» позволяют
  оценить последствия поправки, не изменяя исходные CSV.
- **Проверка человеком перед экспортом.** Менеджер выбирает позиции,
  проверяет объёмы и подтверждает выгрузку. Кнопка экспорта не отправляет
  заказ поставщику и не проводит документ в 1С.
- **Работа с плотными данными.** Закреплённые заголовки, сортировка,
  фильтры и числовое выравнивание облегчают сравнение SKU; на мобильном
  экране таблица заменяется карточками.
- **Явные состояния интерфейса.** Загрузка, ошибка, отсутствие результатов
  и предупреждения качества данных отображаются отдельно. Неуспешный
  запрос не выдаётся за выполненный расчёт.

Точка входа — [App.tsx](frontend/src/App.tsx), сетевой слой —
[client.ts](frontend/src/api/client.ts), визуальные компоненты —
[components/](frontend/src/components/), тематические стили —
[styles/](frontend/src/styles/). Это позволяет менять представление,
не затрагивая формулу потребности и серверный контракт.

## Backend: проверяемый расчёт и сохранение результатов

Backend реализует **разделение транспорта, прикладного сценария и расчётного
ядра**. FastAPI принимает запрос, сервис координирует обработку, оркестратор
выполняет последовательность шагов, а слой хранения сохраняет результат.
Такое разделение позволяет тестировать алгоритм независимо от HTTP и UI.

| Слой | Ответственность | Реализация |
|---|---|---|
| HTTP | Валидация запросов, маршруты, коды ошибок, загрузка и экспорт | [backend/main.py](backend/main.py) |
| Прикладной сервис | Набор данных, overrides, запуск workflow и сохранение | [agent/service.py](agent/service.py) |
| Расчётное ядро | Аномалии, потерянный спрос, прогноз, количество и срочность | [agent/workflow/](agent/workflow/) |
| Оркестрация | Порядок шагов, проверки и журнал выполнения | [agent/orchestrator.py](agent/orchestrator.py) |
| Хранение | Источники, запуски, рекомендации и история SKU | [database/](database/) |

**Воспроизводимость:** одинаковые валидные входные данные, overrides и настройки
дают одинаковые числовые рекомендации. Идентификатор и время нового запуска
при этом различаются; текст необязательного AI-пояснения не является частью
детерминированной гарантии.

**Прослеживаемость:** `run_id` связывает рекомендации, историю товара и экспорт
с конкретным сохранённым запуском. Последующий пересчёт не меняет экспорт
предыдущего запуска. Входные нормализованные данные и поправки доступны для аудита.

**Контролируемая деградация:** нехватка сезонной истории приводит к коэффициенту
`1.0`, отсутствие строки поставки — к нулю с пояснением. Отрицательный остаток
является ошибкой данных, а не поводом незаметно подменять значение.

**Граница ответственности:** сервис поддерживает решение менеджера,
но не принимает коммерческое обязательство от его имени. Текущий MVP —
однопроцессное приложение с SQLite, а не распределённая production-платформа.
Промышленное развёртывание потребует отдельной проработки доступа,
резервного копирования, наблюдаемости и конкурентного выполнения.

## Коротко для презентации

> FruktAI превращает разрозненные складские данные в проверяемую очередь
> закупок: от очистки истории спроса до объяснимой рекомендации и экспорта.
> Прозрачный алгоритм отвечает за количество, интерфейс — за проверку решения,
> а сохранённый запуск — за возможность восстановить контекст расчёта.

## Формулы активного расчёта

Источник истины: [спрос и аномалии](agent/workflow/demand.py),
[количество и срочность](agent/workflow/recommendations.py).
Это прозрачные эвристики MVP, а не обученная модель прогнозирования.

1. **Выбросы.** Для дневных продаж `IQR = Q3 − Q1`; порог `Q3 + 1.5 × IQR`.
   Если IQR равен нулю, порог — `3 × Q3`. Проверка требует минимум 4 наблюдения
   и положительный Q3. При наличии минимум 8 групп клиент/день сначала
   исключаются одиночные клиентские пики выше `max(Q3 + 3 × IQR, 5 × median)`.
2. **Окно спроса.** Последние максимум 28 календарных дней относительно последней
   даты продаж/stockout в источнике. `U` — сумма пригодных продаж, `N` — число
   календарных дней. Пропущенный день даёт нулевые продажи; выбросы и stockout
   не добавляют продажи, но дни остаются в знаменателе.
3. **Упущенный спрос.** `baseline = U / N`; `lost = baseline × stockout_days`;
   `avg_daily_demand = (U + lost) / N`. Это оценка, не известные фактические продажи.
4. **Сезонность.** При 28 днях: `seasonality = clamp(mean_7 / baseline, 0.75, 1.50)`.
   При нехватке истории или нулевой базе — `1.0`. Это недельная эвристика, не годовая модель.
5. **Рост.** `growth = clamp(mean_last_14 / mean_previous_14, 1.0, 1.30)`:
   нужны 28 дней, минимум 7 пригодных дней в каждом окне и положительная предыдущая
   средняя. Обе суммы делятся на 14; иначе коэффициент — `1.0`.
6. **Прогноз.** `forecast_demand = avg_daily_demand × lead_time_days × seasonality × growth`.
7. **Страховой запас.** `safety_stock = avg_daily_demand × safety_stock_days`;
   по умолчанию 7 дней, настройка `FRUKTAI_SAFETY_STOCK_DAYS`.
8. **Заказ.** Прогноз и страховой запас округляются до двух знаков, затем
   `recommended_qty = ceil(max(0, forecast_demand + safety_stock − on_hand − in_transit))`.
9. **Покрытие.** `(on_hand + in_transit) / avg_daily_demand`; при нулевом спросе
   возвращается `0.0` с пояснением, не бесконечность.

Пример: спрос 10 ед./день, срок поставки 7 дней, оба коэффициента 1,
страховой запас 70, остаток 25, в пути 20 → `ceil(max(0, 70 + 70 − 25 − 20)) = 95`.
При замене остатка на 125 рекомендация станет нулевой.

Срочность: `high`, если остаток равен нулю или остаток + поставки меньше прогноза;
`medium`, если их хватает на прогноз, но не на прогноз + страховой запас;
иначе `low`. AI не меняет эти числа и статусы.

MOQ, кратность упаковок, backorders и задержки ETA не входят в формулу.
Для [LOGISTIQ Excel](docs/INPUT_OUTPUT.md#logistiq-xlsx) импортируются реальные
входные строки; лист Expected Results не становится готовым ответом API.

## Быстрый запуск на Windows

Нужны Python 3.10+ и Node.js 22+. Команды выполнять из корня репозитория:

```powershell
git fetch origin
git switch main
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
npm --prefix frontend ci
.\.venv\Scripts\python.exe scripts/run_local.py
```

Оставьте терминал открытым. Остановка обоих серверов — Ctrl+C.

- Интерфейс: http://127.0.0.1:5173
- Swagger: http://127.0.0.1:8000/docs
- Health: http://127.0.0.1:8000/health

`run_local.py` запускает оба процесса и по умолчанию **отключает платные AI-вызовы**.
Существующий `.env` перезаписывать не нужно. SQLite создаётся автоматически.

Для macOS/Linux: вместо `.\.venv\Scripts\python.exe` используйте `.venv/bin/python`.

## Первый прогон: ваши файлы → рекомендации → экспорт

После обновления кода обязательно повторите установку зависимостей из команды
выше: для загрузки добавлены multipart, openpyxl, xlrd и pdfplumber.
Каждая команда — отдельная строка; не склеивайте run_local.py и smoke_test.py.

1. Откройте интерфейс → **«Загрузить данные / выгрузку 1С»**.
2. Скачайте Excel-шаблон. Для проверки можно сразу загрузить его обратно:
   это явно синтетический набор, а не данные партнёра.
3. Для настоящего расчёта замените строки своими: продажи (дата, артикул,
   количество, обезличенный клиент, цена), справочник товаров/поставщиков,
   остатки по складу, stockout, товары в пути. Материальная ведомость 1С
   может заменить таблицу остатков. Если предоставлены обе, остатки сверяются.
4. Выберите XLSX/XLS, CSV/TSV, JSON или текстовый табличный PDF.
   Для отдельных файлов/листов обязательны имена и заголовки из шаблона.
   Если складов несколько — укажите его код. Подтвердите обезличивание.
5. Нажмите «Загрузить и проверить»: проверьте строки, склад, предупреждения
   и предпросмотр. Загрузка сама по себе не запускает расчёт.
6. Нажмите «Рассчитать загруженные данные». Получите рекомендации, причины,
   срочность, график и группировку по поставщикам. Пересчёт использует этот же
   набор; обновление страницы его не заменяет на demo.
7. Измените остаток / товар в пути в карточке и пересчитайте.
8. «Проверить заказ» → CSV или Excel → подтвердить проверку → скачать.
   Экспорт содержит именно сохранённый run_id, даже если позже был другой расчёт.
   В 1С и поставщикам автоматически ничего не отправляется.

**Граница интеграции 1С:** реализован файловый обмен и сверка ведомости, а не
прямое подключение к вашей базе. Для OData/HTTP нужны конфигурация, доступный
интерфейс и реальный пример структуры данных. PDF-сканы/фото требуют OCR и
сейчас отклоняются с понятной ошибкой; произвольные печатные формы не угадываются.

Полные форматы, обязательные колонки и ограничения:
[Вход/выход и 1С](docs/INPUT_OUTPUT.md).
Для backend/frontend: [HTTP-контракт](docs/API_CONTRACT.md),
[структура входов](docs/DATA_CONTRACT.md), [JSON Schema](contracts/README.md).

## Запуск с OpenAI

Ключ должен быть только в корневом `.env`:

```env
OPENAI_API_KEY=ваш_ключ
OPENAI_MODEL=gpt-6-astra
OPENAI_EXPLANATIONS_ENABLED=true
```

После остановки обычного запуска:

```powershell
.\.venv\Scripts\python.exe scripts/run_local.py --ai
```

Один пересчёт вызывает одну пакетную AI-операцию с ограниченными повторами.
При отказе провайдера сохраняются детерминированные причины; подробности видны
в серверном логе. Наличие ответа HTTP 200 само по себе не доказывает работу LLM.
Успешное AI-пояснение начинается с `AI-пояснение:`.

Полный live-тест AI → HTTP → SQLite на временной БД (один платный пакетный
запрос по учебным данным): `python scripts/test_ai_integration.py`.
Тест требует корневой `.env` с ключом и явно завершается ошибкой при fallback.

Настройки лимитов и fallback: [OpenAI integration](docs/OPENAI_INTEGRATION.md).
Описание входа и выхода: [AI contract](docs/AI_API_CONTRACT.md).

## Полный автоматический прогон

В отдельном терминале из корня:

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
.\.venv\Scripts\python.exe scripts/test_full_stack.py
.\.venv\Scripts\python.exe scripts/validate_api_contracts.py
.\.venv\Scripts\python.exe scripts/test_agent_workflow.py
.\.venv\Scripts\python.exe scripts/test_database.py
.\.venv\Scripts\python.exe scripts/test_workflow_service.py
.\.venv\Scripts\python.exe scripts/test_openai_explainer.py
npm --prefix frontend test
npm --prefix frontend run build
```

`test_full_stack.py` сам запускает настоящий HTTP-сервер на свободном порту,
выполняет health → расчёт → изменение остатка → историю товара, затем перезапускает
сервер и проверяет сохранность результата в SQLite. Использует временную БД,
не меняет рабочую БД и не вызывает OpenAI.

Если сервер не стартует, тест выводит код завершения, путь к Python и исходный
лог Uvicorn. Проверяйте зависимости тем же интерпретатором из `.venv`, которым
запускаете тест. `test_full_stack.py` запускает свой сервер автоматически;
`smoke_test.py` требует уже запущенного приложения.

Для проверки уже запущенного приложения, включая Vite-прокси:

```powershell
.\.venv\Scripts\python.exe scripts/smoke_test.py --base-url http://127.0.0.1:5173
```

Smoke-test создаёт два настоящих расчёта в рабочей БД; последний содержит override.
Нажмите «Обновить данные» в UI, чтобы вернуться к исходным CSV.

Браузерный прогон при работающем `run_local.py`:

```powershell
cd frontend
npx playwright install chromium
npm run test:e2e
cd ..
```

Проверяет таблицу, открытие товара и графика, пересчёт, чтение из API/БД и
скачивание CSV, а также Excel-шаблон → загрузку → предпросмотр → расчёт →
историю конкретного run_id → экспорт XLSX. Для установленного Chrome можно задать
`$env:PLAYWRIGHT_CHANNEL = "chrome"` и пропустить загрузку Chromium.

## Демонстрация за две минуты

1. Откройте http://127.0.0.1:5173 — загрузятся 6 SKU.
2. Откройте «Рекомендации» и любой товар с ненулевым заказом.
3. Посмотрите формулу, причины и график истории.
4. Введите остаток `10000`, нажмите «Пересчитать через API».
   Рекомендация станет нулевой, отобразятся значения до / после.
5. Закройте карточку и откройте «Ход анализа» в отдельном разделе слева:
   там настоящий `run_id` и семь выполненных шагов.
6. Нажмите «Проверить заказ», подтвердите проверку, скачайте CSV.
   Отправка поставщику не выполняется.
7. «Обновить данные» сбрасывает поправки и заново считает исходный набор.

CSV не изменяются при пересчёте; override относится только к текущему запуску.
Внутри UI поправки нескольких SKU накапливаются до «Обновить данные».

- `artifacts/fruktai.sqlite` — SQLite с расчётами, причинами, историей и журналом.
- `artifacts/imports/upload_*/` — нормализованные входы и manifest; оригиналы документов не сохраняются.
- `source_imports` в SQLite — снимок нормализованных таблиц, включая цену и обезличенный ID.
- `artifacts/runs/` — JSON исходного детерминированного этапа, до AI-обогащения.
- Структура: [database/schema.sql](database/schema.sql).
- Для VS Code откройте SQLite через SQLite Viewer; полезны
  `latest_recommendations`, `supplier_order_summary`, `calculation_runs`.
- Ключи, БД, журналы, виртуальное окружение и node_modules исключены из Git.

## Docker Compose

Альтернатива локальному запуску, когда работает Docker Desktop:

```powershell
docker compose up --build -d
docker compose ps
python scripts/smoke_test.py --base-url http://127.0.0.1:5173
docker compose logs --tail=100 backend
docker compose down
```

Те же адреса: UI 5173, API 8000. Не запускайте локальные процессы одновременно
на этих портах. Каталог `./artifacts` примонтирован: БД остаётся после остановки.

Compose читает корневой `.env`. Для прогона без OpenAI:
`$env:OPENAI_EXPLANATIONS_ENABLED = "false"` перед `docker compose up`.
Для включения задайте `true` и выполните `docker compose up -d --force-recreate backend`.
Ключ передаётся только backend и не попадает в frontend build.

## Архитектура и границы интеграции

```text
React :5173 -> Vite/nginx proxy -> FastAPI :8000
                                    |
                              WorkflowService
                              /             \
                       CSV + алгоритм     OpenAI (optional)
                              \             /
                                  SQLite
```

Публичные маршруты: `GET /health`, `POST /api/v1/recalculate`,
`GET /api/v1/items/{sku}` плюс загрузка/метаданные/шаблон в
`/api/v1/datasets/` и экспорт `/api/v1/runs/{run_id}/export`.
Существующие поля рекомендаций не переименованы:
[API](docs/API_CONTRACT.md), [CSV](docs/DATA_CONTRACT.md), [JSON Schema](contracts/README.md).

В API работает только `agent/orchestrator.py`. Исходные
`backend/calculation.py` и `backend/services/` сохранены вместе с тестами как
наработка backend-участника; HTTP их не использует. Для запуска достаточно
`backend/requirements.txt`; pandas/NumPy нужны только для тестов этих наработок.

Происхождение: AI/БД — `83e19ff`, frontend/main — `35ee99e`
(frontend `0c53176`), исходники backend — `9e9aa6c`.
Backend перенесён выборочно: его `.venv`, pycache и конфликтующая реализация
`database/` не включались. Общая БД сохранена из AI-ветки.

Предфинальные ограничения: один процесс API, файловый обмен с 1С, выбор
одного склада на набор, целочисленные остатки/заказ в базовой единице товара.
Сезонность оценивается по неделям, а не полноценной годовой модели.
Выбросы анализируются по SKU/дню и, при наличии, обезличенному клиенту.
Категория и единица берутся только из метаданных входа; ETA в рекомендации
не добавляется. Все товары в пути вычитаются по исходной MVP-формуле без
моделирования задержек. Автоматическая отправка/проведение заказов отсутствует.

Проверено для файлового обмена: 47 pytest-тестов, HTTP-прогон с перезапуском SQLite,
8 JSON Schema, script-тесты workflow/БД/AI-fallback, frontend unit/build,
семь браузерных E2E через установленный Chrome: импорт/экспорт, пересчёт,
раздельные экраны, профиль, навигация и сортировки, мобильный экран,
восстановление после ошибки API. Дополнительный тест локального LOGISTIQ-файла
включается через `E2E_LOGISTIQ_FILE`; без этого пути он пропускается.
В этом прогоне платные AI-запросы не выполнялись.
Compose ранее прошёл проверку конфигурации; повторная проверка в текущей
среде ограничена доступом к Docker config. Запуск контейнеров не проверен.
