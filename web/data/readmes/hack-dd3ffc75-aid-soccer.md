# Adaptive Campaign Portfolio Agent

Решение синтетического кейса Beeline для AI-хакатона. История переходов ранжирует
гипотезы, SMS-пилоты измеряют эффект на текущей аудитории, а оптимизатор выбирает
до 10 кампаний с учётом неопределённости, бюджета и охвата. Итоговая версия
объединена в `main`. Все команды выполняются **из корня репозитория**.

Обычный `Agent()` работает без сети и ключа: применяет сохранённую LLM-рекомендацию
при точном совпадении входного контекста, иначе использует численную политику.
Явный live-режим OpenAI доступен отдельно. Веса модели не обучались.

## Быстрый запуск на новой машине

Нужны Git и Python 3.12. Проверенное окружение: Python 3.12.3, pandas 3.0.3,
NumPy 2.4.4, pytest 9.0.2. Зависимости закреплены в requirements-файлах.

```bash
git clone --branch main https://github.com/BAITC-Hacks/hack-dd3ffc75-aid-soccer.git
cd hack-dd3ffc75-aid-soccer

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt -r requirements-llm.txt

python -m pytest tests -q
python local_eval.py
python local_eval.py --runs 10
python -m tools.benchmark --runs 10 --compare-starter --trace-seed 42
python make_submission.py
python -m reporting --input reports/decision_trace.json --output reports/demo.html
```

Для работы обычного агента достаточно `requirements.txt`. Для полного набора
тестов, включая SDK через mock HTTP transport, команда выше также устанавливает
зависимости разработки и LLM. Тесты не вызывают внешний API. API-ключ для
официального evaluator и генерации submission не требуется.

Публичные CSV и неизменённые скрипты организаторов включены в репозиторий.
Папка `beeline_case_participants ` с пробелом в конце содержит предыдущий
прототип; запускайте корневые скрипты, не эту копию. `task/` для запуска не нужен.

## LLM: фактическое поведение и live-проверка

`llm_advisor.py` передаёт модели до 40 агрегированных гипотез, параметры тарифов,
каналов и доступные ресурсы. Строки клиентов, их ID, скрытые эффекты, seed и
результаты evaluator в запрос не включаются. Модель может предложить до двух
существующих гипотез для пилотов; она не заменяет измеренные эффекты и проверки
лимитов. Если гипотезы уже выбраны, порядок пилотов сохраняется.

| Режим | Поведение |
|---|---|
| Обычный `Agent()` | При наличии `artifacts/llm_policy.json` — офлайн-replay; при несовпадении контекста — численная политика. Без файла — `off`. |
| `Agent({"llm_mode": "off"})` | Численная политика без применения LLM-рекомендаций. |
| `Agent({"llm_mode": "assist"})` | До одного live-запроса на `act`; валидные рекомендации могут изменить выбор пилотов. |
| `Agent({"llm_mode": "shadow"})` | Запрос и запись рекомендации без влияния на выбор пилотов. |

**Подстановка `OPENAI_API_KEY` сама по себе не включает live-режим обычного
`Agent()`. Автоматический переход к API на изменённых данных в текущей версии
не реализован.** В live-режиме ключ читается из переменной окружения
`OPENAI_API_KEY`, как требует ТЗ. Только явно запущенный CLI дополнительно
загружает локальный `.env`; сам `Agent()` этого не делает.

Для локальной live-проверки после установки зависимостей:

```bash
# Создать шаблон только при отсутствии локального .env.
test -f .env || cp .env.example .env
chmod 600 .env
nano .env
# В редакторе заполнить OPENAI_API_KEY и сохранить файл.

python -m tools.llm_eval --check-config
python -m tools.llm_eval --mode assist --runs 1 --seed 42 \
  --output-dir "reports/llm_runs/live-check-$(date +%Y%m%d-%H%M%S)"
```

Ожидается `api_key_configured: true`, затем `llm_status=ok` и `API requests: 1`.
Ключ не выводится и не должен попадать в Git. На судействе для явно включённого
live-режима достаточно переменной окружения; файл `.env` не нужен.

Таймауты, ошибки API, отсутствующий ключ и невалидные ответы переводят агента
на численную политику. CLI возвращает ненулевой код при неудачной live-проверке,
даже если запасная политика завершилась успешно. Сохранённый ответ привязан
к хешам публичного контекста и инструкций; устаревшие рекомендации отвергаются.

В релизной проверке выполнено **11 успешных реальных API-запросов**, включая
10 сравнительных live-прогонов. Модель каждый раз выбрала гипотезы, уже входившие
в численный план, поэтому результаты совпали с baseline. **Рост прибыли от LLM
на этом наборе не подтверждён.** [Ответы и расход токенов](reports/llm_live_evidence.json).

Есть сбор примеров и экспорт проверенной разметки для будущего обучения.
Веса модели пока не обучались; сохранённая рекомендация не является обученной
моделью. Настройка, обновление рекомендации для новых данных и подготовка
обучающих примеров: [LLM_INTEGRATION.md](docs/LLM_INTEGRATION.md).

## Архитектура и опциональные требования

```text
Agent.act(env)
  -> generate_candidates(profile, history, tariffs)
  -> LLM-рекомендация: replay / явно включённый live / off
  -> run_adaptive_pilots(env, candidates)
  -> build_campaigns(env, observations)
  -> список финальных кампаний + last_trace
```

- `candidate_engine.py`: устойчивое историческое ранжирование со shrinkage,
  разнообразием ячеек и каталожными альтернативами; до 40 гипотез по умолчанию.
- `llm_advisor.py`: ограниченные рекомендации, валидация ответа, чтение
  сохранённой политики и безопасное поведение при ошибках API.
- `pilot_policy.py`: до 10 разведочных SMS-пилотов по 80 контактов и до 5
  адаптивно выбираемых подтверждений по 200. Оценки используют фактически
  возвращённые размеры выборок; отрицательные наблюдения сохраняются.
- `portfolio_optimizer.py`: совместный выбор push/SMS/digital_ads, тарифа и
  пропуска ячейки при ограничениях бюджета и охвата. Не более одной финальной
  кампании на ячейку; до 5000 клиентов в порядке числового ID на кампанию.
- `agent.py`: координация модулей, сброс trace на каждом запуске, контроль лимитов.
- `tools/benchmark.py` и `reporting.py`: внешняя проверка и визуализация trace.
  Рендер отчёта не проводит новые пилоты и не меняет кампании.

Неопределённость учитывается через mean/SE/safe lift в нормализованных единицах;
экономика применяет коэффициент канала один раз. Call исключён из-за насыщения
конверсии. Выбор и число подтверждений зависят от измерений и ресурсов.

Дополнительный режим `adaptive_confirmation_n=True` подбирает также размер
подтверждений по текущей неопределённости. В десяти прогонах его медиана составила
**3,002,247.39**, минимум — **1,305,074.91**, положительных — **10/10**. Он ухудшил
минимум относительно основной политики, поэтому **по умолчанию выключен**.

## Ограничения и целостность

Исторический before/after lift среди сменивших тариф не доказывает причинный
эффект кампании. `positive_rate` не является конверсией, а `prior_score` —
прогнозом прибыли. История и текущая аудитория в предоставленных данных не
пересекаются по ID. На новой аудитории решения определяются её данными и пилотами.

После адаптивного отбора интервалы неопределённости являются эвристическими.
Поиск ограниченной ширины не гарантирует глобальный оптимум. Точные ID пилотов
недоступны агенту; оценки финального портфеля не изображают точную дедупликацию
с пилотами. Фактический net gain считает официальный evaluator.

Когда нет положительной консервативной оценки, аварийная push-кампания явно
помечается как рискованная: бесплатный контакт тоже может уменьшить выручку.
Mock-эффекты отличаются от скрытой среды; результаты не являются прогнозом
реального бизнеса или гарантией места на судействе.
