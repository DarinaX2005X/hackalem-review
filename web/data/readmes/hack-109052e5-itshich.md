# Умный подбор подрядчиков (#79-lite)

Сервис принимает параметры заказа (город, дата, тип мероприятия, категория,
бюджет, опционально длительность и язык) и возвращает до 3 карточек
подрядчиков из каталога агрегатора. У каждой карточки есть индивидуальное
объяснение, привязанное к фактам профиля. Кандидатов выбирает и упорядочивает
код, а не модель. LLM пишет только текст объяснения по уже посчитанным фактам.

## Быстрый старт

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/).

Штатный режим работает с сетью: ключ OpenAI нужен, чтобы тексты объяснений
писала модель `gpt-5.4-mini`, а новые тексты запросов и профилей получали
эмбеддинги `text-embedding-3-large`.

```bash
cp .env.example .env         # вписать OPENAI_API_KEY=sk-...
uv sync
uv run uvicorn app:app --port 8000
# http://127.0.0.1:8000/        интерфейс, демо-сценарии внизу страницы
# http://127.0.0.1:8000/tests   результаты тестов и лайв-кейсы
# http://127.0.0.1:8000/docs-ui как устроен подбор, контракт /api/match
```

Ключ должен иметь доступ к моделям `text-embedding-3-large` (1024 dims) и `gpt-5.4-mini`
(в кабинете OpenAI: Settings → Project → Limits → Model access). Модели меняются
через `LLM_MODEL` и `EMBEDDING_MODEL` в `.env` без правки кода.

**Резервный режим без ключа.** Подбор и порядок карточек не зависят от сети:
векторы всех описаний и всех возможных текстов запроса лежат в
`data/embeddings.json` (801 вектор и якоря шкалы). Тексты объяснений для
демо-запросов и лайв-кейсов воспроизводятся слово в слово из
`data/explanations_cache.json`; для любого другого запроса без ключа текст
собирает детерминированный шаблон из тех же кодов причин и чисел. Это
осознанная деградация, а не полноценная замена модели: шаблон короче и
однообразнее. В подвале страницы виден источник объяснений (`llm` или
`template`) и семантика (`embeddings` или `lexical`).

Команды:

```bash
uv run pytest -q                       # все тесты (юнит + property-based + API)
uv run pytest -q -m e2e                # проверка страницы в браузере (Playwright)
uv run playwright install chromium     # один раз, для e2e
uv run python scripts/run_demo.py      # 6 демо-запросов, каждый дважды (детерминизм)
uv run python scripts/build_embeddings.py   # пересчитать кэш эмбеддингов (нужен ключ)
uv run python scripts/browser_check.py      # живая проверка страницы: сервер должен быть запущен на :8000
uv run python scripts/test_report.py        # прогнать тесты и обновить data/test_report.json для /tests
uv run python scripts/run_cases.py          # лайв-кейсы из demo/cases.json: вход, карточки, коды причин, объяснения (раздел на /tests)
uv run python scripts/run_live_tests.py     # 11 лайв-тестов: data/live_tests.json для /api/live-tests; --check ловит изменение порядка, кодов и текстов
```

Все тесты идут без сети и без ключа. Полный прогон около 15 секунд.

## Что происходит внутри

Пайплайн из шести шагов, каждый в своём модуле (`DESIGN.md` описывает
интерфейсы):

1. **Загрузка** (`matcher/data.py`). CSV из 66 профилей превращается в
   неизменяемые объекты. Загрузчик строгий: неизвестный город, формат, язык
   или дата вне окна календаря останавливают запуск с указанием id строки.
2. **Фильтрация** (`matcher/filtering.py`). Пул = подрядчики нужной категории
   в нужном городе. Для каждого считаются все причины отказа: занят на дату,
   цена «от» выше бюджета, не берёт формат, не работает на языке, максимум
   часов меньше запрошенной длительности. Причины сохраняются и показываются
   пользователю в блоке «Почему остальные не попали».
3. **Ранжирование** (`matcher/ranking.py`). Только для прошедших фильтр.
   Итог = взвешенная сумма пяти признаков в [0, 1]: запас по бюджету, близость
   описания к запросу, языки, запас по часам, качество данных. Веса зависят от
   группы категории (`weights_for`):

   | группа | бюджет | описание | языки | часы | данные |
   | --- | ---: | ---: | ---: | ---: | ---: |
   | общий | 0.25 | 0.55 | 0 | 0.05 | 0.15 |
   | площадка (зал, ресторан, отель, загородная) | 0.25 | 0.60 | 0 | 0.05 | 0.10 |
   | ведущий, ведущий церемонии | 0.25 | 0.55 | 0 | 0.10 | 0.10 |
   | флорист, декоратор, сувениры | 0.25 | 0.60 | 0 | 0 | 0.15 |

   Языки весят 0: запрошенный язык уже жёсткий фильтр, а лишние языки клиент
   не просил. Если длительность не запрошена, вес часов обнуляется и остальные
   перенормируются. При равенстве итога порядок по id, поэтому один и тот же
   запрос всегда даёт один и тот же порядок. Веса заданы как приоры и
   проверены слепым LLM-судьёй (`gpt-5.4`, listwise, 16 запросов, согласие
   судьи с самим собой 88–94 %): минимум сетки из 125 конфигураций совпал с
   приорами, на отложенных запросах они согласуются с судьёй в 63.9 % пар
   против 62.2 % у прежних равных весов 0.35/0.35. Подробности в
   `docs/research/calibration.md`.
4. **Причины «почему этот»** (`matcher/reasons.py`). Считает код, не модель.
   Скор линейный, поэтому вклад признака равен `w · (x − среднее по прошедшим
   фильтр)`, точно и без приближений. Семь семейств причин: бюджет, формат,
   язык, длительность, аспект описания, контраст по занятости, оговорки о
   данных. У каждой карточки одна главная причина и до двух поддерживающих из
   других семейств. Главные причины тройки подбираются перебором комбинаций со
   штрафом за повтор, порядок карточек при этом не меняется. «Попал из-за
   занятости» доказывается пересчётом топ-3 без фильтра по дате: если
   конкурент там есть и его возврат вытесняет карточку, причина подтверждена.
   Больные точки заказчика поднимают приоритет причин: бюджет впритык
   (запас меньше 15 %), декабрь или дефицит дат, запрошенный язык, часы.
5. **Аспекты описаний** (`matcher/aspects.py`, `data/aspects.json`). Описания
   размечены один раз офлайн закрытым списком тегов: «опыт бизнес-форумов»,
   «живые инструменты», «оформление под ключ» и т. д. Каждый тег хранит
   дословную цитату только как доказательство, в текст карточки цитаты не
   попадают. Разметка: `uv run python scripts/tag_aspects.py`.
6. **Объяснение** (`matcher/explain.py`). LLM получает только коды причин, их
   смысл и числа: цену, бюджет, запас, часы, дату, тег аспекта. Без описаний,
   без скоров и без имён других подрядчиков. Каждая карточка говорит только
   о себе: почему выбран именно этот подрядчик. Кто занят или не прошёл, видно
   отдельно в блоке «Почему остальные не попали». Валидатор требует все числа
   главной причины, отклоняет числа не из полей профиля, упоминание любого
   другого подрядчика, цитаты, общие фразы, больше двух предложений и текст,
   который подошёл бы соседней карточке (swap-test). Провал валидации, ошибка API или отсутствие ключа:
   шаблон по тем же кодам.

### Три исхода

| Исход | Когда | Что видит пользователь |
| --- | --- | --- |
| Подобрали | есть хотя бы один прошедший фильтр | 1–3 карточки; если меньше трёх, текст объясняет почему |
| В этом городе такой категории нет | пул пуст | сообщение, какие категории есть в городе и есть ли эта категория в другом |
| Кандидаты есть, но ни один не проходит | пул не пуст, все отклонены | сводка по причинам с именами и числами |

Дата вне известного окна календаря (23.09.2026 — 31.12.2026) не является
исходом подбора: сервис отвечает текстом, что занятость на эту дату неизвестна.

### Роль AI

- **Эмбеддинги** (`text-embedding-3-large`, 1024 dims) считают близость описания к
  запросу вида «корпоратив Ведущий Алматы». Косинус переводится в [0, 1] не
  формулой (cos+1)/2 (она сжимала разницу между кандидатами до 0.01–0.04, и
  порядок задавала одна цена), а по фиксированным якорям каталога:
  `clip((cos − P05) / (P95 − P05))`, где P05 и P95 посчитаны по всем парам
  «возможный запрос × описание» и сохранены в `data/embeddings.json`
  (low 0.222, high 0.507). Якоря не зависят от текущего пула:
  бронь одного подрядчика не меняет баллы остальных. Векторы кэшируются по хешу
  текста, поэтому ранжирование воспроизводимо без сети. Порог округления до
  трёх знаков и сортировка по id исключают влияние шума float.
- **LLM при подготовке данных** (`gpt-5.4-mini`) один раз размечает аспекты описаний тегами
  с дословной цитатой-доказательством; результат в `data/aspects.json`.
- **LLM онлайн** (`gpt-5.4-mini` по умолчанию, `temperature=0`, `seed=42`, таймаут
  8 с) превращает коды причин с числами в 1–2 предложения. Модель не выбирает,
  не переставляет кандидатов и не выбирает причины. Ответ проверяет валидатор; провал или ошибка API означают шаблон
  для всего запроса, причина пишется в лог. Удачные ответы кэшируются в
  `data/explanations_cache.json` по хешу запроса, id карточек, модели и версии
  промпта, поэтому повтор запроса даёт тот же текст.

### Ограничения данных

- 66 профилей исходного датасета, из них 13 полностью синтетические, у 18 цена
  и у 8 город проставлены при подготовке датасета. Эти флаги показаны бейджами
  на карточке и упомянуты в объяснении.
- Мы добавили 12 своих профилей (`data/synthetic_extra.csv`, id `SYN-…`,
  `synthetic=True`), в основном в Астане, где каталог тонкий. Их генерирует
  детерминированный скрипт `scripts/make_synthetic.py`. Демо-запросы построены
  на исходных данных и не зависят от добавленных профилей.
- Цена в каталоге это цена «от». Прохождение фильтра означает, что стартовая
  цена укладывается в бюджет, а не что итоговая сумма гарантирована.
- `max_hours = null` означает, что работа не привязана к присутствию на
  площадке (флорист, декоратор, сувениры). Такие профили никогда не отсеиваются
  по длительности.
- Календарь известен только на 100 дней. В декабре 70–80 % дат заняты, это
  свойство сезона, а не ошибка.

## Демонстрация

`demo/queries.json` содержит воспроизводимые запросы на реальных данных.
Кнопки на главной странице подставляют их в форму. Тесты в
`tests/test_service.py` фиксируют ожидаемые id карточек для каждого запроса с
теми же эмбеддингами, что и в проде, поэтому порядок в демо и в тестах один.

| Запрос | Параметры | Исход | Карточки по порядку |
| --- | --- | --- | --- |
| Плотная категория | Ведущий, Алматы, корпоратив, 04.10.2026, 2 000 000 ₸, 4 ч | Подобрали (5 подходят из 10) | HK-75012 Джинбей, HK-35215 Кики, HK-27222 Сон Гоку |
| Редкая категория | Флорист, Алматы, свадьба, 04.10.2026, 250 000 ₸ | Подобрали, 2 из 3: в городе всего 2 флориста | HK-39372, HK-90001 |
| Категории нет в городе | Декоратор, Астана | В этом городе такой категории нет; подсказка, где категория есть | — |
| Никто не проходит | Ведущий, Алматы, корпоратив, 02.10.2026, 500 000 ₸ | Кандидаты есть (10), но заняты, дороже бюджета или не берут формат | — |
| Пара дат, A | Ведущий, Алматы, корпоратив, 04.10.2026, 2 000 000 ₸, 4 ч | Подобрали | Джинбей, Кики, Сон Гоку |
| Пара дат, B | то же, 05.10.2026 | Подобрали; Джинбей и Кики заняты 05.10.2026 (видно в блоке «Почему остальные не попали»), Куррапика вошёл по доступности: «свободен 05.10.2026 и берёт формат «корпоратив»» | HK-77838 Хаул, HK-44733 Буллма, HK-88430 Куррапика |

Время ответа: пустые исходы около 70 мс, с LLM-объяснениями 1.5–3 с, из кэша
объяснений около 120 мс. Полный прогон с повтором каждого запроса делает
`scripts/run_demo.py`.

Примеры объяснений из живого прогона (плотная категория, gpt-5.4-mini);
в скобках главная причина, выбранная кодом:

- Джинбей (аспект описания): «Джинбей: опыт бизнес-форумов и конференций
  хорошо совпадает с форматом корпоратива. Цена от 1 300 000 ₸ при бюджете
  2 000 000 ₸ оставляет запас 35 %.»
- Кики (запас по бюджету): «Кики: цена от 900 000 ₸ при бюджете 2 000 000 ₸
  даёт запас 55 %. Дополнительно подходит ведение на нескольких языках.»
- Сон Гоку (доступность на дату): «Сон Гоку: свободен 04.10.2026 и берёт
  формат «корпоратив». Цена от 1 000 000 ₸ при бюджете 2 000 000 ₸ оставляет
  запас 50 %.»

Главные причины у карточек одного запроса разные, это гарантирует код, а не
удача модели. Каждая карточка говорит только о себе, без сравнения с теми,
кого нет в выдаче. Поэтому объяснения нельзя перепутать между собой, и в них
нет фактов, которых нет в профиле. Живой прогон 11 запросов с ключами причин:
`docs/research/live-tests.md`; устойчивость выдачи к малым изменениям запроса
(бюджет ±100 000 ₸, часы ±1, дата ±1/±7 дней): `docs/research/stability-tests.md`.

## Что реализовано

- Вход: город, дата, тип мероприятия, категория, бюджет; опционально часы и язык.
- Выход: до 3 карточек (имя, категория, город, цена «от», бейджи данных) с
  объяснением в 1–2 предложения из фактов профиля; главные причины у карточек
  одного запроса разные.
- Жёсткие фильтры: занятость на дату, бюджет, формат, язык, длительность;
  занятый на дату подрядчик в выдачу не попадает. Площадки в том же каталоге
  и с тем же календарём.
- Три явных исхода: подобрали / категории нет в городе / кандидаты есть, но
  никто не проходит. Меньше трёх карточек: текст объясняет почему. Пустой
  результат объяснён словами, не ошибкой.
- Детерминизм: тот же запрос даёт тот же порядок и тот же текст (кэш).
- Демо: 6 воспроизводимых сценариев кнопками, включая пару дат, где выдача
  меняется из-за занятости.
- Страницы: `/` интерфейс, `/tests` результаты тестов и лайв-кейсы
  (`demo/cases.json`, `GET /api/cases`, `POST /api/cases/run`), `/docs-ui` описание.

## Технологии

- Python 3.12, FastAPI + Uvicorn, Pydantic, python-dotenv; менеджер `uv`.
- OpenAI API: `text-embedding-3-large` (1024 dims) для близости описаний,
  `gpt-5.4-mini` для текста объяснений и разовой разметки аспектов при
  подготовке данных, `gpt-5.4` как слепой судья при проверке весов (только
  при подготовке, в рантайме не участвует).
- Тесты: pytest, Hypothesis (property-based), Playwright (e2e).
- Фронт: статический HTML + ES-модули без сборки.
- Внешний сервис в рантайме: OpenAI API (штатный режим). Без ключа сервис
  переходит в резервный режим: кэши в репозитории и шаблонные объяснения.
  Базы данных нет: каталог CSV, кэши JSON в репозитории.

## Ограничения решения

- Только рекомендация: бронирования, заявок и уведомлений нет.
- Свободного поля «пожелания» в запросе нет; смысл описания сопоставляется с
  форматом, категорией, городом и языком.
- Календарь известен на 100 дней (23.09.2026 — 31.12.2026); дата вне окна не
  обрабатывается как подбор.
- Ответ LLM недетерминирован по своей природе; повторяемость обеспечивает кэш
  по хешу запроса и версии промпта. Без ключа и без кэша текст даёт шаблон,
  он беднее модельного.
- Веса ранжирования заданы экспертно и проверены LLM-судьёй; клиентских
  предпочтений в данных нет, поэтому это приоры, а не обученная модель.
- Развёрнутой версии нет: запуск локально по инструкции выше.

## Почему коды причин: архитектура и масштабирование

**Решение и формулировка разделены.** Кто попал в тройку, в каком порядке и
почему, решает код по линейному скору. LLM получает готовые коды причин с
числами и только пишет фразу. Объяснение не может разойтись с решением: оно
выводится из тех же чисел, что и порядок. Это проверяется тестами, а не
доверием к модели.

**Линейный скор даёт точные причины.** Вклад признака в скор равен
`w · (x − среднее по прошедшим фильтр)`. Для линейной модели это точное
разложение (то же, что даёт SHAP, но без библиотек и приближений). Контраст
встроен: вклад считается относительно конкурентов, отдельно против соседей по
тройке и против лучшего кандидата за её границей. Поэтому «почему этот, а не
другие» отвечается числом, а не эпитетом.

**Закрытая таксономия это контракт.** Семь семейств и около двадцати кодов с
фиксированной схемой доказательств (`price`, `budget`, `headroom_pct`, `date`,
`aspect`…). На контракт опираются: валидатор (числа только из доказательств,
запрет чужих имён и общих фраз, swap-test), шаблонный fallback без сети,
кэш объяснений, страница `/tests`, лайв-таблица `docs/research/live-tests.md`.
Тот же контракт открывает казахскую и английскую версию выдачи: нужны только
шаблоны и промпт на другом языке, ранжирование и коды не меняются.

**Аспекты описаний размечены один раз.** Свободный текст превращается в теги
офлайн, с цитатой-доказательством в кэше. Новый профиль стоит один вызов LLM
при загрузке, а не при каждом запросе. Новый тег добавляется в enum, ранжирование
не трогается.

**Стоимость запроса не зависит от размера каталога.** Фильтры отрабатывают до
семантики, косинус считается только для прошедших. Векторы и якоря шкалы
посчитаны заранее и зафиксированы на версию каталога: добавление или бронь
подрядчика не меняет баллы остальных. Причины считаются для показанных
карточек, перебор главных причин ограничен 6³ комбинациями, LLM вызывается
только для показанных карточек и кэшируется по хешу. Кэш векторов спрятан за
интерфейсом `SemanticScorer`: сейчас файл, на проде таблица профилей с
колонкой вектора, логика та же.

**Новые сигналы встраиваются без переписывания.** Новый жёсткий критерий это
ещё один `RejectReason`; новый мягкий сигнал (отзывы, скорость ответа, портфолио)
это признак, вес в профиле категории и код причины в том же семействе, после
чего объяснение про него появляется автоматически. Профили весов уже разные для
площадок, ведущих и услуг без присутствия, а скрипт калибровки со слепым
LLM-судьёй позволяет проверить новые веса на 16 запросах за минуты
(`docs/research/calibration.md`). Свободное поле «пожелания» ляжет ещё одним
семантическим признаком рядом с существующим.

**Границы честно обозначены.** Модель линейная, персонализации нет, веса это
приоры, подтверждённые судьёй, а не обученные на клиентских выборах. Именно
поэтому каждое число в карточке можно проверить по профилю.

## Масштабирование

Property-based тесты (`tests/test_properties.py`) генерируют тысячи
синтетических профилей и проверяют инварианты: занятые не попадают в выдачу,
цена «от» не выше бюджета, порядок стабилен, `max_hours = null` не
отсеивается по часам, бронь одного кандидата не меняет баллы остальных.
Тест устойчивости на реальных данных (`docs/research/stability-tests.md`):
при изменении бюджета на ±100 000 ₸ или часов на ±1 состав и порядок тройки
сохраняются, пока не меняется множество прошедших фильтр.
Фильтры отрабатывают до эмбеддингов, поэтому косинус считается только для
десятков кандидатов, а не для всего каталога. Кэш векторов спрятан за
интерфейсом `SemanticScorer`: сейчас это файл, на проде та же таблица профилей
с колонкой вектора. Логика подбора при этом не меняется. Property-based тесты
(`tests/test_properties.py`) генерируют тысячи синтетических профилей и
проверяют инварианты: занятые не попадают в выдачу, цена «от» не выше бюджета,
порядок стабилен, `max_hours = null` не отсеивается по часам.

### Лайв-тесты

`uv run python scripts/run_live_tests.py` сохраняет запросы из
`data/live_tests_requests.json` и ответы пайплайна в `data/live_tests.json`.
`uv run python scripts/run_live_tests.py --check` проверяет порядок карточек,
главные коды причин и тексты объяснений (код выхода 1 при расхождении).
На `/tests#live-tests` видны входные условия, причины, флаги и объяснения;
«Прогнать заново» и «Прогнать все» сравнивают живой ответ с сохранённым по
трём осям и показывают время в мс. Сохранённые результаты доступны без LLM.
