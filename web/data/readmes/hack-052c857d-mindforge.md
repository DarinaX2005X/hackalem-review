# Аким на 5 часов

By Assem Kumarbekova and Alisher Bugubay.

AI-симулятор управления городом.

Представьте: у вас есть 100 условных единиц бюджета, ровно 5 решений, 5 районов города и десятки дискуссионных приоритетов. Где лучше вложить деньги, чтобы не развалить одну часть города ради другой? Этот проект помогает ответить на этот вопрос в формализованной, быстро повторяемой модели условной Астаны.

Пользователь выбирает инициативы, сервер валидирует сценарий, а детерминированный engine рассчитывает эффект на инфраструктуру, экологию, городские сервисы, безопасность и социальную сферу. Результат превращается в Astana Quality of Life Score — число, которое отражает итоговое состояние города, а не просто сумму красивых обещаний.

> AI в проекте не заменяет математику. Он — слой анализа поверх уже рассчитанного сценария: объясняет, куда уходит бюджет, какие решения сильные, где скрытые риски и что можно улучшить дальше.

## Проблема

Городскому управленцу приходится распределять ограниченный бюджет между несколькими направлениями развития:

- транспорт;
- экология и озеленение;
- социальная инфраструктура;
- безопасность;
- городские сервисы.

Инвестиции в одно направление сокращают возможности для другого. Синтетическая модель города позволяет экспериментировать с разными стратегиями и видеть последствия решений без необходимости опираться на реальные данные о текущем состоянии столицы.

Продукт не претендует на прогноз реального развития Астаны. Он моделирует условную городскую систему с заданными эффектами и синергиями.

## Решение

Основной цикл выглядит так:

Исходное состояние города → бюджет 100 → выбор 5 инициатив → валидация → симуляция → применение эффектов и синергий → пересчёт проблемных показателей → Astana Quality of Life Score → результат и объяснение.

Именно здесь проект раскрывает свою идею: он не обещает “магический” прогноз, а показывает, как небольшая серия управленческих решений меняет состояние города в заданной синтетической модели. Это и есть основной продукт — безопасный, быстрый, прозрачный способ тестировать стратегии без риска для реальной городской политики.

Ключевое правило проекта: численные показатели рассчитываются детерминированным алгоритмом. LLM не считается источником баллов, не придумывает эффекты инициатив и не пересчитывает Score.

## Как работает симулятор

1. Пользователь видит исходное состояние пяти районов города.
2. Пользователь получает бюджет в 100 условных единиц.
3. Пользователь выбирает ровно 5 мероприятий.
4. Для районных мер выбирается район, в котором эффект применяется.
5. Система валидирует сценарий по правилам бюджета и совместимости.
6. Если стратегия невалидна, возвращается понятная причина ошибки.
7. Если стратегия валидна, запускается simulation engine.
8. Эффекты корректируются с учётом лага мероприятия.
9. При наличии соответствующих пар инициатив активируются синергии.
10. Показатели районов пересчитываются и ограничиваются диапазоном 0–100.
11. Считается районный Score по весам показателей.
12. Считается Astana Quality of Life Score по итоговой формуле.
13. Результат отображается в интерфейсе с изменением относительно базового состояния.
14. Если AI доступен, LLM объясняет уже рассчитанный результат, но не влияет на числа.

## Правила

Фактически реализованные правила в [backend/internal/simulation/simulation.go](backend/internal/simulation/simulation.go):

- бюджет равен 100;
- пользователь выбирает ровно 5 решений;
- повтор одной и той же инициативы запрещён;
- для районной инициативы район обязателен;
- для городской инициативы район не указывается;
- не более 2 мероприятий в одном направлении;
- M1 и M3 несовместимы;
- M4 и M7 нельзя размещать в одном районе;
- M5 и M13 нельзя размещать в одном районе;
- порядок выбора решений не влияет на итоговый расчёт, поскольку эффекты суммируются и синергии проверяются по набору выбранных инициатив.

Если стратегия невалидна, сервер возвращает читаемое сообщение и не считает Score.

## Математическая модель

### Горизонт симуляции

Горизонт симуляции равен 8 кварталам.

### Лаг и реализация эффекта

Для мероприятия с лагом L фактическая доля эффекта рассчитывается так:

```text
realized_fraction = (8 - L) / 8
```

Реализованный эффект от инициативы:

```text
realized_effect = full_effect × (8 - L) / 8
```

Пример из реализации: для `M7` эффект по `S1` равен +16, а лаг равен 3.

```text
16 × (8 - 3) / 8 = 16 × 5/8 = 10
```

То есть при выборе `M7` к соответствующему показателю добавляется +10 в текущем расчёте, а не полный +16.

## Синергии

В проекте реализованы три фиксированные синергии:

| Синергия | Эффект | Где активируется |
| --- | --- | --- |
| M1 + M2 | T1 +2 | в районе M1 |
| M10 + M12 | B1 +2 | в районе M10 |
| M5 + M6 | E2 +2 | в районе M5 |

Эти бонусы фиксированные, применяются после индивидуальных эффектов и не масштабируются лагом.

## District Score

Для района рассчитывается агрегированный Score по формуле:

```text
D_d = Σ w_k × I_dk
```

Где веса текущей реализации такие:

- T1 = 0.10
- T2 = 0.10
- E1 = 0.09
- E2 = 0.11
- S1 = 0.11
- S2 = 0.11
- B1 = 0.09
- B2 = 0.09
- C1 = 0.10
- C2 = 0.10

То есть формула в коде выглядит так:

```go
districtScore(m Metrics) float64 {
    return .10*m.T1 + .10*m.T2 + .09*m.E1 + .11*m.E2 + .11*m.S1 + .11*m.S2 + .09*m.B1 + .09*m.B2 + .10*m.C1 + .10*m.C2
}
```

Это означает, что итоговый районный балл — это взвешенная сумма показателей. Слабые показатели в одном районе влияют на итог сильнее, поскольку в формуле общего Score учтён минимум по районам.

## Astana Quality of Life Score

Итоговый городской балл рассчитывается следующим образом:

```text
Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit
```

Где:

- `D_avg` — средневзвешенный районный Score с учётом доли населения;
- `min(D_d)` — наихудший район по Score;
- `N_crit` — число пар `район × показатель`, где итоговое значение строго меньше 40.

В текущей реализации это соответствует коду:

```go
func cityScore(ms []Metrics) (float64, int) {
    avg, minScore := 0.0, math.Inf(1)
    crit := 0
    for i, m := range ms {
        s := districtScore(m)
        avg += Districts[i].Population * s
        if s < minScore {
            minScore = s
        }
        crit += critical(m)
    }
    return .7*avg + .3*minScore - float64(crit), crit
}
```

Смысл формулы:

- 70% веса у среднего по городу состояния;
- 30% веса у самого слабого района;
- штраф за критические показатели ниже 40;
- формула не позволяет «победить» только за счёт сильного центра, если в другом районе показатели падают слишком низко.

## AI-анализ

AI-слой в проекте реализован как анализ уже рассчитанной симуляции. Он не должен:

- рассчитывать Score;
- менять бюджет;
- пересчитывать эффекты мер;
- генерировать численные показатели.

Он делает следующее:

- объясняет итоговые результаты;
- выделяет сильные стороны сценария;
- перечисляет ключевые риски;
- описывает компромиссы;
- предлагает следующие шаги и альтернативные направления.

Примечание: в текущем коде AI-путь зависит от корректной настройки `OPENAI_API_KEY` и доступности OpenAI API. Если ключ отсутствует, функция анализа считается недоступной, а основной симулятор продолжает работать без её участия.

## Отказоустойчивость AI

Даже если OpenAI недоступен, пользователь должен иметь возможность:

- выбрать инициативы;
- получить валидный сценарий;
- увидеть Budget, Score, изменения по районам и синергии;
- пользоваться детерминированной моделью без внешнего сервиса.

Это реализовано в текущем проекте: AI не является обязательным компонентом.
