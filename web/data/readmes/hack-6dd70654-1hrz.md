# Money Graph AML

**Explainable graph analytics for financial transaction networks**

Money Graph AML — локальный аналитический инструмент для AML/финансового мониторинга. Система строит направленный граф переводов, рассчитывает структурные и временные признаки, присваивает каждому узлу объяснимую роль, формирует приоритетный список для проверки и предоставляет интерактивный веб-интерфейс для исследования сети.

> Результаты системы являются **аналитическими гипотезами для дальнейшей проверки**, а не утверждением о виновности клиента.

---

## Что решает проект

На вход система получает обезличенную транзакционную сеть, построенную от известных `seed`-клиентов на глубину до 4 колен. Вместо ручного просмотра тысяч связей аналитик получает:

- роль каждого клиента в наблюдаемой сети;
- `role_score` — степень соответствия правилам роли;
- `priority_score` — приоритет для аналитической проверки;
- человекочитаемое объяснение `evidence` / `why`;
- разбиение сети на сообщества;
- топ наиболее значимых узлов;
- интерактивный граф с поиском по `gid`, 1-hop и 2-hop анализом;
- данные по входящим/исходящим потокам и транзакциям выбранного узла.

Система работает **локально** и не требует внешнего LLM API или облачных сервисов для основного анализа.

# Быстрый запуск

## 1. Python backend

Открой терминал в корне проекта.

Создай виртуальное окружение:

### Windows

```powershell
py -m venv .venv
.venv\Scripts\activate
```

Установи зависимости:

```powershell
python -m pip install "pandas>=2.2,<4" "numpy>=1.26,<3" "networkx>=3.3,<4" "pyarrow>=17,<30"
```

Запусти аналитику:

```powershell
python backend/main.py
```

Backend автоматически читает:

```text
backend/data/nodes.parquet
backend/data/edges.parquet
backend/data/transactions.parquet
```

и создаёт результаты в:

```text
backend/output/
```

Успешный запуск заканчивается сообщением вида:

```text
[OK] 2248 nodes; ... clusters; ... sec
```

python prepare_web_data.py

# Входные данные

## `nodes.parquet`

Одна строка на клиента.

| Поле | Значение |
|---|---|
| `gid` | обезличенный идентификатор клиента |
| `depth` | минимальное расстояние от seed, 0–4 |
| `is_seed` | является ли узел исходным известным клиентом |

## `edges.parquet`

Агрегированная направленная связь между клиентами.

| Поле | Значение |
|---|---|
| `src` | отправитель |
| `dst` | получатель |
| `sum_kzt` | сумма переводов по связи |
| `n_tx` | число транзакций |
| `depth` | глубина обхода |

## `transactions.parquet`

Отдельные операции.

| Поле | Значение |
|---|---|
| `src` | отправитель |
| `dst` | получатель |
| `date` | дата операции |
| `sum_kzt` | сумма операции в KZT |

# Как работает алгоритм

## 1. Валидация

Перед анализом backend проверяет:

- обязательные колонки;
- пустые значения;
- корректность `gid`;
- диапазон `depth`;
- согласованность `is_seed` и `depth=0`;
- наличие всех `src/dst` в `nodes`;
- совпадение агрегатов `edges` с `transactions`;
- корректность дат и сумм.

При некорректном датасете процесс завершается с понятной ошибкой вместо генерации недостоверного результата.

## 2. Направленный граф

Формируется `NetworkX.DiGraph`:

```text
A ──100 000 KZT──> B
```

Направление ребра соответствует направлению перевода денег.

## 3. Признаки узла

Для каждого `gid` рассчитываются, среди прочего:

- `in_degree` — число уникальных отправителей;
- `out_degree` — число уникальных получателей;
- `incoming_sum` / `outgoing_sum`;
- количество входящих/исходящих транзакций;
- `pass_ratio = outgoing / incoming`;
- weighted PageRank;
- betweenness centrality;
- связь с seed-узлами;
- связи между кластерами;
- временной коэффициент быстрого прохождения средств;
- число синхронных отправителей в один день.

## 4. Кластеризация

Для поиска сообществ используется **Louvain community detection** на неориентированной проекции сети с весом `sum_kzt`.

Каждый клиент получает `cluster_id`.

## 5. Роли

Система использует объяснимые правила и скоры, а не black-box классификатор.

### `consolidator`

Признаки точки сбора средств:

- несколько уникальных отправителей;
- высокий входящий поток;
- выраженный входящий профиль.

### `distributor`

Признаки распределения:

- большое число получателей;
- высокий исходящий поток;
- fan-out структура.

### `transit`

Признаки транзитного счёта:

- присутствуют входящие и исходящие средства;
- `outgoing / incoming` находится примерно в диапазоне `0.8–1.2`;
- учитывается быстрое дальнейшее движение средств в течение 0–2 дней.

### `terminal`

Признаки наблюдаемого конечного получателя:

- есть входящий поток;
- наблюдаемый исходящий поток мал относительно входящего;
- узел не находится на искусственной границе `depth=4`.

### `coordinator`

Признаки структурно важного посредника:

- высокий betweenness;
- входящие и исходящие связи;
- соединение нескольких частей/сообществ сети;
- связь с несколькими seed-потоками.

### `peripheral`

Назначается, если выраженные критерии остальных ролей не выявлены.

`role_score` означает **силу соответствия определённым правилам**, а не вероятность виновности или истинность роли.

---

# Priority Score

`priority_score` отвечает на вопрос:

> Какой узел аналитику целесообразно изучить раньше других?

В итоговый скор входят четыре группы факторов:

```text
30%  money importance
25%  structural importance
20%  seed connectivity
25%  role strength
```

Используются нормализованные/percentile-признаки, поэтому абсолютный размер отдельных метрик не доминирует над всей формулой.

`priority_score` также является **аналитическим индексом**, а не вероятностью нарушения.

---

# Объяснимость

Для каждого клиента backend создаёт поле `evidence`.

Пример:

```text
Признаки сбора: 15 отправителей; вход 1,165,815 KZT; получателей 17.
```

Для узлов в топе создаётся более подробное поле `why`, включающее составляющие приоритета:

```text
Приоритет: поток=0.98; структура=0.91; seed-связи=0.85; сила роли=0.96.
```

Это позволяет объяснить решение системы без необходимости интерпретировать внутренности ML-модели.

# Веб-интерфейс

Frontend построен на React + Cytoscape.js и предназначен для работы аналитика с сетью.

Доступные функции:

- отображение полного графа;
- поиск клиента по `gid`;
- выделение выбранного узла;
- 1-hop анализ непосредственного окружения;
- 2-hop анализ расширенного окружения;
- визуальное различие seed и уровней `depth`;
- просмотр входящих и исходящих связей;
- суммы и число транзакций;
- временной диапазон активности;
- последние транзакции;
- топ связей выбранного клиента;
- базовая гипотеза по поведению узла.

### Важно о текущей интеграции

Backend формирует аналитические результаты в `backend/output/graph.json` и `report.json`, а `prepare_web_data.py` помещает их в `frontend/public/data/`.

Текущая версия `frontend/src/App.jsx` при построении основного графа продолжает читать legacy-файлы:

```text
/nodes.json
/edges.json
/transactions.json
```

и часть UI-метрик считает самостоятельно. Поэтому **backend и frontend уже входят в один репозиторий и запускаются вместе, но отображение `role`, `role_score`, `priority_score` и `evidence` непосредственно из `graph.json` требует последнего шага интеграции frontend**.

Это специально отмечено здесь, чтобы не смешивать алгоритмический `priority_score` backend с упрощённым UI-score текущего интерфейса.

# Особенности и ограничения данных

Алгоритм специально учитывает ограничения выборки.

### Обрыв на depth=4

Узлы на глубине 4 находятся на границе выгрузки. Отсутствие исходящих переводов у такого узла не означает, что деньги действительно остановились.

Поэтому `depth=4` не классифицируется как достоверный `terminal` только на основании отсутствия исходящих рёбер.

### Неполные входящие seed

Граф построен от seed-клиентов по исходящим переводам, поэтому их полный входящий поток неизвестен.

Соотношение `outgoing / incoming` для seed не используется как обычное доказательство transit/terminal поведения.

### Это не трассировка конкретных денег

Наличие маршрута:

```text
A → B → C
```

не доказывает, что одна и та же денежная единица прошла от A до C. Система выявляет структурные и временные паттерны.

### Дубликаты

В текущих транзакциях присутствуют совпадающие строки. Без отдельного `transaction_id` они сохраняются, поскольку нельзя доказать, что это ошибочные дубликаты.

# Масштабирование до ~1 млн узлов

Текущая версия оптимизирована под хакатонный объём и использует NetworkX в памяти.

Для сети порядка 1 млн узлов архитектуру следует разделить на batch-compute и serving layer:

```text
Parquet / data warehouse
        │
        ▼
Polars / DuckDB / Spark
        │
        ▼
igraph / graph-tool / cuGraph / distributed graph engine
        │
        ▼
precomputed features + roles + ranking
        │
        ▼
DB / graph storage
        │
        ▼
API + web interface
```

Рекомендуемые изменения:

- отказаться от полного NetworkX-графа в одном Python-процессе;
- использовать более компактные graph engines (`igraph`, `graph-tool`, `cuGraph`) либо distributed processing;
- считать тяжёлые центральности приближённо;
- хранить рассчитанные признаки и роли в БД;
- frontend запрашивает только выбранный узел и локальное окружение;
- не передавать миллион узлов целиком в браузер;
- incremental/batch пересчёт вместо полного пересчёта при каждом запросе.

# AI-интерпретатор: возможное развитие

Основной аналитический pipeline **не зависит от LLM**.

Для production можно добавить локальный AI-интерпретатор по принципу:

```text
Analytical backend
      │
      ▼
structured facts for selected GID
      │
      ▼
local small LLM (on-demand)
      │
      ▼
human-readable AML explanation
```

При этом модель должна работать только по выбранному узлу/окружению и использовать рассчитанные факты, а не обрабатывать весь миллионный граф через внешний API.

Это позволяет:

- не платить за миллионы API-запросов;
- не отправлять банковские данные внешнему провайдеру;
- сохранять explainability;
- генерировать объяснение только по запросу аналитика;
- кэшировать уже созданные интерпретации.

В текущем репозитории LLM-интерпретатор **не реализован**; объяснения `evidence` и `why` формируются детерминированными правилами backend.

Для базовой проверки исходных parquet:

- один `nodes_roles` на каждый входной `gid`;

- `depth=4` не должен ошибочно становиться `terminal` из-за одного только обрыва данных.

# Безопасность и интерпретация

Система предназначена для **поддержки решения аналитика**, а не автоматического обвинения клиента.

Корректная формулировка:

> «Узел демонстрирует признаки консолидации и имеет высокий аналитический приоритет; требуется дополнительная проверка.»

Некорректная формулировка:

> «Клиент является организатором преступной схемы.»

Идентификаторы `gid` являются обезличенными, а текущий pipeline не требует ФИО, ИИН, возраста, дохода или иных персональных атрибутов.
