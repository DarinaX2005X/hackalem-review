# Firebird — умный подбор подрядчиков (#79-lite)

Сервис помогает заказчику выбрать до трёх event-подрядчиков из предоставленного каталога. Каждая карточка объясняет совпадение с запросом и приводит конкретный фрагмент описания профиля. Занятые на дату подрядчики не попадают в выдачу.

**Открыть сайт:** https://imfrqte.github.io/Rampage/index.html  
**Репозиторий команды:** https://github.com/imfrqte/Rampage

## Русский, қазақша, English и ИИ-помощник

Переключатель языка находится в шапке. Он переводит интерфейс, формы, карточки, сравнение, личный кабинет и сообщения, сохраняя введённые параметры. Выбор запоминается в браузере; доступны ссылки `?lang=ru`, `?lang=kk`, `?lang=en`. Имена и исходные тексты описаний/отзывов сохраняются на языке источника.

Кнопка «Помощник» открывает **локального помощника без сервера, регистрации и API-ключей**. После загрузки страницы вопросы обрабатываются в браузере, без сетевых запросов. Он сравнивает текущую подборку, ищет минимальную начальную цену с сохранением остальных ограничений, предлагает план подготовки и разбирает поддерживаемые запросы о городе, дате, категории и бюджете. Изменения формы применяются только по кнопке «Применить параметры».

Это подбор по правилам (`assistant-local.js`), **не нейросеть и не универсальный чат**. Неоднозначные или неподдерживаемые запросы требуют уточнения; цены и доступность берутся из демонстрационного каталога с календарём 23.09–31.12.2026. История диалога хранится только в памяти страницы и исчезает при обновлении. Для первой загрузки опубликованного сайта нужен интернет; офлайн-кеш всего сайта не устанавливается. Тесты: `node --test assistant-local.test.cjs`.

Прежняя облачная интеграция сохранена в папке `assistant/` для отдельного будущего подключения, но текущий интерфейс её не вызывает и `ai-config.json` не читает. Новая локальная реализация помощника не меняет авторизацию: общие аккаунты и письма по-прежнему требуют настроенного backend.

## Аккаунты, заявки и письма

### Без обязательной регистрации

Подбор, избранное, сравнение и просмотр профилей доступны сразу. На статическом GitHub Pages можно создавать, редактировать, отменять и удалять **демо-заявки** без почты и пароля. Они сохраняются только в этом браузере, не отправляются подрядчикам и не превращаются автоматически в настоящие заявки. При недоступном хранилище интерфейс предупреждает, что данные останутся только до перезагрузки. Вход и регистрация сохранены; в формах входа и регистрации есть «Продолжить без входа».

На настроенном Python-сервере доступна **настоящая заявка без аккаунта**: имя, email, дата, бюджет и пожелания. Ссылка из письма подтверждает адрес, после чего запрос поступает оператору. Пароль и регистрация не требуются. Статусы и отмена доступны из браузера, связанного с заявкой. Общая база, доставка писем и проверка CAPTCHA требуют развёртывания по [SERVER.md](SERVER.md); GitHub Pages сам эти службы не запускает. Гостевые запросы не создают записи зарегистрированных пользователей и не подключают рассылку автоматически.

`guest-store.js` хранит только локальные демо-заявки. `node --test guest-store.test.cjs` проверяет календарь, бюджет, сохранение, редактирование, отмену, удаление и работу при недоступном хранилище. Серверный гостевой сценарий проверяет `python -m unittest test_guest_server` без настоящей отправки писем.

В текущий Bento-интерфейс добавлены вход и регистрация, подтверждение почты, восстановление пароля, личный кабинет, подписка на новых подрядчиков и заявки с датой, примерным бюджетом и пожеланиями. В карточках и профилях кнопка называется «Демо-заявка» на GitHub Pages и «Оставить заявку» на настроенном сервере. Статусы и отмена находятся в соответствующем списке заявок; гостевой список доступен и после входа в аккаунт.

Кнопка «Продолжить без входа» возвращает к подбору с сохранением параметров или продолжает гостевую заявку на уже выбранного подрядчика. Личный кабинет требует входа; гостевые заявки доступны отдельно, без пароля. Настоящую заявку нужно подтвердить по почте.

**На GitHub Pages сервер не работает:** каталог, отзывы в браузере и избранное доступны, но настоящая регистрация, сохранение общих заявок, CAPTCHA и отправка писем требуют отдельного запуска сервера. До подключения формы явно показывают этот статус и не создают фиктивные аккаунты.

Серверная часть — `server.py` (Flask/SQLite), интерфейс — `accounts.js` и `accounts.css`. Настройка, локальный режим без реальных писем, обработка заявок и запуск рабочего почтового процесса описаны в [SERVER.md](SERVER.md). Секретные ключи и базу данных нельзя добавлять в GitHub. `test_server.py` проверяет API и ограничения доступа.

Заявка — запрос на согласование, а не оплата или гарантированная бронь. Каталог демонстрационный; реальные контакты подрядчиков не предоставлены, поэтому заявки не рассылаются им автоматически. Подписка добровольная и работает только после подтверждения почты.

## Быстрый запуск

Каталог разделён на HTML, CSS и JavaScript. Все рабочие файлы находятся непосредственно в корне репозитория. `index.html` — главная страница, `Firebird.html` — такая же страница для совместимости со старыми ссылками. Для статического каталога API-ключи, сборка и установка пакетов не нужны. Для аккаунтов, заявок и почты используйте серверный запуск из [SERVER.md](SERVER.md), а не простой HTTP-сервер ниже.

Скачайте репозиторий и запустите из его корня локальный HTTP-сервер (нужен Python 3):

```sh
python -m http.server 4173 --bind 127.0.0.1
```

Откройте http://127.0.0.1:4173.

## Совместное редактирование

Участники с правом записи в репозиторий могут редактировать файлы через GitHub или локально. Для одновременной работы используйте отдельные ветки и pull request в `main`. После сохранения изменений в `main` GitHub Pages публикует обновлённый сайт. Наличие имени в списке Contributors само по себе не предоставляет право записи.

При изменении разметки обновляйте `index.html` и `Firebird.html` одинаково. При изменении CSS или JavaScript обновляйте параметр `?v=` соответствующего ресурса в обеих HTML-страницах, чтобы сбросить браузерный кеш.

Старые архивы, отдельная прежняя серверная версия, автономная копия и дублирующая документация убраны; их можно восстановить через историю Git. Новый `server.py` обслуживает текущий сайт, а не отдельный HTML-дубликат. [Версия до очистки](https://github.com/imfrqte/Rampage/tree/04a6ad6d602b0a46816bd7c30506cefbd521bf2b) также содержит исходный CSV, прежний сборщик и тесты подбора внутри архива проекта.

До 20 локальных отзывов на профиль хранятся только в текущем браузере (`firebird:reviews:v1`); их можно удалить. Это не серверная публикация, другим посетителям они не видны. Собственные отзывы показаны отдельно от демо-рейтинга.
- Избранное: до трёх профилей, сохранение в текущем браузере и таблица сравнения цены, языков, форматов и длительности.

- Предпочтения хранятся локально под ключом `firebird:preferences:v1`, не отправляются на сервер. При недоступном хранилище подбор и избранное работают в пределах открытой страницы.

## Что реализовано

- Все 66 профилей, 17 категорий, 6 форматов из датасета; справочник расширен до 20 городов Казахстана и «Зарубежья».
- Обязательные входы: город, дата, формат, категория, бюджет в тенге за мероприятие. Опциональные: язык и длительность присутствия.
- До трёх карточек с именем, категорией, городом, ценой «от» и объяснением на основании полей и дословного фрагмента описания.
- Три явных исхода: `matched` — подобрали; `no_category` — в городе нет этой категории; `no_matches` — категория есть, но никто не прошёл все условия.
- Если карточек меньше трёх, указано количество исходных кандидатов и причины исключения. У профиля может быть несколько причин; их счётчики не нужно складывать.
- Площадки и люди проходят один и тот же фильтр занятости. Поиск по любой категории из списка профиля поддерживается.
- После смены только даты показано, кто из прежней подборки теперь занят и кто из новой был занят раньше.
- Цены и города, заполненные при подготовке датасета, отмечены отдельно. Синтетические профили организаторов отличимы от остальных анонимизированных профилей.
- Пять кнопок демонстрационных запросов, подробный профиль с источником, адаптивная форма и необязательный WebMCP-инструмент для поддерживающих браузеров.

## Как устроено решение

1. **Валидация.** Проверяем значения справочников, дату, бюджет, язык и длительность. Календарь известен только с 23.09.2026 по 31.12.2026 включительно; вне этого окна выдаём понятную ошибку, не предполагаем свободные даты.
2. **Город и категория.** Сначала формируем исходный список. Пустой список означает отдельный исход `no_category`, независимо от других фильтров.
3. **Жёсткие фильтры.** Исключаем занятых (`busy_dates`), неподдерживаемый формат, начальную цену выше бюджета, неподдерживаемый язык, недостаточный `max_hours`. Пустая начальная цена не принимается за ноль. `max_hours = null` означает работу без привязки к присутствию, поэтому фильтр длительности не применяется.
4. **Детерминированное ранжирование.** Считаем число различных тематических основ слов в описании для выбранного формата. Например, для корпоратива: `корпоратив`, `бизнес`, `делов`, `бренд`, `компан`, `тимбил`. При равенстве сначала идут записи без `price_imputed`, затем без `city_imputed`, затем с меньшей начальной ценой и меньшим лексикографическим ID. `synthetic` не влияет на порядок.
5. **Объяснение.** В карточке отдельно показаны совпадения по полям, статус календаря и дословный фрагмент описания. В подробном профиле доступно полное текстовое объяснение. Выбор фрагмента учитывает формат, слова об услуге и редкость слов в корпусе; приветствия и перечисления клиентов штрафуются. Это извлечение текста, не генерация новых фактов. Полный исходный текст и ID доступны в карточке.
6. **Выдача.** Берём первые три записи. Объясняем недостаток вариантов и сохраняем проверяемые причины исключения остальных.

Одинаковый запрос возвращает одинаковые ID, порядок и объяснения. Время, случайные числа и сетевые ответы не участвуют в расчёте. Числовой балл — прозрачная эвристика, не вероятность качества подрядчика.

## Архитектура и технологии

Подбор и локальный помощник работают в статических HTML/CSS/JavaScript без библиотек, API-ключей и сервера приложений. Аккаунты, общие заявки и письма используют отдельную серверную часть на Python. `assistant.js` — интерфейс чата, `assistant-local.js` — локальный разбор запросов с использованием того же `matcher.js`; форма не меняется без нажатия кнопки применения. Обученная модель, эмбеддинги и дообучение в текущем браузерном режиме не используются.

```text
catalog.js → данные каталога в браузере
Форма → matcher.validate → фильтры → ранжирование → объяснения → app.js → карточки
```

- `index.html`, `Firebird.html`, `styles.css` — основные страницы и оформление.
- `catalog.js` — типизированные поля исходного CSV и происхождение данных (включая SHA-256).
- `matcher.js` — фильтрация, ранжирование, объяснения и сравнение дат.
- `app.js` — форма, карточки, состояния, примеры, диалог профиля и WebMCP.
- Остальные CSS/JS расширяют интерфейс, как описано выше.

## Данные и смысл цены

Источник — предоставленный участником `hackathon dataset anonymized .csv`; для текущего сайта данные включены в `catalog.js`. Исходный CSV сохранён без изменения байтов в прежнем архиве проекта, доступном через историю Git. HTML-превью использовалось только как справочный материал; основным источником служит CSV. JSONL не предоставлялся.

В датасете 66 записей: 53 анонимизированных несинтетических профиля и 13 синтетических профилей организаторов. Город заполнен при подготовке в 8 записях, цена — в 18. Собственные синтетические профили не добавлены. Имена вымышленные. У одного подрядчика может быть несколько категорий, поэтому сумма численности категорий превышает 66.

`price_from_kzt` — цена **от** за мероприятие, не фиксированная смета и не почасовая ставка. Проверка `price_from_kzt <= budget` означает только прохождение фильтра начальной цены. Не обещаем экономию, фиксированный пакет или окончательную стоимость. Цена не умножается на часы.

`busy_dates` полностью определяет календарь в указанном 100-дневном окне. Отсутствие даты в списке означает «не занят по календарю датасета», а не подтверждение от реального подрядчика.

## Ограничения и развитие

Нет оплаты и независимой проверки сведений у подрядчиков. Заявки и почтовые уведомления требуют настроенного сервера; подтверждение заявки оператором не заменяет договорённость с реальным подрядчиком. Поиск работает только по предоставленному каталогу и календарю. Свободный текст не переопределяет структурированные город, формат, язык, цену или занятость. Лексическая эвристика может пропускать синонимы и не понимает отрицания как полноценная языковая модель.

Следующий шаг — сравнить текущий метод с готовыми эмбеддингами на оценённых запросах, сохранив жёсткие фильтры и проверяемые объяснения. API-ключи при такой интеграции должны храниться на сервере. Автоматическая отправка решения на платформу хакатона не выполнялась.
