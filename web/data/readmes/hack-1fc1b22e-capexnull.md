# Аким на 5 часов

AI-симулятор городских управленческих решений для Астаны. Пользователь получает бюджет 100 условных единиц, выбирает ровно пять мероприятий и назначает районы для районных мер. Приложение рассчитывает последствия, показывает Astana Quality of Life Score и объясняет результат с помощью AI. После расчёта можно проверить устойчивость стратегии к неожиданному городскому событию.

Городское управление требует одновременно учитывать транспорт, экологию, социальную инфраструктуру, безопасность и городские сервисы при ограниченном бюджете. Симулятор помогает сравнивать последствия распределения ресурсов, замечать слабые места районов и понимать компромиссы выбранной стратегии.

## Как работает приложение

1. На главной странице показаны исходные показатели пяти районов: Есиль, Алматы, Сарыарка, Байконур и Нура.
2. Пользователь выбирает пять мероприятий из каталога M1–M14. Для каждой районной меры назначает район; городская действует на все районы.
3. Панель «Выбранные мероприятия» показывает состав набора, использованный бюджет и остаток.
4. По кнопке «Рассчитать сценарий» система проверяет допустимость набора и рассчитывает последствия на горизонте восьми кварталов.
5. Результат содержит итоговую оценку, изменение относительно исходных **52.56**, сравнение районов и изменения показателей.
6. AI-анализ объясняет сильные стороны, риски, компромиссы и рекомендации.
7. В блоке «Неожиданное городское событие» можно выбрать событие и район, получить новое состояние города и объяснение последствий.

## Архитектура

Интерфейс собирает решения, сервер проверяет их и выполняет математический расчёт. Только после этого рассчитанные факты передаются AI для объяснения. Отображение результата отделено от вычислений.

```text
UI → Validator → Mathematical Engine → Agentic AI → UI
                         ↓
              структурированный результат
```

| Компонент | Ответственность | Реализация |
| --- | --- | --- |
| Пользовательский интерфейс и ввод | Каталог, выбор районов, бюджет, состояния загрузки и ошибок | `index.html`, `src/ui/`, `src/scenario/` |
| Validator | Проверка структуры, бюджета, количества мер и несовместимостей до расчёта | `src/validator/index.js` |
| Mathematical Engine | Исходные данные, эффекты, лаги, синергии, ограничения и детерминированная оценка | `src/engine/` |
| Agentic AI backend | Вызов OpenAI API, получение и проверка объяснения | `src/ai/backend.js` |
| Слой событий | Каталог воздействий, независимое состояние после события и пересчёт оценки | `src/dynamic/` |
| Представление результата | Оценки, сравнение районов и AI-анализ | `src/result/index.js` |
| Сервер и API | Статические файлы, последовательность обработки запросов, хранение рассчитанных сценариев в памяти | `server.js` |

Сервер управляет последовательностью действий. LLM интерпретирует результат и не запускает математический расчёт самостоятельно. При ошибке AI численный результат остаётся доступен, а интерфейс сообщает о недоступности объяснения.

### API

| Запрос | Назначение |
| --- | --- |
| `GET /api/scenario` | Исходные показатели, каталог, районы и бюджет. Повторяемый параметр `measure`, например `?measure=M7&measure=M8`, возвращает предварительную стоимость набора |
| `POST /api/scenario` | Проверка и анализ набора: объект с `mode: "MATAN-only"` и массивом `decisions`; каждое решение содержит `measureId`, а районное — также `districtId` |
| `POST /api/event` | Анализ события: объект с `scenarioId`, `eventType` и `district`; идентификатор сценария берётся из заголовка `X-Scenario-Id` базового ответа, тип события — из `src/dynamic/catalog.js` |

Базовый ответ содержит `calculation` — математический результат, `aiAnalysis` — объяснение и `aiError` — сообщение при недоступности AI. Ответ события содержит `event` — рассчитанные последствия, а также `aiAnalysis` и `aiError`.

Недопустимый набор получает HTTP 422 с причиной: его оценка не рассчитывается, AI не вызывается. Запрос события без сохранённого базового сценария получает HTTP 409. Сценарии хранятся в памяти процесса; после перезапуска сервера нужно выполнить базовый расчёт снова.

## Показатели и математическая модель

Каждый район описан десятью показателями по шкале **0–100: больше — лучше**. Исходные значения, веса, доли населения и каталог мероприятий находятся в `src/engine/data.js`.

| Код | Показатель | Вес |
| --- | --- | --- |
| T1 | Разгрузка дорог | 0.10 |
| T2 | Доступность общественного транспорта | 0.10 |
| E1 | Озеленение | 0.09 |
| E2 | Качество воздуха | 0.11 |
| S1 | Школы и детсады | 0.11 |
| S2 | Поликлиники и первичная медпомощь | 0.11 |
| B1 | Безопасность улиц | 0.09 |
| B2 | Безопасность дорожного движения | 0.09 |
| C1 | Надёжность ЖКХ | 0.10 |
| C2 | Скорость решения обращений жителей | 0.10 |

Доли населения в модели: Есиль — 0.27, Алматы — 0.24, Сарыарка — 0.20, Байконур — 0.13, Нура — 0.16.

### Эффекты мероприятий

Лаг — задержка реализации мероприятия в кварталах. На горизонте восьми кварталов эффект учитывается с множителем `(8 − лаг) / 8`. Районный эффект применяется только к назначенному району, городской — к каждому из пяти районов.

Для формул: `d` — район, `k` — показатель, `m` — мероприятие; `I_dk` — исходное значение, `I'_dk` — итоговое значение, `effect_m,k` — эффект мероприятия, `L_m` — его лаг. Сумма включает только меры, действующие на данный район. Дополнительные совместные эффекты обозначены `synergies_dk`. Функция `clip(x, 0, 100)` ограничивает значение диапазоном от 0 до 100.

```text
I'_dk = clip(I_dk + Σ_m(effect_m,k × (8 − L_m) / 8) + synergies_dk, 0, 100)
```

Совместные эффекты применяются после обычных эффектов, без масштабирования по лагу:

- M1 + M2: разгрузка дорог +2 в районе M1.
- M5 + M6: качество воздуха +2 в районе M5.
- M10 + M12: безопасность улиц +2 в районе M10.

Ограничение диапазона применяется после суммирования всех эффектов и синергий. Промежуточного округления нет.

### Итоговая оценка

Оценка района (`D_d`) — взвешенная сумма его итоговых показателей; `w_k` — вес показателя. Средневзвешенная оценка города (`D_avg`) учитывает долю населения каждого района (`pop_d`). Количество критических показателей (`N_crit`) — число пар «район × показатель» со значением **строго ниже 40**; значение 40 критическим не считается.

```text
D_d = Σ_k(w_k × I'_dk)
D_avg = Σ_d(pop_d × D_d)
N_crit = число пар (d, k), для которых I'_dk < 40
Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit
```

Последняя формула задаёт Astana Quality of Life Score: 70% приходится на среднюю оценку города, 30% — на оценку самого слабого района, затем вычитается по одному баллу за каждый критический показатель. Такой расчёт учитывает и общий уровень, и территориальный дисбаланс.

Все численные результаты рассчитываются детерминированным Mathematical Engine и модулем пересчёта состояния события по той же формуле. Agentic AI самостоятельно оценку, бюджет и другие математические показатели не рассчитывает. Для отображения оценки округляются до двух знаков; изменение вычисляется из неокруглённых значений.

## Правила сценария

- Общий бюджет — 100 условных единиц; стоимость набора не должна его превышать.
- Требуется ровно пять разных мероприятий. Каждое используется максимум один раз.
- Для районной меры выбирается один из пяти районов. Для городской район не назначается.
- Допускается максимум два мероприятия одного направления.
- M1 «Районная мобильность» и M3 «Транспортная инфраструктура» несовместимы независимо от района.
- M4 «Экология района» и M7 «Социальная инфраструктура» несовместимы в одном районе.
- M5 «Экологическая инфраструктура» и M13 «Районные сервисы» несовместимы в одном районе.

Validator отклоняет нарушения до расчёта последствий. Порядок выбора не влияет на результат: решения приводятся к фиксированному порядку по номерам мероприятий. Предварительное обновление бюджета при выборе мер не является расчётом итоговой оценки сценария.

## Agentic AI и внешний сервис

OpenAI API используется сервером для интерпретации рассчитанных результатов. В основном сценарии AI получает проверенный набор решений и рассчитанные численные факты. При событии передаётся только рассчитанный результат события, включая показатели и оценки до и после воздействия.

Объяснение состоит из итога, сильных сторон, рисков, компромиссов и рекомендаций. Сервер запрашивает структурированный ответ через Responses API (`https://api.openai.com/v1/responses`) и проверяет пять обязательных полей: `summary`, `strengths`, `risks`, `tradeoffs`, `recommendations`. Дополнительно проверяются пользовательские формулировки и формат чисел. Эти проверки не доказывают смысловую точность каждого утверждения AI.

Вызов ограничен 30 секундами. Ошибка сервиса, отказ или некорректный ответ приводят к сообщению о недоступности AI без потери математического результата. Формулировки объяснений могут различаться; численные результаты одинакового сценария воспроизводимы.

## Проверка устойчивости к событиям

Динамический режим позволяет проверить выбранную стратегию при неожиданном изменении городской ситуации:

```text
Рассчитанная стратегия → выбранное событие и район → изменение показателей
→ новое состояние города → повторный расчёт оценки → AI-анализ последствий
```

| Демонстрационное событие | Воздействие на выбранный район |
| --- | --- |
| Перекрытие крупной магистрали | Разгрузка дорог −20 |
| Сильное загрязнение воздуха | Качество воздуха −20 |
| Рост нагрузки на социальную инфраструктуру | Школы и детсады −10; поликлиники и первичная медпомощь −10 |
| Ухудшение дорожной безопасности | Безопасность дорожного движения −20 |
| Авария теплосети | Надёжность ЖКХ −20 |

Эти воздействия — **синтетические демонстрационные параметры проекта**, отсутствующие в исходном датасете организаторов.

Событие запускается пользователем. Оно изменяет только предусмотренные каталогом показатели выбранного района, с ограничением значений до 0–100. Остальные показатели сохраняются. Оценка пересчитывается по приведённой выше формуле, включая строгий критический порог ниже 40.

Каждый запуск начинается с неизменяемого результата выбранных пяти мероприятий. Воздействие применяется один раз; повторный запуск не накапливает ущерб, а мероприятия M1–M14 заново не применяются. После проверки допустимости сохраняется результат события и запрашивается AI-анализ. AI может объяснить необходимость пересмотра стратегии, но автоматического перераспределения бюджета или второго инвестиционного цикла приложение не выполняет.

## Технологии и системные требования

- **Node.js ≥22** — сервер, встроенные HTTP, файловые операции, `fetch` и средство тестирования `node:test`. Это минимальная версия, указанная в `package.json`.
- **JavaScript с ES-модулями, HTML и CSS** — приложение без frontend-фреймворка и этапа сборки.
- **OpenAI Responses API** — объяснение результатов; запросы выполняются встроенным `fetch`, без отдельного SDK.
- **Git** — получение официального репозитория.
- **Современный браузер** — работа с интерфейсом. Полный набор тестов запускает Microsoft Edge в фоновом режиме без окна.

Внешних npm-зависимостей нет. База данных и отдельный сервер статических файлов не требуются. Приведённые команды рассчитаны на Windows 11 / PowerShell. Для реального AI-анализа нужны HTTPS-доступ к `api.openai.com`, действующий API-ключ и доступ к выбранной модели. Для получения репозитория нужен доступ к GitHub.

## Установка

Установите Git и Node.js с npm, затем откройте PowerShell в каталоге, где будет размещён проект:

```powershell
git clone https://github.com/BAITC-Hacks/hack-1fc1b22e-capexnull.git
Set-Location hack-1fc1b22e-capexnull
node --version
npm --version
```

Команда `node --version` должна показать версию не ниже 22. Отдельный `npm install` не нужен: в `package.json` нет внешних зависимостей. Сборка также не требуется.

## Настройка окружения

| Переменная | Назначение |
| --- | --- |
| `OPENAI_API_KEY` | Серверный ключ для реального AI-анализа. Без него математический расчёт работает, а вместо объяснения отображается сообщение о недоступности AI |
| `OPENAI_MODEL` | Необязательное имя модели; при отсутствии или пустом значении используется `gpt-5.6-luna`, заданная в backend |
| `PORT` | Необязательный порт сервера, по умолчанию `3000` |
| `EDGE_PATH` | Необязательный путь к исполняемому файлу Microsoft Edge для браузерного теста; на работу приложения не влияет |

В той же сессии PowerShell, из которой будет запущен сервер, введите ключ через скрытый запрос. Команды не записывают его в файл или историю команд:

```powershell
$secureKey = Read-Host 'OPENAI_API_KEY' -AsSecureString
$env:OPENAI_API_KEY = [System.Net.NetworkCredential]::new('', $secureKey).Password
Remove-Variable secureKey
```

Если `OPENAI_MODEL` уже настроена для доступной модели, сохраните это значение. При отсутствии переменной сервер использует указанную выше модель по умолчанию. Для явной настройки и стандартного порта:

```powershell
$env:OPENAI_MODEL = 'gpt-5.6-luna'
$env:PORT = '3000'
```

Приложение читает переменные окружения процесса. Файлы `.env` автоматически **не загружаются**.

### Проверка AI-функций

Основная математическая логика приложения, проверка сценариев и моделирование городских событий выполняются локально и детерминированно.

Для генерации AI-анализа приложение использует OpenAI API на стороне сервера. Для запуска реального AI-анализа требуется переменная окружения `OPENAI_API_KEY`. API-ключ хранится только в окружении процесса и не передаётся в браузер.

Автоматические тесты проверяют контракт AI-интеграции с помощью mock-ответа и не требуют доступа к OpenAI API. Для проверки реального AI-анализа необходимо перед запуском сервера задать действующий `OPENAI_API_KEY` в окружении.

```powershell
$secureKey = Read-Host 'OPENAI_API_KEY' -AsSecureString
$env:OPENAI_API_KEY = [System.Net.NetworkCredential]::new('', $secureKey).Password
Remove-Variable secureKey
```

Затем в той же сессии PowerShell запустите `npm start` из корня проекта.

## Запуск

Из корня проекта, в подготовленной сессии PowerShell:

```powershell
npm start
```

Откройте **http://127.0.0.1:3000**. Сервер слушает только локальный адрес `127.0.0.1`; при изменении `PORT` используйте соответствующий порт в URL. Остановка — `Ctrl+C`.

Скрипт `start` запускает `node --watch server.js`, поэтому изменения отслеживаемого кода перезапускают сервер. Для запуска без наблюдения за файлами можно использовать `node server.js` вместо `npm start`.

| Мероприятие | Район | Стоимость |

3. Нажмите «Смоделировать событие».
4. Ожидаемый **Astana Quality of Life Score после события — 55.72**, до события — **56.54**, изменение — **−0.82**. Надёжность ЖКХ Нуры меняется с **60** на **40**; критических показателей остаётся **0**. При доступном OpenAI API отображается «AI-анализ события».

Этот пример служит воспроизводимой проверкой динамического режима. Повторное нажатие с теми же параметрами должно дать тот же численный результат, сохраняя исходный результат стратегии.

### Пересмотр стратегии после события

После расчёта события нажмите «Пересмотреть стратегию». В существующем каталоге измените состав пяти мероприятий или их районы, затем нажмите «Рассчитать адаптированную стратегию». Новый набор проходит те же проверки и независимо укладывается в бюджет 100.

Приложение сравнивает две альтернативные стратегии при одном событии в одном районе. Каждый план рассчитывается от исходного состояния города, после чего событие применяется ровно один раз. Первоначальный результат сохраняется. Это контрфактическое сравнение: расходы планов не суммируются, дополнительный бюджет не выделяется, а новый план не считается физически реализованным после события.

В сравнении показаны оценки обеих стратегий после события, их разница, критические показатели, районные оценки, изменения показателей, расходы и остаток каждого плана. AI объясняет рассчитанные различия, риски и компромиссы. Для контрольной проверки оставьте первоначальный набор без изменений: обе оценки после аварии теплосети в Нуре должны быть **55.72**, разница — **0.00**.

Расчёт сравнения реализован в `src/adaptation/index.js`, отображение — в `src/adaptation/ui.js`. Серверный `POST /api/adaptation` принимает `eventId` из заголовка `X-Event-Id` ответа события и альтернативный `scenario`; событие и район берутся из сохранённого сервером результата.

## Безопасность

API-ключ хранится в окружении серверного процесса. Frontend его не получает; сервер передаёт ключ OpenAI в заголовке авторизации и не включает его в пользовательский ответ. Тексты ошибок провайдера пользователю не передаются.

`.gitignore` исключает `.env` и `.env.*`. В отслеживаемых файлах проверенной версии секретного файла окружения и значения API-ключа нет. Реальные ключи и токены не следует добавлять в исходный код или документацию.

## Данные и ограничения

Данные районов синтетические. Числовая модель и каталог мероприятий зафиксированы в коде; внешние городские источники в реальном времени не подключаются. События и их эффекты служат демонстрации устойчивости стратегии.

Приложение является симулятором для анализа управленческих сценариев. Его результаты отражают заданную модель и не являются откалиброванным прогнозом реальных последствий городских решений.
