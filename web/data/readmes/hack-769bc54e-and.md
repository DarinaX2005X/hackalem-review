# ТойМатч

ТойМатч подбирает event-подрядчиков под той, свадьбу или корпоратив: три карточки из каталога,
у каждой своя причина, почему именно она. Название - от «той» и «match».

## Описание решения и его назначение

Сервис помогает заказчику мероприятия в Казахстане выбрать event-подрядчика из каталога:
вместо длинного списка - до трёх карточек, и у каждой объяснение, почему она здесь.

Заказчик уже выбрал город, дату, тип мероприятия и категорию подрядчика и задаёт бюджет;
длительность, язык и пожелания - по желанию. Сервис отсекает занятых на эту дату и не
подходящих по формату, бюджету, языку и часам, ранжирует оставшихся по фиксированной
формуле и объясняет каждую карточку фактами: запас по бюджету, форматы, языки, цитата из
описания. Если подходящих меньше трёх или нет совсем, он говорит, что именно помешало и
какое одно изменение запроса даст результат.

**Отбор и порядок карточек - детерминированный код, модель только пишет объяснения.**
Поэтому тот же запрос всегда даёт тот же порядок (требование 5 ТЗ), а отбор работает и
без ключей к модели. Модель встроена как **агент**: она сама вызывает инструмент поиска,
читает посчитанные факты и пишет по ним объяснения. Каждый шаг виден в журнале. Механизм
подтверждения человеком в ядре есть, но в этой Задаче не задействован: ТЗ исключает
бронирование, заявки и уведомления подрядчику.

## Описание архитектуры

```
форма запроса ──> LLM: вызывает search_contractors с параметрами          ← агентный шаг
                        │
                        ▼  чистый Python: детерминированно, без сети и ключей
     жёсткие фильтры: город, категория, занятость на дату, формат, бюджет, часы, язык
                        ▼
     скоринг с фиксированными весами (WEIGHTS) ──> до 3 карточек + посчитанные факты
                        ▼
     меньше трёх? ──> диагностика: что помешало, какая дата, какой бюджет, сезон
                        │
                        ▼
                  LLM: объяснения к карточкам по фактам, порядок не меняет
                        ▼
     интерфейс: исход, карточки, плашки честности, «почему» и «что сделать», журнал шагов
```

| Слой | Где | За что отвечает |
|---|---|---|
| Цикл агента | `backend/agent/core/loop.py` | шаг за шагом ведёт запуск, ставит на паузу, продолжает |
| Доступ к модели | `backend/agent/core/llm.py` | единственное место вызова LLM; здесь же mock-режим |
| Реестр инструментов | `backend/agent/core/tools.py` | регистрация, JSON-схемы, безопасный вызов |
| **Предметная область** | `backend/agent/core/domains/contractors.py` | фильтры `_reasons`, скоринг `_score` и `WEIGHTS`, диагностика `_diagnose`, инструменты `search_contractors` и `diagnose_request`, промпт и демо-примеры |
| Каталог | `backend/agent/data/contractors.csv` | 66 профилей от организатора, читается без сети |
| Системный промпт | `backend/agent/core/prompts.py` | общая часть + `BRIEF` активного домена |
| HTTP API | `backend/agent/views.py`, `urls.py` | JSON-эндпоинты под `/api/` |
| Интерфейс | `frontend/app/page.tsx`, `frontend/components/` | форма запроса, исход и карточки (`Results.tsx`), журнал шагов (`Journal.tsx`) |
| Команды разработки | `scripts/dev.py`, `scripts/verify.py`, `scripts/check_llm.py` | установка, запуск, тесты, сквозная проверка, проверка провайдера |
| Прогон качества | `backend/agent/evals/` | набор кейсов и отчёт о результатах в `docs/EVAL.md` |

Состояние запуска целиком лежит в БД (`Run.messages`, `Run.pending`), поэтому
запуск можно поставить на паузу ради человека и продолжить позже.
Ядро не знает о предметной области: смена Задачи = новый файл в `core/domains/`
и одна строка в `.env`.

### API

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | режим работы, модель, активный домен |
| GET | `/api/options` | словари формы из каталога: города, категории, форматы, языки |
| GET | `/api/samples` | готовые демо-запросы активного домена |
| POST | `/api/runs` `{task, input}` | запустить подбор: `task` - запрос, собранный формой, `input` - пусто |
| GET | `/api/runs/<id>` | статус и все шаги (интерфейс опрашивает раз в секунду) |
| POST | `/api/runs/<id>/approve` `{approve: bool}` | решение человека по действию, меняющему внешнюю систему; в этой Задаче таких действий нет, эндпоинт остаётся частью ядра |

Контракт продублирован в `frontend/lib/types.ts` - при изменении `views.py` правится в том же коммите.

## Параметры окружения

Все параметры задаются в `.env` в корне (шаблон - `.env.example`). Переменные не обязательны:
без `.env` используются значения по умолчанию.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AGENT_DOMAIN` | `contractors` | имя модуля предметной области из `backend/agent/core/domains/` |
| `OPENAI_API_KEY` | пусто | ключ провайдера. Пусто → автоматически включается mock-режим |
| `OPENAI_BASE_URL` | пусто | пусто = api.openai.com. Любой OpenAI-совместимый endpoint |
| `OPENAI_MODEL` | пусто | модель **с поддержкой tool calling**. Пусто → mock-режим |
| `LLM_MOCK` | `0` | `1` - заскриптованная «модель» без сети. Включается сам, если пуст `OPENAI_API_KEY` или `OPENAI_MODEL` |
| `AGENT_MAX_STEPS` | `12` | предел вызовов модели за один запуск |
| `DJANGO_SECRET_KEY` | `dev-only-change-me` | ключ Django |
| `DJANGO_DEBUG` | `1` | режим отладки |
| `NEXT_PUBLIC_API_URL` | `http://localhost:8000` | адрес API для фронтенда |

**Проверка без наших учётных записей (п. 5.6.6 Положения).** При пустом `OPENAI_API_KEY`
приложение работает в mock-режиме: настоящая модель заменена заскриптованным сценарием,
но отбор, порядок карточек, диагностика, вызовы инструментов и журнал - настоящие, потому
что их делает код, а не модель. Объяснения в карточках в этом режиме собирает код из
посчитанных фактов - в том же формате, что пишет модель: ведущий факт, цена относительно
бюджета, форматы, языки. Личные аккаунты и платные подписки участников для проверки не требуются.
Чтобы увидеть работу с настоящей моделью, впишите в `.env` `OPENAI_API_KEY` и `OPENAI_MODEL`,
поставьте `LLM_MOCK=0` и перезапустите бэкенд. Перед этим стоит проверить провайдера:

```bash
python scripts/dev.py llm
```

Команда покажет endpoint, список доступных моделей и сделает один пробный вызов с
tool calling - именно на нём держится агент, и поддерживают его не все модели.
Смена провайдера - одна строка `OPENAI_BASE_URL`, код не меняется.

Это же место позволяет подключить **свою модель на своём GPU**: NIM-контейнер или vLLM
отдают OpenAI-совместимый `/v1`, поэтому достаточно указать адрес инстанса. Решение не
привязано к вендору - один и тот же агент работает на облачном API и на self-hosted модели.
При self-hosted не оставляйте `OPENAI_API_KEY` пустым: пустой ключ включает mock-режим,
подойдёт любая непустая строка.

## Принятые допущения

Ответов от организаторов на уточняющие вопросы не будет, поэтому мы работали по тексту ТЗ
и двум присланным файлам. В двенадцати местах ТЗ допускает больше одного прочтения, и
каждое из них мы закрыли **решением**, а не вопросом. Ниже - что решили, почему и чем
это проверяется. Тесты лежат в `backend/agent/tests.py` и запускаются командой
`python scripts/dev.py check`.

### Меняют поведение отбора

**1. Бюджет - потолок на одного подрядчика.**
Поле называется `price_from_kzt`, «цена от, ₸ за мероприятие», а вход по ТЗ - «бюджет (₸)»
в одном ряду с категорией, то есть на одну позицию. Фильтр: `price_from ≤ бюджет`.
*Проверка:* `test_diagnosis_names_the_budget_that_would_help`.

**2. Детерминизм обязателен для порядка, текст объяснений может отличаться.**
Требование 5 говорит про порядок карточек. Порядок задаёт код и от модели не зависит
вообще; формулировки пишет LLM, и между запусками они могут разниться.
*Проверка:* `test_order_is_deterministic` - пять прогонов, один порядок.

**3. Язык - жёсткий фильтр, но только когда он указан.**
В ТЗ язык опционален. Указан - подрядчик обязан его заявить: клиент, которому нужен
казахский, не обрадуется ведущему без казахского. Не указан - фильтр не применяется,
но широта языков даёт небольшой плюс в скоринге.
*Последствие:* запрос с казахским отсекает 42 профиля из 66. Это намеренно.
Длительность работает так же: указана - отсекает тех, у кого `max_hours` меньше запрошенного;
профили без часов проходят (допущение 7). В ТЗ (требование 6) названы только занятость,
бюджет и формат, язык и часы отсекают жёстко по нашему решению.

**4. Не проходящий по бюджету в карточки не попадает, но виден среди отсеянных.**
Требование 3 запрещает показывать занятых на дату. Про бюджет такого запрета нет, но
карточка - это рекомендация, а рекомендовать то, что клиенту не по карману, нечестно.
Поэтому такие кандидаты уходят в список отсеянных (`rejected` в ответе поиска) с точной
причиной и процентом превышения, а подсказки (`suggestions`) называют минимальный
достаточный бюджет.

### Краевые случаи

**5. Дата вне окна 23.09–31.12.2026 - предупреждение, а не отказ.**
Календарь занятости в датасете ограничен этим окном. Вне его мы не знаем, кто занят,
и молча считать всех свободными значило бы соврать. Поиск отрабатывает, но ответ
содержит `warning` о том, что данных о занятости на эту дату нет, и интерфейс его показывает.
*Проверка:* `test_date_outside_the_calendar_window_is_flagged`.

**6. «Зарубежье» - отдельный город, в выдачу по Алматы и Астане не подмешивается.**
В датасете такой профиль один. Клиент, ищущий подрядчика в Астане, не ждёт зарубежного.
Если категории нет в его городе, подсказки честно скажут, где она есть.

**7. `max_hours = null` проходит любой фильтр по длительности.**
ТЗ прямо говорит: пусто означает, что работа не привязана к присутствию - флорист,
декоратор, сувениры. Отсекать их по часам значило бы терять правильных кандидатов.
*Проверка:* `test_profile_without_max_hours_survives_duration_filter`.

**8. Категория обязательна на входе.**
По легенде клиент уже получил каталог по своей категории, а требование 6 предусматривает
исход «в этом городе такой категории нет» - значит, категорию задаёт пользователь.
Поиск «по всем категориям сразу» не поддерживается.

### Данные и подача

**9. Свои синтетические профили не добавляли.**
ТЗ это разрешает, но 66 профилей хватает на все сценарии Definition of Done, включая
пустой результат и редкие категории. Добавление своих записей размывает границу
между данными организатора и нашими. Если добавим - только с `synthetic: true`
и видимой пометкой в карточке; механизм пометки уже работает на 13 синтетических
профилях из исходного датасета.

**10. Интерфейс и объяснения - на русском.**
Описания подрядчиков в датасете русские, работаем в казахстанском контексте.
Промпты и описания инструментов - на английском, как и остальной код.

**11. Профиль с несколькими категориями полноправен в каждой.**
`categories` - список, фильтр работает по вхождению.
*Проверка:* `test_category_filter_matches_any_of_the_profile_categories`.

**12. Источник данных - присланный CSV, положенный в репозиторий.**
ТЗ упоминает `.jsonl` как основной формат, но нам прислали `.csv` и HTML-превью.
Файл лежит в `backend/agent/data/contractors.csv`: проверяющий разворачивает проект
без доступа к Google Drive и без интернета.

## Известные упрощения

Заявлены честно, чтобы эксперт не тратил время на их поиск:

- фоновые потоки вместо очереди задач (для продакшена - Celery/RQ, интерфейс тот же);
- SQLite вместо полноценной СУБД;
- нет авторизации, CORS открыт, `ALLOWED_HOSTS = ["*"]` - конфигурация для демонстрации;
- релевантность описания считается лексически, по основам слов, а не эмбеддингами:
  так отбор работает без сети и ключей;
- каталог кэшируется при первом обращении - после правки CSV нужен перезапуск бэкенда;
- данные о занятости есть только на окно 23.09–31.12.2026;
- веса скоринга подобраны вручную и зафиксированы в `WEIGHTS`;
- длина объяснения (1–2 предложения) задана промптом и проверяется прогоном, а не кодом:
  в редких случаях модель пишет три предложения.

Подробнее - в `SCOPE.md`, раздел «Известные ограничения».
