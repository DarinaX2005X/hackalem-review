# Центр закупок · HackAlem AI

**Объяснимое пополнение склада: от данных 1С до проверенного заказа поставщику.**

Проект для ТОО «Электрокомплект» (ekt.kz), трек 05 «Логистика» HackAlem AI. Пользователь — менеджер закупок: он получает рекомендации, видит расчёт по каждому товару, корректирует количество, утверждает заказ и выгружает его в CSV/XLSX.

Сегодня менеджер сводит данные в Excel вручную. Это занимает время, а разовые крупные отгрузки и периоды отсутствия товара искажают обычный спрос. Сервис автоматизирует расчёт и сохраняет его объяснение, чтобы менеджер мог регулярно пересматривать закупки и обоснованно управлять риском дефицита и избыточным запасом. Денежный эффект и точность прогноза на данных партнёра пока не измерены.

Компания-пользователь — Электрокомплект. Спрос — её отгрузки клиентам из собственной 1С. IEK и Systeme Electric — первые поставщики/бренды в переданных данных; архитектура поддерживает других поставщиков и склады компании.

**Начало работы:** начните с [быстрого запуска](#быстрый-запуск) и пройдите [сценарий менеджера](#как-пользоваться-пошаговое-демо). Основной сценарий работает без ключей внешних AI-сервисов; для диалога с AI-помощником ключ нужен отдельно.

## Быстрый запуск

### Что понадобится

- Git и доступ к этому репозиторию.
- Docker с Compose v2; для macOS/Windows — запущенный Docker Desktop.
- Свободные локальные порты `5173` и `7575`.
- Интернет для первой загрузки образов и зависимостей.

Python, Node.js, PostgreSQL и Redis на хост устанавливать не нужно. Команды ниже выполняются из корня репозитория.

### macOS / Linux

```sh
git clone https://github.com/BAITC-Hacks/hack-34b30c3c-ozlteam.git
cd hack-34b30c3c-ozlteam

make dev
make seed
./scripts/dev.sh exec -T api python -m app.seed.replenishment
```

Если репозиторий уже скачан, используйте существующий каталог. Без Make те же действия:

```sh
./scripts/dev.sh up -d
./scripts/dev.sh exec -T api python -m app.seed.seed
./scripts/dev.sh exec -T api python -m app.seed.replenishment
```

Первый запуск собирает контейнеры, устанавливает зависимости, применяет миграции и поднимает сервисы. Если `.env.local` отсутствует, скрипт создаёт его из шаблона и генерирует JWT-секрет. Существующий файл сохраняется.

`make seed` создаёт права, роли и локального администратора. Следующая команда добавляет синтетические данные и ставит расчёт в очередь. Дождитесь его завершения в интерфейсе; для этого должны работать `worker` и Redis.

### Windows / PowerShell

```powershell
git clone https://github.com/BAITC-Hacks/hack-34b30c3c-ozlteam.git
cd hack-34b30c3c-ozlteam

.\scripts\dev.ps1 up -d
.\scripts\dev.ps1 exec -T api python -m app.seed.seed
.\scripts\dev.ps1 exec -T api python -m app.seed.replenishment
```

Для остальных Docker-команд в этом README заменяйте `./scripts/dev.sh` на `.\scripts\dev.ps1`. Многострочные команды из блоков `sh` объединяйте в одну строку, удаляя завершающие `\`: это Bash-синтаксис продолжения строки.

## Как пользоваться: пошаговое демо

### 1. Проверить данные

Откройте **Данные** (`/data`) и найдите синтетический источник. В **Справочниках** (`/data/catalogs`) доступны товары, категории, поставщики и склады. В разделе **Запасы** (`/inventory`) можно сверить остатки, резерв, ожидаемые поступления и интервалы отсутствия товара.

С правом `catalogs.write` в справочниках доступны «Добавить запись», а в карточке — «Изменить», «В архив» и «Восстановить». Изменения сохраняются в БД и доступны помощнику; демо-названия автоматически не заменяются реальными. Для заказа выбирайте товар, поставщика и склад одного источника. [Инструкция и ограничения ручных изменений](docs/catalog-manual-crud.md).

Для демо выбирайте склад «Алматы (демо)». Если на стенд также загружены исходные книги партнёра, у них будет отдельный источник и собственные ограничения.

### 2. Открыть или запустить расчёт

Перейдите в **Рекомендации** (`/recommendations`):

1. Откройте в истории расчёт на `2026-09-22`, созданный сидером, и дождитесь статуса готовности.
2. Для нового расчёта выберите склад, дату среза `2026-09-22` и при необходимости категорию; нажмите **«Рассчитать»**.
3. В дополнительных параметрах доступна глубина истории: по умолчанию 1095 дней, допустимо от 28 до 3650.
4. Откройте результат. Строки сгруппированы по поставщику; доступны фильтры и постраничный просмотр.

Расчёт выполняется в фоне и сохраняется. Обновление страницы не отменяет задачу. Если расчёт завершился ошибкой, сначала устраните указанную причину, затем создайте новый запуск.

### 3. Разобрать рекомендацию

Нажмите на название товара. В карточке рекомендации проверьте:

- сколько было фактических продаж и какой объём исключён как разовый;
- сколько спроса восстановлено за подтверждённые дни отсутствия;
- какой прогноз получен на горизонт поставки и пересмотра;
- какой остаток доступен после резерва и сколько товара поступит в срок;
- страховой запас, MOQ, кратность и итог округления;
- прогнозируемую дату дефицита и ограничения исходных данных.

Ключевой вопрос проверки: **можно ли объяснить рекомендованное количество входными числами и правилами?** Каждая рекомендация хранит подробности расчёта; менять её исходные числа через чат не требуется.

### 4. Создать черновики

Вернитесь к списку, отметьте готовые позиции с положительным количеством и нажмите **«Создать черновики»**. Проверьте предпросмотр и подтвердите.

Сервер разделит выбранные строки по поставщику и складу. Выбор «доступных на странице» относится к текущей странице списка. Заблокированные позиции и нулевые рекомендации не допускаются в заказ. Уже использованная рекомендация показывает ссылку на существующий заказ.

### 5. Скорректировать и утвердить

Откройте черновик в **Заказах** (`/orders`):

1. При необходимости измените количество, укажите причину и сохраните.
2. Проверьте все строки и комментарий.
3. Нажмите **«Просмотреть и утвердить»**, затем **«Утвердить заказ»**.
4. Скачайте **XLSX** или **CSV**.

Алгоритм округляет рекомендацию по MOQ и кратности. При ручном изменении менеджер должен самостоятельно проверить условия поставщика: редактор не повторяет все правила округления расчёта.

Обновите страницу и снова откройте заказ: правки, утверждение и версия должны сохраниться. Экспорт соответствует утверждённой редакции. Если другой сотрудник уже изменил документ, приложение потребует перечитать актуальную версию.

### 6. Проверить AI-помощника

После [настройки модели](#ai-помощник-закупщика) откройте `/assistant`:

- «Как утвердить и выгрузить заказ?» — справочный ответ со ссылками на материалы приложения.
- Выберите демонстрационный склад в контексте и разрешите передачу учётных сводок, затем спросите: «Какие позиции требуют внимания?»
- Попросите объяснить открытую рекомендацию или подготовить черновики по готовым позициям.

Действия, меняющие данные, сначала показываются как предложение. Выполнение начинается после отдельного подтверждения пользователя. Утверждать заказ или отправлять его поставщику AI-помощник не может.

### Отдельный быстрый пример

Страница `/recommendations/demo` позволяет рассчитать встроенный синтетический пример, скачать XLSX-шаблон, загрузить его обратно, изменить количества и экспортировать CSV.

Это отдельный упрощённый калькулятор: его расчёт не сохраняется в историю, а локальное подтверждение не создаёт заказ в PostgreSQL. Для проверки полного сценария используйте `/recommendations` и `/orders`.

## Как рассчитывается заказ

Основной серверный алгоритм — `robust-daily-v2`, [реализация](backend/app/Domains/Replenishment/services/engine.py). Он выполняется детерминированным Python-кодом. LLM помогает пользоваться результатом, но не вычисляет закупочное количество.

### 1. Зафиксировать данные

Расчёт ведётся для выбранного склада и товаров. При начале работы worker сохраняет снимок входов, ревизии источников, параметры и версию алгоритма. Повторное выполнение задачи использует тот же снимок. Незавершённый обмен данными блокирует расчёт.

Дата среза ограничивает факты продаж и запасов. Она не восстанавливает автоматически прежние версии исправленных документов и справочников; для исторического тестирования прогноза нужны архивные снимки.

### 2. Очистить разовые всплески

Продажи суммируются по товару, дню и обезличенному клиенту. Порог:

```text
порог = max(5 × медиана положительных покупок,
            медиана + 8 × MAD)
```

MAD — медиана абсолютных отклонений от медианы. Покупки выше порога исключаются из регулярного спроса с сохранением даты, количества, порога и причины. Если у одного клиента есть минимум три крупные покупки за период не менее 28 дней, такой спрос считается повторяющимся и сохраняется.

При отсутствии клиентских ID доступно только выявление дневных выбросов; это ограничение показывается явно. Для очень короткой истории надёжность такого анализа ограничена. Нетто-возвраты учитываются, отрицательное итоговое значение дневного спроса ограничивается нулём.

### 3. Восстановить упущенный спрос

Для подтверждённых дней stockout оценивается спрос по доступным дням того же месяца и дня недели. Если таких дней меньше трёх, используются доступные дни того же дня недели, затем общий средний спрос.

Оценка может увеличить спрос, но не уменьшает фактические продажи. Если доступных наблюдений нет, позиция блокируется. Ноль в месячном остатке сам по себе не доказывает отсутствие товара весь месяц.

### 4. Учесть сезон, тренд и внешний прогноз

- При истории от 540 дней строится месячный сезонный профиль товара.
- При короткой истории используется профиль категории из достаточно длинных рядов выбранного среза; при отсутствии такого профиля — коэффициент 1 и предупреждение.
- Базовый спрос рассчитывается по последним 56 дням очищенной истории с устранённой сезонностью.
- Рост считается устойчивым, когда три последовательных 28-дневных блока возрастают более чем на 2% каждый, при достаточном числе наблюдений. Скорость роста ограничивается.
- Внешний прогноз применяется только в заданном периоде. Прогноз товара имеет приоритет над категорией; режим позволяет дополнить внутренний тренд или заменить его дальнейшую экстраполяцию.

### 5. Рассчитать количество и риск

```text
горизонт = срок поставки + период пересмотра
прогноз = сумма дневного прогнозируемого спроса на горизонте
страховой запас = средний дневной прогноз × дни страхового запаса
доступный остаток = max(0, остаток − резерв)

потребность = max(0,
  прогноз + страховой запас − доступный остаток − поступления в срок)

если потребность > 0:
  заказ = округлить вверх до кратности(max(потребность, MOQ))
иначе:
  заказ = 0
```

Период пересмотра и страховой запас задаются политикой категории. В пути учитываются подтверждённые/находящиеся в пути поставки после даты среза и внутри горизонта. Просроченные и слишком поздние поступления не закрывают текущую потребность.

Баланс моделируется по дням: поставка позднее даты дефицита может уменьшить общий объём заказа, но риск до её прихода остаётся. Срочность отражает момент прогнозируемого дефицита. Потребность до округления и прибавка до партии сохраняются отдельно.

Неизвестные обязательные условия, отсутствие необходимого остатка/истории или неподтверждённые данные партнёрского импорта блокируют позицию. Правила подробно описаны в [документации расчёта](docs/backend-replenishment.md).

Упрощённый `/recommendations/demo` использует [собственную методику](backend/app/Domains/Replenishment/services/calculation.py): окно до 365 дней и более простой порог выбросов. Его числа не следует сравнивать с серверной методикой как с одним и тем же алгоритмом.

## AI-помощник закупщика

AI встроен в рабочий сценарий через страницу `/assistant` и боковую панель. Главный координатор выбирает одного из пяти специалистов: справка, данные 1С, запасы, спрос/расчёт, заказы. Это профили общего движка с разрешёнными инструментами.

Помощник может читать доступные сотруднику сводки и предложить три операции: применить проверенный пакет, запустить расчёт, создать черновики из готовых рекомендаций. Модель формирует план, а сервер проверяет схему, права, идентификаторы и допустимость операции. Каждое изменение требует подтверждения. Диалоги доступны только их владельцу.

Для OpenAI заполните в локальном `.env.local`:

```dotenv
LLM_PROVIDER=openai
LLM_MODEL=gpt-6-sol
OPENAI_REASONING_EFFORT=medium
OPENAI_API_KEY=ваш_ключ
```

Имя модели выше соответствует шаблону проекта; используйте модель, доступную вашему API-аккаунту. После изменения настроек:

```sh
make dev-env
```

Ключ не нужен для импорта, расчёта, заказов и экспорта. Без ключа ответы модели недоступны, остальные функции работают. В коде также есть адаптеры Anthropic, NVIDIA и OpenAI-совместимого API; настройки перечислены в `.env.local.example`.

Перед передачей учётных сводок пользователь даёт отдельное разрешение в контексте диалога. Права сотрудника проверяются сервером. Сырые книги, строки продаж и клиентские ID через инструменты модели не передаются. Сам текст вопроса отправляется провайдеру — секреты и персональные данные в него вставлять не следует.

В разработке проекта используется Codex. Это отдельно от AI-помощника внутри продукта. Устройство движка, инструменты, ограничения и проверочные запросы — в [docs/ai-agents.md](docs/ai-agents.md).

## Загрузка своих данных и обмен с 1С

### Нормализованный импорт

На `/data` добавьте источник, загрузите CSV в UTF-8 или XLSX, проверьте сопоставление полей, предпросмотр и ошибки. Затем явно примените проверенный файл. Лимиты обычного импорта: 25 МиБ и 10 000 нормализованных строк на запрос.

Контракт охватывает девять типов: категории, поставщики, склады, товары, продажи, остатки, поступления, интервалы отсутствия и прогноз прироста. Сначала должны быть известны справочники, на которые ссылаются факты. Поля, порядок загрузки и примеры — в [docs/backend-data.md](docs/backend-data.md) и Swagger.

Для больших обменов есть API версионированных пакетов: промежуточные передаются с `complete=false`, завершение — с `complete=true`. До завершения источник не допускается к расчёту.

### Исходные Excel-книги партнёра

Для 12 книг IEK/Systeme Electric реализован отдельный пакетный адаптер: проверка состава, сопоставление кодов, сохранение происхождения, фоновые задачи и готовность товаров. Это широкие отчёты со своими профилями, отличающиеся от нормализованного шаблона.

Если книги доступны в вашем checkout, после основного запуска можно выполнить:

```sh
make seed-excel
```

Команда подключает `TrackLogic` только для чтения, проверяет манифест файлов и проходит штатный процесс импорта. Первая загрузка может занимать 8–10 минут; команда показывает прогресс и ожидает завершения. Повтор сохраняет UUID и не дублирует уже принятый пакет. После ошибки доступен явный повтор:

```sh
./scripts/seed-excel.sh --retry-failed
```

Зафиксированный набор даёт 2 поставщика, 7 категорий, 1 склад, 3 908 товаров и 248 467 принятых продаж. Это результат импорта, а не количество товаров, готовых к заказу.

Без дополнительных подтверждений все 3 908 товаров первоначально заблокированы для заказа: не хватает части актуальных остатков и условий. В исходных динамиках отсутствуют обезличенный клиент и цена, точные интервалы stockout и подтверждённый lead time. Эти сведения не подменяются выдуманными значениями. Полный сценарий демонстрируется на синтетических данных.

Подробности: [пакетный импорт](docs/partner-workbook-import.md), [состав и ограничения исходных данных](docs/hackathon/tracklogic.md). Коммерческие книги доступны в закрытом командном репозитории и не предназначены для открытой публикации.

### Подключение 1С

На `/data/integrations` есть конструктор REST-отчётов: адрес JSON-отчёта, сопоставление полей, проверка и явное применение. Для исходящих запросов серверу задаются `ONEC_ALLOWED_ORIGINS` и секрет авторизации; в интерфейсе используется имя настройки, а не её значение.

Код также поддерживает входящие версионированные пакеты и исходящий JSON заказа с отдельным подтверждением обработки. Код 1С хранится строкой, внешний ID источника — отдельно, внутренние сущности используют UUIDv7. Реестр сопоставлений находится в нашем адаптере и БД.

Для конкретной конфигурации партнёра ещё требуется согласовать и проверить транспорт, ID документов/строк, единицы, знаки операций и формат заказа. Реальная база партнёра в рамках описанного демо не подключена. Автоматическое расписание REST-отчётов и обход страниц пока не реализованы. [Инструкция интеграции](docs/onec-rest-reports.md).

## Архитектура и API

```text
Выгрузки / нормализованный API / REST-отчёты 1С
                  ↓
Импорт → сопоставление → проверка готовности → PostgreSQL
                                              ↓
React UI → FastAPI → фоновая задача → Redis / worker
                                              ↓
                          снимок → прогноз → рекомендации
                                              ↓
                      черновик → правка → утверждение → CSV/XLSX

AI-помощник → разрешённые бизнес-сервисы → сводки / предложение действия
```

| Слой | Технологии и ответственность |
| --- | --- |
| Интерфейс | React, TypeScript, Vite; модульные страницы и общие компоненты. |
| API | FastAPI, Pydantic; авторизация, контракты, бизнес-сервисы. |
| Расчёт и импорт | Python, Decimal, openpyxl; алгоритм и обработка XLSX без внешней модели. |
| Хранилище | PostgreSQL 18, SQLAlchemy, Alembic; данные, снимки, заказы, диалоги. |
| Фоновые задачи | Redis, arq, worker; состояние задач сохраняется в PostgreSQL. |
| AI | Адаптеры провайдеров, серверная проверка планов и разрешённых инструментов. |
| Запуск | Docker Compose; зависимости зафиксированы в uv.lock и package-lock.json. |

Предметные модули: `backend/app/Domains/{DataImports,Integrations1C,Catalogs,Inventory,Replenishment,Procurement,Ai}`. Контроллеры вызывают сервисы, SQL находится в репозиториях. Frontend: `frontend/src/modules`, переиспользуемые элементы — `frontend/src/shared`. Миграции — `backend/migrations`.

Для проверки API откройте Swagger, выполните `POST /api/v1/auth/login` с почтой и паролем, скопируйте `access_token` и вставьте его в **Authorize**. Рабочие endpoints требуют Bearer-сессию и права роли. Локальный администратор получает полный набор прав; `purchaser` — роль менеджера закупок.

Основные группы API: `/api/v1/catalogs`, `/api/v1/imports`, `/api/v1/integrations/1c`, `/api/v1/inventory`, `/api/v1/replenishment/runs`, `/api/v1/recommendations`, `/api/v1/orders`. Точные тела запросов и ответы генерируются из кода в OpenAPI.

Пароли хешируются Argon2; JWT ссылается на серверную сессию. Права читаются из БД. После выхода сессия удаляется. Данные закупок общие для одной компании; отдельная многокомпанейная изоляция не реализована.

## Проверки

Команды выполняются после `make dev`. Тесты ниже используют синтетические данные; основные тесты алгоритма не обращаются к LLM.

### Алгоритм, API и заказы

```sh
./scripts/dev.sh exec -T api pytest -q \
  tests/test_replenishment_engine.py \
  tests/test_replenishment_api.py \
  tests/test_replenishment.py \
  tests/test_procurement.py \
  tests/test_recommendation_explanation.py \
  tests/test_product_quality_contract.py
```

Здесь проверяются влияние входов, сезонность, рост, stockout, разовые/регулярные крупные продажи, сроки поступления, арифметика объяснения, права, группировка заказов, версии, утверждение и экспорт.

### Сквозной сценарий с PostgreSQL

```sh
./scripts/dev.sh exec -T -e RUN_DB_TESTS=1 api pytest -q \
  tests/test_purchasing_database.py \
  tests/test_procurement_database.py
```

Проверяются обмен данными → расчёт → рекомендации → заказ → экспорт, повторы и сохранение. Это интеграционные тесты API и БД, а не автоматизированное прохождение браузера. Запускайте их на локальной тестовой базе, последовательно; они создают тестовые записи и выполняют предусмотренный откат/очистку. Без `RUN_DB_TESTS=1` тесты БД пропускаются.

### AI и полный набор

```sh
./scripts/dev.sh exec -T api pytest -q tests/test_agent_engine.py tests/test_agent_knowledge.py tests/test_agent_conversations.py
./scripts/dev.sh exec -T api pytest -q
./scripts/dev.sh exec -T api ruff check .
./scripts/dev.sh exec -T api ruff format --check .
./scripts/dev.sh exec -T api alembic check
./scripts/dev.sh exec -T frontend npm run build
```

Тесты движка AI используют подменные ответы провайдера. Для проверки конкретной внешней модели требуется настроенный ключ и ручной запрос в чат. Успешная сборка и тесты не заменяют приёмку прогноза на данных партнёра.

## Настройки и сопровождение

`.env.local` и рабочие секреты исключены из Git; шаблон — [.env.local.example](.env.local.example).

| Настройка | Для чего |
| --- | --- |
| `SECURITY_JWT_SECRET` | Подпись сессий; генерируется скриптом при первом создании env. |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` | Учётная запись первого администратора; пароль минимум 12 символов. |
| `FRONTEND_PORT`, `API_PORT` | Локальные порты интерфейса и API. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | База локального окружения. Изменение env не перенастраивает существующий volume. |
| `LLM_PROVIDER`, `LLM_MODEL`, ключ провайдера | Необязательные настройки AI-помощника. |
| `ONEC_ALLOWED_ORIGINS`, `ONEC_AUTH_EKT` | Разрешённые адреса и серверная авторизация REST-отчётов 1С. |

```sh
make dev-ps       # состояние контейнеров
make dev-logs     # все логи; Ctrl+C прекращает просмотр
make worker-logs  # фоновые расчёты и импорт
make dev-down    # остановка с сохранением данных
make dev         # повторный запуск
make dev-env     # применить изменённый .env.local
make dev-build   # пересобрать после изменения образов / Python-зависимостей
```

Данные находятся в Docker volumes `postgres_data` и `uploads_data` (с префиксом Compose-проекта). Обычная остановка их сохраняет; `down -v` удаляет volumes, поэтому для завершения демо используйте `make dev-down`.

Исходники подключены к контейнерам: Vite HMR и перезапуск Python сохраняют быструю разработку. После получения новых миграций:

```sh
./scripts/dev.sh exec -T api alembic upgrade head
```

Если изменился список задач worker, перезапустите его: `./scripts/dev.sh restart worker`. После изменений Python-зависимостей требуется пересборка; frontend устанавливает зависимости из lock-файла при старте.

В проекте также есть PWA-оболочка и необязательный Telegram-бот (`make dev-bot`, требуется `BOT_TOKEN`; команды `/start`, `/status`). Они не нужны для проверки закупочного сценария. Загрузка учётных данных, расчёт и сохранение заказов требуют соединения с API.

## Если что-то не работает

| Симптом | Что проверить и сделать |
| --- | --- |
| Приложение ещё не открылось после первого запуска | `make dev-ps`, затем `./scripts/dev.sh logs --tail=100 migrate api frontend`. Дождитесь установки зависимостей и готовности API. |
| Не удаётся войти | Выполнен ли `make seed`; верны ли почта и пароль. Замените предварительно заполненный demo-пароль на пароль администратора. |
| Вход возвращает 503 | В старом `.env.local` может быть пустой JWT-секрет. Создайте случайное значение, например `openssl rand -hex 32`, внесите его в файл и выполните `make dev-env`. Не публикуйте значение. |
| Изменение env не подействовало | Выполните `make dev-env`; обычный restart не обновляет переменные контейнера. Проверьте, не перекрывает ли их окружение shell. |
| Нет склада и рекомендаций | Выполните сидер `app.seed.replenishment`, выберите «Алматы (демо)» и дату `2026-09-22`. |
| Расчёт долго остаётся в очереди | Проверьте `worker` и `redis` через `make dev-ps`, затем `./scripts/dev.sh logs --tail=100 worker`. |
| Нельзя создать заказ по товару | Откройте причины блокировки. Нужны готовые данные, положительная потребность и рекомендация, ещё не включённая в заказ. |
| Все товары из исходных Excel заблокированы | Это ожидаемо без подтверждённых остатков и условий. Для полного демо используйте синтетический источник; для реального — дополните недостающие сведения. |
| Конфликт версии при изменении заказа | Обновите документ, проверьте чужие изменения и повторите действие с актуальной версией. |
| Помощник не отвечает | Проверьте ключ, выбранную модель и доступ к провайдеру; после изменения env примените настройки. |
| Порт уже занят | Измените `FRONTEND_PORT`/`API_PORT` в env. При смене порта frontend также обновите `CORS_ORIGINS`; примените настройки и открывайте новый адрес. |

## Ограничения и следующий этап

Это локально воспроизводимый MVP с сохраняемым закупочным сценарием, синтетической проверкой требований и адаптером переданных Excel-книг.

- Нет подтверждённой промышленной связи с реальной базой 1С партнёра. Формат экспорта и обработку документов нужно согласовать и проверить на её конфигурации.
- Нет измеренной точности прогноза или подтверждённого процента экономии. Следующий этап — историческая проверка на согласованных данных и сравнение с текущим расчётом менеджера.
- Клиентские выбросы, точный stockout и срок поставки нельзя полностью проверить на исходных книгах без дополнительных сведений.
- AI-помощник зависит от внешнего провайдера; качество конкретной модели требует отдельной проверки.
- Интерфейс справочников поддерживает просмотр и поиск; изменение данных выполняется через импорт/API.
- В репозитории есть вспомогательные и незавершённые экраны каркаса. В объём решения входят страницы, описанные в сценарии выше.
- Публичный стенд в этом README не заявлен. Текущий Compose предназначен для локальной разработки: для размещения нужны production-конфигурация, HTTPS, собственные секреты и резервное копирование. `.env.production.example` сам по себе не создаёт production-развёртывание.
