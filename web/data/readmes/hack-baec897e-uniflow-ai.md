# OrbitDuo Campaign Studio

Приложение для аналитика маркетинга в кейсе **Beeline Tariff Marketing Campaigns**:
аудит аудитории → пробные кампании → выбор плана → объяснение результата → экспорт.
В проекте реализованы React-интерфейс, FastAPI, локальный расчётный агент и история
запусков в SQLite. Агент выбирает аудиторию, тариф и канал с учётом бюджета,
контактов, пересечений и неопределённости наблюдений.

**Все данные синтетические; реальные рассылки не выполняются.** Денежные значения
указаны в **у.е. (CU)**. `net_arpu_gain` — моделируемый прирост выручки за вычетом
расходов на коммуникации. Это не полная прибыль оператора и не доказанный эффект
для реальных абонентов.

## Что можно показать

1. **Обзор:** размер аудитории, исходная выручка и конкурсные ограничения.
2. **Аудитория:** группы клиентов, поиск по тарифу, фильтры допуска, сортировка
   и страницы таблицы; выбранные условия сохраняются в URL.
3. **Подбор кампаний:** сбалансированный или осторожный подход к риску,
   номер сценария (`seed`), прогресс, фактические пилоты и журнал решений.
4. **Результат:** выбранный план, расходы, контакты, уникальный охват,
   разбор слабых мест и карточка каждого предложения с основаниями выбора.
5. **История и сравнение:** поиск и фильтры среди последних 100 записей,
   понятные названия, заметки и избранное; сравнение 2–3 запусков по эффекту,
   ресурсам и составу предложений с проверкой сопоставимости условий.
6. **Предварительный калькулятор:** ползунки аудитории, бюджета и предположений
   об отклике, мгновенная оценка эффекта, порог окупаемости и сравнение каналов;
   сохранённые сценарии, ссылки с параметрами и три варианта чувствительности.
7. **Проверка исключений:** убрать предложения из отдельного учебного варианта
   и пересчитать эффект, расходы и охват с учётом пересечений и порядка исполнения.
   Сохранённые пилоты учитываются, исходный план остаётся неизменным.
8. **Экспорт:** CSV плана, JSON результата и оформленный отчёт с графиком,
   выводами и ограничениями; PDF сохраняется через системное окно печати браузера.

Справка с поиском и пояснения показателей доступны на всех экранах. Технические
записи можно раскрыть отдельно; экспорт сохраняет исходные поля. Интерфейс
предусматривает работу с клавиатурой и мобильный экран.

| Данные результата | Что означают |
|---|---|
| `forecast` — прогноз агента | Оценка эффекта после обновления по пилотам, с неопределённостью |
| `pilots` — наблюдения | Шумные результаты пробных кампаний в учебной среде |
| `local_evaluation` — локальная симуляция | Оценка уже выбранного плана публичным оценщиком |

`null` означает отсутствие оценки; отрицательные значения сохраняют знак.
Контакты учитывают повторные обращения, уникальный охват — отдельных клиентов.
Разбор результата объясняет сохранённые данные. Отдельная проверка исключений
доступна для завершённого расчёта с подключённой учебной средой; она повторяет
локальную оценку оставшихся предложений и не заменяет прогноз агента.
Несовпадение исходных данных или результата воспроизведения блокирует эксперимент.

Названия, заметки, избранное и сценарии калькулятора хранятся только в текущем
браузере. Ссылка на сценарий передаёт параметры без названия и заметки; получателю
нужны доступ к приложению и совместимые исходные данные. При сравнении запусков
интерфейс отдельно предупреждает, что совпадение версии алгоритма не подтверждено.

Сценарий выступления: [показ за 3 минуты](docs/DEMO.md).

## Запуск всего приложения через Docker

Из корня проекта, при запущенном Docker Desktop с Linux-контейнерами:

```powershell
docker compose up -d --build --wait
```

- Приложение OrbitDuo: <http://localhost:8080>.
- Предварительный калькулятор: <http://localhost:8080/calculator> — ползунки
  аудитории, бюджета и отклика, мгновенная оценка эффекта и сравнение каналов.
- Документация API: <http://localhost:8000/docs>.
- Проверка состояния: `docker compose ps`.
- Журнал: `docker compose logs --tail=100 backend frontend`.
- Остановка с сохранением запусков: `docker compose down`.

Frontend работает с настоящим API; демонстрационный режим выключен. Nginx
раздаёт сборку и передаёт `/api/v1` backend. SQLite хранится в отдельном Docker
volume и переживает перезапуск/пересоздание контейнеров. `docker compose down -v`
удаляет этот volume и историю: для обычной остановки флаг `-v` не нужен.
Порты доступны только на локальной машине. При занятых портах задайте
`ORBITDUO_WEB_PORT` и `ORBITDUO_API_PORT` перед запуском, например 8081 и 8001.

Образы Python, Node и Nginx зафиксированы по digest. Оба сервиса выполняются
без root с доступом к записи только во временные каталоги и volume базы.
На первой сборке интернет нужен для загрузки образов и зависимостей;
готовому агенту и приложению внешние сервисы или API-ключи не нужны.

Сквозная проверка Docker из подготовленного Python-окружения:

```powershell
.\.venv\Scripts\python.exe -m scripts.verify_stack --restart
```

Она проверяет настоящий API через Nginx, исполнение плана, экспорт, повторный
POST, ETag, SPA-маршруты и сохранность результата после перезапуска backend.
Штатный `make_submission.py` отдельно запускается в чистом каталоге внутри
Linux-контейнера; его CSV сравнивается с экспортом API побайтно. С локальным
Windows-файлом сравниваются строки CSV: окончания строк платформ различаются.

## Локальный запуск без Docker

Команды ниже — для PowerShell из корня репозитория. Docker использует Python 3.13;
в сохранённых локальных проверках использовался также Python 3.14.4.
Frontend требует Node **24.15.0+ в ветке 24 или 26+** и npm. Версии Python-пакетов
зафиксированы в [backend/requirements.txt](backend/requirements.txt) и
[participant_package/requirements.txt](participant_package/requirements.txt),
frontend — в `frontend/package-lock.json`.

Подготовка окружения при первом запуске и после изменения зависимостей:

```powershell
$env:PYTHONUTF8 = '1'
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r participant_package/requirements.txt -r backend/requirements.txt
.\.venv\Scripts\python.exe -m pip check
Push-Location frontend
npm ci
Pop-Location
```

Для конкурсной части достаточно `participant_package/requirements.txt`.

Общий запуск frontend и API:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-demo.ps1
```

Скрипт проверяет Python, npm и свободные порты 8000/5173, устанавливает недостающие
зависимости, запускает один backend и Vite с `VITE_DEMO_MODE=false`.
Он использует корневую `.venv`, а при её отсутствии — существующую
`participant_package/.venv` либо создаёт окружение. После обновления зависимостей
выполните подготовку выше: наличие окружения само по себе не обновляет его пакеты.

- Frontend: <http://127.0.0.1:5173>.
- Swagger: <http://127.0.0.1:8000/docs>.
- Логи обоих процессов: `backend/data/*.log`.
- Остановка: Enter в окне скрипта.
- Отдельная БД: параметр `-DatabasePath 'C:\path\orbitduo.sqlite3'`.

Для ручного запуска откройте два терминала. В первом, из корня:

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

Во втором, также из корня:

```powershell
Set-Location frontend
$env:VITE_DEMO_MODE = 'false'
npm run dev -- --host 127.0.0.1
```

Vite передаёт `/api/v1` на `127.0.0.1:8000`. Пример настроек —
[frontend/.env.example](frontend/.env.example); `VITE_*` читаются при старте Vite
или сборке Docker. При недоступном API автоматического перехода на demo нет.
Для разработки интерфейса без backend явно задайте `VITE_DEMO_MODE=true` перед
запуском Vite. Демо использует fixtures и localStorage; его числа не являются
измерением агента. Сценарии описаны в [frontend/README.md](frontend/README.md).

## API, сохранение и восстановление

Один процесс, без `--workers`. SQLite по умолчанию находится в
`backend/data/runs.sqlite3`; другой путь задаётся через `ORBITDUO_DB_PATH`.
ОС-блокировка не допускает второй сервер с той же БД. Миграция существующей базы
сохраняет результаты и ключи идемпотентности. После аварии незавершённые задания
получают `failed / SERVER_RESTARTED`; готовые результаты остаются доступны.
Расчёт выполняется в выделенном worker, HTTP продолжает отвечать.

- [Health](http://127.0.0.1:8000/api/v1/health).
- [Аудит и справочники](http://127.0.0.1:8000/api/v1/overview).
- [Swagger](http://127.0.0.1:8000/docs).
- [Общий API-контракт](docs/team/API_CONTRACT.md) и [Pydantic DTO](backend/models.py).
- [Подробности backend](backend/README.md).

Из другого окна PowerShell:

```powershell
$runKey = [guid]::NewGuid().ToString()
$run = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8000/api/v1/runs' -ContentType 'application/json' -Headers @{ 'Idempotency-Key' = $runKey } -Body '{"seed":42,"risk_profile":"balanced"}'
Invoke-RestMethod "http://127.0.0.1:8000/api/v1/runs/$($run.id)"
```

Polling примерно раз в секунду до `completed` или `failed`. Повтор POST использует
тот же ключ; новый эксперимент — новый ключ. Второй активный расчёт возвращает
`409 RUN_ALREADY_ACTIVE`. Опциональный `If-None-Match` с предыдущим `ETag`
позволяет получить `304`, когда результат не изменился.
После завершения доступны `/runs/{id}/campaigns.csv` и `/runs/{id}/report.json`.
Экспорт читает сохранённый план и не запускает агента заново.

При обновлении страницы интерфейс открывает тот же `run_id`. Во время сетевого
сбоя сохраняет последний полученный снимок, показывает приостановку обновления
и повторяет опрос. Повтор создания после потери ответа использует прежний
`Idempotency-Key`; двойная отправка блокируется. Ошибка `RUN_ALREADY_ACTIVE`
предлагает перейти к активному запуску.

## Проверки

Ниже команды повторного запуска проверок. Сохранённые результаты предыдущих
прогонов перечислены отдельно в конце README.

Ядро и backend, из корня после установки зависимостей:

```powershell
.\.venv\Scripts\python.exe -m pytest participant_package/tests backend/tests -q
.\.venv\Scripts\python.exe -m backend.final_smoke
```

`backend.final_smoke` сам запускает сервер на временном порту с отдельной БД,
проверяет balanced/42, CSV, события, идемпотентность, ETag и перезапуск.
Он не изменяет пользовательские запуски. Дополнительный замер хранилища:
`.\.venv\Scripts\python.exe -m backend.benchmark_storage`.

Frontend, из корня перейти в `frontend/`:

```powershell
Set-Location frontend
npm run build
npm run lint
npm run test
npx playwright install chromium
npm run test:e2e
npm run test:e2e:real
```

| Браузерный набор | Окружение и назначение |
|---|---|
| `npm run test:e2e` | Собственный Vite, явное demo; сценарии UI, ошибки, справка, таблицы и ширины 1440/1280/768/390 px |
| `npm run test:e2e:real` | Собственные FastAPI и Vite, demo выключен, временная SQLite; настоящий расчёт, reload, история, экспорты и сетевые сбои |
| `npm run test:e2e:live` | Уже запущенное приложение; один сценарий с настоящим расчётом и регрессии на сохранённом API-снимке |

Перед `test:e2e` и `test:e2e:real` освободите порт 5173, перед вторым — также 8000:
наборы не переиспользуют серверы. Запускайте их последовательно.
Для real-набора нужен Python с зависимостями backend в корневой
`.venv/Scripts/python.exe`. Другой абсолютный путь задаётся через `ORBITDUO_PYTHON`
(в том числе `.venv/bin/python` на Linux).
Вместо установки Chromium можно использовать установленный браузер:
`$env:ORBITDUO_BROWSER_CHANNEL = 'msedge'` или `'chrome'`.

Live-проверка работающего Docker-приложения, из `frontend/`:

```powershell
$env:ORBITDUO_BASE_URL = 'http://127.0.0.1:8080'
npm run test:e2e:live
```

Этот набор добавляет запуск в историю работающего backend. Основной сценарий
не подменяет API и сравнивает оба скачанных файла с экспортом сохранённого запуска.
Дополнительные сценарии читают fixture `tests/fixtures/real-run.json` через подмену
GET и проверяют тексты, анализ, клавиатуру и мобильный вид.
Сквозная Docker-проверка `scripts.verify_stack --restart`, описанная выше,
также создаёт запуск и перезапускает backend.

## Оценка и submission

Из корня перейти в пакет участника:

```powershell
$env:PYTHONUTF8 = '1'
Set-Location participant_package
..\.venv\Scripts\python.exe local_eval.py
..\.venv\Scripts\python.exe local_eval.py --runs 10
..\.venv\Scripts\python.exe make_submission.py
$submissionHash = (Get-FileHash -LiteralPath submission.csv -Algorithm SHA256).Hash
..\.venv\Scripts\python.exe make_submission.py
if ((Get-FileHash -LiteralPath submission.csv -Algorithm SHA256).Hash -ne $submissionHash) { throw 'CSV не воспроизводится' }
..\.venv\Scripts\python.exe -m pytest -q
..\.venv\Scripts\python.exe -m orbitduo.evaluation
..\.venv\Scripts\python.exe -m experiments.verify_delivery
```

`local_eval.py` перехватывает ошибки агента, поэтому exit code недостаточен.
Строгий adapter дополнительно проверяет 1-10 непустых кампаний, успешные пилоты,
санитаризацию, поля, фактические аудитории и совпадение ресурсов с оценщиком.
`verify_delivery` проверяет неизменность организаторских файлов относительно
Git HEAD и совпадение submission в чистой копии без backend.

Сдавать `agent.py`, каталог `orbitduo/`, `requirements.txt`, `submission.csv`
и исторический `data/change_tariff.csv`, если его нет в поставке организатора.
Без истории предусмотрен нейтральный prior, но для повторения результатов нужны
те же входные CSV. Точка входа — `Agent().act(env)`.
Balanced/42 через API использует ту же конфигурацию.

Конкурсные ограничения: 1–10 финальных кампаний, минимум один успешный пилот,
до 20 пилотов с запрашиваемым размером 10–200 клиентов, до 5 000 клиентов
на кампанию. Общий бюджет — 100 000 у.е., лимит — 15 000 контактов, включая
пилоты и повторы. Доступны `push`, `sms`, `digital_ads`, `call`.
Агент читает фактические остатки из публичной среды. Организаторские скрипты
и исходные CSV сохраняются неизменными.

## Что улучшено во второй версии

Пилоты уточняют не только эффект предложения, но и степень доверия к истории
и масштаб неопределённости. Разведка сравнивает размеры выборок, учитывает цену
информации и обычно сохраняет 80% бюджета для финала. Fallback при отрицательных
оценках выбирает минимальный ущерб по той же риск-цели.

Планировщик кэширует аудитории и суммы по префиксам, пересчитывая только затронутые
группы. На замороженном posterior тот же план получен за 0.076 с вместо 0.613 с
(около 8 раз быстрее; измерен именно шаг планирования). Дополнительный поиск
каналов/порядка включён после более широкого парного сравнения сценариев:
первые три seed не показали разницы, но на других семействах выигрыш обнаружен.
Вариант без расширения доступен как `Agent(advanced_search=False)`.

Backend сохраняет неизменяемые завершённые результаты, стабильные события,
версию snapshot и краткие сводки для списка. В отдельном измерении списка из
100 запусков чтение ускорилось с 62.05 до 7.86 мс. Это скорость хранилища,
а не всей HTTP-операции.

Подробнее: [математика и допущения](participant_package/docs/approach.md),
[конкурсный контракт](participant_package/docs/contract.md).

В этой серии средний net вырос примерно на 66%; обе версии дали положительные
результаты во всех пяти запусках. Это малая выборка шума той же mock-модели,
не гарантия переноса на неизвестные эффекты. Другие серии содержат ухудшения.

Стандартный seed 42: net **431 321.12 CU**, расходы **20 000**, контакты **10 355**,
уникальный охват **8 620**, **16 пилотов и 5 финальных кампаний**.
В v1 на этом seed было 928 158.79 CU при расходах 99 646: улучшение среднего
не означает улучшения каждого запуска.

Смена seed проверяет шум одной mock-модели. Дополнительные семейства меняют
истинные эффекты, однако гарантии на неизвестной модели нет. Возможны убытки
при слабых эффектах и перестановке лидеров. Пересечения с пилотами приближённые,
posterior-прогноз не откалиброван как гарантированный интервал.
Conservative также не гарантирует положительного результата.
