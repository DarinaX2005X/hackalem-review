# Граф денег

Локальный инструмент для первичной AML-проверки транзакционной сети. По трём обезличенным parquet-файлам он строит направленный граф, присваивает каждому `gid` объяснимую роль, делит сеть на сообщества и выдаёт ранжированную очередь клиентов для углублённой проверки. Инструмент отвечает на вопрос аналитика «кого из 2 248 клиентов смотреть первым и почему».

Роль и позиция в очереди означают **структурную гипотезу для проверки**, а не причастность к преступлению.

## Быстрый старт

Нужен Python 3.10+ и доступ к PyPI при первом запуске. Из корня репозитория:

```bash
./run.sh
```

Скрипт создаёт локальное окружение, устанавливает зависимости из `requirements.txt` и запускает полный пересчёт. Папка `data/` должна содержать `nodes.parquet`, `edges.parquet`, `transactions.parquet`. Другой путь передаётся так: `./run.sh --data /path/to/data --out /path/to/out`.

В Windows (PowerShell):

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe run.py
```

Если окружение `.venv` уже подготовлено, достаточно последней команды — она работает без интернета.

**Что появляется в `out/`:** три обязательные выгрузки `nodes_roles.csv`, `clusters.csv`, `top_nodes.csv`, ещё 37 CSV с опциональными разборами и автономная страница `network.html`. Полный перечень — в разделе [Выгрузки](#выгрузки). HTML открывается в браузере как обычный файл, без сервера и интернета.

**Производительность.** На предоставленных 2 248 узлах прямой расчёт `run.py` занимает около 2,5 секунды на тестовой машине; установка пакетов в это время не входит. Предел по ТЗ — 5 минут.

## Сценарий аналитика

1. Поместить выгрузку в `data/` и запустить `./run.sh`.
2. Открыть `out/network.html`, найти `gid` из списка правоохранительных органов или взять узел из топ-листа слева.
3. Переключиться на один или два шага связей, изучить направление стрелок, суммы и карточку узла. Переключить окраску между ролями и кластерами.
4. Использовать `top_nodes.csv` как очередь углублённой проверки; `evidence` и числовые поля `nodes_roles.csv` позволяют проверить каждый вывод.
5. Сверить `attention` у выбранных узлов и сформировать запрос на недостающие данные по `data_gaps.csv`.
6. Уточнить связи вопросом ассистенту: `assistant.py "кто собирает деньги с этих пятерых: …"`.

## Как устроено решение

![Схема пайплайна](architecture.svg)

### Построение графа

Граф направленный: ребро `src → dst` означает перевод от отправителя получателю. `edges.parquet` сверяется с суммами и количеством операций в `transactions.parquet`. Все узлы из `nodes.parquet`, включая изолированные seed, остаются в результате.

### Проверка входных данных

Обязательные поля не допускают пропусков. Идентификаторы, глубина и число операций должны иметь целочисленный тип, `is_seed` — булев тип. Суммы должны быть конечными положительными числами; допустимое расхождение агрегата с транзакциями — не более 0,01 KZT на пару. Пустой список узлов отклоняется с сообщением об ошибке. Перед построением графа узлы и рёбра сортируются, поэтому перестановка строк во входных файлах не меняет результат.

### Метрики узла

| Метрика | Смысл |
|---|---|
| `in_deg`, `out_deg` | число разных плательщиков и получателей |
| `in_kzt`, `out_kzt` | суммы, видимые внутри выгрузки |
| `seed_reach` | из скольких seed узел достижим по направлению переводов за ≤ 4 ребра |
| `bridge` | нормированное посредничество на направленном графе по 96 фиксированным источникам (`seed=42`) |
| `rapid_48h` | доля входящих операций, после которых у того же узла есть исходящая в следующие 48 часов — временной сигнал, не сопоставление конкретных денег |

### Правила ролей

Правила применяются в указанном порядке; первое выполненное задаёт основную роль:

| Роль | Условие |
|---|---|
| `coordinator` | Не seed; `seed_reach ≥ 3`, `in_deg ≥ 3`, `bridge` не ниже 90-го процентиля **положительных** значений в текущей выгрузке. Кандидат на координирующий узел, не идентификация организатора. |
| `distributor` | `out_deg ≥ 8` и `out_deg ≥ 2 × max(in_deg, 1)`. |
| `consolidator` | `in_deg ≥ 4` и `in_deg ≥ 2 × max(out_deg, 1)`. |
| `transit` | Не seed; есть вход и выход, `0.8 ≤ out_kzt / in_kzt ≤ 1.2`. Сравнение сумм остаётся приблизительным из-за неполной видимости. |
| `terminal` | Не seed; `in_deg > 0`, `out_deg = 0`, `depth < 4`. Это только наблюдаемый конечный получатель в границах выборки. |
| `peripheral` | Остальные узлы, в том числе обрыв на 4-м колене без исходящих. |

`role_score` лежит в диапазоне 0–1 и отражает силу выполнения выбранного **правила**: базовое значение 0.60 растёт с запасом по числу связей, seed и близостью доли пропуска к единице; для терминалов базовое значение 0.62, для граничной периферии 0.55. Это эвристическая оценка, **не калиброванная вероятность**. Точные формулы — в `score_roles()` в [run.py](run.py).

Для каждого `gid` поле `evidence` содержит числа, на которых основана роль, и не превышает 200 символов. Дополнительные колонки `nodes_roles.csv` позволяют разобрать любой узел за минуту. Например, для граничного узла пояснение прямо говорит, что исходящие после четвёртого колена неизвестны.

### Кластеры

Кластеры вычисляются детерминированным Louvain (`seed=42`) по **ненаправленной проекции** графа с весом `sum_kzt`. Направление сохраняется в исходном графе, ролях, метриках и интерфейсе; проекция используется только для поиска плотно связанных групп. Изолированные узлы получают собственный кластер. `sum_kzt_internal` включает только рёбра, где оба конца в данном кластере. `top_gids` — пять клиентов кластера с наибольшим приоритетом. `hypothesis` описывает наблюдаемый характер группы и требует проверки.

### Приоритет

Приоритет — взвешенная сумма процентильных рангов в текущей выгрузке:

```text
base = 0.20·P(in_deg) + 0.20·P(in_kzt) + 0.20·P(seed_reach)
     + 0.20·P(bridge) + 0.15·P(out_deg) + 0.05·rapid_48h
priority_score = base × role_factor × boundary_factor × seed_factor
```

`P` — процентильный ранг признака; совпадающие значения получают одинаковый ранг.

| Множитель | Значение |
|---|---|
| `role_factor` | 1 для coordinator/consolidator/distributor; 0,95 для transit; 0,85 для terminal; 0,75 для peripheral |
| `boundary_factor` | 0,65 для узлов четвёртого колена без исходящих; иначе 1 |
| `seed_factor` | 0,85 для известных seed; иначе 1 |

Итог ограничен диапазоном 0–1. Узлы сортируются по убыванию приоритета, при равенстве — по возрастанию `gid`; в `top_nodes.csv` попадают первые 100 (минимум по ТЗ — 20). Эти коэффициенты задают очередь проверки, а не оценку вины.

Чтобы приоритет был проверяемым, `nodes_roles.csv` содержит разбор формулы: `priority_base`, вклады `priority_payers`, `priority_incoming`, `priority_seed_reach`, `priority_bridge`, `priority_recipients`, `priority_rapid` и множители `priority_role_factor`, `priority_boundary_factor`, `priority_seed_factor`. Те же числа видны в карточке узла в `network.html`.

## Дополнительные сигналы

Эти признаки закрывают опциональные пункты ТЗ. Они **не меняют** роль и приоритет, а попадают в колонку `attention` (`nodes_roles.csv`, `top_nodes.csv`) и в карточку узла. Так каждый флаг проверяется отдельно и не смешивается с правилами ролей. Если флагов нет, в `attention` записано `нет`.

| Признак | Колонка | Как считается | Флаг в `attention` |
|---|---|---|---|
| Возвратные потоки | `cycles`, `cycle_with_seed` | простые направленные циклы длиной ≤ 4 перевода (`nx.simple_cycles`); список — в `cycles.csv`, `bottleneck_kzt` — минимальная сумма на ребре цикла | узел лежит хотя бы на одном цикле |
| Повторная пересылка | `relay_routes`, `chain_transits` | A→B→C: B отправил C 50–105% входа от A в течение 0–2 дней минимум в 2 разных дня; A→B→C→D связывает два таких эпизода | узел — посредник маршрута или звено цепочки |
| Всплески активности | `timeline.csv` | входящие и исходящие переводы агрегируются по календарному дню и `gid` | показываются в карточке узла как самые активные дни |
| Синхронные входы | `sync_payers_max` | максимум разных плательщиков в один календарный день | ≥ 3 |
| Дробление | `repeat_amount_max` | сколько раз узел отправил одну и ту же сумму | ≥ 4 |
| Суммы у порога | `near_threshold_in` | входящие переводы 5 000–9 999 KZT | ≥ 3 и не меньше половины входящих |
| Выброс для колена | — | `in_deg` выше 99-го процентиля своего колена | при `in_deg ≥ 3` |
| Скрытый выход | `p_hidden_outgoing` | см. ниже | ≥ 50%: «продлить обход» |

### Обрыв 4-го колена

Обход раскрывает исходящие всех узлов колен 0–3, поэтому у них `p_hidden_outgoing = 0`. Для 444 узлов 4-го колена исходящие не выгружались. Их вероятность оценивается эмпирически: какая доля не-seed узлов колен 1–3 с тем же числом плательщиков (1, 2, 3–4, 5+) имеет исходящие. На текущей выгрузке это 29% для одного плательщика, 57% для двух и 73% для 3–4. Так 434 граничных узла с одним плательщиком ближе к настоящим конечным получателям, а 10 узлов с 2+ плательщиками стоит раскрыть дальше в первую очередь. Все граничные узлы остаются `peripheral`: оценка задаёт очередь дозапроса, а не роль.

### Устойчивость сети

`resilience.csv` сравнивает изъятие топ-N по `priority_score` с N случайными узлами (`seed=42`). `seed_reach_share` — доля пар «seed → узел в пределах 4 переводов», которые остались связаны. На текущей выгрузке изъятие топ-10 оставляет 74% таких пар и 70 связных фрагментов, топ-50 — 47%; 50 случайных узлов — 96%. Значит, приоритет действительно выделяет узлы, на которых держится сеть.

### Маршруты пересылки

`routes.csv` показывает повторные A→B→C и сквозные A→B→C→D цепочки, где суммы и даты похожи на пересылку. Совпадение времени и размера перевода остаётся структурной гипотезой: оно не доказывает, что дальше ушли именно те же деньги.

### Белые пятна

`data_gaps.csv` перечисляет, чего не хватает в выгрузке, сколько узлов это затрагивает и какой запрос сделать следующим: продление обхода от граничных узлов, входящие и межбанковские переводы seed без исходящих, переводы ниже 5 000 KZT для узлов с суммами у порога, источники для узлов, которые отдали больше, чем получили, и для фрагментов вне основной компоненты.

В `network.html` эти же правила показываются в карточке конкретного узла как короткий список «что запросить дальше». Экспорт Markdown-отчёта включает эти запросы вместе с `evidence`, `attention` и заметками аналитика.

## AI-ассистент аналитика

Вопрос на естественном языке превращается в ответ по графу со ссылками на `gid`:

```bash
# Один раз задайте адрес внутреннего или локального OpenAI-compatible endpoint:
export OPENAI_BASE_URL=http://127.0.0.1:8000/v1
export OPENAI_MODEL=my-local-model
# export OPENAI_API_KEY=...  # только если внутренний endpoint требует токен

.venv/bin/python assistant.py "Кто собирает деньги с 100000000437046100, 100000000331309100 и 100000008346837100?"
.venv/bin/python assistant.py            # диалог с уточняющими вопросами
.venv/bin/python assistant.py --offline "..."   # без обращения к API
```

Параметры можно передать и явно: `assistant.py --base-url http://127.0.0.1:8000/v1 --model my-local-model "..."`. Шаблон переменных с примерами для Ollama и LM Studio лежит в [.env.example](.env.example); скопируйте его в `.env` и примените командой `set -a; source .env; set +a`. Файл `.env` в репозиторий не попадает.

**Как устроено.** Модель за локальным или внутренним OpenAI-compatible Chat Completions API только планирует запросы и пишет ответ. Каждый факт она берёт из детерминированных инструментов `graph_tools.py`, которые работают на том же графе и тех же ролях, что `run.py`:

| Инструмент | Что возвращает |
|---|---|
| `node_profile` | роль, место в очереди, метрики, `evidence`, `attention` |
| `counterparties` | прямые плательщики и получатели с суммами |
| `shared_counterparties` | кто получает деньги от нескольких `gid` (downstream) или платит им (upstream) в пределах N переводов |
| `money_paths` | цепочки переводов от одного `gid` к другому с суммой на каждом шаге |
| `top_nodes` | очередь приоритетов с фильтром по роли, кластеру, флагам |
| `cluster_summary` | размер, seed, внутренний оборот, роли и лидеры кластера |
| `node_cycles` | возвратные потоки через узел |

Системная инструкция требует ссылаться только на данные инструментов, писать `gid` полностью, формулировать выводы как гипотезы и учитывать ограничения выгрузки. Инструменты выполняются локально и доступны модели как стандартные function tools.

**Доступ.** `OPENAI_BASE_URL` обязателен: приложение не подставляет адрес публичного API и не отправляет данные во внешний сервис автоматически. `OPENAI_MODEL` задаёт имя модели на вашем endpoint. `OPENAI_API_KEY` необязателен и нужен, только если внутренний шлюз требует авторизацию. Без endpoint, модели или соединения ассистент сообщает об этом и отвечает офлайн: по `gid` в вопросе выбирает один инструмент (один `gid` — профиль и связи, несколько — общие получатели или, при словах «кто платит», «откуда», «источник», общие источники; без `gid` — очередь приоритетов).

## Выгрузки

`gid` — синтетический идентификатор. В интерфейсе он передаётся строкой, чтобы JavaScript не терял точность 64-битного числа. В CSV это целочисленный идентификатор.

| Файл | Содержание |

## Ограничения интерпретации

- Граф построен только по исходящим переводам от seed на четыре колена. **444 узла на 4-м колене без исходящих не считаются terminal**: это артефакт границы обхода; `p_hidden_outgoing` лишь оценивает вероятность продолжения. У других узлов также могут быть невидимые связи за рамками выгрузки.
- Цикл, маршрут пересылки, синхронность и повтор суммы — структурные совпадения. Они не доказывают, что по цепочке прошли одни и те же деньги.
- Входящие seed из-за пределов выборки не видны. Для seed не применяется правило транзита по отношению `out_kzt / in_kzt`. Нельзя считать это отношение полным балансом и для остальных узлов.
- Переводы ниже 5 000 KZT и операции в других банках отсутствуют. Временной признак не доказывает прохождение одних и тех же средств.
- Клиентских атрибутов и размеченных истинных ролей нет. Числовые пороги и веса являются проверяемыми эвристиками; качество оценивается аналитиком по подтверждённым внешним данным.
